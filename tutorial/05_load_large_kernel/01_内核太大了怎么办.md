# 内核太大了怎么办

说实话，我受够了。

---

## 前言 - 一个真实的故事

就在昨天，我给内核加了几个打印函数，心想这下能更好地调试了。结果呢？一运行 QEMU，黑屏，什么输出都没有。

我一开始以为代码写错了，反复检查逻辑，没发现问题啊。然后我用 GDB 单步调试，发现代码根本没跑到内核里——直接卡在了 bootloader 阶段。

后来我才发现，**内核变大了，超过了 bootloader 能读取的大小**。

你可能会问："等一下，之前不是说 bootloader 能加载内核吗？"

是的，但那是之前的"小内核"。问题出在我们的 bootloader 代码里：

```asm
; boot2.asm 中的内核加载代码（阶段 04）
load_kernel:
    mov ax, 0x1000      ; ES = 0x1000
    mov es, ax
    mov bx, 0x0000      ; BX = 0x0000
    ; ES:BX = 0x10000，这是内核要加载到的内存地址

    mov ah, 0x02        ; BIOS 磁盘读取功能
    mov al, 0x01        ; ← 问题在这！只读 1 个扇区（512 字节）
    mov ch, 0x00        ; 柱面号 = 0
    mov cl, 0x03        ; 扇区号 = 3（从磁盘第 3 扇区开始读）
    mov dh, 0x00        ; 磁头号 = 0
    mov dl, 0x80        ; 驱动器号 = 0x80（第一个硬盘）
    int 0x13            ; 调用 BIOS 中断

    jc disk_error       ; 如果出错，跳转到错误处理
    ; ... 继续执行
```

看到那行 `mov al, 0x01` 了吗？

**它告诉 BIOS：只读 1 个扇区。**

这意味着，你的内核最多只能是 512 字节。超过这个大小，多出来的部分根本不会被加载到内存里。

你可以想象一下：你写了一大堆内核代码，编译出来有 2KB，结果只有前 512 字节被加载了。剩下的代码在哪里？还在磁盘上躺着呢，根本没被读到内存里。那你的 CPU 执行着执行着，跑到某个地方，指令根本不存在——系统就炸了。

---

## 环境说明

在我们开始解决这个问题之前，先说明一下当前的开发环境，因为不同的环境可能会遇到不同的问题：

**开发平台**：WSL2 (Ubuntu 22.04) + QEMU 7.0+
**工具链**：NASM 2.16.01，CMake 3.28.1
**目标架构**：x86_64，实模式启动，最终切换到长模式
**磁盘约束**：512 字节标准扇区，16 磁头，63 扇区/磁道

这些约束很重要，因为我们的解决方案必须在 BIOS 的限制下工作。特别是 512 字节扇区和 CHS 寻址模式，这些是从 PC 诞生以来就存在的"历史包袱"。

---

## 那直接把 0x01 改成 0x10 不就行了吗？

你可能想："简单啊，把 `mov al, 0x01` 改成 `mov al, 0x10`，让它读 16 个扇区（8KB）不就完事了？"

这个问题问得好，但有一个更大的问题：**你怎么知道你的内核有多大？**

每次你修改内核代码，内核的大小都会变化。你总不能每次编译后，手动去查看内核文件大小，然后算出扇区数，再回来改 bootloader 的代码吧？

而且，这里还有一个更隐蔽的问题：

```asm
mov cl, 0x03        ; 扇区号 = 3
```

这个 `0x03` 是硬编码的，意思是"从磁盘第 3 扇区开始读"。

那问题来了：**如果你的 bootloader 大小变了，这个数字也得跟着变啊！**

我们现在的磁盘布局是这样的：扇区 1 是 bootloader Stage 1（512 字节），扇区 2 到 N 是 bootloader Stage 2（大小不固定），然后从扇区 N+1 开始才是内核。内核的起始扇区 = bootloader 占用的扇区数 + 1。如果你改了 bootloader，让它变大或变小，内核的起始位置就会变。那你得手动更新这个 `cl` 的值。

**这就是硬编码的痛：所有东西都写死在代码里，改一处就要改另一处，容易出错，还不好维护。**

我之前就踩过这个坑。有一次我把 bootloader 改小了一点，结果忘记更新内核起始扇区，内核被加载到了错误的位置，系统启动后直接 Triple Fault。那种感觉，真的血压拉满。

⚠️ **注意**
千万别低估这个问题的严重性。我见过太多人因为硬编码了扇区号，导致后来改代码时系统突然起不来，然后花半天时间调试才发现是扇区号没更新。这种问题很难排查，因为你的代码逻辑完全正确，只是数据被加载到了错误的位置。

---

## 我们需要一个配置系统

所以，我们现在的目标是：

1. **把所有这些"魔法数字"从代码里抽离出来**
2. **让构建系统能自动计算这些数值**
3. **每次编译时，自动更新 bootloader 的配置**

也就是说，我们想要一个配置文件，像这样：

```asm
; boot_config.inc - bootloader 配置文件
%define KERNEL_SECTOR_COUNT       31      ; 内核占用的扇区数（自动计算）
%define KERNEL_LBA_START          4       ; 内核的起始 LBA 扇区号
%define KERNEL_LOAD_SEGMENT       0x1000  ; 内核加载到的内存段地址
%define KERNEL_LOAD_OFFSET        0x0000  ; 内核加载到的内存偏移地址
```

然后在 bootloader 代码里，直接引用这些配置：

```asm
; bootloader.asm
%include "boot_config.inc"    ; 引入配置文件

load_kernel:
    mov ax, KERNEL_LOAD_SEGMENT   ; 使用配置中的值
    mov es, ax
    mov bx, KERNEL_LOAD_OFFSET    ; 使用配置中的值

    mov ah, 0x02
    mov al, KERNEL_SECTOR_COUNT   ; ← 使用配置中的扇区数！
    ; ... 其他代码
```

这样一来，每次构建时，CMake 会：先编译内核得到 kernel.bin，然后计算 kernel.bin 的实际大小并转换为扇区数，接着生成 boot_config.inc 文件并写入正确的数值，最后编译 bootloader 时使用这个配置文件。

**完美！我们再也不用手动改这些数字了。**

---

## 但是，有个鸡生蛋的问题

等等，你可能会发现一个问题：首次构建时，bootloader.asm 需要 boot_config.inc 才能编译，但 boot_config.inc 需要内核大小才能生成，而内核还没编译！这是一个循环依赖！

怎么办？我们用一个小技巧：**Mock 配置**。

第一次构建时，我们先用一个"假"的配置文件，里面的值是保守的估计：

```asm
; boot_config.inc (Mock 版本)
%define KERNEL_SECTOR_COUNT       1       ; 假设最小内核
%define KERNEL_LBA_START          4       ; 假设 bootloader 占 4 扇区
%define KERNEL_LOAD_SEGMENT       0x1000
%define KERNEL_LOAD_OFFSET        0x0000
```

这样首次构建能通过。后续构建时，内核已经有了，我们就可以用真实的内核大小来重新生成配置文件。

这个技巧我们后面会详细讲。

---

## 内存布局的另一个问题

除了磁盘上的位置，我们还要考虑内存中的布局。

现在我们的内存布局是这样的：0x07C00 是 Stage 1 开始的地方（512 字节），然后是 Stage 2（假设占 3 个扇区，约 1.5KB），结束位置大约在 0x08400。中间有一大段空白区域，然后内核加载到 0x10000（64KB 边界）。

你可能会问："为什么内核要加载到 0x10000？直接放到 0x08400 后面不就行了，省内存啊。"

这个问题问得好。但我们要考虑几个因素：首先是安全性，如果内核直接紧贴着 bootloader，万一内核写大了，可能会覆盖 bootloader 自己的代码；其次是对齐，0x10000 是一个 64KB 对齐的地址，对 CPU 访问更友好；最后是扩展性，未来如果要支持更大的内核，有足够的缓冲空间。

所以，我们选择在中间留一个"安全间隙"，让内核加载到 0x10000（64KB 边界）。

⚠️ **千万别**
为了省几百字节的内存就把内核紧贴着 bootloader 放。我见过有人这么干，结果后来内核稍微变大一点就直接覆盖了 bootloader，系统启动时直接卡死。这种问题非常难调试，因为你完全不知道是哪里出了问题。

---

## 总结一下

我们现在面临的问题是：内核超过 512 字节就炸，原因是 bootloader 硬编码只读 1 扇区。解决方法是改成动态读取 N 扇区。但我们不知道内核多大，手动算太麻烦，所以要用配置文件加自动计算。另外，bootloader 大小变了会导致内核起始位置要跟着变，这也要用配置文件自动更新。首次构建有循环依赖问题，解决方法是用 Mock 配置首次构建。
