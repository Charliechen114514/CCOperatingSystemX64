# 上板测试

代码写完了，构建也通过了，现在让我们验证一下。

---

## 前言 - 紧张时刻

每次改完代码，我最紧张的就是第一次运行。

**编译通过不代表能运行。** 你可能遇到各种问题：磁盘读取失败、内存布局冲突、CHS 参数错误、或者某个地方少写了一条指令。

所以，测试是非常重要的。

---

## 环境说明

在我们开始测试之前，确认一下你的环境：

**开发平台**：WSL2 (Ubuntu 22.04) + QEMU 7.0+
**工具链**：NASM 2.16.01，CMake 3.28.1，GDB 12.1
**测试工具**：QEMU，hexdump，ndisasm
**目标**：验证 bootloader 和内核能正常启动

如果你在真实硬件上测试，环境会有些不同，但基本的验证步骤是一样的。

---

## 第一步：编译验证

首先，确保代码能编译通过：

```bash
cmake --build build --clean-first
```

`--clean-first` 会在构建前清理旧的构建产物，确保从头开始编译。

你应该看到类似这样的输出：

```
[0/4] Copying mock boot configuration
[1/4] Building bootloader
[2/4] Building kernel
[3/4] Generating boot image
[4/4] Verifying disk layout
CCOS Disk Layout Verification
============================================================
Analyzing bootloader...
  Size: 1999 bytes (4 sectors)
  Valid MBR signature
Analyzing kernel...
  Size: 15680 bytes (31 sectors, 0.01 MB)
============================================================
✓ PASSED: Layout is valid
```

检查一下：bootloader 大小应该在 2KB 左右，kernel 大小根据你的代码而定，boot.img 应该成功生成，验证脚本应该通过。如果这些都 OK，我们可以继续了。

---

## 第二步：检查二进制文件

在运行之前，让我们先检查生成的二进制文件是否正确。

```bash
ls -lh build/bootloader.bin build/kernel.bin build/boot.img
```

输出示例：

```
-rwxr-xr-x 1 user user 2.0K Feb 15 16:45 build/bootloader.bin
-rwxr-xr-x 1 user 16K  Feb 15 16:45 build/kernel.bin
-rwxr-xr-x 1 user 1.5M Feb 15 16:45 build/boot.img
```

接下来检查 MBR 签名。MBR 签名是磁盘启动扇区的最后两个字节，必须是 0x55AA（注意字节序，小端序）。如果不是这个值，BIOS 不会识别这是一个可启动的磁盘。

```bash
xxd -s 0x1FE -l 2 build/bootloader.bin
```

你应该能看到：

```
000001fe: 55 aa
```

如果看到其他值，说明 MBR 签名不对，需要检查 bootloader 代码。

---

## 第三步：反汇编验证

让我们验证生成的二进制文件是否正确。反汇编 Stage 1（从 0x7C00 开始）：

```bash
ndisasm -b 16 -o 0x7C00 build/bootloader.bin | head -30
```

输出示例：

```
00007C00  FA                cli
00007C01  B8007C            mov ax,0x7C00
00007C04  8ED8              mov ds,ax
00007C06  8EC0              mov es,ax
00007C07  8ED0              mov ss,ax
...
```

检查 Stage 2（从文件偏移 0x200 开始，即第 2 扇区）：

```bash
ndisasm -b 16 -o 0x7E00 -e 0x200 build/bootloader.bin | head -30
```

`-e 0x200` 告诉 ndisasm 从文件偏移 0x200（512 字节）开始反汇编。

---

## 上号！QEMU 运行测试

### 基本运行

```bash
qemu-system-x86_64 -drive format=raw,file=build/boot.img -serial stdio
```

参数说明：`-drive format=raw,file=build/boot.img` 指定磁盘镜像文件，`-serial stdio` 把串口输出重定向到标准输出（终端）。

你应该能看到 VGA 和串口都有输出：

```
=== BootLoader Stage Start ===
READY TO BOOT CCOS
[1] Stage 1: Loading second stage...
[2] Stage 2: Loading kernel...
[MODE] Using CHS mode
[LOAD] CHS: loading 31 sectors from (0,0,5)
READY TO BOOT KERNEL
=== BootLoader Stage End ===
```

很好！如果你能看到这些输出，说明 bootloader 工作正常。

### 检查各个阶段

如果系统卡住，检查是哪个阶段出了问题。如果你看不到任何输出，可能是 BIOS 没识别到磁盘或 MBR 签名错误。如果你看到 `[1]` 但卡住，可能是 Stage 1 磁盘读取失败。如果你看到 `[2]` 但卡住，可能是 Stage 2 磁盘读取失败。如果你看到 `[MODE]` 但卡住，可能是 CHS 参数错误。如果你看到 `[LOAD]` 但卡住，可能是内核读取失败。如果你看到 `READY TO BOOT KERNEL`，说明 bootloader 成功！问题可能在内核。

### 带调试输出运行

如果需要更详细的调试信息，可以加上 `-d` 参数：

```bash
qemu-system-x86_64 -drive format=raw,file=build/boot.img -serial stdio -d int,cpu_reset
```

---

## GDB 调试

如果系统卡住，我们需要用 GDB 来定位问题。

### 启动 QEMU GDB 服务器

在一个终端运行：

```bash
qemu-system-x86_64 -drive format=raw,file=build/boot.img -s -S
```

参数说明：`-s` 启动 GDB 服务器（监听 1234 端口），`-S` 让 CPU 在启动时暂停，等待 GDB 连接。

### 连接 GDB

在另一个终端运行：

```bash
gdb build/bootloader.bin
```

然后在 GDB 中：

```
(gdb) target remote :1234
(gdb) break *0x7C00
(gdb) continue
```

### 常用断点位置

Stage 1 入口在 `0x7C00`，Stage 2 入口在 `0x7E00`，内核入口在 `0x10000`。

单步执行用 `si`（汇编指令）或 `ni`（下一行），继续执行用 `continue`。检查寄存器用 `info registers` 或 `print $eax`，查看内存用 `x/10x 0x7C00`（十六进制）或 `x/10i 0x7C00`（反汇编）。

---

## 常见问题排查

### 问题 1：系统启动后直接卡死

可能原因是 Stage 1 代码有问题、MBR 签名不正确、串口初始化有问题。解决方法是检查 MBR 签名是否为 55 AA，用 GDB 单步执行 Stage 1 定位问题。

### 问题 2：看不到 Stage 2 输出

可能原因是 Stage 2 磁盘读取失败、Stage 1 → Stage 2 跳转地址不对、vstart 设置错误。解决方法是检查 Stage 1 的磁盘读取代码，用 GDB 断点在 `0x7E00` 看是否能到达，检查 `boot_config.inc` 中的 `KERNEL_LBA_START` 值。

### 问题 3：看到 Stage 2 输出但卡在磁盘读取

可能原因是 CHS 参数计算错误、内核扇区数不正确、BIOS 不支持 CHS 模式。解决方法是检查 `boot_config.inc` 中的 CHS 配置，用 GDB 检查磁盘读取后的内存内容，尝试强制使用 LBA 模式（如果支持）。

### 问题 4：内核无法执行

可能原因是内核没有正确加载、内核入口地址错误、内核代码有问题。解决方法是检查 `boot_config.inc` 中的 `KERNEL_LOAD_SEGMENT` 和 `KERNEL_LOAD_OFFSET`，用 GDB 检查 0x10000 处的内存内容，单独测试内核。

⚠️ **千万别**
如果 GDB 无法连接到 QEMU，检查是否正确使用了 `-s -S` 参数。如果忘记加 `-S`，QEMU 会在 GDB 连接之前就开始执行，你可能错过关键的启动代码。如果忘记加 `-s`，GDB 服务器根本不会启动，当然连不上。

## 完整验证清单

### 编译阶段
- bootloader 编译成功
- kernel 编译成功
- boot.img 生成成功
- 文件大小在预期范围内

### 二进制检查
- MBR 签名正确（55 AA）
- Stage 1 代码从 0x7C00 开始
- Stage 2 代码从 0x7E00 开始

### 运行阶段
- VGA 输出正常
- 串口输出正常
- Stage 1 消息显示
- Stage 2 消息显示
- 磁盘模式选择（CHS/LBA）
- 扇区数显示正确
- 内核开始执行

### 调试阶段（如果需要）
- GDB 能连接到 QEMU
- 断点设置成功
- 单步执行正常
- 寄存器和内存检查正常
