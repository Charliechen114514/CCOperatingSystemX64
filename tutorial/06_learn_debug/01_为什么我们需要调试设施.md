# 为什么我们需要调试设施

说实话，如果你一直用 print 大法来调试内核，迟早会崩溃的。

---

## 写在前面：调试的痛苦

在之前的开发中，我们每次想看看内核在干什么，基本上就是这几个套路：先在代码里插入输出语句往 VGA 显存里写字符，然后重新编译整个项目，接着运行 QEMU，最后盯着黑乎乎的屏幕看有没有输出。一旦发现不对劲，就得回到第一步继续循环。这种循环真的让人血压拉满。

更糟糕的是，如果你想查看某个变量的值，还得专门写个函数把数字转换成字符串再输出。这意味着改一个小 bug 可能要重复这个流程十几次。每次编译等待、启动 QEMU、观察输出，发现问题后再改代码，周而复始。

如果你跟我一样有过这种经历，你肯定会问自己：难道就没有更好的办法吗？

答案当然是有的。现代操作系统开发早就有一套成熟的调试工具链，但我们现在是在裸机环境里，没有这些现成的东西可以用。所以我们需要自己搭建。

---

## 我们的目标

我们现在要做的是建立一套**完整的内核调试基础设施**，让我们能够像调试用户态程序那样调试内核。

具体来说，我们想要：

在源码层面设置断点，而不用硬编码内存地址。这意味我们可以在 `kernel_main` 函数名上直接打断点，而不是去查链接地址然后 `break *0x10000`。

单步执行代码，一条指令一条指令地看发生了什么。当程序卡死时，我们可以一步步执行，找到到底是哪一行出了问题。

直接查看变量和寄存器的值，不用自己写输出函数。鼠标悬停就能看到变量内容，或者输入 `p variable` 就能打印值。

查看调用栈，知道是怎么来到这里的。当程序在某个深层函数里 crash 时，我们可以看到完整的调用链。

某种程度上的热重载，虽然内核不能像脚本语言那样完全热更新，但至少改代码不用重新烧录到真实硬件。

这些功能在现代 IDE 里都是天经地义的存在，但在裸机开发里，每一样都得自己搭建。

---

## 技术方案选择

在选择调试方案之前，我们先分析一下当前的约束条件。

### 我们的约束

内核运行在 QEMU 虚拟机里，不能直接像调试用户态程序那样 attach 到进程。我们的代码是最底层的系统代码，下面没有操作系统支撑。

没有操作系统支持意味着没有 ptrace，没有信号，没有那些我们习以为常的调试机制。所有的一切都要从头开始。

我们需要控制整个启动过程，从第一条指令开始调试。这意味着在 bootloader 阶段就要能够介入，而不是等内核启动完成后再连接。

### 方案对比

看看市面上有哪些调试方案可用。

print 大法是最简单直接的，往 VGA 或串口输出信息。但这效率太低，每次改代码都要重新编译。而且一旦输出滚动太快，前面的信息就丢了。

QEMU monitor 可以查看 CPU 状态、内存内容，但不支持源码级调试。你只能在汇编层面操作，看不到 C 代码对应关系。

GDB 远程调试是功能最完整的方案，生态也很成熟，但需要花时间搭建环境。

JTAG 或硬件调试可以调试真实硬件，但需要额外的硬件设备，成本较高。

**我们的选择是 GDB 远程调试配合 QEMU。** 原因很简单：QEMU 内置了 GDB server 支持，不需要额外配置。GDB 是最成熟的调试工具，各种资料丰富。可以配合 VSCode 做图形化调试，体验更好。未来如果迁移到真实硬件，只需要换成 JTAG，调试流程不需要大改。

## 调试架构概览

在正式开始之前，我们先看看整个调试链路是怎么样的，这样大家对后续的工作有个整体概念。

整个调试架构分为三个层次：最上层是 VSCode 或终端，这是我们和调试工具交互的界面。中间层是 GDB 客户端，它负责发送调试命令、接收调试信息。最下层是 QEMU 的 GDB Server，它实际控制着 CPU 的执行。

```
┌─────────────────────────────────────────────────────────────┐
│                      调试架构示意图                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐   │
│  │  VSCode/    │    │     GDB     │    │    QEMU     │   │
│  │   终端      │◄──►│  (客户端)   │◄──►│ (GDB Server)│   │
│  │             │    │             │    │             │   │
│  └─────────────┘    └─────────────┘    └─────────────┘   │
│         │                   │                   │         │
│  ┌──────▼──────┐    ┌───────▼───────┐   ┌──────▼──────┐  │
│  │ launch.json │    │   .gdbinit    │   │   -s -S     │  │
│  └─────────────┘    └───────────────┘   │  GDB Server │  │
│                                         └─────────────┘  │
│                                                   │        │
│                                         ┌─────────▼────┐  │
│                                         │   CCOS Kernel│  │
│                                         │   + VGA Driver│ │
│                                         └──────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

简单来说整个流程是这样的：QEMU 以调试模式启动，监听 1234 端口等待连接。我们通过 VSCode 或终端启动 GDB，GDB 连接到 QEMU 的 GDB Server。然后我们在 VSCode 或 GDB 中发送调试命令，比如设置断点、单步执行等。GDB 把这些命令转发给 QEMU，QEMU 执行相应的操作并把结果返回。调试信息可以通过 VGA 或串口输出，这样我们就能看到程序的运行状态。

这套架构的好处是层次清晰，每一层各司其职。QEMU 负责实际执行，GDB 负责调试协议，VSCode 负责用户界面。我们可以在不同层面选择适合自己的工具。

## 开始前的准备

在开始搭建调试环境之前，请确保你的开发环境已经就绪。

### 检查工具

首先确认 QEMU 和 GDB 是否已经安装。

```bash
# 检查 QEMU 是否安装
qemu-system-x86_64 --version

# 检查 GDB 是否安装
gdb --version

# 检查当前项目状态
ls -la build/
```

你应该能看到类似这样的版本信息输出。QEMU 版本应该是 7.0 或更高，GDB 版本应该在 10 以上。如果看到 command not found 之类的错误，需要先安装这些工具。

### 当前项目状态

在上一阶段结束时，我们的项目应该已经能够编译出 bootloader 和 kernel，生成 boot.img 启动镜像，并且能在 QEMU 中正常启动，至少有基本的串口输出。

如果你还没有做到这些，建议先回到前面的教程把基础打牢。调试基础设施是在一个能工作的系统上添加便利工具，不是在一堆问题上面叠加新东西。

验证一下当前状态是否正常。

```bash
# 尝试构建
cmake -B build
cmake --build build

# 尝试运行
qemu-system-x86_64 -drive format=raw,file=build/boot.img -serial stdio
```

如果 QEMU 窗口能正常启动并且有输出，那我们就可以开始了。

## 我们即将要做的

在接下来的几个文档中，我们会一步步搭建完整的调试基础设施。

首先我们会配置 CMake 的 Debug 模式，生成带调试符号的内核。调试符号是源码级调试的基础，没有它我们就只能在汇编层面操作。

然后我们会创建 debug.sh 脚本，实现一键启动调试环境。这个脚本会自动处理 QEMU 和 GDB 的启动，让我们不用每次都记一堆命令。

接下来我们会配置 .gdbinit 文件，让 GDB 自动连接和设置。这样每次启动 GDB 时不需要手动输入一堆初始化命令。

之后我们会实现 VGA 文本驱动，用于调试输出。虽然串口也能输出，但 VGA 直接显示在屏幕上更直观一些。

最后我们会配置 VSCode 集成，实现图形化调试体验。有了图形界面，调试效率会提升不少。

每一步都是独立的，你可以跟着做一部分，也可以全部做完。相信我，等你完整搭建起来之后，你会感谢现在努力的自己。这套调试基础设施会成为后续开发的得力助手。
