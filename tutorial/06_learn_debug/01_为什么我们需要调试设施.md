# 为什么我们需要调试设施

说实话，如果你一直用 print 大法来调试内核，迟早会崩溃的。

---

## 写在前面：调试的痛苦

在之前的开发中，我们每次想看看内核在干什么，基本上就是这几个套路：

1. **在代码里插入输出语句** —— 往 VGA 显存里写字符
2. **重新编译整个项目**
3. **运行 QEMU**
4. **盯着黑乎乎的屏幕** 看有没有输出
5. **发现不对劲**，回到步骤 1

这种循环真的让人血压拉满。更糟的是，如果你想知道某个变量的值，还得专门写个函数把数字转换成字符串再输出。改一个小 bug 可能要重复这个流程十几次。

如果你跟我一样有过这种经历，你肯定会问自己：

> "难道就没有更好的办法吗？"

---

## 我们的目标

我们现在要做的是建立一套**完整的内核调试基础设施**，让我们能够：

- ✅ **在源码层面设置断点** —— 不再用硬编码地址
- ✅ **单步执行代码** —— 一条指令一条指令地看
- ✅ **查看变量和寄存器的值** —— 直接看，不用自己写输出
- ✅ **查看调用栈** —— 知道是怎么来到这里的
- ✅ **热重载（某种程度上）** —— 改代码不用重新烧录

这些在现代 IDE 里都是天经地义的功能，但在裸机开发里，每一样都得自己搭建。

---

## 技术方案选择

在选择调试方案之前，我们先分析一下约束条件：

### 我们的约束

1. **内核运行在 QEMU 虚拟机里** —— 不能直接 attach 到进程
2. **没有操作系统支持** —— 没有 ptrace，没有信号
3. **需要控制整个启动过程** —— 从第一条指令开始调试

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| print 大法 | 简单直接 | 效率低，需要重新编译 |
| QEMU monitor | 可以查看状态 | 不支持源码级调试 |
| GDB 远程调试 | 功能完整，生态成熟 | 需要搭建环境 |
| JTAG/硬件调试 | 可以调试真实硬件 | 需要额外硬件 |

**我们的选择**：**GDB 远程调试 + QEMU**

原因很简单：
- QEMU 内置了 GDB server 支持
- GDB 是最成熟的调试工具
- 可以配合 VSCode 做图形化调试
- 未来迁移到真实硬件也容易（只需要换成 JTAG）

---

## 调试架构概览

在正式开始之前，我们先看看整个调试链路是怎么样的：

```
┌─────────────────────────────────────────────────────────────┐
│                      调试架构示意图                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐   │
│  │  VSCode/    │    │     GDB     │    │    QEMU     │   │
│  │   终端      │◄──►│  (客户端)   │◄──►│ (GDB Server)│   │
│  │             │    │             │    │             │   │
│  └─────────────┘    └─────────────┘    └─────────────┘   │
│         │                   │                   │         │
│         │                   │                   │         │
│  ┌──────▼──────┐    ┌───────▼───────┐   ┌──────▼──────┐  │
│  │ launch.json │    │   .gdbinit    │   │   -s -S     │  │
│  └─────────────┘    └───────────────┘   │  GDB Server │  │
│                                         └─────────────┘  │
│                                                   │        │
│                                         ┌─────────▼────┐  │
│                                         │   CCOS Kernel│  │
│                                         │   + VGA Driver│ │
│                                         └──────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

简单来说：
1. QEMU 以调试模式启动，监听 1234 端口
2. GDB 连接到 QEMU，发送调试命令
3. 我们通过 VSCode 或终端操作 GDB
4. 调试信息通过 VGA 或串口输出

## 开始前的准备

在开始之前，请确保你的环境已经就绪。

### 检查工具

```bash
# 检查 QEMU 是否安装
qemu-system-x86_64 --version

# 检查 GDB 是否安装
gdb --version

# 检查当前项目状态
ls -la build/
```

你应该看到类似这样的输出：

```
QEMU emulator version 7.0.0 (Debian 1:7.0+dfsg-7)
Copyright (c) 2003-2022 Fabrice Bellard and the QEMU Project

GNU gdb (Ubuntu 12.1-0ubuntu1~22.04) 12.1
...
```

### 当前项目状态

在上一阶段结束时，我们的项目应该已经能够：

- ✅ 编译出 bootloader 和 kernel
- ✅ 生成 boot.img 启动镜像
- ✅ 在 QEMU 中正常启动
- ✅ 有基本的串口输出

如果你还没有做到这些，建议先回到前面的教程把基础打牢。
