# 为什么需要文件系统 —— 从块设备到 VFS

说实话，在 Stage 24 我们终于把 ATA 驱动搞定了，能读写硬盘扇区了，当时感觉挺爽的 —— 至少数据能持久化了。但当你真正开始用这个功能的时候，很快就会发现一个问题：我们只是会"读写扇区"，而不是"读写文件"。

这区别可太大了。想象一下，你想保存一个配置文件，结果你得记住它从第 123456 个扇区开始，占用了 50 个扇区；你想读取一个文本文件，结果你得先记下它的起始位置和长度。每次新增一个文件，你都得拿个小本本记下它的位置信息，不小心搞混了数据就全乱套了。这种感觉就像你住在没有门牌号的城市里，每次想找某个人的房子都得靠记忆和运气。

更糟糕的是，如果你删除了一个文件，它占用的空间就空出来了，但你怎么知道哪些空间是空闲的？如果你想在文件中间插入一些内容，后面的数据是不是都要往后移？这些问题在简单的块设备访问模式下根本没有答案。

## 现在我们有什么

在 Stage 24 结束时，我们有了 ATA 驱动，可以：

```c
// 读取扇区
ata_read(device, lba, buffer, nsectors);

// 写入扇区
ata_write(device, lba, buffer, nsectors);
```

看起来功能挺全的，但问题在于：**这只是原始的块设备访问，没有任何文件的概念**。你只能通过 LBA（逻辑块地址）来访问数据，必须自己记住哪个文件存放在哪些块上。

这带来了一系列问题：

**数据组织困难**：你必须手动管理每个文件的位置和大小。创建新文件时得找空闲空间，删除文件后要标记空间为可用，文件增长时要能找到后续的空闲块。这些都需要你自己来维护。

**命名空间缺失**：文件靠名字来识别，而不是靠块地址。你没法说"打开 config.txt"，只能描述成"读取从块 1000 开始的 50 个块"。这让程序和人都不好理解。

**元数据管理缺失**：一个文件不仅仅是一堆数据块，它还有创建时间、修改时间、访问权限、所有者等信息。块设备访问模式下，这些元数据只能靠自己想办法存储和解析。

**目录结构缺失**：现代文件系统都是层次化的，有目录和子目录。你需要一种方式来表示"A目录下B子目录里的C文件"，这在纯块设备访问模式下基本不可能实现。

## 什么是文件系统

文件系统就是为了解决这些问题而诞生的。它是在原始块设备之上的一层抽象，负责管理数据的存储、组织、命名和访问。

从技术角度看，文件系统做了这几件事：

**命名管理**：给每个数据块一个人类可读的名字，而不是让用户记住数字地址。你可以说"打开 /etc/config.txt"，而不是"读取从块 123456 开始的数据"。

**空间管理**：自动跟踪哪些块是空闲的，哪些已被占用。当你创建文件时，文件系统负责分配空间；删除文件时，负责回收空间。

**元数据管理**：存储文件的各种属性信息 —— 大小、时间戳、权限、所有者等。这些信息让文件系统可以支持访问控制、时间查询等功能。

**目录层次**：支持树状的目录结构，让文件可以分类组织。这对组织大量数据来说至关重要。

## 为什么选择 EXT2

在众多文件系统中，我们选择实现 EXT2，这是经过深思熟虑的。

**EXT2 是 Linux 历史上最重要的文件系统之一**。它在 1993 年被引入 Linux 内核，取代了原来的 MINIX 和 EXT 文件系统，成为 Linux 的默认文件系统多年。直到今天，虽然 EXT4 已经成为主流，但 EXT2 仍然是理解文件系统原理的最佳选择。

**设计清晰简洁**。EXT2 的设计非常经典，结构清晰，没有太多复杂的特性。这对于学习来说非常重要 —— 你可以理解每一部分的设计意图，而不是被各种优化和扩展搞得晕头转向。

**文档和参考资料丰富**。因为 EXT2 使用了这么多年，网上有大量的文档、教程和示例代码。遇到问题时，你总能找到参考资料。而且 Linux 内核的 EXT2 实现本身就是最好的参考。

**工具支持广泛**。你可以用 `mkfs.ext2` 创建 EXT2 文件系统，用 `debugfs` 调试，用各种工具查看和修改。这让我们可以在主机上准备测试用的磁盘镜像。

**实用性高**。EXT2 仍然被广泛使用，特别是在嵌入式系统和一些特殊场景。学会 EXT2，你在实际项目中也能用上。

其他候选方案我们也考虑过。FAT32 虽然简单，但功能太弱 —— 没有权限控制、没有硬链接、文件名长度限制严重。EXT3/4 增加了日志功能，实现复杂度大大提升，不适合作为第一个实现的文件系统。更现代的 Btrfs、XFS 等更是过于复杂，不适合教学用途。

## 为什么需要 VFS

你可能要问：为什么不直接实现 EXT2，还要搞一个 VFS 层？

这是一个非常好的问题。VFS（Virtual Filesystem Switch，虚拟文件系统）是 Linux 内核中文件系统的抽象层，它的存在有几个重要的原因。

**统一接口**。想象一下，如果你的程序直接调用 EXT2 的函数，那当你想换个文件系统（比如以后支持 FAT32）时，所有代码都要重写。而有了 VFS，你的程序调用的是统一的 API —— `open()`、`read()`、`write()`，底层换成什么文件系统都不影响。

**多文件系统共存**。一个实际的操作系统需要同时支持多种文件系统。系统盘可能是 EXT2，U 盘是 FAT32，光盘是 ISO9660。VFS 让这些不同的文件系统可以同时工作，应用程序可以用相同的方式访问它们。

**缓存优化**。VFS 层可以实现统一的缓存策略。比如 inode 缓存和 dentry 缓存，无论底层是什么文件系统，都可以使用同一套缓存机制，提高性能。

**可扩展性**。当你想添加新的文件系统支持时，只需要实现 VFS 定义的接口，就可以无缝集成到系统中。这种插件式的设计让系统更易于扩展。

可以这么说，没有 VFS 的话，文件系统和应用程序就是紧耦合的；有了 VFS，它们之间就是松耦合的，这是操作系统设计中"抽象层"思想的典型应用。

## 整体架构设计

我们接下来要实现的文件系统子系统采用三层架构：

```
┌─────────────────────────────────────────────────────────┐
│                     应用程序层                           │
│                  (open, read, write)                    │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│                      VFS 层                              │
│  统一接口: vfs_open, vfs_read, vfs_write, vfs_close     │
│  - 路径解析     - 权限检查     - 缓存管理                │
└────────────────────────┬────────────────────────────────┘
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   EXT2      │  │   FAT32     │  │   其他      │
│  文件系统    │  │  文件系统    │  │  文件系统    │
└──────┬──────┘  └──────┬──────┘  └─────────────┘
       │                │
       └────────┬───────┘
                ▼
┌─────────────────────────────────────────────────────────┐
│                     块设备层                             │
│  - 块 I/O 抽象   - 设备管理    - 同步/异步操作            │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│                    ATA 驱动                             │
│  (Stage 24 已完成)                                       │
└─────────────────────────────────────────────────────────┘
```

**最底层是块设备层**，它是对 ATA 驱动的封装。VFS 和 EXT2 不直接调用 ATA 函数，而是通过块设备层的统一接口。这样做的好处是，如果以后有了 SATA、NVMe 等其他存储设备，只需要在块设备层添加相应的实现，上层代码无需改动。

**中间是具体文件系统层**，目前我们只实现 EXT2。这一层负责解析 EXT2 的磁盘结构，实现 EXT2 特定的操作。

**最上层是 VFS 层**，它提供统一的 API，管理文件系统的挂载、路径解析、缓存等。

## 这一阶段我们要达成什么

经过这一系列文档的学习和动手实践，我们将实现一个完整的文件系统子系统。具体来说：

**块设备层**：实现对 ATA 驱动的封装，提供统一的块读写接口。

**VFS 核心结构**：定义超级块、inode、dentry、file 等核心数据结构，用 C 语言的函数指针实现面向对象的设计模式。

**VFS 功能实现**：实现 inode 缓存、dentry 缓存、路径解析、文件打开关闭等核心功能。

**EXT2 文件系统**：解析 EXT2 的磁盘结构，实现超级块读取、inode 操作、目录查找、文件读写等功能。

**演示程序**：实现 ls（列出目录）、cat（显示文件内容）、df（显示文件系统信息）等实用命令。

这些功能实现后，我们的内核就真正迈入了"有文件系统"的时代。用户可以通过路径名访问文件，不再需要记住神秘的块地址；内核可以自动管理空间，我们不再需要手动维护哪些块是空闲的。这是一个质的飞跃。

## 环境确认

在开始之前，我们先确认一下环境。你应该已经完成了 Stage 24 的工作，拥有一个可以正常工作的 ATA 驱动。内核能够正常启动，串口有日志输出，VGA 有欢迎界面。

如果你还没完成 Stage 24，建议先回去把 ATA 驱动搞定，因为文件系统是建立在块设备访问的基础之上的。

另外，由于我们将实现一个相当大的子系统，代码量会比较多。建议你保持耐心，跟着文档一步步来，不要跳过任何步骤。文件系统的每个部分都有其设计原因，理解了这些原因，代码就变得顺理成章了。

准备好了吗？让我们开始这场从块设备到文件系统的进阶之旅。
