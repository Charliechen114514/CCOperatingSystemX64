# 栈回溯从零开始 —— Stage 11 调试支持实战指南

## 前言

在内核开发中，最痛苦的事情莫过于遇到一个莫名其妙的崩溃，但你完全不知道是哪里出了问题。程序停在了一个随机的地址，寄存器值看起来毫无意义，你甚至不知道是怎么来到这里的。这时候如果能看到调用栈，就能知道程序是怎么一路走到这里的，问题排查会容易得多。

说实话，刚开始写内核的时候我完全不知道怎么实现栈回溯。用户态程序可以直接调用 `backtrace()` 函数，但内核里没有 libc 支持，这些函数根本不存在。我那时候只能对着汇编代码和 GDB 输出慢慢推演调用关系，效率低得令人发指。

后来我才发现，x86_64 的调用约定其实非常适合栈回溯。每个函数调用时都会保存前一个栈帧的基址（RBP）和返回地址（RIP），只要沿着这些指针一路往上找，就能重建完整的调用链。而且实现起来并没有我想象的那么复杂，几十行代码就能搞定。

所以这一篇我们会一起实现一套完整的栈回溯系统。从理解 x86_64 的栈帧结构开始，逐步构建出能读取寄存器、验证栈帧、遍历调用链、解析符号的完整功能。每写一个函数我都会解释清楚它背后的原理，确保你不仅知道怎么用，还知道为什么这样设计。准备好了吗？我们继续。

## 第一步：理解 x86_64 栈帧结构

在开始写代码之前，我们需要理解 x86_64 的栈帧是怎么组织的。这是实现栈回溯的基础。

当一个函数被调用时，调用者会按照 System V AMD64 ABI 的约定传递参数：
- 前六个整数/指针参数通过寄存器传递：RDI, RSI, RDX, RCX, R8, R9
- 剩余参数通过栈传递
- 返回地址通过 `call` 指令压栈

被调用者（callee）的序言（prologue）通常会做这些事情：

```asm
push rbp           ; 保存调用者的 RBP
mov rbp, rsp       ; 设置当前栈帧的 RBP
; 可选：sub rsp, N  ; 为局部变量分配空间
```

函数返回时的尾声（epilogue）会做相反的事情：

```asm
mov rsp, rbp       ; 恢复栈指针
pop rbp            ; 恢复调用者的 RBP
ret                ; 返回（弹出返回地址）
```

所以每个栈帧的结构是这样的：

```
高地址
    +------------------+
    |  参数（如果有）  |  <- 调用者压入的参数
    +------------------+
    |  返回地址 (RIP)  |  <- call 指令压入
    +------------------+
    |  保存的 RBP      |  <- push rbp 压入，当前 RBP 指向这里
    +------------------+
    |  局部变量        |  <- RSP 指向这里附近
    +------------------+
低地址
```

关键的观察是：`[RBP]` 存储的是调用者的 RBP，`[RBP + 8]` 存储的是返回地址。所以我们可以通过这两个指针遍历整个调用链。

## 第三步：实现寄存器读取函数

栈回溯的第一步是获取当前的 RBP 和 RSP 寄存器值。这需要用内联汇编来实现。

创建 `kernel/stacktrace/stacktrace.c`：

```c
/**
 * @file stacktrace.c
 * @brief 栈回溯实现
 * @date 2026-02-17
 */
#include "stacktrace.h"
#include "klogs/kprintf.h"

/**
 * @brief 获取当前栈指针
 *
 * @return 当前的 RSP 值
 */
static inline uintptr_t get_rsp(void) {
    uintptr_t rsp;
    __asm__ volatile("mov %%rsp, %0" : "=r"(rsp));
    return rsp;
}

/**
 * @brief 获取当前帧指针
 *
 * @return 当前的 RBP 值
 */
static inline uintptr_t get_rbp(void) {
    uintptr_t rbp;
    __asm__ volatile("mov %%rbp, %0" : "=r"(rbp));
    return rbp;
}
```

这两个函数非常简单，就是用 `mov` 指令把寄存器值读到变量里。注意这里的内联汇编语法：`"mov %%rsp, %0"` 中的 `%0` 是一个占位符，会被替换成后面的输出操作数 `=r(rsp)`。`=r` 表示输出操作数，可以用任何寄存器。`%%rsp` 中的两个百分号是因为在内联汇编中，寄存器名需要用 `%%` 转义。

## 第四步：实现栈帧验证

栈回溯有一个潜在的危险：如果栈帧损坏了（比如被缓冲区溢出破坏），RBP 可能指向一个无效的地址。如果我们继续遍历，可能会访问非法内存导致系统崩溃。所以我们需要一个函数来验证 RBP 是否看起来像一个有效的栈帧指针。

在 `stacktrace.c` 中添加：

```c
// 栈边界定义（用于验证）
#define STACK_BASE    0x80000UL    // 大约的栈顶（来自 kernel_entry.asm）
#define STACK_SIZE    0x10000UL    // 64KB 栈大小

/**
 * @brief 验证指针是否像一个有效的栈帧
 *
 * @param ptr 要验证的指针
 * @return true 如果指针可能是有效的帧指针，false 否则
 */
static bool is_valid_frame(uintptr_t ptr) {
    // 检查对齐（x86_64 上栈帧应该 8 字节对齐）
    if (ptr & 0x7)
        return false;

    // 检查是否在合理的栈范围内
    // 栈向下增长，所以有效地址应该在 STACK_BASE 以下
    if (ptr > STACK_BASE)
        return false;

    // 检查是否不会太低（合理的下界）
    if (ptr < (STACK_BASE - STACK_SIZE))
        return false;

    return true;
}
```

这个验证函数做了三件事：检查对齐、检查上界、检查下界。对齐检查是因为栈帧指针在 x86_64 上应该是 8 字节对齐的（64 位架构的栈是 8 字节对齐的）。上界和下界检查确保指针在栈的合理范围内。

注意这里使用的 `STACK_BASE` 和 `STACK_SIZE` 是经验值。如果你的内核栈布局不同，需要调整这些值。一个更健壮的实现会从内核初始化代码中获取真实的栈边界。

## 第五步：实现核心栈回溯逻辑

现在我们来实现核心的栈回溯逻辑。在 `stacktrace.c` 中添加：

```c
void dump_stack(int max_frames) {
    // 如果指定了 0，使用默认值
    if (max_frames <= 0)
        max_frames = DUMP_STACK_DEFAULT_FRAMES;

    // 限制最大值，防止无限循环
    if (max_frames > DUMP_STACK_MAX_FRAMES)
        max_frames = DUMP_STACK_MAX_FRAMES;

    uintptr_t rbp = get_rbp();
    uintptr_t rsp = get_rsp();

    // 打印表头
    kprintf(KLOG_BACKEND_SERIAL, "\n");
    kprintf(KLOG_BACKEND_SERIAL, "Stack Trace:\n");
    kprintf(KLOG_BACKEND_SERIAL, "  RSP: 0x%016lx\n", rsp);
    kprintf(KLOG_BACKEND_SERIAL, "  RBP: 0x%016lx\n", rbp);
    kprintf(KLOG_BACKEND_SERIAL, "  %-2s  %-16s  %s\n", "#", "Address", "Function");
    kprintf(KLOG_BACKEND_SERIAL, "  %-2s  %-16s  %s\n", "--", "----------------", "--------------------------------");

    int frame = 0;
    bool found_valid_frame = false;

    while (rbp != 0 && frame < max_frames) {
        // 验证帧指针
        if (!is_valid_frame(rbp)) {
            kprintf(KLOG_BACKEND_SERIAL, "  %-2d  <invalid frame: 0x%016lx>\n", frame, rbp);
            break;
        }

        found_valid_frame = true;

        // 获取返回地址（保存的 RIP 在 RBP + 8 位置）
        uintptr_t* frame_ptr = (uintptr_t*)rbp;
        uintptr_t prev_rbp = frame_ptr[0];      // 保存的 RBP
        uintptr_t rip = frame_ptr[1];           // 保存的返回地址

        // 打印帧信息
        if (rip != 0) {
            // TODO: 这里可以添加符号解析，暂时只打印地址
            kprintf(KLOG_BACKEND_SERIAL, "  %-2d  0x%016lx  %s\n", frame, rip, "???");
        } else {
            kprintf(KLOG_BACKEND_SERIAL, "  %-2d  %s\n", frame, "<no return address>");
        }

        // 移动到上一个帧
        rbp = prev_rbp;
        frame++;

        // 检测可能的循环（同一帧重复）
        if (rbp == get_rbp()) {
            kprintf(KLOG_BACKEND_SERIAL, "  <frame loop detected>\n");
            break;
        }
    }

    if (!found_valid_frame) {
        kprintf(KLOG_BACKEND_SERIAL, "  <no valid stack frames>\n");
    } else if (frame >= max_frames && rbp != 0) {
        kprintf(KLOG_BACKEND_SERIAL, "  ... (truncated, max frames reached)\n");
    }

    kprintf(KLOG_BACKEND_SERIAL, "\n");
}

void dump_stack_full(void) {
    dump_stack(DUMP_STACK_DEFAULT_FRAMES);
}
```

这个函数的逻辑很直观：
1. 获取当前的 RBP 和 RSP
2. 打印表头
3. 循环遍历栈帧链：
   - 验证 RBP 是否有效
   - 从 `[RBP + 8]` 获取返回地址
   - 从 `[RBP]` 获取上一个 RBP
   - 打印帧信息
   - 移动到上一个帧
4. 处理各种边界情况（无效帧、循环、截断）

注意我们在循环开始时保存了 `get_rbp()` 的返回值，用于检测循环。如果栈帧损坏导致 RBP 形成了一个循环，这个检测能防止无限循环。

## 第六步：添加符号解析支持

到目前为止，我们的栈回溯只能打印返回地址的数值。如果能把地址解析成函数名，调试起来就方便多了。

但符号解析是个比较复杂的话题，需要链接器提供符号表信息。在内核环境中，我们通常没有完整的符号表，但可以通过一些技巧来获取基本的符号信息。

这里我们先实现一个简单的版本，假设你在链接器脚本中导出了符号地址。创建一个简单的符号查找接口：

在 `stacktrace.c` 中修改打印部分：

```c
// 简单的符号查找（假设链接器导出了这些符号）
extern const char _start;
extern const char kernel_main;

/**
 * @brief 简单的符号查找
 *
 * @param addr 要查找的地址
 * @param name 输出：符号名称
 * @param offset 输出：偏移量
 * @return true 如果找到符号，false 否则
 */
static bool find_symbol(uintptr_t addr, const char** name, uintptr_t* offset) {
    // 这里只是一个示例，实际实现需要完整的符号表
    // 我们可以硬编码几个已知的符号

    if (addr == (uintptr_t)&kernel_main) {
        *name = "kernel_main";
        *offset = 0;
        return true;
    }

    if (addr >= (uintptr_t)&_start && addr < (uintptr_t)&kernel_main) {
        *name = "_start + ???";
        *offset = addr - (uintptr_t)&_start;
        return true;
    }

    return false;
}
```

然后在 `dump_stack` 中使用符号查找：

```c
// 打印帧信息
if (rip != 0) {
    const char* sym_name;
    uintptr_t sym_offset;

    if (find_symbol(rip, &sym_name, &sym_offset)) {
        if (sym_offset == 0) {
            kprintf(KLOG_BACKEND_SERIAL, "  %-2d  0x%016lx  %s\n", frame, rip, sym_name);
        } else {
            kprintf(KLOG_BACKEND_SERIAL, "  %-2d  0x%016lx  %s+0x%lx\n",
                    frame, rip, sym_name, sym_offset);
        }
    } else {
        kprintf(KLOG_BACKEND_SERIAL, "  %-2d  0x%016lx  %s\n", frame, rip, "???");
    }
} else {
    kprintf(KLOG_BACKEND_SERIAL, "  %-2d  %s\n", frame, "<no return address>");
}
```

注意这里的符号查找只是一个非常简化的版本。一个完整的实现需要解析 ELF 符号表，或者使用链接器导出的 `__start_mcount` / `__stop_mcount` 之类的标记。如果你需要完整的符号解析，可以考虑：
1. 在链接器脚本中导出符号地址范围
2. 解析 ELF 文件的 `.symtab` 或 `.dynsym` 段
3. 使用 DWARF 调试信息获取行号

## 常见问题与解决方案

### 问题 1：帧指针被优化掉了

如果你的代码用 `-O2` 或 `-O3` 编译，编译器可能会优化掉帧指针，导致 `rbp` 寄存器不再指向栈帧。这种情况下栈回溯会失败。

解决方案：
1. 编译时添加 `-fno-omit-frame-pointer` 选项
2. 或者对需要栈回溯的函数使用 `__attribute__((no_omit_frame_pointer))`

### 问题 2：内联函数

如果函数被内联了，它就不会出现在调用栈中。这是正常的，因为内联函数的代码被直接嵌入到调用者中了。

如果需要看到内联函数，可以：
1. 用 `-fno-inline` 禁用内联
2. 或者使用 DWARF 调试信息进行更精确的栈回溯

### 问题 3：尾调用优化

尾调用优化会把函数调用转换成跳转，导致调用栈不完整。

解决方案：
1. 编译时添加 `-fno-optimize-sibling-calls` 选项
2. 或者在关键函数上使用 `__attribute__((noinline))`
