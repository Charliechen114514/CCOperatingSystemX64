# 为什么需要侵入式链表 —— Stage 11 基础数据结构实战指南

## 前言

写到 Stage 11 的时候，我意识到一个被忽略很久的问题：我们的内核一直在用各种数据结构，但从来没有认真思考过这些数据结构到底是怎么实现的。更准确地说，我们一直在用 C 语言写代码，但如果你让我实现一个高效的链表，我大概会写出教科书上那种最传统的版本——包含一个 `void* data` 指针，每次插入都要 `malloc` 一个新节点。

说实话，这种写法在用户态程序里还凑合，但在内核里简直就是灾难。你想啊，内核本来就没有多少内存可用，每次插入一个节点还要额外分配内存，这不是自己给自己找麻烦吗？而且这种设计还有个更隐蔽的问题：数据和链表节点是分开存储的，访问一个节点时，CPU 先要从内存里读取链表节点，然后才能通过 `data` 指针去访问真正的数据。这意味着两次内存访问，缓存完全不友好。

Linux 内核的开发者们早就遇到了这个问题，他们的解决方案叫做"侵入式链表"（Intrusive Linked List）。这个设计的核心思想非常简单：与其让链表节点指向数据，不如让数据结构直接包含链表节点。这样的话，数据和链表节点在内存里是连续存储的，访问时只需要一次内存读取，而且不需要额外的内存分配。

所以这一篇我们会一起手把手实现一套完整的侵入式双向链表。别担心，我们不会跳过任何步骤，从最基础的概念开始，每写一个函数都会解释清楚它是怎么工作的，为什么要这么写，有哪些坑需要避开。准备好了吗？我们开始。

## 环境说明

在开始之前，先确认一下你的开发环境。这篇文章假设你已经完成了 Stage 10，日志系统已经能正常工作了。

```
操作系统: Ubuntu 22.04 LTS / WSL2 / Arch WSL
编译器:   GCC x86_64-elf-gcc 或类似交叉编译器
构建工具: CMake 3.25 或更高版本
模拟器:   QEMU 7.0 或更高版本
```

可能有人会问，为什么不直接用 C++ 的 `std::list` 或者其他现成的容器库？这个问题问得好。内核环境和用户态程序有本质区别。内核是最底层的代码，没法链接 C++ 标准库，更别说 STL 了。而且内核需要极致的性能，每个字节的内存、每个 CPU 周期都宝贵得很。侵入式链表的设计正是为了满足这些需求：零额外内存分配、缓存友好、编译时类型安全。

听起来有点抽象？没关系，我们接下来一步步实现，你会看到这个设计到底有多优雅。

## 第一步：理解传统链表的问题

在开始写代码之前，我们先来看看传统链表到底有什么问题。这样你才能理解为什么要用侵入式链表。

传统双向链表大概长这样：

```c
typedef struct node {
    void* data;
    struct node* next;
    struct node* prev;
} node_t;
```

使用起来是这样的：

```c
// 假设我们有一个任务结构
typedef struct task {
    int pid;
    char name[32];
    // ... 其他字段
} task_t;

// 创建任务
task_t* task1 = malloc(sizeof(task_t));
task1->pid = 1;
strcpy(task1->name, "init");

// 创建链表节点
node_t* node = malloc(sizeof(node_t));
node->data = task1;

// 插入链表
list_add(node, &task_list);
```

看出来问题了吗？每次添加一个任务到链表，我们需要分配两次内存：一次分配 `task_t` 结构体，一次分配 `node_t` 链表节点。这还不够完蛋，更糟糕的是这两个内存块在堆里可能离得很远，访问时 CPU 缓存根本用不上。

侵入式链表的思路是：把链表节点直接放进数据结构里。像这样：

```c
typedef struct task {
    int pid;
    char name[32];
    list_head list;  // 链表节点嵌入数据结构
} task_t;

// 创建任务
task_t task1 = { .pid = 1, .list = LIST_HEAD_INIT(task1.list) };

// 直接添加到链表
list_add(&task1.list, &task_list);
```

这样设计的好处显而易见：数据和链表节点在内存里是连续的，访问时缓存命中率高，而且不需要额外的内存分配。一个 `task_t` 结构体可以同时存在于多个链表中，只需要在里面放多个 `list_head` 字段就行。

理解了这个设计思想，我们就开始动手实现吧。

## 第三步：定义 list_head 结构体

现在我们来定义最核心的 `list_head` 结构体。这个结构体出奇的简单，只有两个指针：一个指向下一个节点，一个指向上一个节点。

创建 `kernel/list/list.h`：

```c
/**
 * @file list.h
 * @brief Linux kernel style intrusive doubly-linked list implementation.
 * @date 2026-02-17
 */
#pragma once

#include "defines/types.h"

/**
 * @struct list_head
 * @brief 双向链表节点结构
 *
 * 这个结构体设计为直接嵌入到用户定义的结构体中
 * 一个 list_head 可以同时属于多个链表
 */
typedef struct list_head {
    struct list_head* next; /**< 指向下一个节点 */
    struct list_head* prev; /**< 指向上一个节点 */
} list_head;
```

就这么简单。两个指针，没有别的。这个结构体设计得非常精妙，它不包含任何数据，只包含指向其他 `list_head` 的指针。正是这种简洁性使得它可以嵌入到任何结构体中。

等等，你可能会问：没有数据字段，我们怎么访问包含这个节点的结构体？问得好！这就是 `container_of` 宏的用武之地了，我们稍后会详细讲解。

## 第四步：实现链表初始化

接下来我们需要能够初始化链表节点。一个空链表（或者说一个单独的节点）应该指向自己，这样 `next` 和 `prev` 都有合法的值，不会是悬空指针。

在 `list.h` 中添加初始化宏和函数：

```c
/* ===== 初始化宏和函数 ===== */

/**
 * @brief 静态初始化一个链表头
 *
 * 在编译时初始化链表头，用于全局变量
 */
#define LIST_HEAD(name) \
    list_head name = { &(name), &(name) }

/**
 * @brief 动态初始化一个链表头
 *
 * 在运行时初始化链表头，用于局部变量或动态分配的结构
 */
static inline void INIT_LIST_HEAD(list_head* ptr) {
    ptr->next = ptr;
    ptr->prev = ptr;
}
```

这里有两个初始化方式。`LIST_HEAD` 是一个宏，用于在编译时初始化全局变量。你可以在文件作用域这样使用：

```c
LIST_HEAD(global_task_list);
```

这会创建一个名为 `global_task_list` 的 `list_head` 变量，并且它的 `next` 和 `prev` 都指向自己。

`INIT_LIST_HEAD` 是一个内联函数，用于在运行时初始化链表头。你可以在函数里这样使用：

```c
void some_function(void) {
    list_head local_list;
    INIT_LIST_HEAD(&local_list);
    // ...
}
```

注意这两种方式都能达到同样的效果：让 `next` 和 `prev` 都指向节点自己。这是空链表的标准表示方式。你可能会问，为什么要区分这两种方式？直接用函数不就行了吗？好问题。`LIST_HEAD` 宏的优势是它可以在编译时初始化，不需要等到运行时。这在某些场景下很重要，比如全局变量的初始化必须能在编译时完成。

## 第五步：理解 container_of 宏

现在我们来到最关键的部分：如何从 `list_head` 指针获取包含它的结构体指针？这就是 `container_of` 宏的作用。

在 `list.h` 中添加：

```c
/* ===== 结构体访问宏 ===== */

/**
 * @brief 获取包含 list_head 的结构体指针
 *
 * 根据 list_head 成员的地址，计算出包含它的结构体的地址
 *
 * @param ptr 指向 list_head 成员的指针
 * @param type 包含结构体的类型
 * @param member list_head 在结构体中的成员名
 * @return 指向包含结构体的指针
 */
#define list_entry(ptr, type, member) \
    ((type*)((char*)(ptr) - (unsigned long)(&((type*)0)->member)))
```

这个宏看起来有点复杂，我们慢慢拆解。核心思想是：如果我们知道一个结构体中某个成员的地址，也知道这个成员在结构体中的偏移量，那么用成员地址减去偏移量就能得到结构体的地址。

让我举个例子。假设我们有这样的结构体：

```c
typedef struct task {
    int pid;          // 偏移量 0
    char name[32];    // 偏移量 4
    list_head list;   // 偏移量 36
} task_t;
```

如果我们有一个指向 `list` 成员的指针，想要获取整个 `task_t` 结构体的指针，只需要用 `list` 的地址减去 36（`list` 成员的偏移量）就行了。

那么怎么获取偏移量呢？这就是 `&((type*)0)->member` 的巧妙之处。它把 0 强制转换成 `type*` 指针，然后访问 `member` 成员。因为地址是 0，所以 `member` 的地址就是它的偏移量。

当然，实际代码中我们不会真的访问地址 0，这只是编译时的技巧，编译器会计算出偏移量，不会真的去解引用空指针。

现在你可以这样使用 `list_entry`：

```c
typedef struct task {
    int pid;
    char name[32];
    list_head list;
} task_t;

void process_task(list_head* node) {
    // 从 list_head 获取 task_t 指针
    task_t* task = list_entry(node, task_t, list);

    klog_info("Processing task: PID=%d, Name=%s\n", task->pid, task->name);
}
```

这个宏是整个侵入式链表设计的核心，理解了它，你就理解了侵入式链表的精髓。

## 第七步：编写简单测试验证功能

现在我们来测试一下目前写的东西是否能正确工作。虽然我们还没有实现完整的链表操作，但至少可以验证 `list_head` 结构体和初始化宏是否正常工作。

在 `kernel_main.c` 中添加测试代码：

```c
#include "kernel/list/list.h"
#include "klogs/kprintf.h"

void test_list_head_init(void) {
    klog_info("=== list_head 初始化测试 ===\n");

    // 测试静态初始化
    LIST_HEAD(static_list);
    klog_info("静态初始化: next=%p, prev=%p (应该都指向自己)\n",
              static_list.next, static_list.prev);

    // 测试动态初始化
    list_head dynamic_list;
    INIT_LIST_HEAD(&dynamic_list);
    klog_info("动态初始化: next=%p, prev=%p (应该都指向自己)\n",
              dynamic_list.next, dynamic_list.prev);

    // 验证指针确实指向自己
    if (static_list.next == &static_list && static_list.prev == &static_list) {
        klog_info("静态初始化验证通过\n");
    } else {
        klog_error("静态初始化失败！\n");
    }

    if (dynamic_list.next == &dynamic_list && dynamic_list.prev == &dynamic_list) {
        klog_info("动态初始化验证通过\n");
    } else {
        klog_error("动态初始化失败！\n");
    }

    // 测试 list_entry 宏
    typedef struct {
        int value;
        list_head node;
    } test_struct_t;

    test_struct_t test_item = { .value = 42 };
    INIT_LIST_HEAD(&test_item.node);

    test_struct_t* recovered = list_entry(&test_item.node, test_struct_t, node);
    if (recovered->value == 42) {
        klog_info("list_entry 宏测试通过：value=%d\n", recovered->value);
    } else {
        klog_error("list_entry 宏测试失败！\n");
    }
}
```

在 `kernel_main` 函数中调用这个测试：

```c
void kernel_main(void) {
    // ... 其他初始化代码 ...

    klog_init(KLOG_BACKEND_SERIAL);
    test_list_head_init();

    // ... 其他代码 ...
}
```

编译并运行：

```bash
cd build
cmake ..
make
./run.sh
```

你应该在串口输出中看到类似这样的结果：

```
[INFO ] === list_head 初始化测试 ===
[INFO ] 静态初始化: next=0xXXXXXXXX, prev=0xXXXXXXXX (应该都指向自己)
[INFO ] 动态初始化: next=0xXXXXXXXX, prev=0xXXXXXXXX (应该都指向自己)
[INFO ] 静态初始化验证通过
[INFO ] 动态初始化验证通过
[INFO ] list_entry 宏测试通过：value=42
```

如果输出不对，别慌。先检查编译是否通过，然后看看 `klog_init` 是否被正确调用。我当时遇到的问题是忘记链接 `list` 库，导致链接器报找不到符号。确保 `kernel/CMakeLists.txt` 中的依赖关系正确设置，`kernel_main` 所在的目标需要链接 `list` 库。

## 到这里我们完成了什么

让我们回顾一下这篇文章的内容。我们建立了侵入式链表的基础框架，包括：

- `list_head` 结构体 — 双向链表节点，只有两个指针
- `LIST_HEAD` 宏 — 编译时初始化链表头
- `INIT_LIST_HEAD` 函数 — 运行时初始化链表头
- `list_entry` 宏 — 从链表节点获取包含结构体的指针

这些是侵入式链表设计的核心概念。理解了这些，你就理解了为什么 Linux 内核要用这种设计。数据结构本身不包含数据，而是嵌入到数据结构中，这样既节省内存，又提高缓存命中率，还支持一个数据结构同时存在于多个链表中。

说实话，第一次看到 `container_of` 宏的时候我也有点懵，觉得这玩意儿也太黑魔法了。但仔细想想，它其实就是利用了 C 语言的指针算术特性，没什么神秘的。而且这个模式在内核开发中随处可见，以后你会经常遇到类似的技巧。
