# 为什么需要堆内存分配器

说实话，当我们把虚拟内存管理系统（VMM）搞定之后，我一度以为内存管理的事情就到此为止了。毕竟我们有了页分配器，可以按 4KB 为单位分配内存，看起来应该够用了吧？直到我真正开始写内核代码，才发现这个想法有多天真。

---

## 我们现在在哪里

如果你一路跟着前面的教程走过来，我们现在在 `stage/16_vmm_pagefaults` 完成后的位置。这个阶段我们实现了虚拟内存管理系统和页错误处理，内核可以以 4KB 页为单位管理内存了。看起来很美好，对吧？

让我们看看问题出在哪里。假设你想在内核里创建一个链表节点，比如用来管理进程的任务结构体。这个结构体大概是这样：

```c
typedef struct task {
    int pid;
    char name[32];
    list_head list;    // 侵入式链表节点
    // ... 其他字段
} task_t;
```

这个结构体有多大？算一下，`int` 是 4 字节，`name` 是 32 字节，`list_head` 是 16 字节，再加上其他字段，撑死也就 100 字节左右。但是，如果我们用 VMM 来分配这个结构体，会发生什么？

```c
// 用 VMM 分配一个任务结构体
task_t* task = (task_t*)vmm_alloc_pages(1, VMAP_FLAG_WRITE);
```

这一行代码给我们分配了整整一页 —— 4096 字节！但我们实际只用了不到 100 字节。剩下的 4000 字节呢？浪费了。这就像你想买一瓶水，结果超市告诉你只能按箱买，一箱 100 瓶，你喝一瓶剩下的只能扔掉。

更糟糕的是，如果你要创建 100 个任务，用 VMM 就要分配 100 页，总共 400KB。但实际上这 100 个任务结构体加起来才 10KB 左右。在内存资源紧张的内核环境中，这种浪费是不可接受的。

---

## 当前阶段的两大痛点

### 痛点一：粒度太大，浪费严重

VMM 提供的是页级内存管理，4KB 的粒度对于大块内存分配来说是合适的，比如内核代码段、数据段，或者大的缓冲区。但对于小对象分配来说，这个粒度实在是太大了。

想想看，内核里有多少小对象需要动态分配？链表节点、树节点、哈希表条目、字符串缓冲区、消息队列……这些都是几十到几百字节的小对象。如果每个都分配一整页，内存利用率会低到令人发指的地步。

这还不是最糟的。更严重的问题是，页级分配根本无法支持精细的内存管理。你无法知道一页里有多少字节真正被使用了，有多少是空闲的。你无法在一页里分配多个小对象。这意味着，无论你的小对象有多小，都要占用一整页的虚拟地址空间。

### 痛点二：缺少灵活的动态内存管理接口

标准 C 库提供了 `malloc` 和 `free` 函数，用于动态内存分配和释放。但在内核环境中，我们没有标准 C 库的支持。这意味着什么？意味着如果你想分配一块内存，要么用 VMM 分配整页，要么自己实现一个分配器。

很多初学者会选择自己实现一个简单的分配器，比如一个大的静态数组作为内存池，然后用一个简单的算法来管理。但这有几个问题：第一，静态数组的大小是固定的，不够灵活；第二，你需要自己管理空闲块、已用块，容易出错；第三，这种实现通常没有考虑内存碎片、对齐、合并等复杂情况。

相比之下，一个成熟的堆分配器可以解决这些问题。它可以按需分配任意大小的内存，自动管理空闲块和已用块，处理内存碎片，支持对齐分配，提供统计和调试功能。

---

## 为什么现在才实现堆分配器

你可能会问，堆分配器这么重要，为什么不早点实现？这是个好问题。原因在于，堆分配器需要一个可靠的底层内存管理机制作为后备存储。

在 Stage 16 之前，我们还没有完整的虚拟内存管理系统。如果我们那时候实现堆分配器，要么只能使用固定的静态内存区域，要么需要直接操作物理内存 —— 这两种方案都有很大局限性。

现在不同了。我们有了 VMM，可以：
- 按需分配虚拟页
- 动态扩展堆的大小
- 利用页错误处理实现懒分配
- 与其他内核模块共享统一的内存管理接口

这就是为什么堆分配器在 Stage 17 才登场。它站在 VMM 的肩膀上，提供了更高级、更灵活的内存管理能力。

---

## 我们要达成的目标

在这个阶段（`stage/17_kmalloc_kfree`），我们要实现一个完整的内核堆内存分配器。这不是一个简单的玩具实现，而是一个功能完整、考虑周到的生产级分配器。

### 核心功能

我们需要实现四个核心函数：

- `kmalloc(size_t size)` —— 分配指定字节数的内存
- `kfree(void* ptr)` —— 释放之前分配的内存
- `krealloc(void* ptr, size_t new_size)` —— 重新分配内存大小
- `kmalloc_aligned(size_t size, size_t alignment)` —— 分配对齐的内存

这些函数的语义与标准 C 库的 `malloc`、`free`、`realloc` 类似，但运行在内核环境中，使用 VMM 作为后备存储。

### 设计目标

我们的堆分配器要满足以下目标：

**字节级粒度** —— 可以分配任意大小的内存，从 16 字节到几兆字节，而不是只能按 4KB 页分配

**高效利用内存** —— 多个小对象可以共享一个页，内存利用率接近 100%

**自动管理** —— 自动处理空闲块、已用块、块合并、堆扩展等复杂操作

**调试支持** —— 提供统计信息、堆转储、魔数检测等调试功能

**对齐支持** —— 支持任意 2 的幂对齐分配，满足 DMA、SIMD 等特殊需求

### 前后对比

完成这个阶段后，我们的内核会有哪些变化？

在 stage/16，我们只有页级内存管理（VMM），分配内存只能按 4KB 页为单位，小对象分配浪费严重。在 stage/17，我们将拥有完整的堆内存分配器，可以按需分配任意大小的内存，内存利用率大幅提升，内核可以使用更灵活的数据结构和算法。

这不是小改进，这是内存管理能力的质的飞跃。

## 我们即将要做的

在接下来的几篇文章中，我们会一步步完成堆内存分配器的实现。

首先，我们会学习堆分配器的设计基础。我们会了解不同的分配算法（First-Fit、Best-Fit、Buddy System），比较它们的优缺点，然后选择最适合我们场景的算法。我们还会设计堆块的数据结构，理解为什么需要这样设计。

然后，我们会实现核心数据结构。这包括堆块头部结构、堆全局状态、返回码定义、统计信息结构。我们还会配置 CMake 构建系统，把新的模块集成到内核中。

接下来是核心的 `kmalloc` 实现。我们会实现 Best-Fit 搜索算法，找到最合适的空闲块。我们会实现块分割逻辑，把大块切割成精确的大小。我们会处理从空闲链表移除块、标记为已使用、返回用户指针等一系列操作。

之后是 `kfree` 的实现。释放看起来简单，但实际上有不少细节需要处理。我们需要验证魔数确保块没有被损坏，检测双重释放避免重复释放，标记块为空闲并加入空闲链表，最重要的是实现块合并算法 —— 把相邻的空闲块合并成大块，减少内存碎片。

再之后，我们会实现堆扩展机制。当堆的空闲内存不够用时，我们需要向 VMM 申请更多的虚拟页，动态扩展堆的大小。我们会实现 `heap_init` 初始化流程，设置堆的初始状态。

然后是高级功能。`krealloc` 可以重新调整已分配内存的大小，这在动态增长数据结构时非常有用。`kmalloc_aligned` 可以分配满足特定对齐要求的内存，这对 DMA 操作和 SIMD 指令是必需的。

最后，我们会实现统计和调试功能。`heap_get_stats` 可以获取堆的统计信息，帮助分析内存使用情况。`heap_dump` 可以转储整个堆的状态，每个块的大小、使用状态、魔数验证结果都一目了然。我们还会编写一个演示程序，包含各种测试用例，验证堆分配器的正确性。

每一步都是独立的，你可以跟着做一部分，也可以全部做完。相信我，等你完整实现之后，你会对内存管理有更深入的理解。
