# 堆分配器设计基础

在上一篇中，我们讨论了为什么需要堆分配器。现在让我们来深入探讨一下堆分配器的设计。这不仅仅是写几行代码那么简单，我们需要仔细选择算法、设计数据结构、考虑各种边界情况。说实话，这部分工作如果设计不好，后面改起来会非常痛苦，所以值得我们花点时间把基础打牢。

---

## 堆与栈的区别

在开始设计之前，我们先搞清楚堆和栈的区别。这两个概念经常被混淆，但它们在内存管理中扮演完全不同的角色。

栈是由编译器自动管理的内存区域。每次你调用一个函数，编译器就会在栈上分配一块空间来存储局部变量、返回地址、调用链信息。函数返回时，这块空间自动释放。栈的分配和释放非常快，只需要移动栈指针就行了。但栈有几个限制：第一，大小有限，通常只有几兆字节；第二，生命周期由函数调用决定，你不能跨函数使用栈上的内存；第三，分配模式严格遵循后进先出（LIFO），你不能随机释放中间某个栈帧。

堆就不同了。堆是程序显式管理的内存区域。你可以用 `kmalloc` 在任意时刻分配任意大小的内存，这块内存会一直存在，直到你显式调用 `kfree` 释放它。堆可以分配很大的内存，可以达到几十GB。堆的分配和释放模式是自由的，你可以先分配 A、再分配 B、然后释放 A、最后释放 B。但这种灵活性是有代价的 —— 堆的管理比栈复杂得多，分配和释放也慢得多。

理解这个区别很重要，因为它决定了我们堆分配器的设计目标。我们不需要追求栈那样的极致速度，但需要提供灵活的分配模式和高效的内存利用率。

---

## 堆内存布局

让我们先来看一下堆在内核虚拟地址空间中的位置。

```
内核虚拟地址空间 (高地址)
┌────────────────────────────────────┐
│ 0xFFFFFFFFFFFFFFFF  内核空间结束    │
├────────────────────────────────────┤
│         ... (其他区域)              │
├────────────────────────────────────┤
│ 0xFFFFFFFF89000000  KERNEL_HEAP_MAX │  堆最大边界
│                                    │
│         ┌──────────┐               │
│         │  Block 1 │ 已使用        │  ← 可能有多个块
│         ├──────────┤               │
│         │  Block 2 │ 空闲          │
│         ├──────────┤               │
│         │  Block 3 │ 已使用        │
│         ├──────────┤               │
│         │    ...   │               │
│                                    │
│ 0xFFFFFFFF81000000  KERNEL_HEAP_BASE│  堆起始地址
├────────────────────────────────────┤
│         ... (其他区域)              │
├────────────────────────────────────┤
│ 0xFFFFFFFF80000000  内核代码起始    │
└────────────────────────────────────┘
```

堆被安排在内核虚拟地址空间中的一个固定区域，从 `0xFFFFFFFF81000000` 开始，最大可以扩展到 `0xFFFFFFFF89000000`，总共 128MB。这个区域被分成连续的块，每个块要么是已使用的，要么是空闲的。

初始的时候，堆只有 64KB（16 页）。当需要更多内存时，堆会向 VMM 申请更多的页，动态扩展。这种设计的好处是，堆不会一开始就占用大量虚拟地址空间，而是按需增长。

---

## 单个块的布局

每个块都有这样一个头部结构：

```
┌────────────────────────────────────────┐
│ heap_block_t (32 字节)                 │
├────────────────────────────────────────┤
│ size:    8 字节 (总大小，包含头部)      │
│ used:    1 字节 (使用状态)             │
│ padding: 3 字节                        │
│ prev:    8 字节 (前块指针)             │
│ next:    8 字节 (下块指针，空闲链表)    │
│ magic:   4 字节 (魔数 0x00114514)      │
│ _pad:    4 字节 (对齐填充)             │
├────────────────────────────────────────┤
│ 用户数据 (size - 32 字节)              │
│ ...                                    │
└────────────────────────────────────────┘
```

这个头部设计有几个巧妙之处。`size` 字段记录整个块的大小，包括头部本身。这样我们可以通过当前块的地址和大小，计算出下一个块的地址，实现块的遍历。`used` 字段标记块是已使用还是空闲。`prev` 和 `next` 指针用于空闲链表，但这里有个细节 —— `prev` 指针指向的是物理内存中的前一个块，而 `next` 指针是空闲链表中的下一个块。这两个指针的作用不同，后面我们会详细解释。

`magic` 字段是一个魔数，值为 `0x00114514`。这个数字看起来很奇怪，但实际上是作者的一个小彩头。它的作用是检测内存损坏。如果某个地方的代码错误地写了一块内存，覆盖了块头部，魔数就会被破坏。当我们验证块的时候，发现魔数不对，就能立即知道出问题了。

整个结构体被强制 16 字节对齐，这确保了用户数据的指针也是 16 字节对齐的，满足大多数性能要求。

## 分配算法选择

堆分配器的核心算法决定了如何选择空闲块来满足分配请求。常见的算法有几种，我们来分析一下它们的优缺点。

### First-Fit（首次适应）

First-Fit 的思想很简单：从头遍历空闲链表，找到第一个足够大的块就使用它。这个算法的优势是速度快，找到第一个合适的就停止了。但缺点也很明显：它倾向于在堆的前面分配小块，导致前面产生大量的小碎片。想象一下，堆前面全是各种小碎片，后面有一个大空闲块。这时候你要分配一个中等大小的块，First-Fit 可能会把后面的大块切割，而不是利用前面的小碎片。

### Worst-Fit（最差适应）

Worst-Fit 是 First-Fit 的反向：它遍历整个空闲链表，找到最大的空闲块。这样分配后剩余的部分尽可能大，有利于后续分配。但这个算法的问题是，它会把大块不断切割，最终导致没有足够大的连续块可分配。

### Best-Fit（最佳适应）

Best-Fit 的目标是找到大小最接近的空闲块。它遍历整个空闲链表，在所有足够大的块中选择最小的一个。这样可以减少大块被切割的概率，保留大块给大分配请求。但这个算法需要遍历整个空闲链表，分配时间较长。不过对于内核场景来说，分配大小相对固定，空闲块数量不会太多，这个开销是可以接受的。

**我们的选择是 Best-Fit**。原因有几点：第一，内核的内存分配模式相对可预测，大多数分配大小集中在几个固定值；第二，Best-Fit 能减少外部碎片，提高内存利用率；第三，我们可以通过优化遍历算法来提升性能，比如在找到精确匹配时提前返回。

### Buddy System（伙伴系统）

伙伴系统是另一种常见的分配算法，它按固定大小（2 的幂）分配内存。比如 16 字节、32 字节、64 字节、128 字节等等。分配时向上取整到下一个 2 的幂。释放时，如果相邻的块也是空闲的，就合并成更大的块。

伙伴系统的优势是合并非常简单，只需检查伙伴是否空闲。但缺点是内部碎片严重，比如你分配 100 字节，会被分配 128 字节的块，浪费 28 字节。对于内核这种对内存效率要求高的场景，伙伴系统不太适合。

## 双指针系统的设计

我们的块头部有两个指针：`prev` 和 `next`。这两个指针的作用不同，这里值得仔细解释一下。

`prev` 指针指向物理内存中的前一个块。注意，这里说的是物理内存中的前一个块，不管它是空闲的还是已使用的。这个指针的作用是支持块合并。当我们释放一个块时，需要检查它的前后邻居是否也是空闲的，如果是就合并。有了 `prev` 指针，我们可以方便地找到前一个块。

但这里有个问题：只有空闲块才需要被链接起来用于快速搜索。已使用的块不需要在空闲链表中。所以 `next` 指针只在块空闲时有效，它指向空闲链表中的下一个块。空闲链表是按地址排序的，这样合并时查找相邻块更方便。

这种设计意味着，当块被分配后，它的 `next` 指针就没有意义了，我们可以用它存储其他信息，或者干脆不用。但 `prev` 指针始终有效，因为它记录的是物理内存中的前一个块，不管这个块是什么状态。

---

## 魔数的作用

我们在块头部放了一个魔数 `0x00114514`。这个数字有什么特殊含义吗？说实话，它只是作者的一个小幽默，但它的作用是很严肃的。

魔数的核心作用是检测内存损坏。想象这样一个场景：你的代码里有个缓冲区溢出 bug，写数据时越界了，覆盖了相邻的块头部。如果没有魔数，这个错误可能不会被立即发现，等到后面某个时刻程序崩溃时，你已经完全不知道是哪里出了问题。有了魔数，每次操作块时我们都检查魔数是否正确，如果不正确就立即报错，告诉你内存损坏了。

魔数还能检测另一种错误：野指针。如果你释放了一块内存，但没有把指针置空，然后又使用了这个指针，这时块可能已经被重新分配给其他地方了。通过检查魔数，我们可以发现这个问题。

当然，魔数不是万能的。如果错误恰好把魔数改成了另一个有效的值，或者错误发生在魔数检查之后，它就检测不到了。但它确实是一个简单而有效的调试工具，能帮你快速定位很多内存错误。

---

## 块分割策略

当我们找到一个足够大的空闲块，但它比我们需要的大很多时，我们应该怎么做？直接使用整个块会很浪费，更好的做法是把块分割成两部分：一部分分配给用户，另一部分作为新的空闲块。

但分割有个阈值问题。如果剩余部分太小，比如只有几个字节，分割就没有意义了，因为新的块头部都要占 32 字节。所以我们定义了一个最小块大小 `HEAP_MIN_BLOCK`（32 字节）。只有当剩余部分至少有这么大时，我们才分割。

举个例子，假设我们需要 100 字节（包括头部对齐后是 112 字节），找到一个 200 字节的空闲块。分割后，第一个块是 112 字节（已使用），第二个块是 88 字节（空闲）。因为 88 大于 32，分割是值得的。但如果剩余只有 20 字节，就不分割了，直接把整个块给用户，虽然有点浪费，但避免了产生一个无法使用的小碎片。

---

## 块合并策略

与分割相反的是合并。当我们释放一个块时，如果它的邻居也是空闲的，我们应该把它们合并成一个大块。这样可以减少外部碎片，保留更大的块给大分配请求。

合并需要检查前后两个邻居。检查后邻居比较简单，通过当前块的地址和大小，可以计算出后邻居的地址。然后检查后邻居是否空闲。如果空闲，就把两个块合并：把当前块的大小加上后邻居的大小，更新后邻居的链接。

检查前邻居稍微复杂一点。我们需要找到物理内存中紧邻当前块的前一个块。这可以通过 `prev` 指针实现，但要注意 `prev` 指针指向的是物理内存中的前一个块，不管它是空闲还是已使用。所以我们还需要检查前一个块是否空闲，以及它是否真的紧邻当前块（通过地址计算验证）。

合并后，原来分开的两个块变成一个大块，块数量减少，空闲块总大小增加。这就是合并的价值。

---

## 堆扩展策略

堆不是一开始就分配全部 128MB 的。初始的时候，堆只有 64KB。当需要更多内存时，堆会向 VMM 申请更多的页。

但这里有个问题：每次扩展多少页？如果每次只扩展一页（4KB），频繁的扩展会增加开销。如果每次扩展太多，可能浪费内存。我们的策略是，每次至少扩展 4 页（16KB）。如果请求的大小更大，就按请求大小扩展，但向上取整到页边界。

扩展的时机是在 `kmalloc` 找不到合适的空闲块时。这时我们尝试扩展堆，然后在新的空闲块中搜索。如果扩展失败（比如 VMM 没有足够的物理内存），就返回 NULL，表示内存不足。

堆只能扩展到最大边界 `KERNEL_HEAP_MAX`。一旦达到这个边界，即使物理内存还有剩余，堆也无法继续扩展了。这个限制是虚拟地址空间规划决定的，如果需要更大的堆，只能调整虚拟地址空间布局。

---

## 对齐要求

内存对齐是性能优化的关键。现代 CPU 访问对齐的内存比访问未对齐的内存快得多，某些架构甚至直接不支持未对齐访问。

我们的堆分配器保证返回的指针是 16 字节对齐的。这是因为块头部本身就是 16 字节对齐的，用户数据紧跟着头部，自然也是对齐的。16 字节对齐能满足大多数需求，包括 SSE 指令和缓存行对齐。

但有些场景需要更大的对齐，比如 DMA 操作通常需要 4KB 对齐，AVX 指令可能需要 32 字节对齐。对于这些需求，我们提供了 `kmalloc_aligned` 函数，可以指定任意的 2 的幂对齐。这个函数的实现有一个巧妙的设计：它分配额外的空间，在对齐的地址前存储原始指针，这样释放时可以找到真正的块头部。
