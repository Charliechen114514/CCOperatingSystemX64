# 时间片与定时器集成 —— Stage 22 调度类框架实战指南（五）

## 前言

前几篇文章我们搭建了框架，实现了 RR 调度类。但有一个关键的东西我们还没深入讲：时间片是怎么工作的？定时器中断是怎么触发调度的？说实话，这是调度器中最容易出问题的地方。

时间片用完没重置会导致进程永远不再被调度；定时器回调没注册会导致调度器永远不会切换任务；重调度标志设置不当会导致调度延迟或过度调度。这些都是我在实现过程中踩过的坑，这篇文章会把它们都讲清楚。

这篇文章我们会深入讲解时间片管理和定时器集成的完整机制。虽然我们已经在 `sched.c` 中写了一些代码，但现在是时候完整理解它们是怎么工作的了。

---

## 现在我们要做什么

这篇文章的目标是彻底理解时间片和定时器的工作机制：

1. 理解定时器中断的完整流程
2. 理解时间片的递减和重置机制
3. 理解 `need_resched` 标志的作用
4. 理解 `schedule()` 函数的完整流程
5. 排查时间片相关的常见问题

## 定时器中断流程

### 1000Hz 定时器

我们的系统使用 1000Hz 的定时器，也就是每毫秒触发一次中断。这个频率不是随便选的，它有几个好处：

第一，时间片单位是 1ms，调度粒度足够细。对于大多数交互式程序来说，10ms 的时间片已经足够响应迅速。

第二，1000Hz 的中断开销是可以接受的。现代 CPU 处理每秒 1000 次中断毫无压力。

第三，时间片计算简单。10ms 就是 10 个 tick，不需要复杂的换算。

### 定时器中断处理流程

让我们从定时器中断开始，追踪整个调度流程：

```
定时器硬件触发中断
    │
    ▼
CPU 跳转到 IDT 的 timer 中断向量
    │
    ▼
timer_irq_handler() (汇编入口)
    │
    ├─> 保存寄存器
    ├─> 调用 C 语言处理函数
    ▼
timer_handler() (C 处理函数)
    │
    ├─> 调用注册的回调函数
    ▼
sched_timer_tick_handler()
    │
    ├─> 获取调度器锁
    ├─> 检查是否有当前进程
    ├─> 调用进程调度类的 task_tick()
    │       │
    │       └─> rr_task_tick() 或 prio_task_tick()
    │           └─> 递减 time_slice
    │               │
    │               └─> 如果 time_slice == 0，设置 need_resched
    │
    ├─> 释放调度器锁
    ▼
中断返回到被打断的代码
    │
    ▼
如果 need_resched == true，稍后调用 schedule()
```

这个流程的关键点是：时间片的递减发生在中断上下文中，而实际的调度发生在稍后的某个时刻（可能是中断返回后，也可能是主动让出 CPU 时）。

## 时间片管理详解

### 时间片的两个字段

你可能注意到了，`sched_entity_t` 中有两个时间片相关字段：

```c
uint32_t          time_slice;     /* 剩余时间片（毫秒） */
uint32_t          time_slice_total; /* 完整时间片（毫秒） */
```

为什么要两个字段呢？因为当一个任务的时间片用完后，我们需要知道它的完整时间片是多少，才能在它再次获得 CPU 时重置。如果只有一个字段，时间片用完变成 0，我们就不知道原始值了。

### 时间片初始化

进程创建时，时间片在 `task_fork()` 中初始化：

```c
static void rr_task_fork(struct pcb* pcb, int nice) {
    /* ... 其他初始化 ... */

    pcb->sched_entity.time_slice = RR_TIMESLICE_DEFAULT;       /* = 10 */
    pcb->sched_entity.time_slice_total = RR_TIMESLICE_DEFAULT; /* = 10 */
}
```

新进程获得完整的 10ms 时间片。

### 时间片递减

每毫秒，定时器中断调用 `task_tick()`：

```c
static void rr_task_tick(struct sched_rq* rq, struct pcb* pcb) {
    if (pcb->sched_entity.time_slice > 0) {
        pcb->sched_entity.time_slice--;
    }
}
```

这里有个细节：我们在递减前检查 `time_slice > 0`。这是为了防止下溢变成一个非常大的无符号数。虽然正常情况下时间片不会变成负数，但加上这个检查更安全。

注意这里我们没有直接设置 `need_resched` 标志。这是框架的责任，不是调度类的责任。框架会在 `task_tick()` 之后检查时间片是否为 0，然后决定是否需要重调度。

### 时间片重置

当一个任务被选中运行时，它的时间片需要重置。这发生在 `schedule()` 函数中：

```c
void schedule(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);

    /* 选择下一个任务 */
    struct pcb* next = sched_pick_next_task();

    if (next) {
        /* 重置时间片 */
        sched_reset_time_slice(next);
    }

    /* ... 切换上下文 ... */

    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

`sched_reset_time_slice()` 的实现很简单：

```c
void sched_reset_time_slice(struct pcb* pcb) {
    if (!pcb || !pcb->sched_entity.sched_class) {
        return;
    }

    pcb->sched_entity.time_slice = pcb->sched_entity.time_slice_total;
}
```

## need_resched 标志机制

### 为什么需要延迟调度

当定时器中断发现时间片用完时，它不应该立即触发调度。原因是：

第一，我们在中断上下文中，直接调度可能导致复杂的竞态条件。

第二，频繁的上下文切换会影响性能。如果多个任务的时间片几乎同时用完，我们希望在一次调度操作中处理完，而不是调度多次。

第三，某些操作可能需要短暂禁止调度。使用标志位可以延迟调度到合适的时间。

### 设置标志

时间片用完时，框架设置重调度标志：

```c
static void sched_timer_tick_handler(uint64_t ticks) {
    /* ... 获取锁 ... */

    if (scheduler.current && scheduler.rq != NULL) {
        if (scheduler.current->sched_entity.sched_class) {
            sched_rq_t* rq = &scheduler.rq[scheduler.current->sched_entity.policy];
            scheduler.current->sched_entity.sched_class->task_tick(rq, scheduler.current);

            /* 检查时间片是否用完 */
            if (scheduler.current->sched_entity.time_slice == 0) {
                sched_set_resched_locked();
            }
        }
    }

    /* ... 释放锁 ... */
}
```

`sched_set_resched_locked()` 是设置标志的内部版本，调用时必须已经持有调度器锁：

```c
void sched_set_resched_locked(void) {
    scheduler.need_resched = true;
}
```

### 检查标志

代码可以通过 `sched_needs_reschedule()` 检查是否需要调度：

```c
bool sched_needs_reschedule(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);
    bool needs = scheduler.need_resched;
    spin_unlock_irqrestore(&g_scheduler_lock, flags);
    return needs;
}
```

这个函数在内核的很多地方被调用，比如中断返回前、系统调用返回前、自旋锁释放后等。如果需要调度，就会调用 `schedule()`。

### 清除标志

调度完成后，标志需要被清除：

```c
void sched_clear_resched(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);
    scheduler.need_resched = false;
    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

这通常在 `schedule()` 函数的最后调用：

```c
void schedule(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);

    /* ... 调度逻辑 ... */

    sched_clear_resched_locked();

    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

## schedule() 完整流程

现在我们可以看一下 `schedule()` 函数的完整流程了。这个函数是调度的核心，每个字都很重要。

### 函数入口

```c
void schedule(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);

    struct pcb* prev = scheduler.current;
    struct pcb* next;

    /* ... 调度逻辑 ... */

    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

首先获取调度器锁，并禁用中断。这是必须的，因为调度过程中我们要修改运行队列等关键数据结构，不能被并发访问打断。

### 选择下一个任务

```c
/* 选择下一个任务 */
next = sched_pick_next_task();

if (next == NULL) {
    /* 没有可运行的任务，切换到 idle */
    next = scheduler.idle;
}

if (next == prev) {
    /* 选择的还是当前任务，不需要切换 */
    sched_clear_resched_locked();
    spin_unlock_irqrestore(&g_scheduler_lock, flags);
    return;
}
```

`sched_pick_next_task()` 我们在框架代码中已经实现了。它会优先检查 Priority 队列，如果没有再检查 RR 队列。

如果返回 `NULL`，说明没有可运行的任务，我们切换到 idle 任务。

如果返回的还是当前任务，说明不需要切换，直接返回即可。这种情况发生在当前任务还有时间片，且没有更高优先级任务时。

### 处理当前任务

```c
/* 处理当前任务 */
if (prev->state == PROC_RUNNING) {
    /* 当前任务仍在运行状态，重新入队 */
    sched_enqueue_task_locked(prev, false);
} else {
    /* 当前任务已阻塞或退出，不需要入队 */
}
```

如果当前任务还在 `PROC_RUNNING` 状态，说明它只是时间片用完，应该重新加入队列等待下一轮。如果任务已经变成其他状态（阻塞、退出等），就不需要重新入队了。

### 切换到下一个任务

```c
/* 重置下一个任务的时间片 */
sched_reset_time_slice(next);

/* 更新当前任务 */
scheduler.current = next;

/* 清除重调度标志 */
sched_clear_resched_locked();

/* 准备切换上下文 */
switch_to(prev, next);
```

重置时间片是关键的一步。如果忘记这步，任务会一直带着 0 时间片运行，永远不会被调度切换。

然后更新 `scheduler.current`，清除重调度标志，最后调用 `switch_to()` 完成实际的上下文切换。

## 常见陷阱与调试

### 陷阱 1：时间片没有重置

症状是进程运行一次后，永远不再被调度。

原因是在选择下一个任务后，忘记调用 `sched_reset_time_slice()`。

调试方法：在 `schedule()` 中加日志：

```c
klog_info("[SCHED] Next PID=%d, time_slice=%d/%d\n",
          next->pid, next->sched_entity.time_slice, next->sched_entity.time_slice_total);
```

如果 `time_slice` 是 0 而 `time_slice_total` 不是 0，说明重置函数没有被调用。

### 陷阱 2：定时器回调没有注册

症状是时间片永远不会递减，进程一直运行不被切换。

原因是定时器回调没有注册。检查 `sched_class_init()` 中是否有：

```c
timer_set_callback(sched_timer_tick_handler);
```

调试方法：在 `rr_task_tick()` 中加日志，如果没有日志输出，说明回调函数没有被调用：

```c
klog_info("[RR] PID=%d tick, time_slice=%d\n", pcb->pid, pcb->sched_entity.time_slice);
```

### 陷阱 3：中断上下文中的锁使用

症状是系统死锁或崩溃。

原因是在定时器回调中使用了普通的自旋锁，而不是 `irqsave` 变体。定时器中断可能在持有锁的时候发生，导致死锁。

正确做法是使用 `spin_lock_irqsave()` 和 `spin_unlock_irqrestore()`：

```c
spinlock_flags_t flags;
spin_lock_irqsave(&g_scheduler_lock, &flags);
/* ... 临界区 ... */
spin_unlock_irqrestore(&g_scheduler_lock, flags);
```

### 陷阱 4：调度器锁未释放

症状是系统停止响应，CPU 空转。

原因是获取了调度器锁但忘记释放，或者在某条路径上提前返回导致锁未释放。

调试方法：使用静态分析工具检查代码路径，确保每个 `spin_lock_irqsave()` 都有对应的 `spin_unlock_irqrestore()`。

## 调试技巧

### 查看运行队列状态

在调试调度问题时，知道哪些任务在队列上非常有用。可以添加一个调试函数：

```c
void sched_dump_queues(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);

    klog_info("[SCHED] Dumping run queues:\n");

    for (int i = 0; i < SCHED_MAX; i++) {
        sched_rq_t* rq = &scheduler.rq[i];
        klog_info("[SCHED] Policy %d: nr_running=%d\n", i, rq->nr_running);

        struct pcb* pcb;
        list_for_each_entry(pcb, &rq->queue, sched_entity.run_list) {
            klog_info("[SCHED]   PID=%d, time_slice=%d/%d\n",
                      pcb->pid, pcb->sched_entity.time_slice,
                      pcb->sched_entity.time_slice_total);
        }
    }

    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

### 查看当前任务状态

```c
void sched_dump_current(void) {
    spinlock_flags_t flags;
    spin_lock_irqsave(&g_scheduler_lock, &flags);

    if (scheduler.current) {
        klog_info("[SCHED] Current: PID=%d, state=%d, policy=%d, time_slice=%d/%d\n",
                  scheduler.current->pid, scheduler.current->state,
                  scheduler.current->sched_entity.policy,
                  scheduler.current->sched_entity.time_slice,
                  scheduler.current->sched_entity.time_slice_total);
    }

    spin_unlock_irqrestore(&g_scheduler_lock, flags);
}
```

### 跟踪调度事件

在关键调度点添加日志：

```c
void schedule(void) {
    /* ... */

    klog_info("[SCHED] Schedule: prev=PID:%d, next=PID:%d\n",
              prev ? prev->pid : -1, next ? next->pid : -1);

    /* ... */
}
```
