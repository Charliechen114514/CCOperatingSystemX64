# 从简单轮转到调度类框架 —— Stage 22 调度类框架实战指南（一）

## 前言

写到 Stage 22 的时候，我意识到一个问题：虽然我们已经在 Stage 21 实现了进程管理，有了进程切换、有了简单的调度，但这个调度器实在是太"简单"了。简单到什么程度呢？所有进程都用同一种调度策略，一个全局运行队列，FIFO 轮转，没有优先级，没有抢占，更谈不上为不同类型的进程提供不同的服务。

说实话，在早期开发阶段，这样简单的设计确实让我们快速跑起来了。但当你开始思考更实际的问题时，这个设计就会暴露出明显的局限。比如，你希望系统关键进程能够更快地响应？做不到。你希望后台任务不要抢占交互式程序？也做不到。你想添加一个新的调度算法试试？那就更麻烦了，得把整个调度器的代码都改一遍。

这就像开了一家只有一个窗口的餐厅，不管你是 VIP 客户还是普通顾客，都得排同一个队。VIP 客户肯定不乐意，因为他们希望有专属通道；餐厅老板也不乐意，因为无法灵活调整服务策略来提高营收。

我们需要的正是一个灵活的、可扩展的调度框架——调度类框架。这个想法直接来自于 Linux 的调度器设计。Linux 内核支持多种调度策略（SCHED_NORMAL、SCHED_FIFO、SCHED_RR、SCHED_DEADLINE 等），而且可以轻松添加新的策略。这一切的基础就是一个模块化的调度类架构。

所以这一篇，我们会一起把简单粗暴的单一调度器，改造成一个支持多种调度策略共存的调度类框架。别担心，我们不会跳过任何步骤，每写一个函数都会解释清楚它是怎么工作的，为什么要这么写。准备好了吗？我们开始。

## 回顾 Stage 21 的简单调度

让我们先来看看 Stage 21 的调度器是怎么工作的。在那个时候，调度器的设计非常直接：

```c
// Stage 21 的简化调度逻辑（示意）
void schedule(void) {
    if (list_is_empty(&scheduler.run_queue)) {
        return;  // 没有可运行的任务
    }

    // 从队列头部取下一个任务
    pcb_t* next = list_first_entry(&scheduler.run_queue, pcb_t, run_list);
    list_del_init(&next->run_list);

    // 切换到 next
    switch_to(scheduler.current, next);
}
```

这个设计有几个特点：

第一，**单一队列**。所有进程都挂在同一个 `run_queue` 上，排队等待 CPU 时间。

第二，**FIFO 调度**。谁先来谁先执行，没有优先级概念。

第三，**固定时间片**。每个进程运行一段时间后被强制切换，时间片长度是固定的。

第四，**硬编码逻辑**。调度的所有逻辑都写死在 `schedule()` 函数里，想改算法就得改这个函数。

说实话，这个设计在 Stage 21 是完全够用的。我们的目标只是让多个进程能够轮流运行，不追求任何高级特性。但随着系统越来越复杂，这个简单设计就开始让人感到束缚了。

---

## 单一调度算法的局限性

那么，简单调度到底有什么问题呢？让我们从几个实际场景来看。

**场景一：系统关键进程需要更快响应**

假设你的操作系统有一个处理键盘输入的系统进程。当用户按下键盘时，中断处理程序会唤醒这个进程来处理输入。但如果这个进程和其他所有进程排同一个队，而前面正好有一个 CPU 密集型的计算任务在运行，那么键盘输入的响应就会明显延迟。这对用户体验来说是灾难性的。

你可能会说，那就给键盘进程更高的优先级吧。但问题是，我们的简单调度器根本不支持优先级。要加优先级，就得改调度器的核心逻辑，把单一队列改成优先级队列，这可不是小改动。

**场景二：不同类型的进程需要不同的调度策略**

有些进程是交互式的（比如 Shell），它们需要快速响应用户输入；有些进程是批处理任务（比如编译），它们不关心响应时间，只希望获得更多 CPU 时间；还有些进程是实时任务（比如音频播放），它们必须在指定时间内完成工作，否则就会出现卡顿。

这些不同类型的进程，本质上需要不同的调度策略。但我们的简单调度器只能提供一种策略——固定时间片的 FIFO。你想为不同进程提供不同服务？做不到。

**场景三：添加新的调度算法很困难**

假设你想尝试一个新的调度算法，比如完全公平调度器（CFS）。在简单调度器的设计下，你得修改 `schedule()` 函数，把原来的逻辑删掉，换成新算法的逻辑。这不仅工作量大，而且意味着你无法同时保留多种算法，只能二选一。

这在研究和开发阶段是很不方便的。你可能希望同时运行多种调度算法，对比它们的性能差异。或者你希望某些进程用旧算法，某些进程用新算法，逐步迁移。简单调度器无法满足这些需求。

## 模块化调度类框架的解决方案

面对这些问题，Linux 内核给出的解决方案是：调度类（Scheduling Class）框架。这个框架的核心思想是，将调度器的"通用逻辑"和"具体算法"分离开来。

通用逻辑包括：什么时候触发调度、如何切换上下文、如何处理定时器中断等。这些是所有调度算法都需要做的事情。

具体算法包括：如何选择下一个任务、如何处理时间片耗尽、如何判断抢占等。这些是不同算法有不同实现的部分。

通过这种分离，我们就可以实现：

**第一，多策略共存**。系统可以同时注册多个调度类，每个进程可以选择使用其中一个调度类。不同调度类的进程可以同时运行，调度器会根据优先级规则选择合适的进程。

**第二，易于扩展**。要添加新的调度算法，只需要实现调度类接口，然后注册到系统即可。不需要修改调度器的核心代码。

**第三，类型隔离**。系统进程可以使用 Priority 调度类获得快速响应，用户进程可以使用 Round-Robin 调度类获得公平分配。两者的运行队列是独立的，互不干扰。

这就是我们这一阶段要实现的目标。

## 调度类框架的核心概念

在深入代码之前，让我们先理解调度类框架的几个核心概念。这些概念来自于 Linux 的调度器设计，我们会做适当的简化。

### 调度类（Scheduling Class）

调度类是一个"虚函数表"，定义了一组操作函数。每个具体的调度算法（比如 RR、Priority）都需要实现这些函数。

```c
typedef struct sched_class {
    const char* name;              // 类名称（调试用）
    sched_policy_t policy;         // 策略标识

    // 入队操作
    void (*enqueue_task)(struct sched_rq* rq, struct pcb* pcb, bool head);

    // 出队操作
    void (*dequeue_task)(struct sched_rq* rq, struct pcb* pcb);

    // 选择下一个任务
    struct pcb* (*pick_next_task)(struct sched_rq* rq, struct pcb* prev);

    // 抢占判断
    bool (*should_preempt)(struct pcb* p, struct pcb* curr);

    // 时间片处理（定时器回调）
    void (*task_tick)(struct sched_rq* rq, struct pcb* pcb);

    // 任务 fork 回调
    void (*task_fork)(struct pcb* pcb, int nice);

    // 获取时间片
    uint32_t (*get_time_slice)(const struct pcb* pcb);
} sched_class_t;
```

你可以把它理解为 C 语言中的"接口"或"抽象类"。每个调度类都必须实现这些函数，但具体实现可以完全不同。

### Per-Policy 运行队列

每个调度策略维护自己的运行队列。RR 调度类有一个队列，Priority 调度类有 128 个队列（每个优先级一个）。这样不同策略的任务不会互相干扰。

```c
typedef struct sched_rq {
    sched_class_t* sched_class;    // 关联的调度类
    list_head        queue;         // 通用运行队列
    uint32_t         nr_running;    // 队列中的任务数
    void*            class_data;    // 类特定的私有数据
} sched_rq_t;
```

`class_data` 字段很重要，它允许每个调度类存储自己需要的额外数据。比如 Priority 调度类需要 128 个队列，就可以把队列数组放在这里。

### 调度实体（Scheduling Entity）

每个进程 PCB 中嵌入一个调度实体，存储这个进程的调度相关信息。

```c
typedef struct sched_entity {
    sched_policy_t    policy;         // 调度策略
    sched_class_t*    sched_class;    // 指向调度类
    uint32_t          time_slice;     // 剩余时间片
    uint32_t          time_slice_total; // 完整时间片
    int               priority;       // 优先级
    int               nice;           // Nice 值（预留）
    uint64_t          last_ran;       // 上次运行时间（预留）
    list_head         run_list;       // 队列节点
} sched_entity_t;
```

这样，调度器可以通过进程的 PCB 找到它的调度实体，进而知道它属于哪个调度类、有多少时间片、优先级是多少等信息。

## 本阶段要实现的目标

在这个阶段，我们需要实现以下组件：

**调度类框架核心**：
- sched.h/sched.c —— 框架接口和实现
- 调度类注册机制
- Per-Policy 运行队列管理
- 任务选择和调度流程

**Round-Robin 调度类**：
- sched_rr.h/sched_rr.c —— RR 调度实现
- 简单 FIFO 调度
- 固定 10ms 时间片
- 适合普通用户进程

**Priority 调度类**：
- sched_prio.h/sched_prio.c —— Priority 调度实现
- 128 级优先级（0-127）
- Active/Expired 队列机制
- 优先级抢占支持
- 适合系统关键进程

**进程管理集成**：
- 扩展 PCB 添加 sched_entity
- fork 时设置调度策略
- 调度器集成到进程切换流程

**演示程序**：
- sched_demo.h/sched_demo.c —— 演示和测试程序
- RR 调度测试
- Priority 调度测试
- 抢占行为测试

实现之后，我们的内核将能够：
- 同时运行 RR 和 Priority 两种调度策略
- 不同策略的进程使用独立的运行队列
- 高优先级任务可以抢占低优先级任务
- 方便地扩展新的调度算法

## 与前一阶段对比

让我们通过一个表格来看看从 Stage 21 到 Stage 22 的变化：

| 特性 | Stage 21 (简单进程管理) | Stage 22 (调度类框架) |
|------|------------------------|----------------------|
| 调度架构 | 单一简单轮转 | 模块化调度类框架 |
| 调度算法 | 固定 Round-Robin | RR + Priority（可扩展） |
| 运行队列 | 单一全局队列 | per-policy 运行队列 |
| 时间片管理 | 简单递减 | 类定义时间片策略 |
| 抢占机制 | 无 | 优先级抢占支持 |
| 调度实体 | 简单 run_list | 完整 sched_entity_t |
| 优先级 | 不支持 | 128 级优先级 |
| Active/Expired | 无 | Priority 类支持 |
| 扩展性 | 低 | 高（虚函数表） |

可以看到，Stage 22 的调度器要复杂得多，但这种复杂带来的好处是系统变得更加灵活和可扩展。
