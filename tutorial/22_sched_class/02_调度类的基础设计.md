# 调度类的基础设计 —— Stage 22 调度类框架实战指南（二）

## 前言

上一篇文章我们讲了为什么需要调度类框架，以及这个框架要解决什么问题。现在我们正式进入设计环节。说实话，设计一个可扩展的调度器架构并不容易，特别是我们用的是 C 语言，没有类和继承这些高级特性。但 Linux 内核做到了，用的是一种叫做"虚函数表"的技术。

这篇文章我们会详细讲解调度类的基础设计：虚函数表是什么，调度类结构怎么定义，调度实体有什么用，per-policy 队列为什么需要。这些设计不是凭空想象出来的，每一项都有它的原因。

我第一次学习 Linux 调度器的时候，被这些嵌套的结构体绕晕了好几天。但当你真正理解了每个字段的用途，理解了它们之间的关联，你会发现这个设计其实很优雅，每一步都恰到好处。

## 虚函数表模式

### C 语言中的多态

在 C++ 或 Java 这样的面向对象语言中，多态是通过虚函数实现的。你定义一个基类，声明一些虚函数，然后派生类可以重写这些函数。当你通过基类指针调用虚函数时，实际执行的是派生类的版本。

C 语言没有这种机制，但我们可以用函数指针来模拟。这就是"虚函数表"模式。

核心思想很简单：定义一个结构体，里面包含一组函数指针。不同的实现提供不同的函数，调用者通过这些函数指针来调用具体实现。

```c
// 虚函数表示例
typedef struct animal_ops {
    void (*speak)(void);           // 叫声
    void (*move)(void);            // 移动
    void (*eat)(const char* food); // 进食
} animal_ops_t;

// 狗的实现
void dog_speak(void) { printf("Woof!\n"); }
void dog_move(void) { printf("Running\n"); }
void dog_eat(const char* food) { printf("Eating %s\n", food); }

animal_ops_t dog_ops = {
    .speak = dog_speak,
    .move = dog_move,
    .eat = dog_eat,
};

// 猫的实现
void cat_speak(void) { printf("Meow!\n"); }
void cat_move(void) { printf("Sneaking\n"); }
void cat_eat(const char* food) { printf("Eating %s\n", food); }

animal_ops_t cat_ops = {
    .speak = cat_speak,
    .move = cat_move,
    .eat = cat_eat,
};

// 通过虚函数表调用
void interact(animal_ops_t* animal) {
    animal->speak();
    animal->move();
    animal->eat("fish");
}
```

这就是调度类框架的核心模式。每个调度类（RR、Priority）都有自己的虚函数表，调度器框架通过这个表来调用具体实现。

### 为什么选择虚函数表

你可能会问，为什么不用 switch-case 或者宏定义？那些不是更简单吗？

确实，switch-case 更简单直接。但它的问题是扩展性差。每加一个新调度策略，你就得修改调度器核心代码，在所有涉及调度的地方加一个新的 case 分支。这不仅工作量大，而且容易出错。

宏定义也有类似的问题，而且类型不安全，调试起来更是让人血压拉高。

虚函数表虽然多了一层间接调用，但它带来的好处是巨大的：添加新策略不需要修改核心代码，只需要实现接口并注册即可。这种"开闭原则"——对扩展开放，对修改封闭——是优秀软件设计的基本要求。

## 调度类结构详解

### sched_class_t 定义

让我们来看看调度类结构的完整定义：

```c
typedef struct sched_class {
    const char* name;              /* 类名称，用于调试和日志 */
    sched_policy_t policy;         /* 策略标识符 */

    /**
     * @brief 将任务加入运行队列
     * @param rq 运行队列
     * @param pcb 要加入的任务
     * @param head 如果为 true，加到队列头部；否则加到尾部
     */
    void (*enqueue_task)(struct sched_rq* rq, struct pcb* pcb, bool head);

    /**
     * @brief 将任务移出运行队列
     * @param rq 运行队列
     * @param pcb 要移出的任务
     */
    void (*dequeue_task)(struct sched_rq* rq, struct pcb* pcb);

    /**
     * @brief 选择下一个运行的任务
     * @param rq 运行队列
     * @param prev 上一个运行的任务
     * @return 下一个要运行的任务，队列为空时返回 NULL
     */
    struct pcb* (*pick_next_task)(struct sched_rq* rq, struct pcb* prev);

    /**
     * @brief 判断是否应该抢占
     * @param p 候选任务
     * @param curr 当前运行的任务
     * @return 如果 p 应该抢占 curr，返回 true
     */
    bool (*should_preempt)(struct pcb* p, struct pcb* curr);

    /**
     * @brief 定时器 tick 回调
     * @param rq 运行队列
     * @param pcb 当前运行的任务
     *
     * 这个函数每毫秒被调用一次（1000Hz 定时器）
     * 用于递减时间片，检测是否需要重调度
     */
    void (*task_tick)(struct sched_rq* rq, struct pcb* pcb);

    /**
     * @brief 任务 fork 时的初始化回调
     * @param pcb 新创建的任务
     * @param nice 优先级修饰符（预留）
     */
    void (*task_fork)(struct pcb* pcb, int nice);

    /**
     * @brief 获取时间片长度
     * @param pcb 任务
     * @return 时间片长度（毫秒）
     */
    uint32_t (*get_time_slice)(const struct pcb* pcb);

} sched_class_t;
```

### 各个函数的作用

每个函数都有它的用途，让我们逐一分析。

**enqueue_task**：当进程变为可运行状态时被调用。比如进程刚创建，或者从阻塞状态被唤醒时。`head` 参数控制加入位置，一般来说新任务加到尾部，但有些特殊情况需要加到头部。

**dequeue_task**：当进程不再可运行时被调用。比如进程阻塞、退出，或者被抢占时。调度类需要从自己的队列中移除这个任务。

**pick_next_task**：调度器需要选择下一个运行的任务时调用这个函数。不同的调度类有不同的选择逻辑：RR 返回队列头，Priority 返回最高优先级的任务。

**should_preempt**：判断一个任务是否应该抢占当前运行的任务。这主要用于优先级调度，高优先级任务应该能够抢占低优先级任务。RR 调度通常不抢占，除非当前任务时间片用完。

**task_tick**：这是定时器中断的回调函数，每毫秒调用一次。调度类在这里递减时间片，如果时间片耗尽就设置重调度标志。这是调度器能够"按时"切换任务的基础。

**task_fork**：创建新进程时调用这个函数初始化调度实体。调度类可以在这里设置时间片、优先级等初始值。

**get_time_slice**：获取任务的时间片长度。不同调度类可能返回不同的值，Priority 调度可能根据优先级动态计算时间片。

### 调度策略枚举

我们需要一个枚举来标识不同的调度策略：

```c
typedef enum sched_policy {
    SCHED_NORMAL   = 0,    /* 普通 Round-Robin 调度 */
    SCHED_PRIORITY = 1,    /* 优先级调度（系统进程） */
    SCHED_MAX      = 2,    /* 调度策略数量 */
} sched_policy_t;
```

这个枚举有两个用途：第一，作为索引访问调度类数组和运行队列数组；第二，标识一个进程使用哪种调度策略。

## Per-Policy 运行队列设计

### 为什么需要 Per-Policy 队列

在简单调度器中，我们只有一个全局运行队列。但在多策略系统中，这不够用。

首先，不同调度策略的数据结构不同。RR 只需要一个简单队列，Priority 需要 128 个队列（每个优先级一个）。如果混在一起，管理起来会很麻烦。

其次，我们希望不同策略的任务互不干扰。RR 的任务不应该影响 Priority 的调度决策，反之亦然。per-policy 队列提供了这种隔离。

### sched_rq_t 结构

```c
typedef struct sched_rq {
    sched_class_t* sched_class;    /* 关联的调度类 */
    list_head        queue;         /* 通用运行队列 */
    uint32_t         nr_running;    /* 队列中的任务数 */
    void*            class_data;    /* 类特定的私有数据 */
} sched_rq_t;
```

**sched_class**：指向这个队列关联的调度类。这样我们可以通过队列找到对应的操作函数。

**queue**：通用的双向链表头。RR 调度类直接用这个队列，Priority 调度类会忽略它，使用 class_data 中的复杂队列结构。

**nr_running**：记录队列中有多少任务。这个字段在判断是否需要切换到 idle 任务时很有用。

**class_data**：这是一个设计得很巧妙的地方。由于不同调度类可能需要完全不同的私有数据，我们用一个 void 指针来存放。RR 类可能不需要这个字段（设为 NULL），Priority 类会把一个包含 256 个队列的结构体指针放在这里。

### 全局运行队列数组

在框架实现中，我们维护一个运行队列数组：

```c
static sched_rq_t s_run_queues[SCHED_MAX];
```

`s_run_queues[0]` 是 RR 的运行队列，`s_run_queues[1]` 是 Priority 的运行队列。要扩展新策略，只需要增加数组大小和对应的枚举值即可。

## 调度实体设计

### 为什么需要 sched_entity

调度实体（sched_entity_t）是嵌入在 PCB 中的一块数据，存储了调度器需要的所有信息。

为什么不直接把这些字段加到 PCB 里呢？原因有二：

第一，模块化考虑。调度相关的字段应该聚在一起，这样可以清晰地划分"进程管理"和"调度"的职责边界。

第二，扩展性考虑。未来如果每个调度类需要不同的私有数据，可以在 sched_entity 中增加一个 void 指针，类似于 sched_rq 的 class_data。

### sched_entity_t 结构

```c
typedef struct sched_entity {
    sched_policy_t    policy;         /* 调度策略 */
    sched_class_t*    sched_class;    /* 指向调度类 */
    uint32_t          time_slice;     /* 剩余时间片（毫秒） */
    uint32_t          time_slice_total; /* 完整时间片（毫秒） */
    int               priority;       /* 优先级（0-127，越小越高） */
    int               nice;           /* Nice 值（预留，用于动态优先级） */
    uint64_t          last_ran;       /* 上次运行时间（预留） */
    list_head         run_list;       /* 队列节点 */
} sched_entity_t;
```

**policy**：标识这个进程使用哪种调度策略。调度器根据这个值找到对应的运行队列和调度类。

**sched_class**：指向具体的调度类结构。这样我们可以直接调用 `pcb->sched_entity.sched_class->task_tick()` 之类的函数，而不需要每次都查表。

**time_slice / time_slice_total**：记录时间片信息。`time_slice` 是剩余时间，每毫秒递减；`time_slice_total` 是完整时间片，用于重置。

**priority**：优先级，用于 Priority 调度。数值越小优先级越高，0 是最高优先级，127 是最低。

**nice**：这是从 Unix 借鉴的概念，用于调整优先级。正数 nice 值降低优先级，负数提高优先级。目前预留未用，未来可以实现动态优先级调整。

**last_ran**：记录上次运行的时间戳。预留字段，用于实现 CFS 这样的基于虚拟运行时间的调度器。

**run_list**：链表节点。进程通过这个节点挂在调度类的运行队列上。

### PCB 中的嵌入

```c
typedef struct pcb {
    /* ... 其他字段 ... */

    sched_entity_t sched_entity;   /* 调度实体 */

    /* ... 其他字段 ... */
} pcb_t;
```

这里使用的是"嵌入"而不是"指针"。意思是 sched_entity 直接作为 PCB 的一个字段存在，而不是动态分配的内存。这样做的好处是访问更快，不需要额外的内存分配和释放操作。

## 设计中的权衡

### 为什么用数组而不是链表

调度类数组和运行队列数组使用的是固定大小的数组，而不是动态链表。这是有意为之的。

数组的好处是访问速度快，O(1) 时间复杂度。而且调度策略的数量是有限的，不需要动态扩展。在内核开发中，简单高效往往比极致的灵活性更重要。

### 为什么用函数指针而不是回调注册

有些系统可能使用"注册回调"的方式，比如 `sched_register_enqueue(callback)`。我们的方式是把所有函数指针打包在一个结构体里。

这样做的好处是接口更清晰。你只需要注册一个 sched_class_t 结构体，而不是分别注册七八个回调函数。而且调度类作为一个完整的"对象"，更容易理解和维护。

### 为什么有 time_slice 和 time_slice_total 两个字段

只保留一个 time_slice 不够吗？当任务重新入队时，我们需要知道它的完整时间片是多少，才能重置。如果只有一个字段，时间片用完后变成 0，就无法知道原始值了。

当然，你也可以在调度类中硬编码时间片值，但这样就失去了灵活性。比如 Priority 调度可能希望根据优先级动态调整时间片，就需要能够为每个任务设置不同的值。

## 与 Linux 调度器的对比

我们的设计借鉴了 Linux，但做了简化。下面是一些主要区别：

**简化之处**：
- 我们只有两个调度类，Linux 有五个（stop、deadline、rt、fair、idle）
- 我们的优先级范围是 0-127，Linux 实时优先级是 0-99
- 我们没有实现组调度（cgroup）
- 我们没有实现负载均衡（单核系统）

**保留的核心**：
- 虚函数表模式
- Per-Policy 运行队列
- 调度实体嵌入 PCB
- 时间片管理机制
- 抢占判断接口

这些简化是为了让代码更容易理解，同时保留了扩展性。如果你理解了我们的设计，再看 Linux 的调度器代码，会发现结构是相似的，只是细节更复杂。
