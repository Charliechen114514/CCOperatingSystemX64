# 为什么需要进程管理

## 前言

写完 Stage 20 系统调用框架之后，我盯着代码看了半天，突然意识到一个尴尬的事实：我们的内核虽然有了系统调用机制，有了内存管理，有了中断处理，但本质上还是个"单线程世界"。整个内核只能按顺序执行代码，一次只能做一件事。你想在后台打印日志的同时处理键盘输入？做不到。你想让多个程序"同时"运行？更做不到。

这就像开了一家只有一个服务员的餐厅，即使厨房里有十个厨师，服务员一次也只能服务一张桌子。其他桌子只能干等着。解决这个问题的办法很简单：雇佣更多服务员。在操作系统的世界里，这些"服务员"就是进程。

说实话，进程管理是操作系统最核心、最复杂的功能之一。它涉及到 CPU 调度、内存隔离、上下文切换、进程间通信等一堆让人头秃的概念。但这也是区分"玩具内核"和"实用操作系统"的分水岭。一个没有进程管理的操作系统，就像一辆只有一个档位的汽车，能跑，但跑不远。

## 我们现在在哪里

如果你跟着之前的教程一路走来，我们现在在 Stage 20 完成后的位置。系统调用框架已经就绪，内核可以通过 syscall 指令安全地从用户态切换到内核态。但问题来了：我们只有一个"执行流"，整个内核还是按顺序执行代码。

让我们看看这个单线程模型的问题在哪里。假设你想在内核里做两件事：一个是定时打印系统状态，另一个是响应键盘输入。在单线程模型下，你大概会这样写：

```c
void kernel_main(void) {
    while (1) {
        // 检查键盘输入
        if (check_keyboard()) {
            handle_keyboard();
        }

        // 打印系统状态
        if (time_to_print_status()) {
            print_status();
        }

        // 其他任务...
        do_other_stuff();
    }
}
```

这看起来可以工作，但实际上有一堆问题。首先是响应性问题：如果 `print_status()` 耗时较长，键盘输入就会被延迟处理。其次是隔离问题：所有代码共享同一地址空间，一个任务出错可能把整个系统搞崩。再者是公平性问题：你怎么保证每个任务都能得到合理的 CPU 时间？

更糟糕的是，如果你想运行多个独立的程序，单线程模型根本做不到。程序 A 必须等程序 B 执行完才能开始，这种串行执行在现代操作系统里是不可接受的。

## 单线程模型的根本问题

单线程内核的核心问题是"无法并发"。这里的"并发"不是指真的同时运行（那需要多核 CPU），而是指"看起来同时运行"。通过快速切换不同任务，让每个任务都觉得自己在独占 CPU。

但单线程模型无法做到这一点，因为只有一个执行流。CPU 从头到尾只执行一条指令序列，无法"半途切换"到另一个任务。想要实现并发，必须支持"暂停当前任务，保存状态，切换到另一个任务，稍后再恢复"的能力。这正是进程管理要解决的问题。

除了无法并发，单线程模型还有另一个严重问题：没有隔离性。所有代码共享同一个地址空间，任何代码都可以读写任意内存。这意味着一个 buggy 的程序可能意外覆盖内核数据结构，或者一个恶意程序可以窃取其他程序的机密。这在现代操作系统里是绝对不允许的。

进程管理通过给每个进程分配独立的地址空间来解决这个问题。每个进程只能访问自己的内存，无法越界。这就像给每个房间装了门锁，没有钥匙的人进不去。

## 进程管理带来的改变

实现进程管理之后，我们的内核会有质的飞跃。

首先，我们终于可以"同时"运行多个程序了。虽然单核 CPU 一次只能执行一个进程，但通过快速切换，用户会觉得所有程序都在同时运行。这就像电影虽然一帧一帧播放，但看起来是连续的。

其次，我们实现了内存隔离。每个进程有独立的页表，只能访问自己的虚拟地址空间。一个进程崩溃不会影响其他进程，更不会搞垮整个内核。这大大提高了系统的稳定性。

再者，我们可以公平地分配 CPU 时间。调度器会按照一定策略（比如 Round-Robin）轮流执行每个进程，确保没有进程会饿死。这对多任务系统至关重要。

最后，我们可以实现更复杂的功能。比如守护进程可以在后台持续运行，用户程序可以 fork 创建子进程来做特定任务，进程间可以通过管道、共享内存等方式通信。这些都是单线程模型无法实现的。

## 与标准 Linux 进程 API 的对比

Linux 提供了一套经典的进程管理 API，我们的实现会尽量与之兼容：

```c
// Linux 标准 API
pid_t fork(void);           // 创建新进程
void exit(int status);      // 退出当前进程
pid_t wait(int *status);    // 等待子进程
pid_t waitpid(pid_t pid, int *status, int options);  // 等待指定进程
pid_t getpid(void);         // 获取当前进程 ID
pid_t getppid(void);        // 获取父进程 ID
```

我们的实现会提供类似的接口，语义上也尽量保持一致。但有几个重要的区别：

首先是运行环境。Linux 运行在成熟的操作系统上，而我们是在裸机上从零开始。这意味着很多 Linux 认为理所当然的事情（比如完整的 C 库、文件系统、信号机制），我们可能还没有实现。

其次是实现简化。Linux 的 fork 会做写时复制（Copy-on-Write），这是一种非常聪明但也很复杂的优化。我们的初期实现会选择更简单的方式：直接给子进程分配新的地址空间。这会牺牲一些性能，但大大简化了实现。

再者是调度算法。Linux 使用复杂的完全公平调度器（CFS），我们会先实现简单的 Round-Robin。这不是因为 CFS 不好，而是因为它太复杂了，不适合作为教学实现。

最后是线程支持。Linux 用 `clone()` 系统调用来创建线程（其实就是共享地址空间的进程），我们会提供更明确的 `pthread_create` 风格的接口。虽然底层原理相同，但 API 层面会更清晰。

## 为什么现在才实现进程管理

你可能会问，进程管理这么重要，为什么不早点实现？这是个好问题。

原因在于，进程管理需要很多基础设施作为前置条件。首先是内存管理：每个进程需要独立的地址空间，这需要虚拟内存管理（VMM）的支持。我们在 Stage 16 才完成 VMM。其次是系统调用：用户进程需要通过系统调用来请求内核服务，我们在 Stage 20 才完成系统调用框架。再者是中断处理：时钟中断是实现抢占式调度的基础，我们在 Stage 14 才完整实现中断系统。

如果在这些基础设施不完善的时候就实现进程管理，要么只能做非常简陋的版本，要么需要大量返工。这就是为什么我们等到现在才动手的原因。现在我们有了 VMM、系统调用、中断处理，实现进程管理的时机已经成熟。

## 我们要实现的目标

在这个阶段，我们要实现一个功能完整的进程管理系统。这不是一个简化的玩具实现，而是一个具备生产级特性的进程管理器。

核心功能包括：

- **进程控制块（PCB）管理**
  每个进程都有一个 PCB，存储了进程的所有信息：PID、父进程 ID、状态、内存上下文、CPU 上下文等。PCB 是进程存在的标志。

- **进程状态机**
  进程有多个状态：READY（就绪）、RUNNING（运行）、BLOCKED（阻塞）、ZOMBIE（僵尸）。进程会在这些状态之间转换，比如从 READY 到 RUNNING（被调度），从 RUNNING 到 BLOCKED（等待 I/O），从 RUNNING 到 ZOMBIE（退出）。

- **PID 分配器**
  每个进程都需要一个唯一的进程 ID。我们会基于 bitmap 实现一个高效的 PID 分配器，支持 O(1) 的分配和释放。

- **调度器**
  调度器负责选择下一个运行的进程。我们会实现可扩展的调度类框架，支持多种调度算法。默认实现 Round-Robin，可选实现优先级调度。

- **上下文切换**
  这是进程管理的核心操作：保存当前进程的 CPU 状态，恢复下一个进程的 CPU 状态。我们会用汇编实现这个操作，确保高效且正确。

- **地址空间管理**
  每个进程有独立的页表，实现内存隔离。我们会扩展 VMM 来支持创建和销毁用户地址空间。

- **系统调用**
  实现 fork、exit、wait4、getpid、getppid 等经典系统调用，让用户程序可以创建和管理进程。

- **线程支持**
  除了进程，我们还会支持线程。线程是同一进程内多个执行流，共享地址空间但有自己的栈和寄存器状态。

## 在开始之前

在正式开始之前，请确保你的 Stage 20 能正常编译和运行。进程管理依赖于系统调用框架，如果系统调用有问题，进程管理肯定跑不起来。

验证一下：

```bash
cd /home/charliechen/CCOperatingSystemX64

# 配置构建
cmake -B build -DCMAKE_BUILD_TYPE=Debug

# 构建
cmake --build build

# 运行
qemu-system-x86_64 -kernel build/kernel.bin -serial stdio
```

你应该能看到 QEMU 启动，串口输出显示系统调用框架初始化成功。如果看到任何错误，先回去修好它。

### 前置知识要求

这个阶段会涉及到一些相对复杂的底层概念。你需要理解：
- 指针和内存布局
- 链表操作（我们在 Stage 11 已经实现过）
- 虚拟内存和页表的基础知识
- x86_64 汇编基础（至少能看懂基本的寄存器操作）
- System V AMD64 ABI 调用约定

如果你对某些概念不熟悉，不用担心，我们会在实现过程中详细解释。这个教程是手把手教学，不会跳过任何步骤。

## 我们即将要做的

在接下来的文章中，我们会一步步完成进程管理的实现。

首先，我们会学习进程管理的设计基础。我们会了解进程与线程的区别，学习进程状态机的工作原理，比较不同的调度算法，设计 PCB 和调度器的数据结构。

然后，我们会搭建脚手架。创建 `kernel/process/` 目录，编写 CMakeLists.txt，定义 `process_defines.h` 和 `process.h`，配置好构建系统。

接下来是 PID 分配器的实现。我们会基于 bitmap 实现 O(1) 的 PID 分配和释放，这是进程管理的基础设施。

之后是 PCB 管理。我们会实现 `proc_alloc_pcb()` 和 `proc_free_pcb()`，学会如何分配和释放进程控制块，如何管理进程的内核栈和 CPU 上下文。

再之后是调度器框架。我们会实现一个可扩展的调度类系统，支持多种调度算法共存。默认实现 Round-Robin，这是最简单也最经典的调度算法。

然后是上下文切换。这是整个进程管理最复杂的部分。我们需要用汇编实现 `switch_context()` 和 `switch_to_first()`，学会如何保存和恢复 CPU 状态，如何切换 TSS 内核栈，如何切换 CR3 页表。

接下来是 fork 系统调用。我们会实现 `proc_fork()`，学会如何创建新进程，如何复制父进程的地址空间，如何建立父子关系，如何让子进程正确返回。

之后是 exit 和 wait4。我们会实现 `proc_exit()` 和 `proc_wait4()`，学会如何处理进程退出，如何管理僵尸进程，如何让父进程等待子进程。

再之后是线程管理。我们会扩展进程管理系统，支持内核线程和用户线程。线程是轻量级的执行流，共享进程的地址空间，但有独立的栈和寄存器。

最后是系统调用集成和测试。我们会把所有功能注册为系统调用，编写用户程序测试，确保一切正常工作。

每一步都是独立的，你可以跟着做一部分，也可以全部做完。相信我，等你完整实现之后，你会对操作系统有更深入的理解。

## 接下来

准备好了吗？让我们从 **进程管理设计基础** 开始，深入了解进程与线程的区别，学习进程状态机的工作原理，设计我们的 PCB 和调度器数据结构。

这会是你的内核开发旅程中的一个重要里程碑。你将学会如何实现一个完整的进程管理系统，理解底层的调度和切换机制，掌握复杂的数据结构和算法。这些知识不仅对内核开发有用，对任何系统编程都大有裨益。
