# 进程管理设计基础

## 前言

在动手写代码之前，我们需要先搞清楚几个基本概念。进程管理看起来很高大上，但本质上就是回答三个问题：什么是进程？进程有哪些状态？如何选择下一个运行的进程？

这三个问题看似简单，但每个都有很多细节需要考虑。比如，进程和线程有什么区别？一个进程可以有多少种状态？调度算法怎么选？这些问题不搞清楚，写出来的代码一定会出问题。

这篇文章会帮你建立进程管理的理论基础。我们不会讲太多抽象的概念，而是直接讨论在设计实现时需要考虑的具体问题。毕竟，我们的目标是写出能跑的代码，而不是通过操作系统考试。

## 进程与线程的区别

很多人对进程和线程的区别感到困惑，这很正常。这两个概念在很多教材里讲得非常抽象，什么"进程是资源分配的单位，线程是调度的单位"，听起来很高级，但不知道具体是什么意思。

让我们用更直白的方式来理解。想象一家公司，进程就是"部门"，线程就是"员工"。每个部门有自己独立的办公室（地址空间）、办公设备（文件描述符、内存等资源），但部门里的员工共享这些资源。不同部门的员工不能随便进入其他部门的办公室，但同一部门的员工可以共用办公设备。

从技术角度来看，进程有自己独立的页表，而同一进程内的所有线程共享同一套页表。这意味着进程间的内存是隔离的，一个进程无法直接访问另一个进程的内存，但同一进程内的线程可以互相访问彼此的内存。

除了地址空间，进程和线程还有很多区别。进程有独立的文件描述符表、信号处理、进程 ID，而线程共享这些。创建进程的开销比创建线程大，因为需要复制页表、分配新的内存。创建线程只需要分配新的栈，开销很小。

在我们这个阶段的实现中，会先实现进程管理，然后再扩展支持线程。这是因为进程是基础，线程可以看作是"轻量级的进程"。理解了进程管理的原理，线程管理其实就是水到渠成的事情。

## 进程状态机

进程在其生命周期中会经历多种状态。理解这些状态以及状态之间的转换条件，是设计进程管理系统的第一步。

最经典的进程状态模型包含五个状态：

**NEW（新建）** - 进程正在被创建。这时候内核已经分配了 PCB，但还没有把进程加入到运行队列。这个状态通常很短，很快就会转换到 READY 状态。

**READY（就绪）** - 进程已经准备好运行，正在等待 CPU。进程的所有资源都已就绪，只要调度器选中它，就能立即执行。一个系统里可能有多个进程处于 READY 状态，它们都在等待 CPU。

**RUNNING（运行）** - 进程正在 CPU 上执行。在任何时刻，单核 CPU 上最多只有一个进程处于 RUNNING 状态。当进程的时间片用完、或者主动等待 I/O、或者被更高优先级进程抢占时，会从 RUNNING 转换到其他状态。

**BLOCKED（阻塞）** - 进程正在等待某个事件，比如等待 I/O 完成、等待信号量、等待子进程退出等。在阻塞期间，进程不会被调度执行。当等待的事件发生时，进程会从 BLOCKED 转换到 READY。

**ZOMBIE（僵尸）** - 进程已经执行完毕，但父进程还没有回收它。这时候进程已经释放了所有资源，但 PCB 还保留着，用来存储退出状态。僵尸进程会被父进程的 wait() 或 waitpid() 回收，之后才会彻底消失。

可以用一个简单的状态图来表示这些转换：

```
                    fork()
    ┌─────────────────────────────────┐
    │                                 │
    ▼                                 │
┌───────┐    schedule()    ┌─────────┐
│  NEW  │ ────────────────> │  READY  │
└───────┘                   └────┬────┘
                                  │
                                  │ schedule()
                                  ▼
                            ┌─────────┐
     sleep()                │ RUNNING │
         │                  └────┬────┘
         │                       │ exit()
         ▼                       ▼
    ┌─────────┐            ┌─────────┐
    │ BLOCKED │            │  ZOMBIE │
    └─────────┘            └────┬────┘
         │                       │
         │ wakeup()              │ wait4()
         └───────────────────────┘
```

这个状态图看起来简单，但实现时有很多细节需要注意。比如，从 RUNNING 到 READY 的转换是什么时候发生的？是时间片用完，还是更高优先级进程就绪？从 BLOCKED 到 READY 的转换是怎么触发的？是中断处理程序唤醒，还是其他进程主动唤醒？

在我们的实现中，会先实现一个简化的状态机：NEW、READY、RUNNING、ZOMBIE。BLOCKED 状态会留到后面实现完整的等待队列机制时再加。这样可以让初学者更容易理解核心概念，不会被太多细节淹没。

## 调度算法选择

调度器是进程管理的心脏，它负责决定下一个运行哪个进程。调度算法的选择直接影响系统的性能和用户体验。

常见的调度算法有很多，每种都有自己的优缺点。

**Round-Robin（轮转）** 是最简单的调度算法。每个进程被分配一个固定的时间片，时间片用完后就被放到运行队列的末尾，调度器选择下一个进程运行。这种算法实现简单，公平性好，每个进程都能得到平等的 CPU 时间。缺点是无法区分进程的优先级，重要的进程得不到更多资源。

**Priority Scheduling（优先级调度）** 按进程的优先级来选择。优先级高的进程先执行，同优先级的进程按 Round-Robin 调度。这种算法可以让重要进程得到更多 CPU 时间，但可能导致低优先级进程"饿死"——一直得不到 CPU。

**Completely Fair Scheduler（CFS）** 是 Linux 使用的调度器。它用红黑树维护进程的虚拟运行时间（vruntime），每次选择 vruntime 最小的进程运行。这种算法非常公平，但实现复杂，性能开销也大。

**Shortest Job First（最短作业优先）** 假设知道每个进程的执行时间，优先执行时间短的。理论上平均等待时间最短，但实际上很难预测进程的执行时间。

在我们的实现中，会选择 Round-Robin 作为默认调度算法。这不是因为它最好，而是因为它最简单，最容易理解，而且足够用。对于教学项目来说，简单清晰的实现比复杂高效的实现更有价值。

但我们不会只实现一种调度算法。我们会设计一个可扩展的调度类框架，允许同时注册多种调度算法。这样以后想添加优先级调度、CFS 或者其他算法时，只需要实现一个新的调度类，而不需要修改核心代码。这种设计思路借鉴了 Linux 的调度器架构，非常值得学习。

## PCB 结构设计

进程控制块（Process Control Block，PCB）是进程存在的标志。内核通过 PCB 来跟踪进程的所有信息：进程 ID、父进程 ID、状态、内存上下文、CPU 上下文等等。PCB 设计得好不好，直接决定了进程管理系统的易用性和扩展性。

一个 PCB 至少需要包含以下信息：

**进程标识** - PID（进程 ID）和 PPID（父进程 ID）是必须的。PID 是进程的唯一标识，内核通过 PID 来查找进程。PPID 用于建立进程树，可以遍历一个进程的所有子进程。

**进程状态** - 前面提到的 NEW、READY、RUNNING、BLOCKED、ZOMBIE。调度器根据状态来决定进程是否可以运行。

**CPU 上下文** - 当进程被切换出去时，需要保存它的 CPU 状态：寄存器值、栈指针、指令指针等。这样下次调度回来时，可以从上次离开的地方继续执行。

**内存上下文** - 进程的页表物理地址（pml4_phys）、堆结束位置（brk）、栈起始地址（stack_start）。切换进程时需要加载这些信息到 CR3 寄存器。

**内核栈** - 每个进程都有自己的内核栈，用于在进入内核时使用。内核栈必须独立，防止栈溢出影响其他进程。

**链表节点** - 进程需要被加入到各种队列：运行队列、父进程的子进程链表、兄弟进程链表等。我们会用侵入式链表来实现，这样 PCB 可以同时存在于多个链表中。

**家族关系** - 父进程指针、子进程链表、僵尸子进程链表。这些用于维护进程树，实现 wait() 和 waitpid()。

**统计信息** - 进程创建时间、运行时间、上下文切换次数等。这些主要用于调试和监控。

如果考虑线程支持，还需要添加：线程组 ID（tgid）、是否为线程的标志、线程链表节点等。同一进程的所有线程共享地址空间，但有自己的调度实体。

在我们的实现中，PCB 大概长这样：

```c
typedef struct pcb {
    // 进程标识
    int32_t pid;                    // 进程 ID
    int32_t ppid;                   // 父进程 ID

    // 进程状态
    process_state_t state;          // 当前状态
    int32_t exit_code;              // 退出码（如果僵尸）

    // 调度相关
    list_head run_list;             // 运行队列链表
    sched_entity_t sched_entity;   // 调度实体

    // 家族关系
    list_head siblings;             // 兄弟进程链表
    list_head children;             // 子进程链表
    list_head zombie_children;      // 僵尸子进程链表
    struct pcb* parent;             // 父进程指针

    // 内存上下文
    memory_context_t mm;            // 地址空间信息

    // CPU 上下文
    cpu_context_t* cpu_ctx;         // 保存的内核上下文
    trap_frame_t* trap_frame;       // 用户陷阱帧

    // 内核栈
    virtual_addr_t kernel_stack;    // 内核栈顶
    virtual_addr_t kernel_stack_base; // 内核栈底

    // 用户态相关
    bool is_user_mode;              // 是否为用户进程
    virtual_addr_t user_stack;      // 用户栈顶
    size_t user_stack_size;         // 用户栈大小

    // 线程相关
    int32_t tgid;                   // 线程组 ID
    bool is_thread;                 // 是否为线程
    list_head thread_list;          // 线程链表
    list_head thread_group;         // 线程组链表节点
    atomic_t mm_refcount;           // 地址空间引用计数

    // 线程 join 相关
    void* join_waiters;             // 等待队列
    bool detached;                  // 是否 detached
    void* return_value;             // 返回值

    // 统计信息
    uint64_t start_time;            // 创建时间
    char comm[16];                  // 命令名
} pcb_t;
```

这个结构看起来很大，但每个字段都有它的用途。我们会在后面的文章中逐个解释它们的用途。

## 调度器结构设计

调度器是进程管理的大脑，它负责选择下一个运行的进程。调度器需要维护全局的运行队列、当前进程指针、进程数量统计等信息。

在我们的实现中，调度器的结构大致如下：

```c
typedef struct scheduler {
    list_head run_queue;      // 运行队列（兼容旧代码）
    pcb_t* current;          // 当前运行进程
    pcb_t* idle;             // 空闲进程
    uint32_t nr_running;     // 就绪进程数
    bool need_resched;       // 需要重新调度标志

    // 调度类框架
    sched_rq_t* rq;          // 每策略运行队列数组
    sched_class_t** classes; // 已注册的调度类数组
} scheduler_t;
```

调度器的核心函数是 `schedule()`，它负责选择下一个进程并执行上下文切换。选择哪个进程由调度类的 `pick_next_task()` 方法决定，不同的调度类可以实现不同的选择策略。

比如，Round-Robin 调度类会从运行队列的头部取下一个进程，而优先级调度类会遍历队列找到优先级最高的进程。调度器不需要关心具体的选择逻辑，只需要调用调度类的方法。

这种设计的好处是解耦：调度器框架和具体算法是分开的。添加新的调度算法不需要修改核心代码，只需要实现一个新的调度类并注册即可。

## CPU 上下文结构

上下文切换的核心是保存和恢复 CPU 状态。哪些寄存器需要保存？哪些不需要？这需要仔细考虑。

按照 System V AMD64 ABI 的约定，函数调用时有些寄存器是"调用者保存"的（caller-saved），有些是"被调用者保存"的（callee-saved）。调用者保存的寄存器（RAX、RCX、RDX、RSI、RDI、R8-R11）由调用者负责保护，被调用者可以随意修改。被调用者保存的寄存器（RBX、RBP、R12-R15）由被调用者负责保护，调用者可以假设这些寄存器在函数调用前后不变。

对于上下文切换来说，我们只需要保存 callee-saved 寄存器。因为 compiler 会在函数调用前后自动保存/恢复 caller-saved 寄存器。我们的上下文切换函数本质上是一个函数调用，编译器会帮我们处理 caller-saved 寄存器。

除了通用寄存器，我们还需要保存 RSP（栈指针）和 RIP（指令指针）。RSP 指向进程的内核栈，RIP 指向进程下次要执行的指令。这两个寄存器对于恢复进程执行至关重要。

CPU 上下文结构定义如下：

```c
typedef struct {
    uint64_t rbx;
    uint64_t rbp;
    uint64_t r12;
    uint64_t r13;
    uint64_t r14;
    uint64_t r15;
    uint64_t rsp;        // 栈指针
    uint64_t rip;        // 返回地址
} cpu_context_t;
```

注意，这个结构不包含 RAX、RCX、RDX、RSI、RDI 等寄存器，因为它们是 caller-saved 的，编译器会自动处理。如果我们自己保存它们，反而会和编译器的处理冲突，导致问题。

## 陷阱帧结构

当用户程序通过 syscall 或中断进入内核时，CPU 会自动保存一些寄存器，形成所谓的"陷阱帧"（trap frame）。这个帧包含了用户程序的完整状态，内核可以通过修改陷阱帧来改变程序返回用户态时的行为。

陷阱帧包含所有通用寄存器、段寄存器、RIP、RFLAGS、RSP 等。它的结构需要和硬件自动保存的格式完全匹配，否则 iretq 指令会出错。

```c
typedef struct PACKED trap_frame {
    uint64_t rax;
    uint64_t rbx;
    uint64_t rcx;
    uint64_t rdx;
    uint64_t rsi;
    uint64_t rdi;
    uint64_t rbp;
    uint64_t r8;
    uint64_t r9;
    uint64_t r10;
    uint64_t r11;
    uint64_t r12;
    uint64_t r13;
    uint64_t r14;
    uint64_t r15;
    uint64_t vector;      // 中断向量
    uint64_t error_code;  // 错误码
    uint64_t rip;
    uint64_t cs;
    uint64_t rflags;
    uint64_t rsp;
    uint64_t ss;
} trap_frame_t;
```

陷阱帧主要用于实现系统调用和异常处理。当用户程序调用 fork() 时，硬件会自动构建陷阱帧，内核可以读取参数（寄存器）、修改返回值（RAX）、然后通过 iretq 返回用户态。
