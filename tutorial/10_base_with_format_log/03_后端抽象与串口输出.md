# 后端抽象与串口输出 —— Stage 10 可扩展架构实战指南

## 前言

上一篇文章我们实现了一个 `kprintf`，但是有一个问题：所有的输出都硬编码到串口上了。你想想，如果以后你想同时输出到串口和 VGA，或者把日志写到文件，甚至通过网络发送日志，难道要为每种情况都写一个不同的 `kprintf` 吗？那也太麻烦了。

所以我们需要一个更灵活的设计：**后端抽象**。这个想法很简单，把"格式化"和"输出"分开。`kprintf` 只负责格式化，至于输出到哪里，由后端决定。这样将来你想添加新的输出方式，只需要写一个新的后端，注册一下就行了，不需要修改任何现有的代码。

这是典型的**关注点分离**原则，也是软件架构设计中最重要的思想之一。格式化逻辑只关心如何把数据变成字符串，输出逻辑只关心如何把字符串发送到具体设备。两者之间通过一个清晰的接口交互，各自可以独立演化和测试。

准备好了吗？我们开始。

## 第一步：设计后端抽象接口

首先我们来定义后端接口。一个后端需要做什么？很简单：接收格式化好的字符串，输出到具体设备。同时还需要告诉调用者自己是否就绪，避免在未初始化的情况下使用。

创建 `kernel/klogs/kprintf_backends.h`：

```c
/**
 * @file kprintf_backends.h
 * @brief kprintf 后端抽象接口
 * @date 2026-02-16
 */
#pragma once
#include "defines/types.h"

/**
 * @brief 后端类型枚举
 */
typedef enum {
    KLOG_BACKEND_NONE = 0,
    KLOG_BACKEND_SERIAL,
    KLOG_BACKEND_VGA,
    KLOG_BACKEND_COUNT  // 用于边界检查
} klog_backend_t;

/**
 * @brief 后端操作接口
 *
 * 每个后端需要实现这个结构体中的函数
 */
typedef struct {
    /**
     * @brief 输出字符串
     *
     * @param str 要输出的字符串
     * @param level 日志级别（-1 表示无级别，使用默认颜色）
     */
    void (*process)(const char* str, int level);

    /**
     * @brief 检查后端是否就绪
     *
     * @return true 后端可以工作
     * @return false 后端未初始化或不可用
     */
    bool (*is_ready)(void);
} KLogBackendOps;

/**
 * @brief 注册后端
 *
 * @param backend 后端类型
 * @param ops 后端操作接口
 */
void klog_register_backend(klog_backend_t backend, const KLogBackendOps* ops);

/**
 * @brief 获取后端操作接口
 *
 * @param backend 后端类型
 * @return 后端操作接口，如果后端未注册则返回 NULL
 */
const KLogBackendOps* klog_get_backend_ops(klog_backend_t backend);

/**
 * @brief 设置默认后端
 *
 * @param backend 后端类型
 */
void klog_set_default_backend(klog_backend_t backend);

/**
 * @brief 获取默认后端
 */
klog_backend_t klog_get_default_backend(void);
```

你可能注意到这里用的是函数指针表，这其实是 C 语言中实现**多态**的标准方式。每个后端实现同样的接口，但行为可以不同。`kprintf` 不需要知道具体是哪个后端，只需要调用 `process` 函数就行。这种设计让我们可以在运行时切换不同的输出方式，而不需要重新编译代码。

## 第二步：实现后端注册表

现在我们来实现后端管理系统。核心思想是用一个数组来存储所有已注册的后端，用后端类型作为索引直接访问。这样查找的时间复杂度是 O(1)，非常高效。

创建 `kernel/klogs/kprintf_backends.c`：

```c
/**
 * @file kprintf_backends.c
 * @brief kprintf 后端管理实现
 * @date 2026-02-16
 */
#include "kprintf_backends.h"

// 后端注册表（存储所有已注册的后端）
static const KLogBackendOps* g_backend_ops[KLOG_BACKEND_COUNT] = {NULL};

// 默认后端
static klog_backend_t g_default_backend = KLOG_BACKEND_NONE;

void klog_register_backend(klog_backend_t backend, const KLogBackendOps* ops) {
    if (backend >= KLOG_BACKEND_COUNT) {
        return;  // 无效的后端类型，直接忽略
    }

    g_backend_ops[backend] = ops;
}

const KLogBackendOps* klog_get_backend_ops(klog_backend_t backend) {
    if (backend >= KLOG_BACKEND_COUNT) {
        return NULL;  // 无效的后端类型
    }

    return g_backend_ops[backend];
}

void klog_set_default_backend(klog_backend_t backend) {
    g_default_backend = backend;
}

klog_backend_t klog_get_default_backend(void) {
    return g_default_backend;
}
```

这个设计有几个优点。首先是类型安全，我们用枚举而不是字符串来标识后端，编译器会帮我们检查错误。然后是查找效率，直接用数组索引，不需要遍历。最后是可扩展性，添加新后端只需要在枚举中添加新类型，实现后端操作接口，然后调用 `klog_register_backend` 注册就行。

你可能想问，为什么不用哈希表或者链表？对于我们的场景，后端数量很少（就几个），数组的效率最高，代码也最简单。如果将来后端数量变多了，可以考虑更复杂的数据结构，但现在没必要过度设计。

## 第三步：实现串口后端

现在我们来实现第一个后端：串口后端。这是最常用的输出方式，因为 QEMU 的串口重定向非常方便，而且串口输出可以保存到文件，方便调试。

创建 `kernel/klogs/backends/serial_backends.h`：

```c
/**
 * @file serial_backends.h
 * @brief 串口后端接口
 * @date 2026-02-16
 */
#pragma once
#include "kprintf_backends.h"

/**
 * @brief 初始化串口后端
 *
 * @return true 初始化成功
 * @return false 初始化失败
 */
bool klog_serial_backend_init(void);

/**
 * @brief 获取串口后端操作接口
 *
 * @return 后端操作接口
 */
const KLogBackendOps* klog_serial_backend_get_ops(void);
```

创建 `kernel/klogs/backends/serial_backends.c`：

```c
/**
 * @file serial_backends.c
 * @brief 串口后端实现
 * @date 2026-02-16
 */
#include "serial_backends.h"
#include "driver/serial/serial.h"
#include "driver/serial/serial_color.h"

/**
 * @brief 检查串口是否就绪
 *
 * 在我们的实现中，串口后端一旦初始化就始终就绪
 */
static bool serial_is_ready(void) {
    return true;
}

/**
 * @brief 处理字符串输出（带颜色支持）
 *
 * @param str 要输出的字符串
 * @param level 日志级别，-1 表示无级别
 */
static void serial_process(const char* str, int level) {
    // 发送颜色代码
    sync_serial_puts(serial_color_for_log_level(level));
    // 发送实际字符串
    sync_serial_puts(str);
    // 重置颜色
    sync_serial_puts(serial_color_for_log_level(-1));  // -1 返回 RESET
}

// 串口后端操作接口
static const KLogBackendOps g_serial_backend_ops = {
    .process = serial_process,
    .is_ready = serial_is_ready,
};

bool klog_serial_backend_init(void) {
    return serial_init();
}

const KLogBackendOps* klog_serial_backend_get_ops(void) {
    return &g_serial_backend_ops;
}
```

这里我们用的是 `sync_serial_puts`，而不是之前你可能见过的 `serial_write`。区别在于 `sync_serial_puts` 是一个更高层的封装，它会自动处理字符串的结束符，而且支持颜色代码。如果你用 `serial_write` 逐字符输出，就需要自己写循环处理，代码会稍微长一点。

## 第四步：理解颜色支持的实现

你可能注意到 `serial_process` 中调用了 `serial_color_for_log_level`。这个函数的作用是根据日志级别返回对应的 ANSI 颜色代码。让我们看看它是怎么实现的。

在 `kernel/driver/serial/serial_color.c` 中：

```c
const char* serial_color_for_log_level(int level) {
    switch (level) {
        case 0:  // TRACE
            return "\033[90m";  // 灰色
        case 1:  // DEBUG
            return "\033[35m";  // 紫色
        case 2:  // INFO
            return "\033[32m";  // 绿色
        case 3:  // WARN
            return "\033[33m";  // 黄色
        case 4:  // ERROR
            return "\033[31m";  // 红色
        case -1:  // RESET
            return "\033[0m";
        default:
            return "\033[0m";  // 默认重置
    }
}
```

ANSI 转义序列的格式是 `\033[参数m`，其中 `\033` 是 ESC 字符的八进制表示。`[30m` 是黑色，`[31m` 是红色，以此类推。`[90-97m` 是亮色版本。`[0m` 是重置所有属性。

这里我们直接返回静态字符串，而不是动态生成。这样效率更高，因为颜色代码是固定的，不需要每次都计算。但这也意味着如果你需要更复杂的颜色效果（比如同时设置前景色和背景色），就需要修改这个函数了。

## 第五步：更新 kprintf 使用后端

现在我们需要修改 `kprintf.c`，让它使用后端系统而不是直接调用串口函数。其实修改不大，主要是把硬编码的串口调用替换成通用的后端接口。

```c
void kvprintf(klog_backend_t backend, const char* format, va_list args) {
    // 获取后端操作接口
    const KLogBackendOps* ops = klog_get_backend_ops(backend);
    if (ops == NULL || !ops->is_ready()) {
        return;  // 后端未注册或未就绪
    }

    // 格式化字符串
    format_string(g_buffer, KPRINTF_BUFFER_SIZE, format, args);

    // 使用后端输出（level = -1 表示无级别）
    ops->process(g_buffer, -1);
}

void kprintf(klog_backend_t backend, const char* format, ...) {
    va_list args;
    va_start(args, format);
    kvprintf(backend, format, args);
    va_end(args);
}
```

变化很明显：不再直接调用 `serial_write` 或 `sync_serial_puts`，而是通过 `ops->process` 来输出。这样如果我们将来添加 VGA 后端或者文件后端，`kprintf` 的代码完全不需要修改，只需要注册新的后端就行。

## 第七步：编写测试

现在我们来测试后端系统是否正常工作。在 `kernel_main.c` 中添加测试代码：

```c
#include "klogs/kprintf.h"
#include "klogs/backends/serial_backends.h"

void test_backends(void) {
    // 初始化串口后端
    klog_serial_backend_init();

    // 注册串口后端
    klog_register_backend(KLOG_BACKEND_SERIAL, klog_serial_backend_get_ops());

    // 设置默认后端
    klog_set_default_backend(KLOG_BACKEND_SERIAL);

    // 测试直接指定后端
    kprintf(KLOG_BACKEND_SERIAL, "Test 1: Direct backend specification\n");

    // 测试使用默认后端
    kprintf(KLOG_BACKEND_SERIAL, "Test 2: Using default backend\n");

    // 测试格式化输出
    kprintf(KLOG_BACKEND_SERIAL, "Test 3: %s = %d (0x%x)\n", "answer", 42, 42);

    // 测试未注册后端（应该没有输出）
    kprintf(KLOG_BACKEND_VGA, "Test 4: This should not appear\n");

    // 测试未就绪后端
    kprintf(KLOG_BACKEND_SERIAL, "Test 5: Backend is ready\n");
}
```

编译并运行：

```bash
cd build
cmake ..
make
./run.sh
```

你应该在串口输出中看到：

```
Test 1: Direct backend specification
Test 2: Using default backend
Test 3: answer = 42 (0x2a)
Test 5: Backend is ready
```

注意 `Test 4` 没有出现，因为 VGA 后端没有注册。这是正确的后端隔离行为：如果后端不存在，输出就被静默丢弃，而不是崩溃或者产生未定义行为。

## 第八步：演示如何添加新后端

现在我们来演示一下添加新后端有多简单。我们来实现一个"空后端"（什么都不做），这在测试和禁用日志时很有用。

在 `kprintf_backends.c` 中添加：

```c
// 空后端：什么都不做
static void null_process(const char* str, int level) {
    (void)str;   // 避免未使用参数警告
    (void)level;
}

static bool null_is_ready(void) {
    return true;  // 空后端总是就绪
}

static const KLogBackendOps null_backend_ops = {
    .process = null_process,
    .is_ready = null_is_ready,
};
```

然后在 `klog_init` 或其他初始化函数中注册：

```c
klog_register_backend(KLOG_BACKEND_NONE, &null_backend_ops);
```

现在 `KLOG_BACKEND_NONE` 也是一个有效的后端了，而不是"无后端"。如果需要表示"无后端"，可以检查返回的 `ops` 是否为 `NULL`。

添加一个新后端就这么简单：实现两个函数（`process` 和 `is_ready`），填充一个 `KLogBackendOps` 结构体，然后注册。不需要修改任何现有代码，这就是良好架构设计的价值。

## 到这里我们完成了什么

让我们回顾一下这篇文章的内容。我们实现了完整的后端抽象系统，包括：

- `kprintf_backends.h/c` — 后端抽象接口和注册表
- `serial_backends.h/c` — 串口后端实现
- 后端注册机制 — O(1) 查找，类型安全
- 可扩展设计 — 添加新后端不需要修改现有代码

这个架构的价值在于**开放封闭原则**：对扩展开放，对修改封闭。你可以添加新的后端，但不需要修改 `kprintf` 的核心代码。这让系统更容易维护和演 化。

说实话，设计这个后端系统的时候我犹豫了一下。对于这么小的项目，会不会是过度设计？但后来想想，良好的架构习惯就是这样养成的。等系统真的变复杂了，你会感谢现在的自己没有偷懒。
