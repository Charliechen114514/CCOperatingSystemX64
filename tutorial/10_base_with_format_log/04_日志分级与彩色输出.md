# 日志分级与彩色输出 —— Stage 10 专业日志系统实战指南

## 前言

写内核的时候，你会遇到各种调试信息："正在初始化内存管理..."、"页表地址：0x100000"、"错误：无法分配内存"、"警告：内存不足，使用备用方案"。这些信息的优先级不一样，有时候你只想看错误信息，不想被调试日志淹没；有时候你想看所有详细信息。

这就是日志分级系统的意义。通过给日志打上"等级"标签，你可以控制看到什么级别的信息。更棒的是，我们可以给不同级别的日志加上颜色。这样在串口终端里一眼就能看出哪些是错误（红色），哪些是警告（黄色），哪些是普通信息（绿色）。

但我们为什么要这样做？说实话，一开始我觉得这个功能有点花哨。但真的用起来之后，才发现彩色日志的价值远超想象。当你的日志刷屏的时候，颜色能帮你快速定位问题。红色的 ERROR 跳出来，你就知道哪里出问题了；绿色的 INFO 淡淡地飘过，你就知道系统运行正常。这种视觉反馈能大大提高调试效率。

准备好了吗？我们开始。

## 第一步：理解 ANSI 转义序列

在实现颜色支持之前，我们需要先理解 ANSI 转义序列。这个名字听起来很高大上，其实就是一种控制终端显示的标准。

**什么是 ANSI 转义序列？**

ANSI 转义序列是一种控制终端显示的标准，最早是美国国家标准协会制定的。它以 `ESC` 字符（ASCII 27，八进制 033）开头，后面跟着 `[` 和一些参数。终端收到这些字符后，不会显示它们，而是执行相应的控制命令。

基本格式是这样的：

```
ESC[参数m
```

在 C 语言中，`ESC` 字符可以用 `\033`（八进制）或 `\x1b`（十六进制）表示。所以一个完整的颜色代码就是 `\033[31m`，表示把后面的文字设为红色。

**常用颜色代码：**

| 代码 | 颜色 | 用途 |
|------|------|------|
| 30 | 黑色 | 前景 |
| 31 | 红色 | 前景（ERROR） |
| 32 | 绿色 | 前景（INFO） |
| 33 | 黄色 | 前景（WARN） |
| 34 | 蓝色 | 前景 |
| 35 | 紫色 | 前景（DEBUG） |
| 36 | 青色 | 前景 |
| 37 | 白色 | 前景 |
| 90 | 亮黑（灰） | 前景（TRACE） |
| 91-97 | 亮色版本 | 前景 |
| 0 | 重置 | 恢复默认 |

一个简单的例子：

```c
// 红色文本
"\033[31m这是红色文本\033[0m"

// 绿色文本
"\033[32m这是绿色文本\033[0m"
```

注意每次输出带颜色的文本后，都要用 `\033[0m` 重置颜色，否则后面的所有文本都会保持那个颜色。这个坑我踩过，输出一次红色 ERROR 后，后面的所有日志都是红色的，吓我一跳。

## 第二步：定义日志级别

首先我们来定义日志级别。我们模仿 Linux kernel 的设计，使用 5 个级别：

| 级别 | 数值 | 用途 | 颜色 |
|------|------|------|------|
| TRACE | 0 | 最详细的调试信息 | 灰色 |
| DEBUG | 1 | 调试信息 | 紫色 |
| INFO | 2 | 一般信息 | 绿色 |
| WARN | 3 | 警告信息 | 黄色 |
| ERROR | 4 | 错误信息 | 红色 |

这个分级方案是业界标准，大家都是这么用的。 TRACE 最详细，一般是进入函数、退出函数这种级别的日志。DEBUG 是普通的调试信息。INFO 是正常运行的信息。WARN 是警告，说明有问题但还能继续。ERROR 是错误，需要立即处理。

在 `kernel/klogs/kprintf.h` 中已经定义了：

```c
typedef enum {
    KLOG_LEVEL_TRACE = 0,
    KLOG_LEVEL_DEBUG = 1,
    KLOG_LEVEL_INFO  = 2,
    KLOG_LEVEL_WARN  = 3,
    KLOG_LEVEL_ERROR = 4,
} klog_level_t;
```

## 第三步：实现 ANSI 颜色支持

现在我们来创建颜色支持模块。在 `kernel/driver/serial/serial_color.h` 中定义颜色枚举：

```c
/**
 * @file serial_color.h
 * @brief ANSI 颜色代码定义
 * @date 2026-02-16
 */
#pragma once
#include "defines/types.h"

typedef enum {
    SERIAL_COLOR_RESET  = 0,
    SERIAL_COLOR_BLACK  = 30,
    SERIAL_COLOR_RED    = 31,
    SERIAL_COLOR_GREEN  = 32,
    SERIAL_COLOR_YELLOW = 33,
    SERIAL_COLOR_BLUE   = 34,
    SERIAL_COLOR_MAGENTA = 35,
    SERIAL_COLOR_CYAN   = 36,
    SERIAL_COLOR_WHITE  = 37,
    SERIAL_COLOR_GRAY   = 90,
    SERIAL_COLOR_BRIGHT_RED   = 91,
    SERIAL_COLOR_BRIGHT_GREEN = 92,
    SERIAL_COLOR_BRIGHT_YELLOW= 93,
    SERIAL_COLOR_BRIGHT_BLUE  = 94,
    SERIAL_COLOR_BRIGHT_MAGENTA=95,
    SERIAL_COLOR_BRIGHT_CYAN  = 96,
    SERIAL_COLOR_BRIGHT_WHITE = 97,
} serial_color_t;

/**
 * @brief 根据日志级别获取 ANSI 颜色代码
 *
 * @param level 日志级别（0-4），-1 表示重置
 * @return ANSI 颜色代码字符串
 */
const char* serial_color_for_log_level(int level);
```

在 `kernel/driver/serial/serial_color.c` 中实现：

```c
/**
 * @file serial_color.c
 * @brief ANSI 颜色代码生成
 * @date 2026-02-16
 */
#include "serial_color.h"

const char* serial_color_for_log_level(int level) {
    switch (level) {
        case KLOG_LEVEL_TRACE:
            return "\033[90m";  // 灰色
        case KLOG_LEVEL_DEBUG:
            return "\033[35m";  // 紫色
        case KLOG_LEVEL_INFO:
            return "\033[32m";  // 绿色
        case KLOG_LEVEL_WARN:
            return "\033[33m";  // 黄色
        case KLOG_LEVEL_ERROR:
            return "\033[31m";  // 红色
        case -1:  // RESET
            return "\033[0m";
        default:
            return "\033[0m";  // 默认重置
    }
}
```

这里我们直接返回静态字符串，而不是动态生成。因为颜色代码是固定的，每次都重新计算没有意义。静态字符串存储在只读数据段，效率很高。

## 第四步：理解颜色选择的心理学

为什么 TRACE 用灰色、DEBUG 用紫色、INFO 用绿色、WARN 用黄色、ERROR 用红色？这不是随便选的，背后有一些心理学考量。

红色对应 ERROR，这是因为红色在自然界中通常代表危险（火、血），人类对这个颜色的反应最强烈。看到红色，人本能地会警觉起来。

黄色对应 WARN，黄色是警告色，介于红色和绿色之间，表示"需要注意但不要惊慌"。

绿色对应 INFO，绿色代表正常、安全，看到绿色让人感觉一切良好。

紫色对应 DEBUG，紫色不是自然界常见的颜色，比较显眼但不会太抢眼，适合调试信息。

灰色对应 TRACE，灰色最不显眼，适合那些最详细但不那么重要的日志。

当然，这些颜色选择是可以调整的。如果你的终端背景是深色的，亮色版本可能更合适；如果是浅色背景，暗色版本可能更清晰。关键是保持一致，让大脑建立起"颜色-级别"的关联。

## 第五步：更新串口后端支持颜色

现在我们需要更新串口后端，让它支持彩色输出。在上一篇文章中，`serial_backends.c` 已经实现了颜色支持，我们来仔细看一下：

```c
static void serial_process(const char* str, int level) {
    // 发送颜色代码
    sync_serial_puts(serial_color_for_log_level(level));
    // 发送实际字符串
    sync_serial_puts(str);
    // 重置颜色
    sync_serial_puts(serial_color_for_log_level(-1));
}
```

这个函数做了三件事：首先输出颜色代码，然后输出实际字符串，最后重置颜色。这样每条日志都有自己的颜色，不会影响其他日志。

如果 `level` 是 -1，`serial_color_for_log_level` 返回重置代码，相当于不设置颜色。这对于普通 `kprintf` 调用很有用，因为它们没有特定的日志级别。

## 第六步：实现日志级别过滤

有了日志级别还不够，我们还需要过滤功能。比如在调试阶段，你想看到所有级别的日志；但在生产环境，你只想看到 WARN 和 ERROR。

在 `kernel/klogs/kprintf.c` 中已经实现了过滤功能：

```c
// 当前日志过滤级别
static klog_level_t g_log_level = KPRINTF_DEFAULT_FILTERED_LOGLEVEL;

void klog_set_level(klog_level_t level) {
    g_log_level = level;
}

klog_level_t klog_get_level(void) {
    return g_log_level;
}
```

在 `klog_log` 函数中：

```c
void klog_log(klog_level_t level, const char* format, ...) {
    // 检查日志级别
    if (level < g_log_level) {
        return;  // 级别太低，不输出
    }

    // ... 格式化和输出 ...
}
```

过滤的逻辑很简单：只有级别大于等于当前过滤级别的日志才会被输出。比如当前级别是 INFO（2），那么 INFO、WARN、ERROR 会被输出，但 TRACE 和 DEBUG 会被丢弃。

## 第七步：编写测试

现在我们来测试分级日志系统。在 `kernel_main.c` 中添加测试代码：

```c
#include "klogs/kprintf.h"
#include "klogs/backends/serial_backends.h"

void test_log_levels(void) {
    // 初始化
    klog_init(KLOG_BACKEND_SERIAL);

    // 测试所有级别（默认 INFO 级别）
    klog_trace("This is a TRACE message (should not appear at INFO level)");
    klog_debug("This is a DEBUG message (should not appear at INFO level)");
    klog_info("This is an INFO message");
    klog_warn("This is a WARN message");
    klog_error("This is an ERROR message");

    // 切换到 TRACE 级别
    klog_info("\n=== Switching to TRACE level ===");
    klog_set_level(KLOG_LEVEL_TRACE);

    klog_trace("Now TRACE messages should appear");
    klog_debug("Now DEBUG messages should appear");
    klog_info("INFO messages still appear");
    klog_warn("WARN messages still appear");
    klog_error("ERROR messages still appear");

    // 切换到 ERROR 级别
    klog_info("\n=== Switching to ERROR level ===");
    klog_set_level(KLOG_LEVEL_ERROR);

    klog_trace("TRACE should not appear");
    klog_debug("DEBUG should not appear");
    klog_info("INFO should not appear");
    klog_warn("WARN should not appear");
    klog_error("Only ERROR appears");

    // 测试格式化
    klog_info("\n=== Testing formatted output ===");
    klog_set_level(KLOG_LEVEL_INFO);
    klog_info("Value: %d, String: %s, Pointer: %p", 42, "hello", test_log_levels);
}
```

编译并运行：

```bash
cd build
cmake ..
make
./run.sh
```

你应该在串口输出中看到：

```
[INFO ] This is an INFO message
[WARN ] This is an ERROR message
[ERROR] This is an ERROR message

=== Switching to TRACE level ===
[TRACE] Now TRACE messages should appear
[DEBUG] Now DEBUG messages should appear
[INFO ] INFO messages still appear
[WARN ] WARN messages still appear
[ERROR] ERROR messages still appear

=== Switching to ERROR level ===
[ERROR] Only ERROR appears

=== Testing formatted output ===
[INFO ] Value: 42, String: hello, Pointer: 0x1000a0
```

如果你的串口终端支持 ANSI 颜色，你会看到：
- TRACE：灰色
- DEBUG：紫色
- INFO：绿色
- WARN：黄色
- ERROR：红色

## 第八步：处理终端兼容性

这里有一个需要注意的问题：不是所有终端都支持 ANSI 颜色。如果你的串口工具不支持，你会看到类似这样的输出：

```
[31m[ERROR][0m This is an error
```

这是 ANSI 转义序列被当作普通文本显示了。现代串口工具（如 picocom、minicom）基本都支持 ANSI 颜色，但如果你用的是老式工具或者某些特殊的终端，可能会有问题。

解决方法有几个：第一个是换一个支持 ANSI 颜色的串口工具。picocom 和 minicom 都是不错的选择，可以直接用 `apt install` 安装。

第二个是添加一个配置选项，让用户可以禁用颜色输出。你可以在 `serial_config.h` 中添加一个宏：

```c
#define SERIAL_COLOR_ENABLE 1
```

然后在代码中检查这个宏，如果禁用了就不输出颜色代码。

第三个是检测终端类型。有些终端会在环境变量中声明自己的能力，你可以检查这些变量来决定是否启用颜色。不过这比较复杂，一般在内核开发中不太常用。
