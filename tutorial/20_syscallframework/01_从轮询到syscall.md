# 从轮询到 syscall —— Stage 20 系统调用框架实战指南（一）

## 前言

写到 Stage 20 的时候，我意识到一个被我们忽略很久的问题：内核虽然跑起来了，有了内存管理，有了中断系统，但它本质上还是个"孤岛"。用户程序无法与内核对话，无法请求服务，甚至连最简单的输出都做不到。你想让用户程序打印一行"Hello World"？抱歉，做不到。

这就像开了一家餐厅，厨房里什么设备都有，但前台没有服务员，顾客无法点餐，厨房也做不出任何菜。我们需要的正是这个"服务员"——系统调用框架。

说实话，在早期开发阶段，我完全没意识到这个问题的严重性。那时候所有代码都在内核里跑，想干什么就直接干，读取端口、操作内存、调用函数，随心所欲。但现实是，一个真正可用的操作系统必须把内核和用户程序隔离开来——这不是为了找麻烦，而是为了安全和稳定。用户程序不能直接访问硬件，不能随便读写内核内存，它们需要通过一个"受控通道"来请求内核的服务。这个通道，就是系统调用。

你可能问，为什么不直接让用户程序调用内核函数？原因很简单：如果你允许用户程序直接跳转到内核代码执行，那就相当于把整个系统的钥匙交给了任何人。一个恶意程序可以轻易地绕过所有保护，直接修改内核数据结构，或者读取其他进程的内存。这在保护模式下是绝对不允许的。

所以这一篇我们会一起实现一个完整的系统调用框架。别担心，我们不会跳过任何步骤，每写一个函数都会解释清楚它是怎么工作的，为什么要这么写，有哪些坑需要避开。准备好了吗？我们开始。

## 环境说明

在开始之前，先确认一下你的开发环境。这篇文章假设你已经完成了 Stage 19，代码重构已经完成，内核的基础设施（GDT、IDT、内存管理等）已经就绪。

```
操作系统: Ubuntu 22.04 LTS / WSL2 / Arch WSL
编译器:   GCC x86_64-elf-gcc 或类似交叉编译器
构建工具: CMake 3.25 或更高版本
模拟器:   QEMU 7.0 或更高版本
汇编器:   NASM 2.15 或更高版本
```

可能有人会问，为什么需要 NASM？这是因为系统调用的底层入口必须用汇编编写，需要手动保存和恢复 CPU 状态。当然你也可以用 GCC 的内联汇编，但那种写法可读性很差，调试起来更是让人血压拉满。

## 内核态与用户态的隔离

在 x86_64 保护模式下，CPU 提供了四个特权级（Ring 0-3），但现代操作系统通常只使用两个：

- **Ring 0（内核态）**：可以执行所有指令，访问所有内存，直接操作硬件
- **Ring 3（用户态）**：受限执行，不能执行特权指令（如修改页表、操作端口等），只能访问自己的内存空间

这个隔离机制是硬件强制的。当用户程序试图执行特权指令时，CPU 会触发 General Protection 异常，内核可以捕获这个异常并终止违规程序。但问题来了：如果用户程序真的需要内核服务（比如读写文件、创建进程），它该怎么办？

答案就是系统调用。系统调用是一种受控的"通道"，允许用户程序安全地切换到内核态，执行一些特权操作，然后再返回用户态。这个过程是受控的，内核可以检查参数、验证权限、记录日志，确保用户程序不会搞乱系统。

你可以把它理解为餐厅的点餐流程：顾客（用户程序）不能直接走进厨房（内核），但可以通过服务员（系统调用接口）提交订单，厨房做好菜后再由服务员送回来。整个过程是受控的、安全的。

## 为什么不能直接调用内核函数

很多人第一次接触系统调用时会有这个疑惑：既然内核代码在内存里，为什么不能直接跳过去执行？

让我们看看如果用户程序直接调用内核函数会发生什么。假设内核有一个 `kmalloc()` 函数用于分配内存，用户程序知道这个函数的地址，直接调用它：

```c
// 用户程序试图直接调用内核函数
extern void* kmalloc(size_t size);
void* ptr = kmalloc(1024);  // 直接跳转到内核代码
```

这样做有几个严重问题：

第一，**权限检查被绕过了**。内核函数假设调用者是内核代码，不会检查参数的合法性。用户程序可以传入任意参数，比如分配 1TB 内存，或者传入恶意构造的指针，内核可能会因此崩溃或被利用。

第二，**内核数据结构可能被破坏**。内核函数通常会操作内核的数据结构（如内存页表、进程表等），如果用户程序随意调用，这些结构可能被篡改，导致整个系统不稳定。

第三，**异常处理会出问题**。内核函数执行时如果发生异常（比如缺页异常），异常处理程序会认为是内核代码出错，而不是用户程序的问题。这会导致错误的处理逻辑。

所以我们必须有一个明确的边界，用户程序只能通过这个边界来请求内核服务，内核可以在边界上进行严格的检查和验证。

## 传统 int 0x80 的局限性

在 x86 的历史上，系统调用是通过软中断实现的，最著名的就是 int 0x80。当用户程序执行 `int 0x80` 指令时，CPU 会触发一个中断，切换到内核态，跳转到 IDT 中向量 0x80 对应的处理函数。这个处理函数会读取寄存器中的参数，分发到对应的系统调用处理函数，然后通过 `iret` 返回用户态。

这种方式工作了很多年，但它有几个性能问题：

首先是开销太大。int 0x80 会触发完整的中断处理流程，CPU 需要保存很多状态：SS、RSP、RFLAGS、CS、RIP，甚至还有错误码。这些操作虽然必要，但对于系统调用这种高频操作来说，开销太大了。

其次是不够优化。中断是一个通用机制，需要处理各种情况，而系统调用的行为是可预测的：我们知道它要传递哪些参数，知道它需要保存哪些寄存器，知道它会怎么返回。如果能有一个专门为系统调用设计的机制，就可以去掉很多不必要的步骤。

还有一个问题是安全。int 0x80 会清除 RFLAGS 的一些标志，但不同的操作系统可能需要不同的行为。这种"一刀切"的方式不够灵活。

---

## syscall/sysret 指令的优势

x86_64 架构引入了专门的 syscall 和 sysret 指令，用于快速系统调用。这两条指令是专门为系统调用场景设计的，优势非常明显：

**速度更快**。syscall 指令只保存必要的寄存器：RCX（用户 RIP）和 R11（用户 RFLAGS）。相比之下，int 0x80 需要保存完整的中断帧，开销大得多。

**更灵活**。syscall 指令的行为由 MSR 寄存器控制，内核可以精确配置返回时用户态的 CS/SS 段选择子，以及需要清除的 RFLAGS 位。这种灵活性是 int 0x80 无法提供的。

**不经过 IDT**。syscall 指令直接从 MSR 寄存器读取目标地址，不需要查 IDT 表。这减少了内存访问，提高了速度，也避免了 IDT 被恶意篡改的风险。

当然，这并不意味着 int 0x80 就没用了。为了兼容性，我们还是会实现 int 0x80 的支持，但现代系统调用会优先使用 syscall 指令。

## 系统调用的工作流程

在我们开始写代码之前，先了解一下系统调用的完整流程。这有助于理解我们接下来要实现的每个组件的作用。

当用户程序发起一个系统调用时，比如写入数据到文件：

```
用户态程序
    │
    │ mov rax, SYS_WRITE    ; 系统调用号
    │ mov rdi, 1            ; 文件描述符 (stdout)
    │ mov rsi, buffer       ; 数据地址
    │ mov rdx, length       ; 数据长度
    │ syscall               ; 发起系统调用
    ▼
syscall 指令执行
    │
    ├─> CPU 自动保存状态
    │   RCX ← 用户 RIP (返回地址)
    │   R11 ← 用户 RFLAGS
    │
    ├─> CPU 加载内核状态
    │   RIP ← IA32_LSTAR (内核入口地址)
    │   CS ← IA32_STAR[47:32] (内核代码段)
    │   SS ← IA32_STAR[47:32] + 8 (内核数据段)
    │   RFLAGS ← RFLAGS & ~IA32_FMASK (清除指定标志)
    │
    ├─> CPU 切换到 Ring 0
    │
    ▼
syscall_handler (汇编入口)
    │
    ├─> 保存所有通用寄存器
    ├─> 加载内核数据段
    ├─> 栈对齐到 16 字节
    ├─> 构建 syscall_frame_t 结构
    │
    ▼
syscall_dispatch (C 分发器)
    │
    ├─> 读取系统调用号 (frame->syscall_number)
    ├─> 边界检查 (确保号在有效范围内)
    ├─> 更新统计信息
    ├─> 查找系统调用表
    │
    ▼
sys_write (系统调用处理函数)
    │
    ├─> 验证参数 (文件描述符、缓冲区地址等)
    ├─> 执行实际操作 (写入数据到输出设备)
    ├─> 返回结果 (写入的字节数或错误码)
    │
    ▼
syscall_handler (汇编恢复)
    │
    ├─> 清理栈
    ├─> 恢复用户 RIP/FLAGS (从 RCX/R11)
    ├─> 恢复所有通用寄存器
    │
    ▼
sysretq 指令
    │
    ├─> CPU 自动恢复用户态
    │   RIP ← RCX
    │   RFLAGS ← R11
    │   CS ← IA32_STAR[63:48] | 3
    │   SS ← IA32_STAR[63:48] + 8 | 3
    │
    ├─> CPU 切换到 Ring 3
    │
    ▼
返回用户态程序
    │
    └─> 返回值在 RAX 中
```

这个流程看起来有点复杂，但我们可以把它分成几个独立的模块，每个模块负责一部分工作。接下来的文章里，我们会一步步实现每个模块。

## 我们要实现的目标

在这个阶段，我们需要实现以下组件：

**系统调用框架核心**：
- MSR 寄存器配置（IA32_LSTAR、IA32_STAR、IA32_FMASK）
- syscall 指令的汇编入口点
- C 语言系统调用分发器
- 系统调用注册表
- 系统调用统计系统

**int 0x80 兼容支持**：
- int 0x80 的汇编入口点
- 参数格式转换
- IDT 注册

**基础系统调用实现**：
- 进程管理：exit、getpid、getppid
- 文件 I/O：write、read、open、close
- 内存管理：brk
- 系统信息：uname

**用户态测试程序**：
- 编写简单的用户程序来测试系统调用
- 验证 syscall 指令工作正常
- 验证系统调用分发和返回

实现之后，我们的内核将能够：
- 接受用户程序的系统调用请求
- 安全地分发到对应的处理函数
- 收集系统调用统计信息
- 支持现代 syscall 指令和传统 int 0x80
