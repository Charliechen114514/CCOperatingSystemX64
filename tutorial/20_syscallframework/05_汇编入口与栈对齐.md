# 汇编入口与栈对齐 —— Stage 20 系统调用框架实战指南（五）

## 前言

在之前的文章里，我们配置了 MSR 寄存器，让 syscall 指令有了"目标地址"。但那个目标地址（我们的 `syscall_handler`）目前只是一个空壳，如果现在执行 syscall 指令，系统会立即崩溃。

这篇文章我们要实现完整的汇编入口代码。说实话，这是整个系统调用框架中最容易出错的部分，因为涉及到很多细节：寄存器保存、栈对齐、数据结构构造，每一步都不能错。但别担心，我会把每个步骤都讲清楚。

---

## syscall_handler 的工作流程

当用户程序执行 `syscall` 指令时，CPU 会自动跳转到我们的 `syscall_handler`。这时 CPU 的状态是：

- RCX = 用户 RIP（返回地址）
- R11 = 用户 RFLAGS
- RAX = 系统调用号
- RDI, RSI, RDX, R10, R8, R9 = 系统调用参数

我们的 `syscall_handler` 需要做这些事：

1. 保存所有通用寄存器（用户程序期望返回后这些寄存器不变）
2. 单独保存 RCX 和 R11（CPU 已经帮我们保存了用户 RIP/RFLAGS，但我们需要把它们挪到安全的地方）
3. 加载内核数据段（DS, ES, FS, GS）
4. 对齐栈到 16 字节边界
5. 在栈上构造 `syscall_frame_t` 结构
6. 调用 C 分发器 `syscall_dispatch`
7. 清理栈
8. 恢复用户 RIP/RFLAGS
9. 恢复所有通用寄存器
10. 执行 `sysretq` 返回用户态

## 栈对齐问题详解

在开始写代码之前，我必须详细解释一下栈对齐问题。这个问题太重要了，我曾经因为理解不到位而浪费了好几个小时。

System V AMD64 ABI 规定：**调用 C 函数时，栈必须 16 字节对齐**。这不是建议，是硬性要求。如果栈不对齐，调用 C 函数时可能会崩溃，或者 SSE/AVX 指令触发异常。

那么问题来了：syscall 指令执行时，栈是对齐的吗？

答案是：**不一定**。这取决于用户程序调用 `syscall` 时栈的状态。如果用户程序的栈在调用 syscall 时是 16 字节对齐的，那么 syscall 指令不会改变栈（它不推送任何东西），所以进入 `syscall_handler` 时栈仍然对齐。但如果用户程序的栈本身就不对齐，那我们进入时栈也不对齐。

所以我们必须在调用 C 函数之前手动对齐栈。方法是 push 一个额外的 qword（8 字节），让栈指针 RSP 变成 16 的倍数。

还有一个细节：我们需要保存用户 RIP 和 RFLAGS，这两个值已经在 RCX 和 R11 中了。但我们需要把它们保存到某个地方，因为后续的代码可能会覆盖 RCX 和 R11。

## 实现 syscall_handler

现在让我们实现完整的 `syscall_handler`。打开 `syscall.asm`，替换之前的空实现：

```asm
; ============================================================================
; syscall Instruction Entry Point
; ============================================================================

global syscall_handler
extern syscall_dispatch

syscall_handler:
    ; At this point:
    ;   RCX = user RIP (saved by syscall)
    ;   R11 = user RFLAGS (saved by syscall)
    ;   RAX = syscall number
    ;   RDI, RSI, RDX, R10, R8, R9 = arguments

    ; -------------------------------------------------------------------------
    ; Step 1: Save all general-purpose registers
    ; -------------------------------------------------------------------------
    push rax                ; Save syscall number
    push rbx
    push rbp
    push r12
    push r13
    push r14
    push r15

    ; -------------------------------------------------------------------------
    ; Step 2: Save RCX and R11 separately (user RIP/RFLAGS)
    ; -------------------------------------------------------------------------
    mov r15, rcx            ; Save user RIP in R15
    mov r14, r11            ; Save user RFLAGS in R14

    ; -------------------------------------------------------------------------
    ; Step 3: Load kernel data segments
    ; -------------------------------------------------------------------------
    mov ax, 0x10            ; GDT_KERNEL_DATA
    mov ds, ax
    mov es, ax
    mov fs, ax
    mov gs, ax

    ; -------------------------------------------------------------------------
    ; Step 4: Align stack to 16 bytes
    ; -------------------------------------------------------------------------
    ; We pushed 7 registers = 56 bytes (56 mod 16 = 8)
    ; Need to push 8 more bytes to align
    push qword 0

    ; -------------------------------------------------------------------------
    ; Step 5: Construct syscall_frame_t on stack
    ; -------------------------------------------------------------------------
    sub rsp, 48             ; Allocate syscall_frame_t

    ; syscall_frame_t layout:
    ; +0x00  syscall_number
    ; +0x08  arg0 (RDI)
    ; +0x10  arg1 (RSI)
    ; +0x18  arg2 (RDX)
    ; +0x20  arg3 (R10)
    ; +0x28  arg4 (R8)
    ; Note: arg5 (R9) is passed separately

    mov qword [rsp], rax    ; syscall_number (original RAX)
    mov qword [rsp+8], rdi  ; arg0
    mov qword [rsp+16], rsi ; arg1
    mov qword [rsp+24], rdx ; arg2
    mov qword [rsp+32], r10 ; arg3
    mov qword [rsp+40], r8  ; arg4

    ; -------------------------------------------------------------------------
    ; Step 6: Call C dispatcher
    ; -------------------------------------------------------------------------
    ; int64_t syscall_dispatch(syscall_frame_t* frame, uint64_t arg5)
    mov rdi, rsp            ; RDI = frame pointer
    mov rsi, r9             ; RSI = arg5
    call syscall_dispatch

    ; Return value in RAX
    ; RAX is overwritten by syscall_dispatch, which is fine
    ; because we saved original RAX on stack

    ; -------------------------------------------------------------------------
    ; Step 7: Clean up frame
    ; -------------------------------------------------------------------------
    add rsp, 48             ; Deallocate syscall_frame_t

    ; -------------------------------------------------------------------------
    ; Step 8: Clean up alignment
    ; -------------------------------------------------------------------------
    add rsp, 8              ; Remove alignment padding

    ; -------------------------------------------------------------------------
    ; Step 9: Restore user RIP/RFLAGS
    ; -------------------------------------------------------------------------
    mov rcx, r15            ; Restore user RIP to RCX (for sysretq)
    mov r11, r14            ; Restore user RFLAGS to R11

    ; -------------------------------------------------------------------------
    ; Step 10: Restore saved registers
    ; -------------------------------------------------------------------------
    pop r15
    pop r14
    pop r13
    pop r12
    pop rbp
    pop rbx
    pop rax                 ; Restore original RAX (will be overwritten)

    ; -------------------------------------------------------------------------
    ; Step 11: Return to user mode
    ; -------------------------------------------------------------------------
    ; RAX already contains return value from syscall_dispatch
    sysretq
```

这段代码做了几件关键的事：

第一，我们保存了所有通用寄存器。注意我们用的是 R15 和 R14 来保存用户 RIP/RFLAGS，因为这两个寄存器是 callee-saved 的，不会被 C 函数修改。

第二，我们加载了内核数据段。这是因为 syscall 指令不会自动切换数据段，我们需要手动确保 DS/ES/FS/GS 指向内核数据段。

第三，我们对齐了栈。我们推送了 7 个寄存器（56 字节），56 mod 16 = 8，所以我们需要再 push 8 字节（一个 qword）来让栈对齐。

第四，我们构造了 `syscall_frame_t` 结构。注意字段顺序必须与 `syscall.h` 中的定义完全一致。

第五，我们调用了 C 分发器。注意这里用 RDI 传递 frame 指针，用 RSI 传递 arg5（R9）。这是因为 System V ABI 规定前两个参数用 RDI 和 RSI 传递。

## 为什么不直接传递所有参数

你可能会问：为什么要在栈上构造 `syscall_frame_t`，而不是直接传递寄存器中的参数？

有几个原因：

第一，**统一的接口**。通过一个结构体传递所有参数，C 函数的接口更清晰，也更容易扩展（比如未来需要添加更多参数）。

第二，**调试方便**。结构体可以在调试器中方便地查看，而散落在各寄存器的参数不那么直观。

第三，**历史原因**。Linux 内核也是这么做的，这种设计经过了时间的考验。

## 栈布局可视化

让我们看看 `syscall_handler` 执行时的栈布局：

```
进入 syscall_handler 时（假设用户栈对齐）:
RSP →  (用户栈顶)

push rax, rbx, rbp, r12, r13, r14, r15 后:
RSP →  [RAX][RBX][RBP][R12][R13][R14][R15]
       -56  -48  -40  -32  -24  -16   -8   (相对于当前 RSP)

push qword 0 后:
RSP →  [padding][RAX][RBX][RBP][R12][R13][R14][R15]
        -8      -16  -24  -32  -40  -48  -56  -64

sub rsp, 48 后:
RSP →  [syscall_frame_t                ][padding][...saved regs...]
       -48             (frame)          -8       -64

frame 内容:
[RSP+0]   = syscall_number
[RSP+8]   = arg0 (RDI)
[RSP+16]  = arg1 (RSI)
[RSP+24]  = arg2 (RDX)
[RSP+32]  = arg3 (R10)
[RSP+40]  = arg4 (R8)
(arg5 在 R9 中，单独传递)

调用 syscall_dispatch 时:
RDI = RSP (frame 指针)
RSI = R9 (arg5)
```

这个栈布局确保了在调用 `syscall_dispatch` 时，RSP 是 16 字节对齐的（假设初始对齐）。
