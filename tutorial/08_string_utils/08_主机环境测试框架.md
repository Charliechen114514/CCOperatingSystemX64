# 主机环境测试框架 —— 秒级反馈的开发效率提升

断言系统搞定了，现在我们来解决一个开发效率问题。你有没有发现，每次改点代码都要重新编译内核、启动 QEMU、等待启动，然后才能验证功能。这套流程下来，改一行代码测试一下的时间都够煮碗泡面了。今天我们要实现一个主机环境的测试框架，让代码验证变得快速而简单。

## 为什么要主机测试

主机环境就是你平时写代码用的操作系统（Linux/Windows/macOS），内核环境是你正在开发的操作系统。两者有很大区别。主机测试的编译时间是秒级，启动时间是毫秒级，你可以用 GDB、Valgrind 等成熟工具，测试成本极低。而内核测试的编译时间是分钟级，启动时间是几十秒，调试工具有限，测试成本高。

所以策略很明确：先用主机环境快速验证逻辑，再在内核环境测试集成。这样大部分问题都可以在几秒内发现并修复，而不是每次都要重新启动内核。

## 第一步：理解测试框架的设计

我们的测试框架要达到几个目标：在主机环境编译运行，不依赖内核代码；提供断言宏用于验证；统计测试结果，显示通过/失败数量；输出清晰，让人一眼就知道哪个测试通过了、哪个失败了。

核心思想是测试程序是独立的可执行文件，不链接任何内核代码。它只测试我们实现的字符串函数。这样做的好处是测试程序可以快速编译运行，而且可以使用标准库的函数（比如 `printf`）来输出结果。

## 第二步：实现 host_support.h

我们创建一个 `test/host_support.h` 文件，提供测试宏和主机环境的替代定义。这个文件定义了测试断言宏，比如 `TEST_ASSERT_EQ` 比较两个整数是否相等，`TEST_ASSERT_STR_EQ` 比较两个字符串是否相等，`TEST_ASSERT_TRUE` 验证条件是否为真。

```c
/* 在 test/host_support.h 中 */

#pragma once

#include <stdio.h>
#include <stdbool.h>
#include <stddef.h>

/* 类型定义 */
typedef enum {
    false = 0,
    true  = 1
} bool;

/* 测试计数器 */
extern int g_test_passed;
extern int g_test_failed;

/* 测试断言宏 */
#define TEST_ASSERT_EQ(actual, expected, msg) \
    do { \
        if ((actual) != (expected)) { \
            printf("  [FAIL] %s: %d != %d\n", (msg), (int)(actual), (int)(expected)); \
            g_test_failed++; \
        } else { \
            g_test_passed++; \
        } \
    } while (0)

#define TEST_ASSERT_STR_EQ(actual, expected, msg) \
    do { \
        const char* a = (actual); \
        const char* e = (expected); \
        if (a == NULL || e == NULL || strcmp(a, e) != 0) { \
            printf("  [FAIL] %s: \"%s\" != \"%s\"\n", (msg), \
                   a ? a : "(null)", e ? e : "(null)"); \
            g_test_failed++; \
        } else { \
            g_test_passed++; \
        } \
    } while (0)

#define TEST_ASSERT_TRUE(condition, msg) \
    do { \
        if (!(condition)) { \
            printf("  [FAIL] %s\n", (msg)); \
            g_test_failed++; \
        } else { \
            g_test_passed++; \
        } \
    } while (0)

#define TEST_INFO(msg) printf("\n--- %s\n", (msg))
#define TEST_PASS(msg) printf("  [PASS] %s\n", (msg))
```

这些宏的设计思路很简单：如果断言失败，打印失败信息并增加失败计数；否则增加通过计数。`do { ... } while (0)` 的包装是为了让宏在语法上像一个单条语句，避免在某些情况下出现语法错误。

## 第三步：编写测试程序

测试程序的主体是一系列测试函数，每个函数测试一组相关的功能。比如 `test_strlen` 测试字符串长度计算，`test_strcmp` 测试字符串比较，等等。

```c
/* 在 test/test_string.c 中 */

#include <stddef.h>
#include <stdio.h>
#include <string.h>

/* 前向声明字符串函数 */
extern size_t strlen(const char* s);
extern int strcmp(const char* s1, const char* s2);
/* ... 其他函数声明 ... */

/* 测试计数器 */
int g_test_passed = 0;
int g_test_failed = 0;

/* 包含测试支持宏 */
#include "host_support.h"

/* 测试函数 */
static void test_strlen(void) {
    TEST_INFO("Testing strlen...");

    TEST_ASSERT_EQ(strlen(""), (size_t)0, "empty string");
    TEST_ASSERT_EQ(strlen("hello"), (size_t)5, "normal string");

    TEST_PASS("strlen: all tests passed");
}

static void test_strcmp(void) {
    TEST_INFO("Testing strcmp...");

    TEST_ASSERT_TRUE(strcmp("abc", "abc") == 0, "identical strings");
    TEST_ASSERT_TRUE(strcmp("abc", "abd") < 0, "abc < abd");

    TEST_PASS("strcmp: all tests passed");
}

int main(void) {
    printf("CCOS String Library Test Suite\n\n");

    test_strlen();
    test_strcmp();

    printf("\nTest Results:\n");
    printf("  Passed: %d\n", g_test_passed);
    printf("  Failed: %d\n", g_test_failed);

    return g_test_failed > 0 ? 1 : 0;
}
```

## 第四步：编译和运行测试

编译测试程序很简单，用 gcc 直接编译就可以了。关键是要正确指定包含目录，让编译器能找到我们的字符串函数和头文件。

```bash
gcc -o test/test_string \
    test/test_string.c \
    kernel/base/string.c \
    -I kernel/base \
    -I test/include

./test/test_string
```

如果一切正常，你会看到一系列测试通过的信息，最后显示总数。如果有测试失败，会显示具体哪个测试失败了，以及失败的原因。

## 第五步：使用 Valgrind 检测内存问题

主机测试的一个好处是可以使用 Valgrind 检测内存错误。Valgrind 是一个强大的工具，可以检测内存泄漏、非法内存访问、使用未初始化的内存等问题。

```bash
sudo apt-get install valgrind
valgrind --leak-check=full ./test/test_string
```

如果一切正常，Valgrind 会报告没有内存泄漏和错误。如果有问题，它会告诉你具体哪里出错了。这在内核开发中特别有用，因为内核环境的内存错误很难调试。

说实话，实现这个测试框架的过程让我意识到测试驱动开发的价值。以前我总是先写代码再测试，现在我会先写测试再写代码。这听起来有点反直觉，但实际上更高效 —— 因为测试迫使你思考接口设计，而且一旦写完就能立即验证。
