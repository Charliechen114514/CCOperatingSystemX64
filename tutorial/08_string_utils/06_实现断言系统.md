# 实现断言系统 —— CCOS_ASSERT 和 CCOS_DEBUG_ASSERT

字符串工具库搞定了，现在该来做一件更重要的事情 —— 断言系统。说实话，写内核代码的时候最怕的就是那种"看起来没问题"的 Bug。你一遍遍地看代码，一遍遍地调试，最后发现是一个空指针被忘了检查。如果有断言系统，这种问题就能在第一时间被发现。

## 什么是断言

断言是一种在代码中声明"某个条件必须为真"的机制。如果条件不满足，程序就会停止运行并报告错误。这不是什么新概念，早在几十年前就已经有了，但很多人还是低估了它的价值。

基本思想很简单：你断言某个条件为真，如果它不为真，程序就停止并告诉你哪里出错了。这听起来没什么，但当你调试一个复杂的内核崩溃时，能立刻知道"哪个断言失败了"比"程序在某处崩溃了"要有用得多。

## 我们需要什么样的断言系统

在我们的内核中，我们需要两种断言。

`CCOS_ASSERT` 是始终启用的断言，用于关键检查。比如空指针检查、数组边界检查、状态不变式验证。这些是绝对不能出问题的地方，无论 Debug 还是 Release 构建，这个断言都会生效。你可能会问，为什么不全部用这种断言？因为性能。每个断言都有运行时开销，有些检查在发布版本中可能不值得。

`CCOS_DEBUG_ASSERT` 是仅 Debug 模式启用的断言，用于调试辅助。比如函数参数验证、内部状态检查、性能相关的断言。在 Release 构建中，这些断言会被完全移除，不影响性能。这样你可以在开发阶段尽情检查，而在发布版本保持高效。

## 第一步：创建断言头文件

断言系统的接口很简单，但设计起来有一些讲究。我们的 `assert.h` 头文件定义了两个宏和一个后端函数。

```c
/* 在 kernel/assert/assert.h 中 */

#pragma once

/* Assert macro - condition expression must be true */
#define CCOS_ASSERT(EXPECTED_EXPR) \
    ccos_assert_impl(EXPECTED_EXPR, #EXPECTED_EXPR, __FILE__, __LINE__, __func__)

/* Backend function declarations */
void ccos_assert_impl(bool condition, const char* expr_str, const char* file, int line,
                      const char* func);

#ifdef NDEBUG
#    define CCOS_DEBUG_ASSERT(EXPECTED_EXPR) (void)(EXPECTED_EXPR)
#else
#    define CCOS_DEBUG_ASSERT(EXPECTED_EXPR) \
        ccos_assert_impl(EXPECTED_EXPR, #EXPECTED_EXPR, __FILE__, __LINE__, __func__)
#endif
```

这个设计有几个值得注意的地方。首先，`CCOS_DEBUG_ASSERT` 在 Release 模式下展开成 `(void)(EXPECTED_EXPR)`，这确保了表达式仍然会被求值（避免"未使用变量"警告），但结果被丢弃。

其次，我们用了宏的字符串化操作符 `#`。它把宏参数转换成字符串字面量。比如 `CCOS_ASSERT(x > 5)` 会被展开成 `ccos_assert_impl(x > 5, "x > 5", "main.c", 42, "main")`。这样我们就能在错误信息中看到原始的表达式，这对调试非常有帮助。

## 第二步：实现断言主体

断言的实现很简单，但需要处理好循环依赖的问题。我们先看基本的实现。

```c
/* 在 kernel/assert/assert.c 中 */

#include "assert.h"
#include "assert_action_backend.h"

void ccos_assert_impl(bool condition, const char* expr_str,
                      const char* file, int line, const char* func)
{
    if (condition) {
        return;  // 断言成功，什么都不做
    }

    // 断言失败！准备错误信息
    struct ccos_assert_context ctx = {
        .expr = expr_str,
        .file = file,
        .line = line,
        .func = func
    };

    // 调用后端处理
    assert_failed_action(&ctx);
}
```

这个实现很简单：如果条件为真，直接返回；否则，收集错误信息并调用后端。后端负责显示错误信息和停止系统。

## 第三步：定义后端接口

后端接口定义在 `assert_action_backend.h` 中。这是一个小型的结构体和函数声明。

```c
/* 在 kernel/assert/assert_action_backend.h 中 */

#pragma once

#include <stdbool.h>

struct ccos_assert_context {
    const char* expr;   /* The failed expression as a string */
    const char* file;   /* Source file where assertion failed */
    int line;           /* Line number where assertion failed */
    const char* func;   /* Function name where assertion failed */
};

void assert_failed_action(const struct ccos_assert_context* ctx);
```

这个结构体包含了断言失败时需要的所有信息：失败的表达式、源文件、行号、函数名。后端函数负责把这些信息显示出来，然后停止系统。

## 循环依赖问题

这里有个有趣的问题：断言系统需要 VGA 驱动来显示错误信息，但 VGA 驱动可能也想使用断言。这会产生循环依赖。

解决方案是分层设计。基础 VGA 函数不使用断言，它们是"原子"操作。包装函数可以使用断言，而断言后端只使用基础函数。这样就避免了循环依赖。

或者更简单的方法：让断言后端完全不使用断言。因为我们已经在处理断言失败了，再触发断言没有意义。

## 使用示例

现在我们可以在代码中使用断言了。

```c
#include "assert/assert.h"

void example_function(int* ptr, int index) {
    // 关键检查 - 始终启用
    CCOS_ASSERT(ptr != NULL);

    // 调试检查 - 仅 Debug 模式
    CCOS_DEBUG_ASSERT(index >= 0);

    // 如果 ptr 是 NULL，程序会立即停止并报告错误
}
```

## 断言 vs 错误处理

重要的是理解断言和错误处理的区别，很多人会混淆这两个概念。

断言用于检测编程错误，那些不应该发生的事情。比如空指针、数组越界、无效的状态。如果断言失败，说明代码有 Bug，需要修复。

错误处理用于处理预期的情况，那些可能发生但不是错误的事情。比如文件不存在、网络超时、用户输入无效。这些情况应该正常处理，而不是让程序崩溃。

```c
// 错误：用断言处理用户输入
CCOS_ASSERT(user_input >= 0 && user_input <= 100);  // 不要这样做！

// 正确：用错误处理
if (user_input < 0 || user_input > 100) {
    print_error("Invalid input range");
    return;
}

// 正确：用断言检测内部错误
CCOS_ASSERT(internal_state != NULL);  // 这应该永远是真的
```

## 验证

创建一个简单的测试来验证断言系统是否工作。

```c
void test_assertion(void) {
    printf("Testing assertion system...\n");
    printf("About to trigger a failing assertion.\n");

    // 这个断言会失败
    CCOS_ASSERT(1 == 2);  // 永远是 false！

    // 下面的代码永远不会执行
    printf("This should not appear.\n");
}
```

编译运行，你应该看到：屏幕突然变红，显示断言失败的详细信息，系统停止。

说实话，实现这个断言系统的过程让我对错误处理有了更深的理解。以前我觉得断言很简单，就是一个宏加一个函数。但真正实现的时候才发现有很多细节需要注意：循环依赖、性能开销、与调试器的集成等等。
