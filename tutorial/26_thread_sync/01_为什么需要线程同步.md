# 为什么需要线程同步 —— 从竞态条件说起

## 前言

写完 Stage 25 文件系统之后，我盯着代码看了半天，突然意识到一个尴尬的事实：我们的内核虽然有了进程管理，有了调度器，可以"同时"运行多个进程，但实际上这些进程之间几乎没有什么协作机制。如果两个进程同时访问同一个数据结构，会发生什么？说实话，我不知道。可能是数据损坏，可能是内核崩溃，也可能是什么都不发生但结果是错的。

这就像两个人同时用同一台打印机打印文档。如果他们不管对方直接操作，最后打印出来的可能是两份文档混杂在一起的垃圾。解决这个问题的办法很简单：加锁，一个人用的时候另一个人等着。在操作系统的世界里，这些"锁"就是同步原语。

说实话，同步原语的实现比我想象中复杂得多。一开始我以为无非就是一些加锁解锁的操作，但真正动手之后才发现：有忙等待锁（spinlock），有可睡眠锁（mutex），有信号量（semaphore），有条件变量（condition variable），有读写锁（rwlock），还有原子操作和内存屏障...每种原语都有自己的适用场景，用错了会有性能问题甚至死锁。

更糟糕的是，这些原语的实现必须精确无误。一个微小的错误就可能导致莫名其妙的 bug，这种 bug 通常很难复现，因为你不知道什么时候才会触发竞态条件。这就是为什么内核开发者经常说并发代码是最难写的代码。

## 我们现在在哪里

如果你跟着之前的教程一路走来，我们现在在 Stage 25 完成后的位置。文件系统已经就绪，可以读写文件，可以创建进程，可以实现调度。但问题来了：我们没有并发控制机制。

让我们看看这个没有同步保护的世界会出什么问题。假设两个进程同时往同一个链表里插入节点：

```c
// 全局链表头
node_t* global_list = NULL;

// 进程 A 执行
void insert_A(node_t* new_node) {
    new_node->next = global_list;  // 步骤 1：设置新节点的 next
    global_list = new_node;        // 步骤 2：更新头指针
}

// 进程 B 同时执行
void insert_B(node_t* new_node) {
    new_node->next = global_list;  // 步骤 1：设置新节点的 next
    global_list = new_node;        // 步骤 2：更新头指针
}
```

如果运气好，进程 A 和进程 B 顺序执行，链表正确工作。但如果它们真的"同时"执行，比如在进程 A 执行完步骤 1 之后、步骤 2 之前发生了调度切换，进程 B 开始执行，会发生什么？

进程 B 会把 `global_list` 指向自己的节点，然后进程 A 恢复执行，又把 `global_list` 指向进程 A 的节点。结果是进程 B 的节点从链表里消失了，永远丢失了。这就是一个典型的竞态条件（Race Condition）。

## 单线程模型的局限 vs 多线程的新问题

在 Stage 26 之前，我们其实也有某种程度的"并发"：通过调度器，多个进程可以轮流使用 CPU。但之前的代码大多是"单线程安全"的，因为每个进程有独立的地址空间，访问的是不同的内存。

但一旦我们开始实现线程（同一进程内的多个执行流共享地址空间），或者多个内核线程访问共享的内核数据结构（比如进程表、文件系统缓存），问题就来了。

竞态条件只是问题之一。更复杂的是死锁（Deadlock）：两个或多个线程互相等待对方持有的锁，所有人都在等，没人能继续执行。想象一下：线程 A 持有锁 1，等待锁 2；线程 B 持有锁 2，等待锁 1。结果就是死锁，程序卡住不动。

还有优先级反转（Priority Inversion）：高优先级线程等待低优先级线程持有的锁，但中优先级线程抢占了低优先级线程的 CPU，导致低优先级线程无法释放锁，高优先级线程也一直等不到。这个问题在实时系统里是致命的。

这些问题的解决方案就是同步原语。它们的作用是保证共享数据在并发访问时的一致性，同时避免死锁、饥饿等问题的发生。

## 为什么需要多种同步原语

你可能会问：为什么不搞一个"万能锁"解决所有问题？这是个好问题，但答案是不存在这样的锁。

不同的同步场景有不同的需求：

**短临界区需要忙等待锁**。如果临界区代码只有几条指令，比如修改一个计数器，使用会睡眠的 mutex 就太重了。调度开销可能比实际工作还多。这时候用 spinlock 更合适，虽然在等待时占用 CPU，但时间很短，总比调度切换快。

**长临界区需要可睡眠锁**。如果临界区代码可能执行较长时间，比如要等待 I/O 或者复制大量数据，用 spinlock 就会浪费大量 CPU。这时候用 mutex 更好，等待的线程可以被调度出去，让其他线程使用 CPU。

**资源计数需要信号量**。如果你有一个连接池，最多支持 10 个连接，现在需要管理这些连接的分配和释放。mutex 只能表示"可用"或"不可用"两种状态，但信号量可以表示"还剩 N 个连接"。

**条件等待需要条件变量**。如果你需要等待某个条件成立才能继续，比如"队列非空时才能取元素"，单纯的锁不够用。你需要一个机制：不满足条件时等待，条件成立后被唤醒。条件变量正是为此设计的。

**读多写少需要读写锁**。如果一个数据结构大部分时候被读取，很少被修改，用 mutex 就太浪费了。读写锁允许多个读者同时访问，只在写者出现时才独占。这对于读多写少的场景（比如配置表、路由表）非常有效。

**简单计数需要原子操作**。如果只是要把一个计数器加 1，用任何锁都是浪费。原子操作直接在硬件层面保证原子性，无需加锁，效率最高。

正因为不同场景需求不同，我们需要多种同步原语。每种原语都是为特定场景优化的，用对了事半功倍，用错了事倍功半。

## 与标准 Linux API 的对比

Linux 提供了一套成熟的同步原语 API，我们的实现会尽量与之兼容：

```c
// 自旋锁 (Linux kernel API)
spinlock_t lock;
spin_lock_init(&lock);
spin_lock(&lock);
// 临界区
spin_unlock(&lock);

// 互斥锁 (pthread API)
pthread_mutex_t mutex;
pthread_mutex_init(&mutex, NULL);
pthread_mutex_lock(&mutex);
// 临界区
pthread_mutex_unlock(&mutex);

// 信号量 (pthread API)
sem_t sem;
sem_init(&sem, 0, 0);
sem_wait(&sem);   // P 操作
sem_post(&sem);   // V 操作

// 条件变量 (pthread API)
pthread_cond_t cond;
pthread_cond_init(&cond, NULL);
pthread_cond_wait(&cond, &mutex);
pthread_cond_signal(&cond);
pthread_cond_broadcast(&cond);

// 读写锁 (pthread API)
pthread_rwlock_t rwlock;
pthread_rwlock_init(&rwlock, NULL);
pthread_rwlock_rdlock(&rwlock);   // 读锁
pthread_rwlock_wrlock(&rwlock);   // 写锁
pthread_rwlock_unlock(&rwlock);
```

我们的内核实现会提供类似的接口，语义上也尽量保持一致。但有几个重要的区别：

首先是运行环境。Linux 的 pthread 库运行在用户态，依赖于内核的 futex 系统调用。而我们是在内核里直接实现，不需要陷入内核态（因为我们已经在内核里了）。这让我们的实现更直接，但也要更小心，因为出错可能导致整个系统崩溃。

其次是功能简化。Linux 的 pthread_mutex 支持很多属性（比如递归锁、错误检查锁、优先级继承锁），我们的初期实现会简化一些。这不是因为它们不重要，而是为了降低实现复杂度，先把基础功能做对。

再者是 futex 机制。Linux 的 futex（Fast Userspace muTEX）是一个非常聪明的设计：在无竞争时完全在用户态执行，只在有竞争时才进入内核。我们的内核版本不需要这么复杂，因为我们的"用户态"是用户程序，"内核态"是我们的内核实现。不过未来可以借鉴这个思路。

## 实现路线图预览

在这个阶段，我们要实现一个功能完整的线程同步系统。这不是一个简化的玩具实现，而是一个具备生产级特性的同步原语库。

我们会按照依赖关系，从底层到上层逐步实现：

**第一层是原子操作**。这是所有同步原语的基础。我们会实现 `atomic_t` 类型和各种原子操作函数，包括算术操作、CAS 操作、位操作，以及内存屏障。这些操作直接使用 GCC 的内置函数，保证在 x86_64 上的正确性。

**第二层是自旋锁和等待队列**。自旋锁是最简单的锁，用原子操作实现，适用于短临界区。等待队列是进程阻塞和唤醒的基础设施，所有可睡眠的同步原语都会用到它。

**第三层是高级同步原语**。包括互斥锁、信号量、条件变量、读写锁。这些原语会使用自旋锁和等待队列来实现，提供更高级的语义。

**第四层是线程支持**。在有了同步原语之后，我们来实现真正的线程。线程共享进程的地址空间，有独立的栈和寄存器状态，需要 join/detach 机制来管理生命周期。

**第五层是演示和测试**。我们会编写演示程序，测试所有同步原语的功能，包括并发计数器、生产者-消费者、读者-写者等经典场景。

最后是系统调用集成。我们会把线程相关的操作注册为系统调用，让用户程序可以创建和管理线程。

## 我们即将要做的

在接下来的文章中，我们会一步步完成线程同步的实现。

首先，我们会学习同步设计基础。了解临界区、互斥、死锁等基本概念，学习不同同步原语的分类和适用场景，研究经典同步问题（生产者-消费者、读者-写者）。

然后，我们会实现原子操作。从最简单的 `atomic_inc` 开始，逐步实现完整的原子操作库，包括 CAS 操作和内存屏障。这是所有同步原语的基石。

接下来是自旋锁和等待队列。自旋锁是最简单的锁，我们会用原子操作实现它，包括中断安全版本。等待队列是进程阻塞和唤醒的基础，我们会实现 `sleep_on` 和 `wake_up` 操作。

之后是互斥锁。这是最常用的同步原语，我们会实现快速路径优化和递归锁支持。快速路径在无竞争时只需要一条原子指令，慢速路径使用等待队列管理等待者。

然后是信号量。信号量支持资源计数，我们会实现 P 操作（wait）和 V 操作（post），并用它来实现生产者-消费者模式。

接下来是条件变量。条件变量必须与 mutex 配合使用，我们会实现 `wait`、`signal` 和 `broadcast` 操作，解释为什么必须用 `while` 检查条件。

之后是读写锁。读写锁允许多个读者并发访问，我们会实现读者优先的策略，讨论写者饥饿问题。

然后是创建同步模块的脚手架。我们会创建 `kernel/sync/` 目录，编写 CMakeLists.txt，把所有同步原语集成到构建系统。

接下来是扩展线程支持。我们会扩展 PCB 结构来支持线程，实现内核线程和用户线程的创建，以及 join/detach 机制。

之后是编写同步演示程序。我们会创建 `kernel/demo/sync/` 目录，编写各种演示程序来测试同步原语的功能。

最后是系统调用集成和调试。我们会把线程操作注册为系统调用，编写用户态测试程序，讨论常见问题和调优建议。

每一步都是独立的，你可以跟着做一部分，也可以全部做完。相信我，等你完整实现之后，你会对并发编程有更深入的理解。

准备好了吗？让我们从 **同步设计基础** 开始，深入了解临界区、互斥、死锁等基本概念，学习不同同步原语的分类和适用场景。
