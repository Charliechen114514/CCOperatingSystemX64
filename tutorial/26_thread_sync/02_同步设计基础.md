# 同步设计基础 —— 理解并发编程的核心概念

## 前言

在上一篇文章中，我们讨论了为什么需要线程同步。但在开始动手写代码之前，我们需要先搞清楚一些基本概念和设计决策。说实话，这些理论部分可能有点枯燥，但如果你不理解它们，后面写代码的时候很容易踩坑。

我记得第一次实现互斥锁的时候，完全不知道什么是"快速路径"和"慢速路径"，结果写出来的代码性能惨不忍睹。还有一次不理解内存屏障的重要性，在多核系统上遇到了各种诡异的 bug。所以相信我，把这些基础搞清楚，后面会省很多时间。

这篇文章会讨论同步设计的核心概念：什么是临界区，什么是互斥，什么是死锁。我们会比较不同的同步原语，看看它们各自的适用场景。我们还会研究几个经典的同步问题，比如生产者-消费者和读者-写者。最后，我们会讨论一些设计决策，比如为什么选择 GCC 内置原子操作而不是手写汇编。

## 基本概念回顾

### 临界区

临界区（Critical Section）是指访问共享资源的代码段，必须互斥执行。换句话说，同一时刻只能有一个线程进入临界区。

想象一下，你要在一个共享的白板上写东西。如果两个人同时写，最后写出来的内容就是一团乱麻。解决办法就是：一个人写的时候，另一个人等着。这个"写"的过程就是临界区。

在代码里，临界区可能只是几条指令：

```c
// 全局计数器
int counter = 0;

// 这个函数的整个函数体都是临界区
void increment(void) {
    counter++;  // 读-改-写，不是原子操作！
}
```

看起来简单的一行 `counter++`，实际在汇编层面是三条指令：把 counter 读到寄存器，寄存器加 1，把结果写回 counter。如果两个线程同时执行这三条指令，结果可能只增加了 1 而不是 2。

保护临界区的方法就是加锁：

```c
mutex_t lock;
mutex_init(&lock);

void increment(void) {
    mutex_lock(&lock);   // 进入临界区前获取锁
    counter++;
    mutex_unlock(&lock); // 离开临界区后释放锁
}
```

### 互斥

互斥（Mutual Exclusion）的意思是：同一时刻只有一个线程能执行某个操作。这是我们用锁要达到的目的。

互斥不仅仅是防止数据损坏，更是保证正确性。比如银行转账，从一个账户扣钱，往另一个账户加钱。如果这两个操作不互斥，可能发生：线程 A 从账户 1 扣了 100 元，还没来得及往账户 2 加钱，线程 B 又从账户 1 扣了 100 元。结果是账户 1 被扣了 200 元，账户 2 只加了 100 元，有 100 元凭空消失了。

### 死锁

死锁（Deadlock）是两个或多个线程互相等待对方持有的资源，所有人都在等，没人能继续执行。

最简单的死锁例子是两个线程和两个锁：

```c
mutex_t lock_a, lock_b;

// 线程 1
void thread1(void) {
    mutex_lock(&lock_a);
    // 如果这里发生调度切换...
    mutex_lock(&lock_b);
    // 临界区
    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);
}

// 线程 2
void thread2(void) {
    mutex_lock(&lock_b);
    mutex_lock(&lock_a);  // 死锁！lock_a 被线程 1 持有
    // 临界区
    mutex_unlock(&lock_a);
    mutex_unlock(&lock_b);
}
```

线程 1 持有 lock_a，等待 lock_b；线程 2 持有 lock_b，等待 lock_a。两个线程互相等待，永远无法继续。

预防死锁的方法有几种：

**固定加锁顺序**。总是按照相同的顺序获取锁。比如规定：先获取 lock_a，再获取 lock_b。这样就不会出现循环等待。

**尝试锁（trylock）**。使用 `mutex_trylock()` 尝试获取锁，如果失败就释放已持有的锁，稍后重试。这样可以避免死锁，但需要小心设计重试逻辑。

**超时锁**。使用带超时的锁，如果等待时间超过某个阈值就放弃。这种方法需要系统支持，我们的基础版本可能不会实现。

## 同步原语分类

### 忙等待 vs 可睡眠

同步原语首先可以分为两大类：忙等待（busy-wait）和可睡眠（sleepable）。

忙等待锁在获取不到锁时会一直循环检测，占用 CPU 直到获取到锁。自旋锁（spinlock）就是典型的忙等待锁。优点是实现简单，响应快（没有调度开销），缺点是浪费 CPU，不适合长临界区。

```c
// 自旋锁的简单实现
void spin_lock(spinlock_t* lock) {
    while (__atomic_test_and_set(&lock->locked, __ATOMIC_ACQUIRE)) {
        // 忙等待，持续占用 CPU
    }
}
```

可睡眠锁在获取不到锁时会让自己阻塞，让出 CPU 给其他线程。互斥锁（mutex）是典型的可睡眠锁。优点是不浪费 CPU，适合长临界区，缺点是有调度开销。

```c
// 互斥锁的简化实现
void mutex_lock(mutex_t* mutex) {
    if (try_acquire_fast(mutex)) {
        return;  // 快速路径：无竞争，直接获取
    }
    // 慢速路径：加入等待队列，阻塞自己
    add_to_wait_queue(mutex);
    block_current_thread();
}
```

那么什么时候用自旋锁，什么时候用互斥锁？经验法则：临界区执行时间短于一次调度开销的，用自旋锁；执行时间长的，用互斥锁。一般来说，临界区只是简单修改几个变量的，用自旋锁；需要分配内存、等待 I/O 的，用互斥锁。

### 互斥 vs 同步

虽然所有的同步原语都是用来"同步"的，但我们可以进一步细分为互斥型和同步型。

互斥型原语用来保护临界区，保证同一时刻只有一个线程能访问共享资源。自旋锁、互斥锁、读写锁都属于这一类。

同步型原语用来协调线程间的执行顺序，传递事件。信号量和条件变量属于这一类。

比如生产者-消费者问题：生产者生产数据后通知消费者，消费者在没有数据时等待。这需要协调，不仅仅是互斥。

```c
// 信号量实现的 bounded buffer
semaphore_t empty;  // 空槽位数
semaphore_t full;   // 满槽位数
mutex_t mutex;      // 保护 buffer

// 生产者
void producer(void) {
    sem_wait(&empty);      // 等待空槽位
    mutex_lock(&mutex);
    buffer.push(item);
    mutex_unlock(&mutex);
    sem_post(&full);       // 增加满槽位
}

// 消费者
void consumer(void) {
    sem_wait(&full);       // 等待满槽位
    mutex_lock(&mutex);
    item = buffer.pop();
    mutex_unlock(&mutex);
    sem_post(&empty);      // 增加空槽位
}
```

## 经典同步问题

### 生产者-消费者

生产者-消费者问题描述的是：一个固定大小的缓冲区，生产者往里面放数据，消费者从里面取数据。缓冲区满时生产者必须等待，缓冲区空时消费者必须等待。

这个问题展示了互斥和同步的结合。我们需要：
1. 互斥访问缓冲区（mutex）
2. 同步等待缓冲区状态（semaphore 或 condition variable）

用信号量实现的版本我们已经看过了。用条件变量实现的版本稍复杂一点，因为条件变量必须和 mutex 配合：

```c
mutex_t mutex;
condvar_t not_empty;  // 缓冲区非空
condvar_t not_full;   // 缓冲区未满

// 生产者
void producer(void) {
    mutex_lock(&mutex);
    while (buffer.is_full()) {
        condvar_wait(&not_full, &mutex);  // 等待缓冲区未满
    }
    buffer.push(item);
    condvar_signal(&not_empty);  // 通知消费者
    mutex_unlock(&mutex);
}

// 消费者
void consumer(void) {
    mutex_lock(&mutex);
    while (buffer.is_empty()) {
        condvar_wait(&not_empty, &mutex);  // 等待缓冲区非空
    }
    item = buffer.pop();
    condvar_signal(&not_full);  // 通知生产者
    mutex_unlock(&mutex);
}
```

注意这里必须用 `while` 检查条件，不能用 `if`。原因我们后面会详细解释。

### 读者-写者

读者-写者问题描述的是：一个共享数据结构，多个读者可以同时读取，但写者必须独占访问。读写锁就是为这个问题设计的。

我们的实现会采用读者优先策略：只要有读者在读，新的读者可以直接进入，写者必须等待所有读者完成。这个策略的好处是读者并发度高，坏处是写者可能饥饿（如果读者源源不断，写者永远等不到）。

```c
rwlock_t rwlock;

// 读者
void reader(void) {
    rwlock_read_lock(&rwlock);
    // 可以多个读者同时在这里
    read_data();
    rwlock_read_unlock(&rwlock);
}

// 写者
void writer(void) {
    rwlock_write_lock(&rwlock);
    // 同一时刻只能有一个写者
    write_data();
    rwlock_write_unlock(&rwlock);
}
```

## 设计决策

### 为什么选择 GCC 内置原子操作

在实现原子操作时，我们有几种选择：

**手写汇编**。直接用 x86_64 的 `lock` 前缀指令实现原子操作。优点是完全控制，缺点是不可移植，而且容易写错。

**编译器内置函数**。使用 GCC 的 `__atomic_*` 或 `__sync_*` 内置函数。优点是可移植，编译器保证正确性，缺点是依赖编译器。

**库函数**。使用 libatomic 或类似的库。优点是标准化，缺点是增加依赖。

我们选择 GCC 内置函数，原因有几个：

首先是正确性。GCC 的内置函数经过充分测试，在各种平台上都能正确工作。手写汇编很容易出 bug，尤其是在内存屏障这种细节上。

其次是可移植性。虽然我们的内核现在只针对 x86_64，但未来可能支持其他架构。GCC 内置函数在不同架构上都能工作，如果需要移植会省很多事。

再者是优化。现代编译器对内置函数有很好的优化，生成的汇编代码往往比手写的还好。

最后是简洁性。内置函数的代码比手写汇编更易读易维护。比如 `__atomic_test_and_set(&lock->locked, __ATOMIC_ACQUIRE)` 一行就完成了原子的 test-and-set 操作，还带了 acquire 语义。

### 为什么需要多种原语

前面我们已经讨论了不同原语的适用场景。这里再强调一次：不存在万能锁，每种原语都是为特定场景优化的。

如果只用一种原语，要么牺牲性能，要么牺牲正确性。比如所有地方都用自旋锁，长临界区会浪费大量 CPU；所有地方都用互斥锁，短临界区的调度开销可能比实际工作还大。

所以我们的设计是提供多种原语，让使用者根据场景选择合适的那一个。这也是 Linux 内核和其他成熟操作系统的做法。

## 在开始之前

在开始实现之前，让我们再确认一下你对这些概念的理解。

你能解释为什么下面这个实现可能出错吗？

```c
// 错误的双重检查锁定示例
static singleton_t* instance = NULL;
singleton_t* get_instance(void) {
    if (instance == NULL) {          // 第一次检查
        mutex_lock(&mutex);
        if (instance == NULL) {      // 第二次检查
            instance = malloc(sizeof(singleton_t));
            init_instance(instance);
        }
        mutex_unlock(&mutex);
    }
    return instance;
}
```

提示：考虑内存可见性和指令重排序。如果线程 A 在 `malloc` 之后、`init_instance` 之前就被调度出去，线程 B 看到的 `instance` 是什么状态？

答案是：线程 B 可能看到一个部分初始化的 `instance`。因为编译器或 CPU 可能重排序指令，`instance` 的赋值可能在 `init_instance` 之前完成。而且在多核系统上，线程 A 的写入可能对线程 B 不可见（缓存一致性问题）。

正确的做法是使用内存屏障，或者用原子操作。我们会在实现原子操作时详细讨论这个问题。
