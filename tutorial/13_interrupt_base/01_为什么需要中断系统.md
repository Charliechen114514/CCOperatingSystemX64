# 为什么需要中断系统 —— Stage 13 中断基础实战指南

## 前言

写到 Stage 13 的时候，我意识到一个被我们忽略很久的问题：内核虽然跑起来了，有了日志系统，有了栈回溯，但它本质上还是个"瞎子"和"聋子"。它不知道什么时候有按键按下，不知道定时器在走，甚至不知道自己犯了什么错 —— 只能傻傻地轮询，等着某个事件"刚好"在它检查的时候发生。

说实话，这种轮询模式我太熟了。你写个死循环，每隔一段时间就去检查键盘有没有数据，串口有没有消息。这种方式不仅效率低下，而且响应延迟不可控。更糟糕的是，当 CPU 真的遇到异常（比如除零错误、缺页异常）时，内核完全没有机制来捕获和处理这些情况，只能眼睁睁看着系统崩溃。

所以这一篇我们会一起实现一个完整的中断子系统。别担心，我们不会跳过任何步骤，每写一个函数都会解释清楚它是怎么工作的，为什么要这么写，有哪些坑需要避开。准备好了吗？我们开始。

## 环境说明

在开始之前，先确认一下你的开发环境。这篇文章假设你已经完成了 Stage 12，栈回溯系统已经实现完毕。

```
操作系统: Ubuntu 22.04 LTS / WSL2 / Arch WSL
编译器:   GCC x86_64-elf-gcc 或类似交叉编译器
构建工具: CMake 3.25 或更高版本
模拟器:   QEMU 7.0 或更高版本
汇编器:   NASM 2.15 或更高版本
```

可能有人会问，为什么需要 NASM？这是因为中断的底层入口必须用汇编编写，需要手动保存和恢复 CPU 状态。当然你也可以用 GCC 的内联汇编，但那种写法可读性很差，调试起来更是让人血压拉满。

## 调试痛点：没有中断时的困境

让我们先想象一下，当你的内核需要响应硬件事件时，会发生什么。假设你想从键盘读取输入：

```c
// 轮询模式的键盘读取
char read_keyboard(void) {
    while (1) {
        if (keyboard_has_data()) {
            return keyboard_read_data();
        }
        // CPU 在这里空转，什么都没做
    }
}
```

你只看到了一个简单的循环，但问题在哪里呢？

第一，**CPU 时间被完全浪费**。在等待键盘输入的时候，CPU 本可以做其他有用的事情，但现在只能傻傻地循环检查。

第二，**响应延迟不可控**。如果键盘刚好在你检查完之后按下，你需要等到下一次循环才能检测到。这个延迟取决于你的轮询频率，太频繁浪费 CPU，太稀疏响应又慢。

第三，**无法处理突发事件**。如果 CPU 在执行某个计算密集型任务，键盘输入可能要等很久才能被处理。

更糟糕的情况是，如果你的内核触发了异常：

```c
void some_function(int x) {
    int y = 10 / x;  // 如果 x = 0 会怎样？
    // ...
}
```

没有中断系统，除零错误会导致 CPU 直接触发 Triple Fault，然后系统重启。你连错误信息都看不到，只能对着黑屏发呆。

## 技术方案对比：中断 vs 轮询

在内核开发中，有两种主要的硬件事件处理方式：

### 方案一：轮询模式

```c
// 轮询模式
void handle_events(void) {
    while (1) {
        if (timer_event()) {
            handle_timer();
        }
        if (keyboard_event()) {
            handle_keyboard();
        }
        if (serial_event()) {
            handle_serial();
        }
        // ... 更多设备
    }
}
```

**优点**：实现简单，逻辑直观。

**缺点**：CPU 利用率低，响应延迟高，无法处理 CPU 异常。

### 方案二：中断驱动模式

```c
// 中断模式
void kernel_main(void) {
    // 注册中断处理程序
    register_timer_handler(timer_handler);
    register_keyboard_handler(keyboard_handler);
    register_serial_handler(serial_handler);

    // 启用中断
    enable_interrupts();

    // 主循环可以做其他事情，或者直接 HLT 等待中断
    while (1) {
        // CPU 可以执行其他任务
        do_useful_work();
        // 或者空闲时暂停 CPU
        __asm__ volatile("hlt");
    }
}
```

**优点**：CPU 利用率高，响应及时，可以处理 CPU 异常。

**缺点**：实现复杂，需要硬件支持。

对于我们的内核来说，答案很明显：必须使用中断模式。

## 中断与异常的区别

在 x86 架构中，"中断"这个词实际上包含了两种不同的概念：

### 中断（Interrupt）

由**外部硬件**触发，是**异步**发生的。典型的例子包括：

- **定时器中断**：定时器周期性地通知 CPU
- **键盘中断**：用户按下键盘时触发
- **串口中断**：串口收到数据时触发

中断是"外部"事件，CPU 无法预测它们何时发生。

### 异常（Exception）

由**CPU 执行指令**触发，是**同步**发生的。典型的例子包括：

- **除零错误**（#DE）：执行除法指令时除数为零
- **缺页异常**（#PF）：访问的页面不在内存中
- **通用保护错误**（#GP）：执行了非法操作

异常是"内部"事件，通常表示程序出现了错误或特殊情况。

### 我们要做的

在本阶段，我们需要同时处理这两类事件：

1. **捕获 CPU 异常**：当异常发生时，显示错误信息并尝试恢复（或优雅地停止）
2. **响应硬件中断**：处理定时器、键盘等设备的中断请求

## 8259 PIC 简介

x86 架构使用可编程中断控制器（PIC）来管理硬件中断。最经典的是 8259A 芯片。

### 为什么需要 PIC？

CPU 只有一个中断引脚（INTR），但系统中有许多设备可能产生中断。PIC 的作用就是：

1. **汇集多个中断源**：接收来自多个设备的中断请求
2. **优先级仲裁**：决定哪个中断应该先被处理
3. **向 CPU 发送中断**：通过 INTR 引脚通知 CPU
4. **提供中断向量**：告诉 CPU 是哪个设备产生的中断

### 双片级联结构

现代 x86 系统使用两片 8259A 级联：

```
          CPU
           │
           │ INTR
           ▼
    ┌──────────────┐
    │   Master     │
    │   PIC        │
    │   (IRQ 0-7)  │
    └──────┬───────┘
           │ IRQ 2
           ▼
    ┌──────────────┐
    │   Slave      │
    │   PIC        │
    │   (IRQ 8-15) │
    └──────────────┘
```

- **Master PIC** 处理 IRQ 0-7
- **Slave PIC** 处理 IRQ 8-15
- Slave 通过 Master 的 IRQ 2 级联

### IRQ 默认分配

| IRQ | 设备 | 优先级 |
|-----|------|--------|
| 0 | 定时器 | 最高 |
| 1 | 键盘 | |
| 2 | 级联（Slave PIC） | |
| 3 | COM2 | |
| 4 | COM1 | |
| 5 | LPT2 | |
| 6 | 软盘 | |
| 7 | LPT1 | |
| 8 | RTC | |
| 9 | 保留/SCSI | |
| 10 | 保留/SCSI | |
| 11 | 保留/SCSI | |
| 12 | PS/2 鼠标 | |
| 13 | FPU | |
| 14 | 主 ATA | |
| 15 | 从 ATA | 最低 |

## IRQ 重映射的必要性

8259 PIC 在默认配置下有一个严重的问题：

```
默认映射：
  IRQ 0-7  →  向量 0x08-0x0F
  IRQ 8-15 →  向量 0x70-0x77
```

但 x86 CPU 规定：

```
  向量 0-31  保留给 CPU 异常
  向量 32-255 可用于用户中断
```

**冲突！** IRQ 0 默认映射到向量 0x08，但向量 0-31 是 CPU 异常专用的。如果我们不重映射，定时器中断会被误认为是 Double Fault 异常，系统完全无法工作。

### 解决方案：重映射

我们需要重新配置 PIC，将 IRQ 映射到向量 32-47：

```
重映射后：
  IRQ 0-7  →  向量 32-39  (0x20-0x27)
  IRQ 8-15 →  向量 40-47  (0x28-0x2F)
```

这样就不会与 CPU 异常冲突了。

## 中断描述符表（IDT）

现在我们知道中断有向量号了，但 CPU 怎么知道每个向量对应什么处理函数呢？答案就是 IDT（Interrupt Descriptor Table）。

IDT 是一个数组，每个条目（称为"门描述符"）包含：

1. **处理函数地址**：中断发生时跳转到哪里
2. **段选择子**：使用哪个代码段
3. **类型属性**：是中断门、陷阱门还是任务门
4. **特权级**：什么权限级别可以调用

x86_64 模式下，每个 IDT 条目是 16 字节，整个表最多 256 个条目。

```
IDT 结构：
┌────────────────────────────────────┐
│  Entry 0  │  Divide Error Handler  │
├────────────────────────────────────┤
│  Entry 1  │  Debug Handler         │
├────────────────────────────────────┤
│  ...      │  ...                   │
├────────────────────────────────────┤
│  Entry 32 │  IRQ0 (Timer) Handler  │
├────────────────────────────────────┤
│  ...      │  ...                   │
└────────────────────────────────────┘
```

CPU 在中断发生时会自动：
1. 读取对应的 IDT 条目
2. 跳转到处理函数
3. 自动推送栈帧（SS, RSP, RFLAGS, CS, RIP, Error Code）

## 我们要实现的目标

现在我们对背景知识有了足够的了解，可以明确一下我们这个阶段要做什么：

1. **8259 PIC 驱动**
   - PIC 初始化和重映射
   - EOI（中断结束）发送
   - IRQ 屏蔽/启用控制

2. **IDT 管理**
   - IDT 初始化和加载
   - 为 CPU 异常设置处理程序
   - 为硬件 IRQ 设置处理程序

3. **中断/异常 Stub**
   - 汇编入口函数
   - CPU 状态保存/恢复
   - 调用 C 语言处理函数

4. **C 语言中断分发器**
   - 异常信息显示
   - IRQ 路由到对应处理程序
   - 定时器滴答计数

5. **中断子系统初始化**
   - 按正确顺序初始化各组件
   - 与现有内核集成

实现之后，我们的内核将能够：
- 捕获并显示 CPU 异常信息
- 响应定时器中断
- 为后续的键盘、串口等设备驱动打下基础
