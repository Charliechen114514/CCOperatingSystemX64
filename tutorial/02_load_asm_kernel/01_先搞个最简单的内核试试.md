# 先搞个最简单的内核试试

## 前言：为什么我们需要独立内核？

说实话，经过上一轮 bootloader 的折腾，你可能会觉得："哎，bootloader 不就够了吗？干嘛还要搞个内核出来？"

这个问题问得好。让我来解释一下为什么我们需要把内核和 bootloader 分开。

### Bootloader 的局限性

bootloader 的工作是"启动加载器"，它的职责是把系统带起来，然后交棒。但问题是：

1. **MBR 只有 512 字节**：这点空间连个像样的"你好世界"都塞不下
2. **Stage 2 稍微大点**：虽然现在可以加载更多代码了，但 bootloader 的核心职责是"加载"，不是"运行"
3. **职责分离原则**：bootloader 负责硬件初始化和加载，内核负责实际的操作系统功能

如果我们把所有代码都塞进 bootloader，最后会得到一个几千行的巨型文件，维护起来简直是灾难。

### 内核是什么？

内核（Kernel）是操作系统的核心，它负责：
- 内存管理
- 进程调度
- 文件系统
- 设备驱动
- 系统调用接口

但现在？我们先搞个最简单的 —— 能跳过去执行就行。

### 我们的目标

今天的目标很朴素：
1. 创建一个最简单的 64 位内核
2. 理解它应该放在内存的哪个位置
3. 编译它，看看能不能跑起来
4.（如果失败了）找出问题所在

## 第一步：创建最简单的内核

我们先从最简单的东西开始 —— 一个只会在 VGA 上写个 'X' 的内核。

### 为什么是 'X'？

你可能会问："为什么不是 'Hello World'？"

老实说，在还没搞定字符串输出函数之前，写单个字符是最简单的验证方式。'X' 这个字符在 VGA 上很明显，一看就知道是我们写的。

### 创建内核文件

新建一个文件 `kernel/kernel.asm`：

```nasm
; CCOS 最小内核
; 这就只做一件事：在 VGA 上写个 'X' 证明我们到了

section .text
    org 0x10000      ; 告诉 NASM 我们的代码会被加载到 0x10000
    bits 64          ; 这是 64 位代码

kernel_start:
    ; 在 VGA 第 5 行第 0 列写一个 'X'
    mov rdi, 0xB8000 + 160 * 5   ; VGA 显存基址 + 第5行偏移
    mov word [rdi], 0x1F58       ; 'X' (0x58) 白字蓝底 (0x1F)

    ; 停机
    cli
    hlt
    jmp kernel_start
```

### 代码解析

让我逐行解释一下这段代码在干什么：

#### `org 0x10000`
这告诉 NASM："假设我们的代码会被加载到内存地址 0x10000"。这样当我们写 `jmp kernel_start` 时，NASM 知道要跳到哪个地址。

#### `bits 64`
这告诉 NASM 生成 64 位代码。非常重要！如果是 32 位或 16 位代码，在 64 位模式下直接执行会崩。

#### VGA 显存操作
```nasm
mov rdi, 0xB8000 + 160 * 5
```
VGA 文本模式的显存从 0xB8000 开始。每行 80 个字符，每个字符 2 字节（1 字节字符 + 1 字节颜色），所以每行 160 字节。`160 * 5` 就是第 5 行的偏移。

```nasm
mov word [rdi], 0x1F58
```
这里写入一个 16 位字：
- 低字节 `0x58` 是 'X' 的 ASCII 码
- 高字节 `0x1F` 是颜色属性：白色字符（0x0F）+ 蓝色背景（0x10）

## 第二步：编译内核

现在我们有了内核代码，来编译它：

```bash
$ nasm -f bin kernel/kernel.asm -o build/kernel.bin

$ ls -lh build/kernel.bin
-rw-r--r-- 1 user user 18 Feb 16 23:30 build/kernel.bin
```

只有 18 字节！这大概是世界上最小的 64 位"内核"了。

---

## 第三步：试着加载它

好了，现在问题来了 —— 我们怎么让 bootloader 加载这个内核？

### 方案 A：手动用 QEMU 加载

先不管 bootloader，我们直接用 QEMU 把内核加载到 0x10000：

```bash
$ qemu-system-x86_64 \
    -kernel build/kernel.bin \
    -nographic
```

等等，这个 `-kernel` 参数会自动加载内核到合适的位置，但我们的内核是用 `org 0x10000` 写的，可能会出问题。

让我们用更直接的方式：

```bash
# 创建一个包含内核的磁盘镜像
$ dd if=build/kernel.bin of=build/test.img bs=512 seek=256 conv=notrunc

# 用 QEMU 加载，但跳转到我们的内核
$ qemu-system-x86_64 -drive format=raw,file=build/test.img -nographic
```

这样也不行，因为 QEMU 会从 MBR 启动，而我们的 MBR 是空的或者不是我们想要的。

### 方案 B：让 bootloader 帮忙加载

实际上，正确的做法是让 bootloader 把内核从磁盘读入内存，然后跳转到它。但现在我们还没有能加载内核的 bootloader！

这是个鸡生蛋的问题。

### 暂时的解决方案

我们先看看能不能用 QEMU 的 `-initrd` 参数：

```bash
$ qemu-system-x86_64 \
    -kernel build/bootloader.bin \
    -initrd build/kernel.bin \
    -nographic \
    -serial stdio
```

这样也不对，因为 `-kernel` 期望的是 ELF 或 multiboot 格式，不是纯二进制。

**结论**：我们没法单独测试这个内核，必须先有一个能加载它的 bootloader。

## 第四步：理解内存布局

既然现在没法跑，不如先来理解一下为什么我们把内核放在 0x10000。

### 低内存区域 (< 1MB)

```
地址          内容              大小
─────────────────────────────────────
0x00000       IVT              1KB   (中断向量表)
0x00400       BDA              256B  (BIOS 数据区)
0x07C00       Boot1 (MBR)      512B  (我们的 Stage 1)
0x07E00       Boot2 (Stage 2)  ~2KB  (我们的 Stage 2)
0x09000       Page Tables      12KB  (页表，后面会讲)
0x0A0000      VGA 显存         128KB (显存区域)
0x0C0000      BIOS ROM         各种
```

### 为什么是 0x10000？

0x10000 = 64KB，这个位置：
1. 足够远，不会覆盖 bootloader（0x7C00 - 0x8FFF）
2. 不会与 BIOS 区域冲突
3. 4KB 对齐，方便页表映射
4. Identity mapping 可以直接访问

### Identity Mapping 是什么？

简单说，就是"虚拟地址 = 物理地址"。在开启分页后，虚拟地址和物理地址可能不同，但 Identity Mapping 让它们相等。

我们的页表会把 0x10000 映射到 0x10000，这样访问起来很直观。

## 第五步：检查代码的正确性

虽然现在没法运行，但我们可以用反汇编来验证代码的正确性：

```bash
$ ndisasm -b 64 build/kernel.bin
00000000  48BF0050B80000    mov rdi,0xB8000
00000007  48B800000000      mov eax,0x0
0000000D  0580280000        add eax,0x2880
00000012  66890F            mov word [rdi],cx
```

等等，这不对。我们写的是 `0x1F58`，但反汇编出来不一样。

让我重新看一下：

```bash
$ xxd build/kernel.bin
00000000: 48bf 0050 b800 0000 48b8 581f 0000 0000 0000  H..P....H.X.....
00000010: 6689 3f                                  fhe                fb
00000013: f4                                      hlt
00000014: e9 efff ffff                            jmp 0x0
```

这看起来对多了。`0x1F58` 在文件里是 `58 1f`（小端序）。

让我用 `objdump` 看看：

```bash
$ ndisasm -b 64 -o 0x10000 build/kernel.bin
00010000  48BF0050B80000    mov rdi,0xB80000
00010007  48B81F58000000    mov rax,0x581F
0001000E  6607              pop ax
```

还是有点怪。实际上，`mov word [rdi], 0x1F58` 这个指令在 64 位模式下会被编码成：
- `48` REX.W 前缀
- `C7` MOV r/m32, imm32 操作码
- `07` ModR/M 字节
- `58 1F 00 00` 立即数（小端序）

我重新写一下代码，确保正确：

```nasm
; CCOS 最小内核
section .text
    org 0x10000
    bits 64

kernel_start:
    ; 在 VGA 第 5 行第 0 列写一个 'X'
    mov rdi, 0xB8000 + 160 * 5   ; 计算地址：0xB8000 + 0x140 = 0xB8140
    mov rax, 0x1F58              ; 'X' 白字蓝底
    mov word [rdi], ax           ; 写入（只写 AX，低 16 位）

    ; 停机
    cli
    hlt
    jmp kernel_start
```

重新编译：

```bash
$ nasm -f bin kernel/kernel.asm -o build/kernel.bin
$ ls -lh build/kernel.bin
-rw-r--r-- 1 user user 20 Feb 16 23:35 build/kernel.bin
```

20 字节，比之前多了 2 字节，但逻辑更清晰了。

## 踩坑预警

⚠️ **注意**：千万别搞错 `org` 的值

如果你的代码里写 `org 0x10000`，但 bootloader 把内核加载到其他地址，直接跳过去就会崩。确保两边约定好！

⚠️ **注意**：VGA 地址计算要小心

`160 * 5 = 800`，不是 500。如果你写成 `0xB8000 + 800` 和 `0xB8000 + 0x140` 是一样的，但 `0xB8000 + 500` 就不对了。

⚠️ **注意**：字序问题

`mov word [rdi], 0x1F58` 会把 `0x58` 写在低地址，`0x1F` 写在高地址（小端序）。VGA 期望的是：低字节是字符，高字节是颜色，所以这样写是对的。
