# 终于可以跳到内核了

## 前言：见证奇迹的时刻

如果你跟着前三篇做下来，现在应该是这样的状态：有一个 20 字节的内核，bootloader 能把它加载到 0x10000，bootloader 已经切换到 64 位长模式。但问题是——内核还没执行！

今天，我们终于要完成这最后一步：跳转到内核并看到那个期待已久的 'X'。说实话，这一步看似简单，但里面有不少细节需要注意。让我们来搞定它。

---

## 跳转方式的选择：jmp 还是 call

在 64 位模式下，我们有几种跳转方式。`jmp` 是无条件跳转，一旦跳过去就不管了，不会返回。`call` 是函数调用，会把返回地址压栈，所以可以返回。对于内核跳转，我们应该用 `call` 而不是 `jmp`，原因是这样的。

首先，内核可能返回——虽然大概率不会，但万一你想做个"优雅关机"之类的功能呢？其次，`call` 符合函数调用约定，看起来更"正规"。最后也是最重要的一点：如果内核崩溃，我们至少知道返回到哪里，可以在 boot2 里加一些错误处理代码。

在 64 位模式下，间接调用是这样的：

```nasm
mov rdi, 0x10000     ; 把地址存入 RDI
call rdi             ; 调用 RDI 指向的函数
```

为什么要用 RDI？这涉及到 System V AMD64 ABI 调用约定，我们来简单说一下。

---

## System V AMD64 ABI：参数怎么传

System V AMD64 ABI 是 Unix-like 系统（Linux、*BSD）上的 64 位调用约定。这个约定定义了参数怎么传、返回值放哪、栈怎么对齐等一系列问题。

前 6 个整数/指针参数依次放在 RDI、RSI、RDX、RCX、R8、R9 这几个寄存器里。如果有更多参数，就放到栈上。返回值放在 RAX 里。栈必须保持 16 字节对齐——这个很重要，如果不对齐，调用某些函数会崩溃。

我们的跳转是这样的：

```nasm
mov rdi, 0x10000     ; 内核地址（也是第 1 个参数）
call rdi             ; 调用内核
```

虽然我们的内核不使用参数，但把地址放在 RDI 是符合规范的。如果你想给内核传参数（比如内存地图、命令行参数之类的东西），RDI 就是第一个参数的位置。

---

## 在 boot2.asm 中添加跳转代码

现在我们实际来写代码。在 `long_mode:` 标签的打印消息之后，我们需要添加跳转逻辑。首先让我们回顾一下当前的 long_mode 代码：

```nasm
long_mode:
    mov ax, 0x20
    mov ds, ax
    mov es, ax
    mov fs, ax
    mov gs, ax
    mov ss, ax
    mov rsp, 0x7E00
```

这部分代码设置了数据段寄存器和栈指针，是进入 64 位模式后的标准初始化。接下来是打印消息的代码，它证明了我们确实进入了长模式：

```nasm
    ; 打印消息（VGA）
    mov rdi, 0xB8000 + 160 * 2
    mov rsi, msg_long_mode
    mov ah, 0x0F
.print_loop:
    lodsb
    test al, al
    jz .print_done
    stosw
    jmp .print_loop
.print_done:
```

现在我们在这之后添加跳转到内核的代码：

```nasm
    ; ===== 跳转到内核 =====
    mov rdi, 0x10000     ; 内核地址
    call rdi             ; 调用内核
```

这里我们把 0x10000 放入 RDI，然后调用它。0x10000 是我们 bootloader 把内核加载到的地址。这个地址不是随便选的——它必须在低内存区域（因为此时高地址映射还没完全建立），而且不能和 bootloader 使用的内存冲突。

如果内核返回了（虽然我们预期它不会），我们应该打印一个警告消息：

```nasm
    ; 如果内核返回，打印错误
    mov rdi, 0xB8000 + 160 * 3
    mov rsi, msg_kernel_returned
    mov ah, 0x0F
.err_loop:
    lodsb
    test al, al
    jz .err_done
    stosw
    jmp .err_loop
.err_done:

.hang:
    hlt
    jmp .hang
```

这会在 VGA 第 3 行打印警告消息，然后进入停机循环。`hlt` 指令让 CPU 停下来，直到中断发生。但我们已经关了中断，所以 CPU 会永远停在这里。

我们还需要在数据区添加消息字符串：

```nasm
msg_long_mode:
    db "[OK] Entered Long Mode!", 0x0D, 0x0A, 0

msg_kernel_returned:
    db "[WARN] Kernel returned!", 0x0D, 0x0A, 0
```

`0x0D` 是回车符，`0x0A` 是换行符，`0` 是字符串结束符。

---

## 确认内核代码

我们的内核应该长这样，来自第一篇教程：

```nasm
; CCOS 最小内核
section .text
    org 0x10000
    bits 64

kernel_start:
    ; 在 VGA 第 5 行第 0 列写一个 'X'
    mov rdi, 0xB8000 + 160 * 5
    mov rax, 0x1F58
    mov word [rdi], ax

    ; 停机
    cli
    hlt
    jmp kernel_start
```

让我们来检查一下关键点。`org 0x10000` 告诉 NASM 这个代码会被加载到 0x10000，这对于地址计算很重要。如果 bootloader 把内核加载到 0x10000，但内核代码里写 `org 0x20000`，跳转后会立即崩溃，因为所有地址都错了。

`bits 64` 告诉 NASM 这是 64 位代码。如果忘记写这个，NASM 会生成 32 位指令，在 64 位模式下执行会产生非法指令异常。

VGA 位置选择也很重要。我们用第 5 行（160 * 5），和 bootloader 的输出不冲突。bootloader 在第 0、2、3 行输出，内核在第 5 行输出，互相不打扰。

`0x1F58` 是要写入的字符数据。低 8 位是 0x58（'X' 的 ASCII 码），高 8 位是 0x1F（颜色属性）。0x1F 表示白字蓝底——在蓝色背景上显示白色字符，非常醒目。

## 完整编译和测试

现在让我们来编译和测试。首先编译所有文件：

```bash
$ nasm -f bin boot/boot.asm -o build/boot.bin
$ nasm -f bin boot/boot2.asm -o build/boot2.bin
$ nasm -f bin kernel/kernel.asm -o build/kernel.bin
```

然后检查一下文件大小，确保没有超出限制：

```bash
$ ls -lh build/*.bin
-rw-r--r-- 1 user user  512 Feb 17 00:05 build/boot.bin
-rw-r--r-- 1 user user  743 Feb 17 00:05 build/boot2.bin
-rw-r--r-- 1 user user   20 Feb 17 00:05 build/kernel.bin
```

很好，boot.bin 正好 512 字节（一个扇区），boot2.bin 是 743 字节（不超过两个扇区），kernel.bin 是 20 字节（很小）。接下来我们把它们合并到一个磁盘镜像：

```bash
$ dd if=build/boot.bin of=build/boot.img bs=512 count=1
$ dd if=build/boot2.bin of=build/boot.img bs=512 seek=1 conv=notrunc
$ dd if=build/kernel.bin of=build/boot.img bs=512 seek=3 conv=notrunc
```

第一个 dd 命令把 boot.bin 写入 boot.img 的第一个扇区（扇区 0）。第二个 dd 命令把 boot2.bin 写入从扇区 1 开始的位置，`conv=notrunc` 确保不会截断输出文件。第三个 dd 命令把 kernel.bin 写入从扇区 3 开始的位置。

现在运行 QEMU：

```bash
$ qemu-system-x86_64 -drive format=raw,file=build/boot.img -nographic
```

你应该能看到以下输出：

```
[1] Stage 1: Loading Stage 2...
[2] Stage 2: Running...
[LOAD] Loading kernel...
[OK] Entered Long Mode!
```

然后屏幕应该会在第 5 行显示一个白字蓝底的 `X`。如果看到这个，恭喜！你的内核成功运行了！

如果想看 VGA 输出，可以用 QEMU 图形模式：

```bash
$ qemu-system-x86_64 -drive format=raw,file=build/boot.img
```

你应该能看到一个 VGA 文本模式的窗口，里面有 bootloader 的输出消息和一个蓝色的 'X'。

---

## 验证内存：确认内核真的执行了

如果你想确认内核确实被执行了，可以用 QEMU monitor。首先用带 monitor 的方式启动 QEMU：

```bash
$ qemu-system-x86_64 -drive format=raw,file=build/boot.img -nographic -monitor stdio
```

启动后，你可以看到 QEMU 的输出。然后在 QEMU monitor 中输入命令来检查内存：

```
(qemu) xp /20hx 0xB8000
```

这个命令会显示从 0xB8000 开始的 20 个十六进制字。你应该能看到 bootloader 输出的字符数据。然后在 0xB8140（第 5 行的起始地址）应该能看到 0x1F58（'X'）：

```
(qemu) xp /hx 0xB8140
00000000000b8140: 0x1f58
```

如果你看到 0x1F58，说明内核确实执行了，并且成功写入了 'X' 到 VGA 显存。

---

## 调试技巧：出问题了怎么办

如果看不到 'X'，哪里出了问题？我们来介绍几种调试方法。

首先是 VGA 调试法。在关键点写入不同的字符：

```nasm
; 在 long_mode 开始时
mov qword [0xB8000], 'A'    ; 证明到了 long_mode

; 在跳转前
mov qword [0xB8000 + 8], 'B' ; 证明准备跳转

; 跳转
mov rdi, 0x10000
call rdi
```

如果启动后看到 'A' 但没看到 'B'，说明跳转前崩溃了。如果两个都看到了，但没有看到内核的输出，说明内核执行出问题了。这种方法虽然原始，但在没有调试器的情况下非常有效。

另一种方法是 GDB 调试。用 GDB 连接 QEMU：

```bash
# 终端 1
$ qemu-system-x86_64 -drive format=raw,file=build/boot.img -s -S

# 终端 2
$ gdb
(gdb) target remote :1234
(gdb) break *0x7E00     ; Stage 2 入口
(gdb) break *0x10000    ; 内核入口
(gdb) continue
```

`-s` 参数让 QEMU 启动 GDB server（监听 1234 端口），`-S` 参数让 CPU 在启动时暂停。这样你可以在启动前设置断点。GDB 的 `break` 命令设置断点，`continue` 命令继续执行。当 CPU 到达断点时，GDB 会暂停执行，你可以检查寄存器、内存、单步执行等。

## 完整启动流程回顾

让我们回顾一下整个启动流程，看看我们走了多远。

1. BIOS 加载 MBR 到 0x7C00。这是 x86 启动的标准流程，BIOS 从磁盘的第一个扇区读取 512 字节到内存地址 0x7C00，然后跳转过去执行。我们的 Stage 1 就在这里。

2. Stage 1（0x7C00）加载 Stage 2 到 0x7E00。Stage 1 的工作很简单：读取磁盘的下一个扇区到 0x7E00，然后跳转过去。这样我们就有了更多的空间来写复杂的代码。

3. Stage 2（0x7E00，16-bit）开始执行。首先打印消息，然后加载内核到 0x10000，接着设置页表、加载 GDT。这些步骤都是为了切换到长模式做准备。

4. 切换到保护模式（32-bit）。设置 CR0 的 PE 位进入保护模式，然后远跳转到 32 位代码。在保护模式下，我们设置段寄存器、启用 PAE、加载 PML4、启用长模式、启用分页。

5. 切换到长模式（64-bit）。当 CR0.PG、CR4.PAE、EFER.LME 都为 1 时，CPU 自动进入长模式。我们在长模式下打印消息，然后跳转到内核（0x10000）。

6. 内核（0x10000）开始执行。内核写 'X' 到 VGA，然后停机。

说实话，这个流程真的很长。从 BIOS 把控制权交给我们，到内核开始执行，中间经过了这么多步骤。但每一步都有它的目的，缺一不可。

---

## 一些容易踩的坑

说几个我踩过的坑，希望能帮你避免同样的错误。

内核地址必须和 bootloader 一致。如果 bootloader 把内核加载到 0x10000，但内核代码里写 `org 0x20000`，跳转后会崩溃。这个问题很隐蔽，因为编译不会报错，运行时才会出问题。

VGA 位置冲突也很常见。如果 bootloader 和内核都用 VGA 第 0 行，后面的输出会覆盖前面的。我们选择第 5 行来避免冲突，但如果你调试时加了更多输出，要注意规划好 VGA 空间。

内核必须在 64 位模式下跳转。如果你在保护模式（32 位）下跳转到 64 位内核，会立即崩溃。必须先进入长模式，然后再跳转。这一点我第一次做的时候就搞错了，导致 triple fault，花了好久才找到原因。

内核大小限制也要注意。我们的 bootloader 只读取 1 个扇区（512 字节）。如果你的内核超过 512 字节，会被截断。这个问题会在后面的教程中解决，但现在要记住这个限制。
