# 常见问题与总结

到这里我们已经完成了 CMake 迁移和 C 内核的实现。说实话，这一路走来确实不容易，但你已经掌握了很多东西。最后一篇，我们总结常见问题和完整经验，帮你扫清最后的障碍。

---

## 写在前面的话

我刚开始折腾内核开发的时候，遇到问题基本靠猜。编译报错了？随便改改试试。链接失败了？把所有文件都加进去试试。结果呢？浪费了大量时间在重复劳动上，而且问题往往越改越多。

后来我发现一个道理：**内核开发最怕的不是问题复杂，而是不知道从何下手**。每个错误背后都有明确的原因，只要你掌握了正确的排查思路，问题其实不难解决。

所以这一篇我不会给你一个简单的错误列表，而是带你理解这些错误背后的机制，让你下次遇到类似问题时能自己分析解决。授人以鱼不如授人以渔，对吧？

## 链接阶段的那些事儿

链接错误往往是最让人头疼的，因为它们的报错信息有时很模糊，但问题根源却很隐蔽。让我们来拆解一下常见的链接问题。

### undefined reference — 找不到符号

这个错误你肯定见过，而且会反复见到。它的形式通常是 `undefined reference to 'xxx'`，意思是链接器找不到某个符号的定义。

最常见的是 `undefined reference to 'kernel_main'`。这个问题你可能会觉得奇怪：明明我写了 `kernel_main.c`，为什么说找不到？原因通常有两个：要么是 C 代码根本没编译，要么是编译了但没链接进最终的 ELF 文件。

你可以用 `nm build/kernel.elf | grep kernel_main` 来检查。如果输出是空的，说明这个符号确实不在 ELF 文件里。那接下来就要看：`build/kernel_main.o` 存在吗？如果存在，那问题就在链接命令上，CMakeLists.txt 里可能忘记把 `kernel_main.o` 加到链接目标里了。

另一个常见的是 `undefined reference to '__bss_start'` 或 `__bss_end`。这个问题很特殊，因为这些符号不是在代码里定义的，而是在链接脚本里定义的。如果链接器找不到它们，说明链接脚本的导出有问题。检查一下 `linker.ld` 里是否有 `__bss_start = .;` 这样的语句，而且必须在 `.bss` 段的开头。

还有一个容易漏的是 `undefined reference to 'memcpy'`。当你用了 `memcpy` 但没实现它，GCC 会尝试链接标准库的版本，但我们在 freestanding 环境下没有标准库。解决方案有两个：要么自己实现 `memcpy`，要么加 `-fno-builtin` 禁用内置函数，这样 GCC 就不会自动插入对 `memcpy` 的调用了。

### relocation truncated to fit — 地址太大了

这个错误很隐蔽，报错信息也不太直观。`relocation truncated to fit` 的意思是重定位信息被截断了，无法容纳目标地址。

这个问题通常出现在 x86_64 上，因为默认的代码模型（small code model）假设代码和数据都在 2GB 范围内。如果你的内核加载地址是 0x10000，看起来没问题，但如果有某个绝对地址引用超出了这个范围，就会触发这个错误。

解决方案是加 `-mcmodel=large`，告诉 GCC 使用 large 代码模型，这样所有符号都用 64 位绝对地址寻址。代价是生成的代码会稍微大一点，但对我们来说这不是问题。

## 编译阶段的坑

编译错误通常比较直接，但有些问题你可能会反复踩到。我们来说说这些坑。

### 头文件找不到

`error: stdio.h: No such file or directory` 这个报错你肯定会看到。原因很简单：我们在 freestanding 环境下，没有标准库头文件。`stdio.h`、`stdlib.h` 这些都不存在。

解决方案也很直接：移除所有对标准头文件的引用。如果你需要类型定义，用我们自己的 `kernel/defines/types.h`。如果你需要字符串函数，自己实现或者用我们后面会讲的小型库。

另一个相关的问题是 `warning: implicit declaration of function`。这个警告加上 `-Werror` 会变成错误。它的意思是你调用了某个函数但没有声明它。在 freestanding 环境下，你要么自己声明函数，要么自己实现它。不能依赖系统头文件帮你声明。

### 类型冲突

`error: conflicting types for 'size_t'` 这个错误有点奇怪。你可能会想：我只定义了一次 `size_t`，为什么说冲突？

原因通常是同时包含了多个头文件，而它们都定义了 `size_t`。比如你既用了 `kernel/defines/types.h`，又包含了 `<stddef.h>`（如果有的话），那 `size_t` 就会被定义两次。

还有一个隐蔽的问题是 `volatile` 的位置。C 语言里 `volatile int *p` 和 `int volatile *p` 是等价的，但有些老编译器可能对格式敏感。如果你的代码报 `error: expected expression before 'volatile'`，检查一下 `volatile` 的位置是否正确。

## 运行时的噩梦：Triple Fault

运行时错误是最难调试的，因为你没有操作系统帮你捕获异常、打印堆栈。一切都靠你自己。最常见也最致命的就是 Triple Fault。

### 什么是 Triple Fault

Triple Fault 是 x86 处理器的一种特殊错误状态。当处理器连续遇到三个异常（通常是 Double Fault 加上另一个异常）时，它会触发 Triple Fault，然后系统会彻底崩溃。在 QEMU 里，这表现为 QEMU 窗口直接关闭，没有任何输出。

为什么会这样？通常是因为栈指针错误或栈溢出。当代码尝试访问无效的栈地址，或者栈指针没有正确对齐，处理器会触发 General Protection Fault（#GP）。如果在处理 #GP 的过程中又出错（比如中断描述符表有问题），就会触发 Double Fault。如果 Double Fault 处理器也出问题，那就是 Triple Fault，处理器直接放弃，系统重启或关机。

### 如何排查

Triple Fault 最难的地方在于你没有任何输出。所以第一步是确认问题确实是 Triple Fault。如果 QEMU 启动后立即退出，而且没有任何 VGA 输出，那很可能是 Triple Fault。

接下来用 GDB 调试。启动 QEMU 时加 `-s -S` 参数，然后在另一个终端用 GDB 连接。设置断点在 `kernel_start`，单步执行，看看在哪里崩溃。

如果你能在崩溃前停下，检查 RSP 寄存器的值。它应该在 0x80000 附近（这是我们在汇编里设置的栈顶）。如果 RSP 的值不对（比如是 0 或一个很小的随机数），说明栈指针没有正确初始化。

另一个常见问题是栈对齐。x86_64 的 ABI 要求栈指针 16 字节对齐，而且 SSE/AVX 指令会严格要求这个对齐。如果 RSP 的低 4 位不是 0，你调用任何使用 SSE 的函数都会触发 #GP。我们在 `kernel_entry.asm` 里用了 `and rsp, -16` 来确保对齐，如果这一行被删掉或改错了，就会出问题。

### 其他运行时问题

如果系统没有 Triple Fault，但行为不对，比如只看到汇编输出的 'X' 而看不到 C 的 'C'，那说明 C 代码没有执行。检查 `kernel_main` 符号是否存在，调用指令是否正确生成。你可以用 `objdump -d build/kernel.elf | grep "call.*kernel_main"` 来确认。

如果屏幕全黑，连 'X' 都看不到，那问题可能在 bootloader 或入口点上。检查 bootloader 是否正确编译，MBR 签名（最后两字节应该是 `55 aa`）是否正确。还要检查链接脚本的入口点设置，`ENTRY(kernel_start)` 这一行存在吗？

## 验证清单：从零到运行的完整路径

到这里我们已经讲了各种问题和解决方案，但实战中你可能还是不知道从哪里下手。所以我整理了一个完整的验证清单，按照构建和运行的顺序，你可以一步步检查，发现问题立即定位。

### 构建系统验证

首先确认 CMake 配置和编译是否成功。运行 `cmake -B build`，如果报错，检查 CMakeLists.txt 的语法，确认所有工具（NASM、QEMU、Python）都能找到。CMake 会告诉你缺少什么工具，按照提示安装即可。

然后运行 `cmake --build build`。如果有编译错误，根据错误信息修复。如果有警告，检查是否有 `-Werror` 把警告变成了错误。我们的配置里开启了 `-Werror`，所以任何警告都会导致构建失败。

编译成功后，检查构建产物是否存在：`build/kernel.elf`（带符号的 ELF 文件）、`build/kernel.bin`（纯二进制文件）、`build/boot.img`（最终的启动镜像）。如果任何一个缺失，检查 CMakeLists.txt 的目标定义和依赖关系。

### 符号和入口验证

用 `nm build/kernel.elf | grep kernel_start` 检查入口符号。你应该看到类似 `0000000000010000 T kernel_start` 的输出。`T` 表示这是一个代码段符号，地址 0x10000 是正确的加载地址。如果没有输出，说明链接脚本有问题或汇编代码没被链接。

然后检查 C 入口：`nm build/kernel.elf | grep kernel_main`。你也应该看到一个 `T` 类型的符号。如果缺失，说明 C 代码没有被编译或链接。

最后检查 ELF 头：`readelf -h build/kernel.elf | grep Entry`。输出应该显示入口点地址是 0x10000。如果不对，说明链接脚本的 `ENTRY(kernel_start)` 没生效或链接命令有问题。

### 内存布局验证

用 `objdump -h build/kernel.elf` 查看各个段的信息。`.text` 段的虚拟地址应该是 0x10000，`.bss` 段的类型应该是 `NOBITS`（表示不占文件空间）。如果 `.text` 的地址不对，说明链接脚本的 `. = 0x10000` 没生效。如果 `.bss` 的类型是 `PROGBITS`，说明 BSS 段被错误地当作已初始化数据处理了。

还要检查 BSS 符号：`nm build/kernel.elf | grep __bss`。你应该看到 `__bss_start` 和 `__bss_end` 两个符号，它们的值应该相同（因为我们的内核很小，BSS 基本为空）。

### 运行验证

启动 QEMU：`qemu-system-x86_64 -drive format=raw,file=build/boot.img`。如果立即退出，很可能是 Triple Fault。用 GDB 调试。如果看到 VGA 输出，检查是否有 'X'（汇编输出）和 'C'（C 输出）。只有 'X' 没有 'C'，说明 C 代码没执行。两个都没有，说明 bootloader 或入口点有问题。

### 调试验证

最后验证调试能力。启动 QEMU 调试模式（加 `-s -S`），然后在另一个终端用 `gdb build/kernel.elf` 连接。运行 `target remote :1234`，如果连接成功，GDB 会显示当前停止的地址。设置断点 `break kernel_main`，然后 `continue`，看看是否能在 C 函数入口停下。如果可以，恭喜你，调试环境配置成功！

## 经验总结：一路走来我们学到了什么

这一路走来，我们积累了不少经验。有些是做对了的事情，有些是容易踩的坑。我把它们总结出来，希望你能少走弯路。

### 渐进式迁移的价值

我们不是一次性把所有东西都改了，而是先确保 CMake 能正常工作，然后再用 CMake 编译内核。这样可以隔离问题，每一步都能验证。如果出错了，你知道是在哪一步出的问题。

这个思路在很多场景下都有用。不仅仅是迁移构建系统，任何大的重构都应该分阶段进行。每走一步验证一下，不要等到最后才发现问题。

### 保留 ELF 文件的必要性

很多人为了省空间，只保留 `.bin` 文件。但这会失去调试能力。我们两个都保留：`.elf` 用于 GDB 调试，`.bin` 用于实际加载。多用的磁盘空间很便宜，这点开销值得花。

而且 ELF 文件包含了符号信息、重定位信息、段信息等，这些在调试和分析问题时非常有用。你不可能每次都靠猜，有符号信息能让调试效率提高十倍不止。

### 模块化设计的好处

把代码分成 `boot/`、`kernel/` 等目录，每个目录管理自己的构建规则。这样结构清晰，扩展方便。添加新模块时，只需要加一个子目录和一个 CMakeLists.txt，不会影响其他部分。

模块化的另一个好处是并行编译。当你的项目变大后，模块化可以让 CMake 更好地利用多核 CPU，加速构建过程。

### 验证每个步骤的重要性

每做一步都验证一下。编译了？检查一下 ELF 文件生成了没有。链接了？检查一下符号对不对。运行了？检查一下输出是否符合预期。发现问题立即解决，不要堆到最后。

这个习惯能帮你节省大量时间。我见过太多人一口气写了很多代码，然后一次性编译，结果报了几十个错误，不知道从哪里改起。如果边写边测，每次只处理一两个错误，效率会高很多。

## 容易踩的那些坑

有些坑我踩过，不希望你再踩。我们来说说这些隐蔽的问题。

### 地址不一致的灾难

bootloader 加载地址、链接脚本地址、QEMU 内存布局必须一致。这是最隐蔽也最致命的坑。我们的 bootloader 这样加载内核：

```nasm
mov ax, 0x1000
mov es, ax          ; ES:BX = 0x1000:0000 = 0x10000
```

链接脚本也要设置 `. = 0x10000`。如果任何一个地方不一致，程序就会跑飞。而且错误症状很奇怪，很难排查。有时会随机崩溃，有时会显示乱码，有时完全没反应。

### 栈对齐的隐蔽问题

栈对齐问题真的很隐蔽。如果你的代码有时候正常、有时候崩溃，而且崩溃地点不固定，很可能是栈对齐问题。检查 RSP 的低 4 位是否为 0，如果不是，说明栈没对齐。

这个问题在 x86_64 上尤其常见，因为编译器会生成大量 SSE/AVX 指令，这些指令要求 16 字节对齐的内存访问。如果栈没对齐，一旦调用这些函数就会立即崩溃。

### 符号可见性

汇编里用 `global` 导出符号，C 里用 `extern` 声明符号。如果忘记声明或导出，链接时会报错 `undefined reference`。这个错误信息很明确，排查起来不难。

但要注意的是，NASM 的 `global` 和 GAS 的 `.global` 语法不同。如果你混用两种汇编器，要注意语法差异。

### BSS 清零的正确性

如果汇编代码清零 BSS 时用到了 `__bss_start` 和 `__bss_end` 符号，链接脚本必须导出它们。而且符号的值必须是 BSS 段的起止地址，如果计算错误，清零会清错内存区域，导致不可预测的后果。

我们的链接脚本里是这样定义的：

```ld
.bss : {
    __bss_start = .;
    *(.bss)
    *(.bss.*)
    *(COMMON)
    __bss_end = .;
}
```

注意 `__bss_start = .;` 在第一个 `*(.bss)` 之前，`__bss_end = .;` 在所有 BSS 内容之后。这样符号的值就是正确的。

### CMake 缓存的坑

CMake 会把配置结果缓存在 `build/CMakeCache.txt` 里。如果你改了参数（比如切换 Debug/Release），但缓存还保留旧值，配置不会更新。解决方法是删除整个 `build` 目录重新配置。这个坑很多人都会踩，注意一下。

一个典型的症状是：你修改了 CMakeLists.txt，但重新构建后行为没变。这时候试着删除 `build` 目录，从头配置，通常能解决问题。

## 调试技巧：工具的威力

在调试过程中，合适的工具能事半功倍。我们来说说这些工具的用法。

### objdump — 看看生成的汇编

如果你不确定代码是否正确编译，用 `objdump -d build/kernel.elf` 看看生成的汇编。如果汇编看起来很奇怪（比如有大量无用的指令），可能是编译选项有问题。

另一个用法是检查函数调用。用 `objdump -d build/kernel.elf | grep -A 5 "call.*kernel_main"` 可以查看调用 `kernel_main` 的指令及其前后几条指令，确认调用逻辑正确。

### nm — 符号的宝库

`nm` 命令会列出所有符号，包括函数名、全局变量名等。如果某个符号不存在，或者类型不对（比如应该有 `T` 类型但实际是 `U`），说明链接或编译出了问题。

`nm` 还有一个有用的选项是 `-u`，只显示未定义的符号。这对于检查链接依赖很有用。如果看到很多意外的未定义符号，说明某个库或目标文件没有被正确链接。

### readelf — ELF 文件的 X 光机

`readelf` 可以显示 ELF 文件的详细布局，包括各个段的位置、大小、属性。如果段地址不对，说明链接脚本有问题。

特别有用的是 `readelf -S`（显示段信息）和 `readelf -s`（显示符号表）。当你需要深入了解 ELF 文件的结构时，这两个命令很有帮助。

### GDB 单步调试

源码级调试是最强大的调试方法。你可以设置断点、单步执行、查看变量、查看调用栈。这对于理解代码执行流程非常有帮助。

但要注意的是，GDB 调试内核有一些限制。比如某些特权指令（如 `cli`、`sti`）可能在 QEMU 里不能正常单步。另外，GDB 的某些高级功能（如 pretty-printing）在 freestanding 环境下可能不可用。

### VGA 输出调试

在没有串口或日志系统的时候，VGA 输出是唯一的调试手段。在不同的位置输出不同的字符，可以快速定位问题所在。

这个方法虽然原始，但很有效。你可以定义一些宏来简化输出：

```c
#define DEBUG_CHAR(c) \
    do { \
        volatile uint16_t *vga = (uint16_t *)0xB8000; \
        vga[160 * 24] = (0x1F << 8) | (c); \
    } while(0)
```

然后在代码里插入 `DEBUG_CHAR('A')`、`DEBUG_CHAR('B')` 等，看看程序运行到哪里。

## Makefile vs CMake：迁移带来了什么

让我们对比一下 Makefile 和 CMake，看看迁移带来了什么变化。这不是说 Makefile 不好，而是要理解为什么我们选择 CMake。

### Makefile 时代的回忆

在 stage/03，我们用的是简单的 Makefile：

```makefile
AS = nasm
ASFLAGS = -f bin
BOOTLOADER = boot/bootloader.asm
KERNEL = kernel/kernel.asm

all:
    $(AS) $(ASFLAGS) $(BOOTLOADER) -o build/bootloader.bin
    $(AS) $(ASFLAGS) $(KERNEL) -o build/kernel.bin
    dd if=build/bootloader.bin of=build/boot.img bs=512 count=1
    dd if=build/kernel.bin of=build/boot.img bs=512 seek=1

run:
    qemu-system-x86_64 -drive format=raw,file=build/boot.img
```

这个 Makefile 很简单、很直观，一眼就能看懂在做什么。但它的缺点也很明显：不支持 Debug/Release 切换，没有工具检测（如果 NASM 不存在，编译时才会报错），难以扩展（加新文件要手动改规则），IDE 支持有限（智能提示、跳转、重构都需要额外配置）。

### CMake 时代的新体验

迁移到 CMake 后（stage/04），我们的构建系统变成了这样：

```cmake
cmake_minimum_required(VERSION 3.20)
project(CCOS_x64 ASM C)

find_program(NASM nasm REQUIRED)
find_program(QEMU qemu-system-x86_64 REQUIRED)

add_compile_options(
    $<$<COMPILE_LANGUAGE:C>:-Wall -Werror -std=c23>
)

add_subdirectory(boot)
add_subdirectory(kernel)

add_custom_target(run COMMAND ${QEMU} ...)
add_custom_target(debug COMMAND ${QEMU} ... -s -S)
```

这个配置看起来复杂一点，但它带来的好处是巨大的：工具检测在配置阶段就完成，如果 NASM 或 QEMU 不存在，CMake 会立即报错，不会等到编译时才发现。多配置支持，Debug/Release 一键切换，只需要 `cmake -B build -DCMAKE_BUILD_TYPE=Debug`。IDE 友好，CMake 会生成 `compile_commands.json`，支持 clangd、VSCode 等工具的自动补全、跳转、重构功能。扩展方便，加新文件只需要更新 CMakeLists.txt，或者在目录结构上遵循约定，CMake 会自动发现新文件。

### 权衡与选择

当然，CMake 也有它的缺点：学习曲线较陡，配置更复杂。对于非常小的项目（比如只有几个文件的练习），可能有点杀鸡用牛刀。但对于一个要长期发展的内核项目来说，CMake 的优势远远大于缺点。

而且，CMake 是跨平台的。如果你将来想在 macOS 或 Windows 上构建你的内核，CMake 可以轻松适配，而 Makefile 需要大量修改。

## 下一步预告

完成 stage/04 后，我们有了：
- CMake 构建系统
- C 内核入口
- Freestanding 环境配置
- 基础类型定义
- 调试能力

这些基础工作看起来不多，但它们是构建复杂系统的基石。下一步 (stage/05) 会面临更有趣的挑战：内核变大了怎么办？目前的 bootloader 只能加载 512 字节的内核，显然不够用。我们需要实现多扇区加载、更完善的内存管理、中断处理、系统调用等。

这些都是更高级的话题，也会遇到更有趣的挑战。但有了现在的基础，你会发现后续的开发会更加顺利。而且你会发现，这些基础工作真的非常有价值。

## 最后的话

说实话，从 Makefile 迁移到 CMake 是个挺折腾的过程。但一旦完成，你会发现调试更方便，ELF + GDB 源码级调试，不再是黑盒调试。开发更高效，IDE 自动补全、跳转、重构，不用记忆一堆命令。扩展更容易，添加新文件只需要更新 CMakeLists.txt，不用手动改规则。配置更灵活，Debug/Release 一键切换，可以轻松比较不同配置的性能。

真正的大坑在后面。当我们开始添加中断、内存管理、多任务的时候，你会发现这些基础工作有多么重要。所以，花时间把基础打牢，后面会轻松很多。而且理解了这些底层原理，你对操作系统和 C 语言的理解会更上一层楼。

到这里，stage/04_cmake_union 的教程就全部结束了。你现在已经理解了 CMake 的基本使用，掌握了 Freestanding C 环境的配置，学会了链接脚本的编写，能够用 GDB 调试内核，实现了基础类型定义和小型库函数。

可以庆祝一下了。
