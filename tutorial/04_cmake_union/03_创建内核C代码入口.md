# 创建内核 C 代码入口

现在我们开始真正写代码了。这一篇我们会实现从汇编到 C 的过渡，你会发现这两者是如何配合工作的。

---

## 为什么要用两阶段入口

你可能会问：**为什么不能直接从 C 开始？为什么要先写一段汇编？**

这是一个非常好的问题。很多人第一次写内核的时候都会有这个疑惑。实际上，你不能直接从 C 开始，因为在调用 C 代码之前，我们需要准备好运行环境。C 语言并不是一种可以"裸奔"的语言，它依赖一些运行时的前提条件。

首先，**C 函数调用需要栈**。当你调用一个 C 函数时，编译器会生成代码来把参数压栈、保存返回地址、分配局部变量空间。所有这些操作都依赖于一个正确设置的栈指针（RSP）。如果没有栈，调用 C 函数会立即崩溃。

其次，**未初始化的全局变量必须是 0**。C 标准规定，未初始化的全局变量和静态变量必须被初始化为 0。这个区域叫 BSS 段。但是，你的程序被加载到内存时，加载器不一定会清零 BSS 段。我们需要手动清零它，否则 C 代码读取这些变量时会得到随机值。

最后，**中断处理**。在初始化期间，我们不希望被中断打断。中断可能在任何时候发生，如果在我们还没初始化好数据结构时就被中断打断，可能会导致不可预测的行为。所以我们先关中断，初始化完成后再开中断。

这些操作用汇编更直接、更可控。C 语言虽然强大，但它无法精确控制 CPU 的底层状态。你无法在 C 语言里直接设置栈指针，无法直接清零一段内存，无法直接关中断。所以我们需要一段"胶水代码"，用汇编来准备好环境，然后跳转到 C 代码。

---

## 启动流程图解

让我们先从整体上理解启动流程。这样你在写代码的时候，会知道每一行代码在整个流程中的位置和作用。

```
┌─────────────────────────────────────────┐
│   Bootloader (跳转到 0x10000)           │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   kernel_entry.asm (汇编入口)            │
│   ┌─────────────────────────────────┐   │
│   │ 1. 关中断 (cli)                 │   │
│   │ 2. 设置栈 (rsp = 0x80000)      │   │
│   │ 3. 清零 BSS                     │   │
│   │ 4. 调用 kernel_main()           │   │
│   └─────────────────────────────────┘   │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   kernel_main.c (C 主函数)              │
│   ┌─────────────────────────────────┐   │
│   │ - VGA 输出 'C'                  │   │
│   │ - 初始化代码                    │   │
│   │ - 主循环                        │   │
│   └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

这个流程图很直观。bootloader 加载内核到 0x10000，然后跳转过去。内核的汇编入口首先关中断，设置栈，清零 BSS，然后调用 C 主函数。C 主函数就可以安心地写内核逻辑了，因为运行环境已经准备好了。

## 编写 kernel_entry.asm

现在我们来写汇编入口代码。我们先来看完整的代码，然后逐段解释。不要被代码的长度吓到，我们一步一步拆解。

### 声明部分

```nasm
; CCOS Kernel Entry Point
; Assembly stub that sets up C environment and jumps to kernel_main
; Loaded at 0x10000 by bootloader (set by linker script)

section .text
    bits 64

; External C function
extern kernel_main

; Kernel entry point - bootloader jumps here
global kernel_start
kernel_start:
```

这部分代码做的是声明工作。`section .text` 告诉 NASM 我们要创建一个 `.text` 段，这是代码段的标准名称。`bits 64` 告诉 NASM 我们要生成 64 位代码。因为我们的内核是在长模式下运行的，所以必须是 64 位代码。

`extern kernel_main` 声明了一个外部符号 `kernel_main`。这个符号是在 C 代码里定义的，汇编代码通过 `extern` 告诉汇编器："这个符号在别的地方定义，链接时会找到"。如果没有这个声明，汇编器会报错说找不到 `kernel_main`。

`global kernel_start` 声明 `kernel_start` 是一个全局符号。这样链接器就能看到这个符号，把它作为程序的入口点。bootloader 跳转到的就是这个地址。

### 关中断和设置栈

```nasm
kernel_start:
    ; Disable interrupts for setup
    cli

    ; Set up stack - grow down from 0x80000
    ; Ensure 16-byte alignment for SSE/AVX instructions used by O2/O3 optimizations
    ; The bootloader's 'call rdi' pushed 8 bytes (return address), so we need to
    ; account for that. We want the stack to be 16-byte aligned BEFORE we call
    ; kernel_main (which will push another 8 bytes).
    mov rsp, 0x80000 - 8  ; Adjust for bootloader's call
    and rsp, -16           ; Align to 16-byte boundary
    mov rbp, rsp
```

`cli` 是 Clear Interrupts 的缩写，它关掉中断。在初始化期间，我们不希望被中断打断。初始化完成后，C 代码里可以再开中断（`sti`）。

接下来是设置栈指针。栈是我们用汇编设置的第一样东西，也是最重要的一样东西。栈的设置有几个细节需要特别注意。

首先，栈从哪里开始？我们选择 0x80000。这个地址不是随便选的，它考虑了很多因素。我们的内核加载在 0x10000，大小约 448KB（0x10000 到 0x7FFFF）。栈放在内核后面，从 0x80000 向下增长。这样栈不会覆盖内核代码，内核代码也不会覆盖栈。

然后，为什么是 `0x80000 - 8`？这个问题很有意思。bootloader 用 `call rdi` 跳转到内核，`call` 指令会把返回地址压栈，占用 8 字节（64 位地址）。所以当我们拿到控制权时，栈已经有一个 8 字节的值了。我们设置栈指针时，需要考虑这个已经存在的值。

更细节地说，我们希望调用 `kernel_main` 时，栈是 16 字节对齐的。这是因为 SSE 和 AVX 指令要求栈 16 字节对齐，如果不对齐，使用这些指令会触发 General Protection Fault。GCC 的 O2 和 O3 优化可能会使用 SSE/AVX 指令，所以我们必须保证栈对齐。

`and rsp, -16` 是一个常用的技巧。`-16` 的二进制是 `...11110000`，按位与就清除了低 4 位，实现 16 字节对齐。这比用除法或取模指令要快得多，因为按位运算是 CPU 最快的操作之一。

`mov rbp, rsp` 保存栈指针到 RBP。这是 C 代码的惯例，RBP 用作帧指针，指向当前栈帧的底部。虽然现代编译器可以用 `-fomit-frame-pointer` 优化掉 RBP，但在内核早期阶段，我们保留它方便调试。

### 清零 BSS 段

```nasm
    ; Clear BSS section (uninitialized data)
    ; Linker puts __bss_start and __bss_end symbols
    extern __bss_start
    extern __bss_end
    cld
    mov rdi, __bss_start
    mov rcx, __bss_end
    sub rcx, rdi
    shr rcx, 3  ; Convert to qwords
    xor eax, eax
    rep stosq
```

这段代码清零 BSS 段。BSS 段存放未初始化的全局变量和静态变量，C 标准要求它们必须是 0。但实际上，程序加载时 BSS 段不会被自动清零（加载器只记录大小，不分配空间），我们需要手动清零。

`extern __bss_start` 和 `extern __bss_end` 声明了两个符号，它们是在链接脚本里定义的。链接脚本会计算 BSS 段的起止地址，导出这两个符号。汇编代码通过这两个符号知道要清零哪些内存。

`cld` 清除方向标志。`rep stosq` 会根据方向标志决定是递增还是递减 RDI。我们希望从低地址向高地址清零，所以需要清除方向标志。

`mov rdi, __bss_start` 设置目标地址为 BSS 段起始。`mov rcx, __bss_end` 把结束地址放到 RCX，然后 `sub rcx, rdi` 计算大小。`shr rcx, 3` 把字节数转换为 qword 数（除以 8）。`xor eax, eax` 把 RAX 清零。`rep stosq` 重复 `stosq` 指令 RCX 次，把 0 填充到 BSS 段。

`stosq` 的功能是：把 RAX 的值存到 [RDI]，然后 RDI += 8。配合 `rep` 前缀，它就成了一个高效的内存填充指令。CPU 会用硬件优化的循环来实现，比手写的 `loop` 循环要快得多。

### 调试输出

```nasm
    ; Optional: Write 'X' to VGA to prove we got here (for debugging)
    mov rdi, 0xB8000 + 160 * 5  ; Line 5
    mov word [rdi], 0x1F58  ; 'X' in white on blue
```

这段代码是可选的，用于调试。它在 VGA 文本缓冲区的第 5 行写一个 'X' 字符。VGA 文本缓冲区在物理地址 0xB8000，每个字符占 2 字节：低字节是 ASCII 码，高字节是颜色属性。`0x1F58` 的高字节 `0x1F` 是颜色属性（白色前景蓝色背景），低字节 `0x58` 是字母 'X' 的 ASCII 码。

这个调试输出非常有用。如果你运行 QEMU 后看到了 'X'，说明汇编代码执行到了这里。如果没看到，说明问题在汇编入口之前，可能是 bootloader 没正确跳转，或者链接地址不对。

### 调用 C 函数

```nasm
    ; Jump to C kernel main
    call kernel_main

    ; If kernel_main returns, halt
halt_loop:
    cli
    hlt
    jmp halt_loop
```

`call kernel_main` 调用 C 主函数。`call` 指令会把返回地址压栈，然后跳转到 `kernel_main`。栈现在是 16 字节对齐的（我们设置 RSP 时已经对齐，`call` 又压了 8 字节，变成了 8 字节对齐。但 C 函数入口会再压 RBP，变成 16 字节对齐）。

如果 `kernel_main` 返回了（虽然它不应该返回），我们会进入死循环。`cli` 关中断，`hlt` 让 CPU 停机，`jmp halt_loop` 跳回前面，形成无限循环。这是一个安全的停机方式，比单纯的 `jmp $` 更省电。

## 编写第一个 kernel_main.c

现在我们来看 C 入口。这是我们的第一个 C 内核代码，虽然简单，但意义重大。

```c
// CCOS Kernel Main Entry
// C code entry point called from kernel_entry.asm
#include "defines/types.h"

void kernel_main(void) {
    // VGA buffer at 0xB8000
    volatile uint16_t *vga = (uint16_t *)0xB8000;

    // Write 'C' to line 6 (to prove C code ran)
    vga[160 * 6] = 0x1F43;  // 'C' in white on blue

    // Halt loop
    while (1) {
        __asm__ volatile("hlt");
    }
}
```

这段代码虽然只有十几行，但每个部分都有它的道理。

### VGA 地址

```c
volatile uint16_t *vga = (uint16_t *)0xB8000;
```

VGA 文本缓冲区在物理地址 0xB8000。每个字符占 2 字节：低字节是 ASCII 码，高字节是颜色属性。我们把这个地址强制转换为 `uint16_t *` 指针，这样就可以像数组一样访问了。

这里有个关键的关键字：`volatile`。它告诉编译器："这个内存访问有副作用，别给我优化掉"。如果没有 `volatile`，编译器可能认为这段代码没用（只是写内存又不读取），直接删掉。或者它可能把多次写合并成一次写，这会导致问题。

VGA 是内存映射 I/O，每次写入都有实际的硬件效果。我们必须确保每次写入都被执行，所以要用 `volatile`。

### 颜色属性

```c
vga[160 * 6] = 0x1F43;
```

这行代码在第 6 行写一个 'C' 字符。VGA 文本模式是 80 列 25 行，每行 160 字节（80 个字符 × 2 字节）。所以第 6 行的起始地址是 `0xB8000 + 160 * 6`。

`0x1F43` 分解来看：
- 低字节 `0x43` 是字母 'C' 的 ASCII 码（0x41 是 'A'，所以 0x43 是 'C'）
- 高字节 `0x1F` 是颜色属性

VGA 颜色属性的格式是：低 4 位是前景色，高 4 位是背景色。`0x0F` 是白色前景（15），`0x10` 是蓝色背景（16），所以 `0x1F` 是白色前景蓝色背景。

### Halt 循环

```c
while (1) {
    __asm__ volatile("hlt");
}
```

这是一个无限循环，每次迭代执行 `hlt` 指令。`hlt` 让 CPU 停机，等待中断。比 `jmp $` 更省电，因为 CPU 会进入低功耗状态。

`__asm__ volatile("hlt")` 是 GCC 的内联汇编语法。`__asm__` 是 `asm` 的宏，避免和变量名冲突。`volatile` 告诉编译器不要优化这条指令。虽然在这个循环里优化也没关系，但用 `volatile` 是个好习惯。

## 验证方法：两个字母

我们用两个字母来验证执行流程。这个方法虽然简单，但非常有效。

1. 汇编代码在第 5 行输出 'X'
2. C 代码在第 6 行输出 'C'

运行 QEMU 后，预期结果应该是：

```
屏幕上应该看到：
第 5 行：X
第 6 行：C
```

如果只看到 'X'，说明 C 代码没执行。可能是链接有问题，或者 `kernel_main` 符号没正确导出。如果两个都没看到，说明汇编入口没执行，可能是 bootloader 没正确跳转，或者链接地址不对。

这种方法看起来简陋，但在内核开发的早期阶段非常有用。你还没有串口、没有日志系统，VGA 输出是你唯一的调试手段。用不同的字母表示不同的执行阶段，可以快速定位问题。

## 编译与链接流程

现在我们把编译流程说清楚。这是连接源代码和可执行代码的桥梁，每一步都有它的作用。

### 第一步：编译汇编

```bash
nasm -f elf64 kernel_entry.asm -o kernel_entry.o
```

`-f elf64` 生成 64 位 ELF 格式的目标文件。ELF 是 Linux 的标准可执行文件格式，包含代码、数据、符号信息等。链接器需要 ELF 格式的输入，才能正确解析符号和重定位。

### 第二步：编译 C

```bash
gcc -c kernel_main.c -o kernel_main.o \
    -ffreestanding \
    -fno-builtin \
    -nostdlib \
    -mcmodel=large
```

这些选项我们下一篇会详细解释。简单来说，它们告诉 GCC："这是 freestanding 环境，没有标准库，不要假设任何东西"。`-mcmodel=large` 使用大代码模型，支持任意大小的内核。

### 第三步：链接

```bash
ld -m elf_x86_64 \
    -T linker.ld \
    -nostdlib \
    -o kernel.elf \
    kernel_entry.o \
    kernel_main.o
```

`-T linker.ld` 指定链接脚本。链接脚本告诉链接器如何把各个段放在一起，从哪个地址开始，哪些符号需要导出。下一篇我们会详细讲解链接脚本。

### 第四步：提取二进制

```bash
objcopy -O binary kernel.elf kernel.bin
```

ELF 包含符号信息（调试用），但 bootloader 只需要纯二进制代码。`objcopy` 从 ELF 里提取出纯代码，生成 `.bin` 文件。这个文件才是真正被加载到内存运行的。

## ⚠️ 常见问题

这里有几个常见的问题，我提前说一下，免得你踩坑。

### undefined reference to `kernel_main`

如果你看到这个错误，说明 C 代码编译失败，或者链接时没包含 C 的 `.o` 文件。检查一下 `kernel_main.o` 是否存在，链接命令是否包含它。

### undefined reference to `__bss_start`

如果你看到这个错误，说明链接脚本没定义 `__bss_start` 符号。检查 `linker.ld` 的 `.bss` 段是否有 `__bss_start = .;` 这一行。

### Triple Fault（QEMU 立即退出）

如果你的内核触发 Triple Fault，最可能是栈指针错误或栈溢出。检查 RSP 初始化是否正确，是否 16 字节对齐。可以用 GDB 单步调试，看看是在哪一行崩溃的。

### 只看到 'X' 不看到 'C'

这说明 C 代码没执行。检查 `kernel_main` 符号是否正确导出，链接命令是否包含 `kernel_main.o`。可以用 `nm kernel.elf | grep kernel_main` 检查符号是否存在。

## 完整验证命令

```bash
# 编译
nasm -f elf64 kernel_entry.asm -o kernel_entry.o
gcc -c kernel_main.c -o kernel_main.o -ffreestanding -nostdlib
ld -m elf_x86_64 -T linker.ld -o kernel.elf kernel_entry.o kernel_main.o
objcopy -O binary kernel.elf kernel.bin

# 检查符号
nm kernel.elf | grep kernel_main
# 应该看到： T kernel_main

# 检查入口点
readelf -h kernel.elf | grep Entry
# 应该看到：Entry point address: 0x10000
```

这些命令可以验证编译是否成功，符号是否正确，入口点是否对。如果任何一个检查失败，停下来排查问题，不要继续。
