# 调试与验证

代码写完了，怎么知道它对不对？说实话，如果你还用 print 大法来调试内核，迟早会崩溃的。这一篇我们完整介绍内核调试的方法，你会发现有了源码级调试，内核开发会轻松很多。

---

## GDB 调试 C 代码

GDB 是最强大的调试工具，但很多人只会用它调普通程序，不知道怎么调内核。说实话，我第一次调内核的时候也是一头雾水，不知道从何下手。但一旦你掌握了它，会发现调试内核和调试普通程序其实差不多，只是启动方式有点不一样。

### 启动 QEMU 调试模式

首先，QEMU 要以调试模式启动。这是很多人容易忘的一步。

```bash
qemu-system-x86_64 \
    -drive format=raw,file=build/boot.img,if=ide \
    -nographic \
    -s -S
```

**参数解释**：

- `-drive format=raw,file=build/boot.img,if=ide` — 用 IDE 接口加载我们的镜像
- `-nographic` — 不使用图形界面，所有输出到终端
- `-s` — 等价于 `-gdb tcp::1234`，开启 GDB 服务器，监听 1234 端口
- `-S` — 启动后暂停，等待 GDB 连接。如果没有这个选项，QEMU 会直接运行，你可能在断点之前就错过了

**为什么需要 `-S`？**

因为内核启动很快，如果 QEMU 直接运行，可能在你连接 GDB 之前就已经跑过了你想调试的地方。`-S` 让 QEMU 在第一条指令前暂停，给你连接和设置断点的时间。

### 连接 GDB

新开一个终端，启动 GDB：

```bash
gdb build/kernel.elf
```

**注意：我们调试的是 `.elf` 文件，不是 `.bin`**。这是一个重要的区别。`.bin` 是纯二进制代码，没有符号信息，GDB 无法设置断点或查看变量。`.elf` 包含完整的符号信息（函数名、变量名、行号等），GDB 需要它来实现源码级调试。

启动后，你会看到 GDB 的提示符：

```
GNU gdb (Ubuntu 12.1-0ubuntu1~22.04) 12.1
Copyright (C) 2022 Free Software Foundation, Inc.
License GPLv3+: GNU GPL version 3 or later
This is free software: you are free to change and redistribute it.
There is NO WARRANTY, to some extent permitted by applicable law.
Type "show copying" and "show warranty" for details.
This GDB was configured as "x86_64-linux-gnu"
Type "show configuration" for configuration information.
Reading symbols from build/kernel.elf...
(gdb)
```

看到 `Reading symbols from build/kernel.elf...` 就说明符号加载成功了。如果这步报错，说明 `.elf` 文件有问题，可能是编译或链接时出了问题。

### GDB 常用命令

连接到 QEMU：

```gdb
target remote :1234
```

如果成功，你会看到：

```
Remote debugging using :1234
0x0000000000007c00 in ?? ()
```

`0x0000000000007c00` 是 BIOS 的地址，说明 QEMU 正确启动了。如果是 `0x0000000000010000`，说明已经跳转到我们的内核了。

**常用命令速查**：

```gdb
# 设置断点
break kernel_main
break *0x10050

# 继续执行
continue

# 单步执行
next    # 跨过函数调用（不进入函数内部）
step    # 进入函数调用（单步进入）

# 查看变量
print vga
print *vga
print/x vga      # 十六进制显示

# 查看寄存器
info registers
info registers rsp rip

# 查看栈
backtrace
frame 0

# 查看汇编
disassemble
disassemble  # 反汇编当前函数
disassemble 0x10000 0x10050  # 反汇编指定地址范围

# 查看内存
x/10x 0xB8000    # 查看 0xB8000 处的 10 个十六进制数
x/10i 0x10000     # 查看 0x10000 处的 10 条指令

# 设置断点并继续
break *0x10050
continue
```

### 实战调试示例

让我们来走一遍完整的调试流程。

```gdb
gdb build/kernel.elf
(gdb) target remote :1234
Remote debugging using :1234
0x0000000000007c00 in ?? ()
(gdb) break kernel_main
Breakpoint 1 at 0x10050: file kernel/kernel_main.c, line 11.
(gdb) continue
Continuing.

Breakpoint 1, kernel_main () at kernel/kernel_main.c:11
11          volatile uint16_t *vga = (uint16_t *)0xB8000;
(gdb) next
12          vga[160 * 6] = 0x1F43;
(gdb) print vga
$1 = (volatile uint16_t *) 0xb8000
(gdb) x/2x 0xb8000 + 160*6
0xb8780:        0x0000000000001f43
(gdb)
```

**你看到什么？**

- `break kernel_main` 在 C 函数入口设置断点。GDB 知道符号信息，可以直接用函数名设置断点。
- `continue` 让 QEMU 运行到断点。程序暂停时，GDB 会显示当前源代码位置。
- `next` 单步执行一行代码。
- `print vga` 显示变量值。`$1` 是 GDB 的历史值编号，可以用来引用之前的值。
- `x/2x` 显示内存内容。`0xb8780` 是第 6 行 VGA 缓冲区的地址。

这就是源码级调试的威力！你可以看到每一行代码的执行，查看变量的值，不需要靠猜测。

## 二进制工具验证

有时候不需要运行代码，我们也能检查很多问题。这些工具在链接阶段就很有用，可以提前发现很多问题。

### objdump - 反汇编

```bash
objdump -d build/kernel.elf | less
```

**你会看到**：

```
0000000000010000 <kernel_start>:
   10000:       fa                      cli
   10001:       48 bc 00 00 80 00 00    mov    rsp,0x80000
   10008:       48 81 e4 f0 0f 00 00    and    rsp,0xfffffffffffffff0
   1000f:       48 89 e5                mov    rbp,rsp
   ...
```

**这告诉我们什么？**

- `kernel_start` 在 0x10000，正确！这是链接脚本设置的地址。
- 汇编代码看起来合理。`cli`、`mov rsp`、`and rsp`、`mov rbp` 都是我们写的代码。
- 如果地址不对（比如 0x400000），说明链接脚本的 `. = 0x10000` 没生效。

### readelf - 查看段信息

```bash
readelf -S build/kernel.elf
```

**关键信息**：

```
  [Nr] Name              Type            Address          Off    Size
  [ 0]                   NULL            0000000000000000 000000 000000
  [ 1] .text             PROGBITS        0000000000010000 001000 000120
  [ 2] .rodata           PROGBITS        0000000000010120 001120 000000
  [ 3] .data             PROGBITS        0000000000010120 001120 000000
  [  [ 4] .bss              NOBITS          0000000000010120 001120 000004
```

**检查点**：

- `.text` 虚拟地址是 0x10000，正确！
- `.bss` 类型是 `NOBITS`（不占文件空间），正确！这是 BSS 段的特征。
- 文件偏移（`Off`）是相对于文件的，加载地址（`Address`）是运行时的地址。

### nm - 查看符号

```bash
nm build/kernel.elf
```

**你会看到**：

```
0000000000010000 T kernel_start
0000000000010050 T kernel_main
0000000000010120 B __bss_end
0000000000010120 A __bss_start
```

**符号类型**：

- `T` — Text 段（代码），这是可执行代码
- `D` — Data 段（已初始化数据）
- `B` — BSS 段（未初始化数据）
- `A` — Absolute（绝对符号），不像任何段

如果没有 `kernel_main` 符号，说明 C 代码没被正确链接。如果没有 `__bss_start` 和 `__bss_end`，说明链接脚本没正确导出这些符号。

### size - 查看段大小

```bash
size build/kernel.elf
```

**输出**：

```
   text    data     bss     dec     hex filename
   288       0       4     292     124 build/kernel.elf
```

**很小的内核！** 只有 288 字节代码，4 字节 BSS。这说明我们的内核还很简洁，只有基本的启动代码和几个未初始化变量。

## 运行时验证

静态分析很重要，但运行时验证更直观。

### VGA 输出验证

我们上一篇说过，用两个字母验证执行流程：

```c
// 汇编输出 'X' 到第 5 行
mov rdi, 0xB8000 + 160 * 5
mov word [rdi], 0x1F58

// C 输出 'C' 到第 6 行
vga[160 * 6] = 0x1F43;
```

**运行 QEMU**：

```bash
qemu-system-x86_64 -drive format=raw,file=build/boot.img -vga std
```

**你应该看到**：

```
第 5 行：X
第 6 行：C
```

如果只看到 'X'，说明 C 代码没执行。检查 `kernel_main` 符号和链接。如果两个都没看到，说明汇编入口没执行，检查 bootloader 和链接地址。

## VSCode 集成

命令行 GDB 强大，但 VSCode 更友好。如果你习惯了图形界面调试，VSCode 的配置其实不复杂。

### .vscode/launch.json

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug CCOS Kernel",
            "type": "cppdbg",
            "request": "launch",
            "program": "${workspaceFolder}/build/kernel.elf",
            "miDebuggerServerAddress": "localhost:1234",
            "miDebuggerPath": "/usr/bin/gdb",
            "MIMode": "gdb",
            "setupCommands": [
                {
                    "description": "Enable pretty-printing",
                    "text": "-enable-pretty-printing",
                    "ignoreFailures": true
                }
            ],
            "preLaunchTask": "start-qemu-debug"
        }
    ]
}
```

这个配置告诉 VSCode：
- 用 cppdbg 调试类型（支持 C/C++）
- 调试目标是 `build/kernel.elf`
- GDB 服务器在 localhost:1234
- 在启动调试前先运行 `start-qemu-debug` 任务

### .vscode/tasks.json

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "start-qemu-debug",
            "type": "shell",
            "command": "qemu-system-x86_64",
            "args": [
                "-drive", "format=raw,file=${workspaceFolder}/build/boot.img,if=ide",
                "-nographic",
                "-s",
                "-S"
            ],
            "isBackground": true,
            "problemMatcher": []
        }
    ]
}
```

这个任务启动 QEMU 调试模式。`isBackground: true` 表示在后台运行，不会阻塞 VSCode。`problemMatcher: []` 表示不匹配错误输出（因为 QEMU 的输出不是错误格式）。

**使用方法**：

1. 按 F5 启动调试
2. VSCode 会自动启动 QEMU 并连接 GDB
3. 设置断点、查看变量、单步执行

真的就这么简单。你再也不用记忆一长串 GDB 命令了，所有操作都是点击按钮。这对于经常调试的开发来说，效率提升巨大。

## 常见调试场景

有些问题会反复出现，我们来说说如何排查。

### 场景 1：内核没启动

**症状**：QEMU 启动但屏幕全黑

**排查**：

```bash
# 检查 bootloader
hexdump -C build/bootloader.bin | head -20

# 检查内核入口
nm build/kernel.elf | grep kernel_start

# 检查链接脚本
cat linker.ld | grep "ENTRY"
```

如果 bootloader 的最后两字节不是 `55 aa`（MBR 签名），说明 bootloader 没编译正确。如果 `kernel_start` 符号不存在，说明链接有问题。

### 场景 2：C 代码没执行

**症状**：只看到汇编输出的 'X'，没看到 C 的 'C'

**排查**：

```bash
# 检查 kernel_main 符号
nm build/kernel.elf | grep kernel_main

# 检查调用指令
objdump -d build/kernel.elf | grep "call.*kernel_main"

# 检查链接是否包含 C 目标文件
ls -la build/ | grep kernel_main
```

如果 `kernel_main.o` 不存在，说明 C 代码没编译。如果链接命令没包含 `kernel_main.o`，说明 CMake 配置有问题。

### 场景 3：Triple Fault

**症状**：QEMU 立即退出，没有任何输出

**排查**：

```bash
# 最可能是栈问题
# 检查栈指针设置
objdump -d build/kernel_entry.o | grep "mov.*rsp"

# 检查栈对齐
objdump -d build/kernel_entry.o | grep "and.*-16"
```

如果 RSP 的值不对（比如 0 而不是 0x80000 附近），或者栈没对齐，就会触发 Triple Fault。用 GDB 单步调试可以在崩溃前看到 RSP 的值。

### 场景 4：断点不生效

**症状**：设置了断点，但程序没有暂停

**排查**：

1. 确认是用 `.elf` 调试，不是 `.bin`
2. 确认断点地址正确（用 `nm` 或 `readelf` 查看）
3. 确认代码真的运行到了断点位置（可能提前崩溃了）

如果断点设在了不会执行的代码里（比如 `if (0)` 分支），断点当然不会生效。

## ⚠️ 常见坑点

这里有几个常见的坑点，我提前说一下，免得你踩进去。

**用 .elf 调试，不是 .bin** — `.bin` 没有符号信息，GDB 无法设置断点。这是一个非常容易犯的错误。

**QEMU 要加 -s -S** — `-s` 开 GDB 服务，`-S` 启动时暂停。如果少了 `-S`，程序会在你连接前就跑过去了。

**断点要设在代码加载后** — 链接脚本地址要对，代码要正确加载到那个地址。

**有些指令会跳过** — GDB 不支持某些特殊指令（比如 `cpuid`），单步时会跳过这些指令。这是正常的，不影响调试。

## 验证清单

开发完成后，用这个清单验证。这看起来有点长，但每一项都很重要。

- [ ] CMake 配置成功（`cmake -B build`）
- [ ] 内核编译无警告（`cmake --build build`）
- [ ] 链接成功（生成 kernel.elf 和 kernel.bin）
- [ ] 符号正确（`nm | grep kernel_main`）
- [ ] 入口点正确（`readelf -h | grep Entry`）
- [ ] QEMU 启动正常（`make run`）
- [ ] VGA 输出正确（看到 X 和 C）
- [ ] GDB 可以连接（`target remote :1234`）
- [ ] 断点工作（`break kernel_main`）
- [ ] 单步执行正常（`next`, `step`）

如果所有检查都通过了，恭喜你，迁移成功了！
