# 07 - 调试与验证

代码写完了，怎么知道它对不对？这一篇我们完整介绍内核调试的方法。

---

## GDB 调试 C 代码

GDB 是最强大的调试工具，但很多人只会用它调普通程序，不知道怎么调内核。

### 启动 QEMU 调试模式

首先，QEMU 要以调试模式启动：

```bash
qemu-system-x86_64 \
    -drive format=raw,file=build/boot.img,if=ide \
    -nographic \
    -s -S
```

**参数解释**：

- `-s` — 等价于 `-gdb tcp::1234`，开启 GDB 服务器
- `-S` — 启动后暂停，等待 GDB 连接
- `-nographic` — 不使用图形界面

### 连接 GDB

新开一个终端：

```bash
gdb build/kernel.elf
```

**注意：我们调试的是 `.elf` 文件，不是 `.bin`**。ELF 包含符号信息，GDB 需要它。

### GDB 常用命令

连接后输入：

```gdb
# 连接到 QEMU
target remote :1234

# 设置断点
break kernel_main

# 继续执行
continue

# 单步执行
next    # 跨过函数调用
step    # 进入函数调用

# 查看变量
print vga
print *vga

# 查看寄存器
info registers

# 查看栈
backtrace
frame 0

# 查看汇编
disassemble

# 查看内存
x/10x 0xB8000    # 查看 0xB8000 处的 10 个十六进制数
```

### 实战调试示例

```gdb
gdb build/kernel.elf
(gdb) target remote :1234
Remote debugging using :1234
0x0000000000007c00 in ?? ()
(gdb) break kernel_main
Breakpoint 1 at 0x10050: file kernel/kernel_main.c, line 11.
(gdb) continue
Continuing.

Breakpoint 1, kernel_main () at kernel/kernel_main.c:11
11          volatile uint16_t *vga = (uint16_t *)0xB8000;
(gdb) next
12          vga[160 * 6] = 0x1F43;
(gdb) print vga
$1 = (volatile uint16_t *) 0xb8000 <_bss_end+453952>
(gdb) x/2x 0xb8000 + 160*6
0xb8780:        0x0000000000001f43
```

**你看到什么？**

- `break kernel_main` 在 C 函数入口设置断点
- `continue` 让 QEMU 运行到断点
- `print vga` 显示变量值
- `x/2x` 显示内存内容

## 二进制工具验证

不运行代码，我们也能检查很多问题。

### objdump - 反汇编

```bash
objdump -d build/kernel.elf | less
```

**你会看到**：

```
0000000000010000 <kernel_start>:
   10000:       fa                      cli
   10001:       48 bc 00 00 80 00 00    mov    rsp,0x80000
   10008:       00 00 00
   ...

0000000000010050 <kernel_main>:
   10050:       55                      push   rbp
   10051:       48 89 e5                mov    rbp,rsp
   10054:       48 be 00 80 0b 00 00    movabs rsi,0xb8000
   1005b:       00 00 00
```

**这告诉我们什么？**

- `kernel_start` 在 0x10000，正确
- `kernel_main` 紧随其后
- 汇编代码看起来合理

### readelf - 查看段信息

```bash
readelf -S build/kernel.elf
```

**关键信息**：

```
  [Nr] Name              Type            Address          Off    Size
  [ 0]                   NULL            0000000000000000 000000 000000
  [ 1] .text             PROGBITS        0000000000010000 001000 000120
  [ 2] .rodata           PROGBITS        0000000000010120 001120 000000
  [ 3] .data             PROGBITS        0000000000010120 001120 000000
  [ 4] .bss              NOBITS          0000000000010120 001120 000004
```

**检查点**：

- `.text` 虚拟地址是 0x10000，正确
- `.bss` 类型是 `NOBITS`（不占文件空间），正确

### nm - 查看符号

```bash
nm build/kernel.elf
```

**你会看到**：

```
0000000000010000 T kernel_start
0000000000010050 T kernel_main
0000000000010120 B __bss_end
0000000000010120 A __bss_start
```

**符号类型**：

- `T` — Text 段（代码）
- `D` — Data 段（已初始化数据）
- `B` — BSS 段（未初始化数据）
- `A` — Absolute（绝对符号）

### size - 查看段大小

```bash
size build/kernel.elf
```

**输出**：

```
   text    data     bss     dec     hex filename
   288       0       4     292     124 build/kernel.elf
```

**很小的内核！** 只有 288 字节代码，4 字节 BSS。

## 运行时验证

### VGA 输出验证

我们上一篇说过，用两个字母验证执行流程：

```c
// 汇编输出 'X' 到第 5 行
mov rdi, 0xB8000 + 160 * 5
mov word [rdi], 0x1F58

// C 输出 'C' 到第 6 行
vga[160 * 6] = 0x1F43;
```

**运行 QEMU**：

```bash
qemu-system-x86_64 -drive format=raw,file=build/boot.img -vga std
```

**你应该看到**：

```
第 5 行：X
第 6 行：C
```

### 串口输出验证（如果有）

如果你实现了串口驱动：

```bash
qemu-system-x86_64 \
    -drive format=raw,file=build/boot.img \
    -nographic \
    -serial stdio
```

串口输出会显示在终端上。

## VSCode 集成

命令行 GDB 强大，但 VSCode 更友好。

### .vscode/launch.json

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug CCOS Kernel",
            "type": "cppdbg",
            "request": "launch",
            "program": "${workspaceFolder}/build/kernel.elf",
            "miDebuggerServerAddress": "localhost:1234",
            "miDebuggerPath": "/usr/bin/gdb",
            "MIMode": "gdb",
            "setupCommands": [
                {
                    "description": "Enable pretty-printing",
                    "text": "-enable-pretty-printing",
                    "ignoreFailures": true
                }
            ],
            "preLaunchTask": "start-qemu-debug"
        }
    ]
}
```

### .vscode/tasks.json

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "start-qemu-debug",
            "type": "shell",
            "command": "qemu-system-x86_64",
            "args": [
                "-drive", "format=raw,file=${workspaceFolder}/build/boot.img,if=ide",
                "-nographic",
                "-s",
                "-S"
            ],
            "isBackground": true,
            "problemMatcher": []
        }
    ]
}
```

**使用方法**：

1. 按 F5 启动调试
2. VSCode 会自动启动 QEMU 并连接 GDB
3. 设置断点、查看变量、单步执行

## 常见调试场景

### 场景 1：内核没启动

**症状**：QEMU 启动但屏幕全黑

**排查**：

```bash
# 检查 bootloader
objdump -d build/bootloader.bin | head -20

# 检查内核入口
nm build/kernel.elf | grep kernel_start

# 检查链接脚本
cat linker.ld | grep "ENTRY"
```

### 场景 2：C 代码没执行

**症状**：只看到汇编输出的 'X'，没看到 C 的 'C'

**排查**：

```bash
# 检查 kernel_main 符号
nm build/kernel.elf | grep kernel_main

# 检查调用指令
objdump -d build/kernel.elf | grep "call.*kernel_main"

# 检查链接是否包含 C 目标文件
ld -m elf_x86_64 -T linker.ld -o kernel.elf \
    kernel_entry.o kernel_main.o  # 确保有 kernel_main.o
```

### 场景 3：Triple Fault

**症状**：QEMU 立即退出

**排查**：

```bash
# 最可能是栈问题
# 检查栈指针设置
objdump -d build/kernel_entry.o | grep "mov.*rsp"

# 检查栈对齐
objdump -d build/kernel_entry.o | grep "and.*-16"
```

## ⚠️ 注意

**GDB 调试内核的坑**：

1. **用 .elf 调试，不是 .bin** — .bin 没有符号信息
2. **QEMU 要加 -s -S** — -s 开 GDB 服务，-S 启动时暂停
3. **断点要设在代码加载后** — 链接脚本地址要对
4. **有些指令会跳过** — GDB 不支持某些特殊指令

## 验证清单

开发完成后，用这个清单验证：

- [ ] CMake 配置成功（`cmake -B build`）
- [ ] 内核编译无警告（`cmake --build build`）
- [ ] 链接成功（生成 kernel.elf 和 kernel.bin）
- [ ] 符号正确（`nm | grep kernel_main`）
- [ ] 入口点正确（`readelf -h | grep Entry`）
- [ ] QEMU 启动正常（`make run`）
- [ ] VGA 输出正确（看到 X 和 C）
- [ ] GDB 可以连接（`target remote :1234`）
- [ ] 断点工作（`break kernel_main`）
- [ ] 单步执行正常（`next`, `step`）
