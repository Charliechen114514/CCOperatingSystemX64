# 链接脚本与内存布局

上一篇我们用了 `linker.ld` 但没解释。这一篇我们彻底搞懂它，因为这是理解程序如何加载和运行的关键。

---

## 什么是链接脚本

说实话，链接脚本这个东西，很多人写了很多年代码，但从来没真正理解过。它在幕后默默工作，出了问题才被人想起。

**你可以把链接脚本理解为给链接器的"装修说明书"。**

编译器把每个源文件编译成 `.o` 目标文件，但这些目标文件还不是可以执行的程序。链接器要把这些 `.o` 文件拼成一个完整的程序。**拼在哪里？按什么顺序？哪些段放在哪里？数据如何对齐？** 这些都是链接脚本决定的。

没有链接脚本，链接器会用默认布局。但那个布局是为普通程序设计的，不适合裸机编程。普通程序有操作系统加载器，会把代码加载到合适的地址，设置好各种段。但我们没有操作系统，一切都要自己来。

### 为什么我们需要链接脚本

我来列举几个具体的原因，这样你更容易理解。

首先，**指定加载地址**。我们的内核必须加载到 0x10000，因为 bootloader 是这样跳转的。如果链接器用默认地址（通常是 0x400000），bootloader 跳转就会跑到错误的地方。

其次，**控制段顺序**。我们希望代码段、只读数据段、已初始化数据段、未初始化数据段的顺序是固定的。这样内存布局清晰，也方便调试。

第三，**导出符号**。我们之前在汇编代码里用了 `__bss_start` 和 `__bss_end`，这些符号是在链接脚本里定义的。没有链接脚本，汇编代码就不知道 BSS 段在哪里。

最后，**丢弃无用段**。编译器会生成一些我们不需要的段，比如 `.comment`（编译器版本）、`.eh_frame`（异常处理帧）。这些段会占用空间，我们可以通过链接脚本把它们丢弃。

## linker.ld 逐段解析

现在我们来看完整的链接脚本。不要被它的长度吓到，我们一段一段来拆解。

### 完整的链接脚本

```ld
/* CCOS Kernel Linker Script */
/* Kernel is loaded at 0x10000 by bootloader */

ENTRY(kernel_start)

SECTIONS
{
    /* Kernel starts at 0x10000 */
    . = 0x10000;

    /* Text section - code */
    .text : {
        *(.text)
        *(.text.*)
    }

    /* Read-only data */
    .rodata : {
        *(.rodata)
        *(.rodata.*)
    }

    /* Initialized data */
    .data : {
        *(.data)
        *(.data.*)
    }

    /* Uninitialized data */
    .bss : {
        __bss_start = .;
        *(.bss)
        *(.bss.*)
        *(COMMON)
        __bss_end = .;
    }

    /* Discard sections we don't need */
    /DISCARD/ : {
        *(.comment)
        *(.eh_frame)
        *(.note.gnu.build-id)
    }
}
```

### ENTRY 声明

```ld
ENTRY(kernel_start)
```

这行代码告诉链接器：**程序的入口点是 `kernel_start` 这个符号**。

这个符号在 `kernel_entry.asm` 里定义：

```nasm
global kernel_start
kernel_start:
    cli
    ...
```

如果没有 `ENTRY`，链接器会尝试自己找一个入口点。通常是第一个出现的 `.text` 段符号，这可能不是我们想要的。而且如果没有明确的入口点，某些工具（如 GDB）可能会困惑。

### SECTIONS 块

```ld
SECTIONS
{
    ...
}
```

所有段定义都在这个块里。`SECTIONS` 是链接脚本的命令，告诉链接器："接下来我要定义内存布局了"。在这个块之外，你可以定义符号、变量，但不能定义段。

### 设置加载地址

```ld
. = 0x10000;
```

这个点的含义很有意思，而且容易让人困惑。

`.` 是**位置计数器**（Location Counter），表示"当前放到了哪里"。你可以把它想象成一个指针，指向下一个要放置内容的内存地址。对位置计数器赋值，就是把位置计数器移动到指定地址。

**`. = 0x10000`** 的含义是："把位置计数器设为 0x10000，后面的代码都从这个地址开始放"。

为什么是 0x10000？这是我们的 bootloader 决定的。bootloader 这样加载内核：

```nasm
; bootloader.asm
mov ax, 0x1000
mov es, ax          ; ES:BX = 0x1000:0000 = 0x10000
mov bx, 0
call load_kernel
```

所以内核必须链接到 0x10000，否则跳转会错位。如果你改了 bootloader 的加载地址，链接脚本也要跟着改。这两个地方必须一致，否则程序会跑飞。

### .text 段（代码）

```ld
.text : {
    *(.text)
    *(.text.*)
}
```

这段代码定义了 `.text` 段，也就是代码段。所有可执行代码都放在这里。

语法解释：`.text :` 定义一个叫 `.text` 的段。`*(.text)` 表示"把所有输入文件的 `.text` 段放进来"。`*(.text.*)` 把所有 `.text.*` 的段也放进来（比如 `.text.hot`、`.text.unlikely`、`.text.startup` 等，这些是编译器生成的特殊段）。

这里的 `*` 是通配符，匹配所有输入文件。链接器会遍历所有输入文件，把它们的 `.text` 段合并到输出的 `.text` 段。

### .rodata 段（只读数据）

```ld
.rodata : {
    *(.rodata)
    *(.rodata.*)
}
```

`.rodata` 段存放只读数据。什么是只读数据？常量、字符串字面量等。比如：

```c
const char *msg = "Hello";  // "Hello" 在 .rodata
const int config = 42;      // config 在 .rodata
```

只读数据段的特点是：程序运行时不能修改这些数据。如果尝试修改，会触发页错误（当然，我们还没开启分页，所以暂时不会出错）。把这些数据放在单独的段，可以让多个进程共享同一份代码（因为它们是只读的）。

### .data 段（已初始化数据）

```ld
.data : {
    *(.data)
    *(.data.*)
}
```

`.data` 段存放已初始化的全局变量和静态变量。比如：

```c
int count = 0;           // 在 .data
char buffer[1024] = {1, 2, 3};  // 在 .data
```

这些变量有明确的初始值，需要在程序加载时被设置。和 `.rodata` 不同，`.data` 段的数据是可修改的。

### .bss 段（未初始化数据）

```ld
.bss : {
    __bss_start = .;
    *(.bss)
    *(.bss.*)
    *(COMMON)
    __bss_end = .;
}
```

`.bss` 段存放未初始化的全局变量和静态变量。比如：

```c
int uninitialized_var;   // 在 .bss
char buffer[4096];       // 在 .bss
static int state;        // 在 .bss
```

**BSS 有一个非常特殊的性质：它不占文件空间。**

你可能会奇怪：如果不占文件空间，那这些变量怎么存在？答案是：BSS 段只记录大小和位置，不记录内容。程序加载时，加载器看到 BSS 段，会分配内存并清零，但不会从文件读取任何内容。

这就是为什么我们需要手动清零 BSS。虽然加载器会分配空间，但不保证清零。我们在汇编入口用 `rep stosq` 清零 BSS，就是为了确保这些变量是 0。

**符号导出**：

```ld
__bss_start = .;
...  /* BSS 内容 */
__bss_end = .;
```

`__bss_start` 和 `__bss_end` 是两个符号，记录 BSS 段的起止地址。汇编代码用它们来清零 BSS：

```nasm
mov rdi, __bss_start
mov rcx, __bss_end
sub rcx, rdi    ; BSS 大小
...             ; 清零
```

这种技术非常常用。链接脚本定义符号，汇编或 C 代码引用符号，这样可以跨越语言的边界，传递运行时信息。

### /DISCARD/ 段

```ld
/DISCARD/ : {
    *(.comment)
    *(.eh_frame)
    *(.note.gnu.build-id)
}
```

`/DISCARD/` 是一个特殊的段名，告诉链接器：**这些段直接扔掉，不要放进输出文件**。

我们丢弃了哪些段？

`.comment` 包含编译器版本信息，比如 "GCC: (Ubuntu 11.3.0-1ubuntu1~22.04) 11.3.0"。这些信息对调试没用，只会增加文件大小。

`.eh_frame` 包含异常处理帧，用于 C++ 异常和栈回溯。我们不需要异常（内核里用异常很危险），也不需要栈回溯（我们有更好的调试方法），所以丢弃。

`.note.gnu.build-id` 包含构建 ID，是一个 160 位的 SHA1 哈希，用于唯一标识构建。这对动态链接和调试有用，但我们不需要。

丢弃这些段可以减小最终二进制的大小。对于 bootloader 和内核这种对大小敏感的程序，每一字节都很重要。

## 内存布局图解

让我们看看最终的内存布局。把抽象的概念具体化，会更容易理解。

```
地址范围          内容              说明
────────────────────────────────────────────────
0x7C00           Bootloader        BIOS 加载到这里
0x7E00           -                 512 字节

0x10000          内核 .text        代码段
0x1xxxx          内核 .rodata      只读数据
0x1xxxx          内核 .data        已初始化数据
0x1xxxx          内核 .bss         未初始化数据
约 0x7FFFF       内核结束

0x80000          栈顶              向下增长
0xB8000          VGA 缓冲区        文本模式显示
```

**内核大小约 448KB**（0x10000 到 0x7FFFF）。栈在内核后面，从 0x80000 向下增长。VGA 缓冲区在 0xB8000，是硬件固定的地址，我们无法改变。

你可能会问：为什么内核和 VGA 之间有这么多空白空间？这是为了扩展性。如果内核将来变大，有足够的空间增长。而且 VGA 地址是硬件固定的，我们无法移动它，只能围绕它来规划内存布局。

## 验证工具

链接脚本写对了没有？用工具验证一下。不要相信"感觉"，要相信"数据"。

### objdump - 查看段信息

```bash
objdump -h build/kernel.elf
```

**你会看到类似这样的输出**：

```
Sections:
Idx Name          Size      VMA       LMA       File off  Algn
  0 .text         00000120  00010000  00010000  00000100  2**4
  1 .rodata       00000000  00010120  00010120  00000120  2**0
  2 .data         00000000  00010120  00010120  00000120  2**0
  3 .bss          00000004  00010120  00010120  00000120  2**2
```

**关键信息**：

- `VMA` (Virtual Memory Address) = 0x10000，正确！这是虚拟地址，也就是程序运行时的地址。
- `LMA` (Load Memory Address) = 0x10000，正确！这是加载地址，也就是程序在内存中的实际位置。
- `.bss` 的 `File off` 和前面的段一样，说明不占文件空间。如果 `.bss` 占用文件空间，`File off` 会更大。

### readelf - 查看符号

```bash
nm build/kernel.elf | grep __bss
```

**你会看到**：

```
0000000000010120 B __bss_end
0000000000010120 A __bss_start
```

`B` 表示 BSS 段符号，`A` 表示绝对符号（Absolute）。`__bss_start` 和 `__bss_end` 的地址都是 0x10120，说明 BSS 段是空的（因为没有未初始化的全局变量）。

### readelf - 查看入口点

```bash
readelf -h build/kernel.elf | grep Entry
```

**你会看到**：

```
Entry point address: 0x10000
```

正确！入口点和链接脚本的 `ENTRY(kernel_start)` 一致。如果入口点不是 0x10000，说明 `ENTRY` 声明有问题，或者 `kernel_start` 符号找不到。

## ⚠️ 常见坑点

这里有几个常见的坑点，我提前说一下，免得你踩进去。

### 入口点找不到

```
ld: warning: cannot find entry symbol _start; defaulting to 0000000000010000
```

这个错误的意思是：链接器找不到 `kernel_start` 符号。可能的原因：

1. `kernel_entry.asm` 里有 `global kernel_start` 吗？如果没有，符号不会被导出。
2. 链接命令包含 `kernel_entry.o` 吗？如果没有，链接器看不到这个符号。
3. 符号名称拼写正确吗？注意大小写，汇编符号是大小写敏感的。

### BSS 符号未定义

```
kernel_entry.asm: undefined reference to `__bss_start'
```

这个错误的意思是：链接脚本没定义 `__bss_start` 符号。检查一下链接脚本的 `.bss` 段里是否有 `__bss_start = .;` 这一行。注意等号两边有空格，没有空格也行，但风格不一致容易出错。

### 地址不一致问题

这个问题非常隐蔽，但很致命。所有地方的地址必须一致：

| 位置 | 地址 | 说明 |
|------|------|------|
| bootloader 加载地址 | 0x10000 | `mov ax, 0x1000` |
| 链接脚本加载地址 | 0x10000 | `. = 0x10000` |
| QEMU 内存布局 | 0x10000 | 内核应该在的地方 |

**任何一个地方不一致，程序就会跑飞。** 你可能看到 QEMU 启动，但屏幕全黑，或者显示乱码，或者立即崩溃。排查起来非常困难，因为看起来代码没问题，就是地址不对。

建议在代码里加一些检查，比如汇编入口输出一个字符，C 入口输出另一个字符。如果只看到第一个，说明跳转地址不对。

### 段对齐问题

某些架构要求段必须特定对齐，比如页对齐（4KB）。x86_64 的要求相对宽松，但如果你看到对齐错误，可能是链接脚本的 `ALIGN` 没设置对。可以在段定义里加 `ALIGN(16)` 或其他对齐值。

## 实战示例：添加一个新段

假设你想添加一个自定义段，比如把启动时的配置数据放在单独的段。怎么做？

首先，在 C 代码里定义段：

```c
__attribute__((section(".bootconfig")))
const boot_config_t boot_config = {
    .magic = 0xCC00CC00,
    .version = 1,
};
```

然后，在链接脚本里定义这个段：

```ld
.bootconfig : {
    *(.bootconfig)
} :data
```

`:data` 表示这个段和 `.data` 段有相同的属性（可读写）。这样链接器就知道怎么处理这个段了。

这种技术非常实用。你可以把不同类型的数据放在不同的段，方便管理和调试。比如把日志缓冲区放在专门的段，方便提取日志。
