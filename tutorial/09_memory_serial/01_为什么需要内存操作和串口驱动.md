# 01 - 为什么需要内存操作和串口驱动

说实话，有段时间我几乎要放弃用 VGA 屏幕来调试内核了。

---

## 我们现在在哪里

如果你一路跟着前面的教程走过来，我们现在在 `stage/08_string_utils`。这个阶段我们实现了字符串工具函数，内核已经能正常输出一些信息到 VGA 屏幕。

看起来一切都很美好，对吧？直到你开始写更复杂的代码。

### 那个让我血压拉高的夜晚

记得有一次，我在调试一个内核崩溃问题。内核在某个特定条件下会触发 triple fault，然后 QEMU 直接重启。我盯着 VGA 屏幕，看到最后输出的消息是 "Entering protected mode..."，然后就是黑屏。

问题来了——崩溃的消息到底在哪里？是 VGA 屏幕滚动太快，把错误信息卷上去了？还是内核在能输出任何东西之前就已经炸了？

我试着在怀疑的每个地方都加上 `print`，但每次修改都要重新编译、启动 QEMU，然后眼睁睁看着消息再次滚动过去。折腾了四个小时，最后还是靠在 Bochs 里单步执行才找到问题——一个指针计算错误导致访问了未映射的内存。

那一刻我就在想：**难道就没有更好的办法吗？**

如果我能把所有输出都保存到一个文件里，如果我能从启动的第一条指令就开始记录日志，如果我能一边盯着 VGA 屏幕一边在终端里看串口输出……这些问题根本不是问题。

---

## 当前阶段的两大痛点

### 痛点一：没有标准 C 库的日子不好过

在 freestanding 环境下，我们没有标准 C 库的支持。这意味着什么？意味着每次要操作内存，你都得自己写一坨循环代码。

```c
// 想清空一块内存？没有 memset，你要自己写循环。
for (int i = 0; i < 100; i++) {
    buffer[i] = 0;
}

// 想拷贝一块内存？没有 memcpy，又要自己写循环。
for (int i = 0; i < 100; i++) {
    dest[i] = src[i];
}
```

这还不算什么。真正麻烦的是当你需要初始化一个结构体数组，或者需要比较两块内存是否相同时。每次都写这些循环代码，不仅啰嗦，还容易出错。

更糟糕的是，你可能根本没意识到自己写错了。比如，当你想要拷贝两块重叠的内存时，从前向后拷贝会覆盖掉还没拷贝的数据。这种 bug 只有在特定条件下才会触发，找起来让人头疼。

### 痛点二：VGA 输出真的不够用

VGA 文本模式（80x25 字符）看起来简单直接，但在实际调试中有几个致命缺陷。

**首先，信息会丢失**。VGA 屏幕只有 2000 个字符的位置，一旦滚动，之前的输出就再也找不回来了。你可能会说："那就把滚动速度调慢点"，但问题是你不知道什么时候会触发崩溃，重要的消息可能就在你眨眼的瞬间滚过去了。

**其次，启动早期的输出难以捕获**。在 Bootloader 刚开始执行的时候，VGA 还可能没初始化好。就算初始化了，那时候屏幕上还是 BIOS 的自检信息，你的输出混杂在里面很难分辨。

**最致命的是，VGA 在进入保护模式后就麻烦了**。虽然理论上可以在保护模式继续写 VGA 显存，但你需要处理段选择子、分页等问题。而一旦进入长模式，VGA 的 I/O 端口地址可能还需要重新配置。

相比之下，串口在这些方面就友好太多了。

串口输出可以被重定向到文件，你可以事后慢慢分析；串口可以从 Bootloader 的第一条指令就开始工作，无论是什么 CPU 模式；串口还支持完整的 ANSI 转义序列，你可以用颜色高亮错误信息、加粗关键数据。

---

## 串口为什么这么重要

你可能会问：都 2026 年了，谁还用串口？

这是个好问题。串口确实是个古老的技术，起源于 1960 年代，但它至今仍然广泛存在。

**在服务器领域**，基板管理控制器（BMC，如 IPMI）几乎都通过串口提供调试接口。当服务器操作系统死机时，管理员可以通过串口访问 BMC，查看硬件状态、重启机器，甚至远程安装系统。

**在嵌入式开发中**，串口更是标配。很多嵌入式设备没有显示输出，串口是唯一的调试手段。

**在虚拟化环境中**，QEMU、VMware 等虚拟机软件都支持串口重定向。你可以把虚拟机的串口输出重定向到主机的文件或网络端口，实现日志收集。

这就是为什么我们需要实现串口驱动——它不仅是调试工具，更是通往专业系统开发的桥梁。

## 我们要达成的目标

在这个阶段（`stage/09_memory_serial`），我们要完成两件大事。

### 第一件事：实现标准 C 内存操作函数

我们需要实现四个函数：`memset`、`memcpy`、`memmove`、`memcmp`。

`memset` 用于填充内存块，这在初始化结构体、清零缓冲区时非常有用。`memcpy` 用于快速拷贝内存，但要注意它不支持重叠区域——这时候就需要用 `memmove`。`memcmp` 用于比较两块内存是否相同，在数据校验时很常用。

这些函数看起来简单，但实现起来有不少细节需要注意。比如 `memmove`，当源和目标内存重叠时，你需要判断拷贝方向，否则就会覆盖掉还没拷贝的数据。

### 第二件事：实现 UART 16550 串口驱动

UART 16550 是 PC 标准的串口控制器，自 1980 年代以来就存在。它的特点是兼容性极好，所有 PC 都支持。

我们会实现串口的初始化、字符输出、字符串输出。配置为 115200 波特率、8 数据位、无校验、1 停止位（8N1）——这是最通用的配置。

实现之后，我们就能在内核和 Bootloader 中使用串口输出，所有调试信息都能被记录和分析。

### 前后对比

完成这个阶段后，我们的内核会有哪些变化？

在 stage/08，我们只有 VGA 输出，没有内存操作函数，调试全靠眼睛看。在 stage/09，我们将拥有完整的内存操作函数、串口驱动、主机端测试框架。调试输出可以从 Bootloader 的第一条指令开始记录，串口日志可以保存到文件，我们还能用 ANSI 颜色高亮不同级别的消息。

这不是小改进，这是开发体验的质的飞跃。

## 在开始之前

在正式开始之前，请确保你的 stage/08 能正常编译和运行。

如果你在 stage/08 还有未解决的问题，先回去修好它。我们是在一个能工作的系统基础上添加新功能，不是在一堆问题上叠加新东西——那样只会让调试变得更加困难。

验证一下：

```bash
cd /path/to/CCOperatingSystemX64

# 配置构建
cmake -B build -DCMAKE_BUILD_TYPE=Debug

# 构建
cmake --build build

# 运行
qemu-system-x86_64 -drive format=raw,file=build/boot.img
```

你应该能看到 QEMU 窗口启动，并且屏幕上有内核的输出。

### 环境准备验证

虽然大部分工具在前面的阶段已经装好了，但我们再确认一遍：

```bash
# 检查编译器
gcc --version
# 输出：gcc (Ubuntu xx.x.x.x) xx.x.x

# 检查 nasm
nasm -v
```

```bash
brew install gcc nasm cmake qemu
```

## 我们即将要做的

在接下来的几个文档中，我们会一步步完成内存操作和串口驱动的实现。

首先，我们会从零实现标准 C 内存函数。这不仅仅是写四个函数，我们还会搭建一个主机端测试环境，让我们能在开发机上直接测试这些函数，而不需要每次都启动 QEMU。

然后，我们会封装 x86 的端口 I/O 操作。这是串口驱动的基础，我们会使用内联汇编直接操作硬件。

接下来是 UART 16550 串口驱动的完整实现。你会了解到串口的历史、寄存器结构、初始化流程，以及为什么有些配置必须按照特定顺序执行。

之后，我们会在内核中集成串口输出，让内核能够同时输出到 VGA 和串口。

再之后，我们会在 Bootloader 中添加串口支持。这有点挑战性，因为 Bootloader 经历实模式、保护模式、长模式三个阶段，每个模式的寄存器和调用约定都不同。

最后，我们会学习如何配置 QEMU 的串口重定向、如何运行测试、如何调试问题。

每一步都是独立的，你可以跟着做一部分，也可以全部做完。相信我，等你完整实现之后，你会感谢现在努力的自己。
