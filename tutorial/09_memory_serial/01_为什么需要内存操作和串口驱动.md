# 01 - 为什么需要内存操作和串口驱动

说实话，一直用 print 大法调试内核，真的绷不住了。

---

## 我们现在在哪里

如果你一路跟着前面的教程走过来，我们现在在 `stage/08_string_utils`。这个阶段我们实现了字符串工具函数，内核已经能正常输出一些信息到 VGA 屏幕。

但是，当你开始写更复杂的代码时，你会发现几个让人血压拉满的问题：

**想清空一块内存？没有 memset，你要自己写循环。**

**想拷贝一块内存？没有 memcpy，又要自己写循环。**

**想看看内核启动时发生了什么？只能盯着 VGA 屏幕，一旦屏幕滚动太快，前面的信息就没了。**

**想调试一个 crash？没有串口日志，你只能靠猜。**

这些事情经历几次之后，你肯定会问自己：

> "难道就没有更好的办法吗？"

---

## 当前阶段的两大痛点

### 痛点一：缺少标准 C 内存函数

在 freestanding 环境下，我们没有标准 C 库的支持。这意味着：

```c
// 这些函数都不能直接用！
memset(ptr, 0, 100);       // ❌ 未定义
memcpy(dest, src, n);      // ❌ 未定义
memmove(dest, src, n);     // ❌ 未定义
memcmp(a, b, n);           // ❌ 未定义
```

每次要操作内存，你都得自己写一坨循环代码。不仅啰嗦，还容易出错。

### 痛点二：调试输出太原始

我们现在只有 VGA 输出。VGA 有几个致命的调试缺陷：

| 问题 | VGA | 串口 |
|------|-----|------|
| 输出会消失 | 屏幕滚动后就没了 | 可以重定向到文件保存 |
| 启动早期输出 | 难以捕获（从第一条指令就开始） | 可以从 Bootloader 开始记录 |
| 远程调试 | 不可能 | 可以通过网络 |
| 颜色支持 | 有限 | 完整 ANSI 颜色 |
| 自动化测试 | 无法捕获输出 | 可以捕获和分析 |

更重要的是，**VGA 在实模式下才能输出**，一旦进入保护模式或长模式，输出就变得麻烦。而串口在所有模式下都能工作。

---

## 我们要达成的目标

在这个阶段（`stage/09_memory_serial`），我们要完成两件大事：

### 1. 实现标准 C 内存操作函数

| 函数 | 功能 | 为什么需要 |
|------|------|------------|
| memset | 填充内存块 | 初始化结构体、清零缓冲区 |
| memcpy | 拷贝内存块（非重叠） | 快速数据传输 |
| memmove | 拷贝内存块（支持重叠） | 安全的内存拷贝 |
| memcmp | 比较内存块 | 数据比较、验证 |

### 2. 实现 UART 16550 串口驱动

串口驱动会给我们带来：

- ✅ **从 Bootloader 开始的完整启动日志**
- ✅ **可以保存到文件的调试输出**
- ✅ **ANSI 颜色支持**（高亮错误信息）
- ✅ **在所有 CPU 模式下都能工作**

### 前后对比

| 特性 | stage/08 | stage/09 (本阶段) |
|-----|----------|------------------|
| memset | 无 | ✅ |
| memcpy | 无 | ✅ |
| memmove | 无 | ✅ |
| memcmp | 无 | ✅ |
| 串口驱动 | 无 | ✅ UART 16550 |
| Bootloader 串口 | 无 | ✅ 全模式支持 |
| 单元测试 | 无 | ✅ 主机端测试 |
| 调试输出 | 仅 VGA | VGA + 串口 |

## ⚠️ 注意

**在开始之前，请确保你的 stage/08 能正常编译和运行。**

如果你在 stage/08 还有未解决的问题，先回去修好它。我们是在一个能工作的系统基础上添加新功能，不是在一堆问题上叠加新东西。

验证一下：

```bash
cd /path/to/CCOperatingSystemX64

# 配置构建
cmake -B build -DCMAKE_BUILD_TYPE=Debug

# 构建
cmake --build build

# 运行
qemu-system-x86_64 -drive format=raw,file=build/boot.img
```

你应该能看到 QEMU 窗口启动，并且屏幕上有内核的输出。

```bash

brew install gcc nasm cmake qemu
```
