# 03 - 端口 I/O 操作封装

在 x86 架构上，访问硬件设备有两种方式：内存映射 I/O 和端口 I/O。串口使用的是端口 I/O，所以我们需要先封装好端口操作。

---

## 我们现在要做什么

我们需要实现两个核心函数：

```c
uint8_t inb(uint16_t port);   // 从端口读取一个字节
void outb(uint16_t port, uint8_t data);  // 向端口写入一个字节
```

这两个函数会直接使用 x86 的 `in` 和 `out` 指令，是串口驱动的基础。

但在这之前，我们需要理解为什么 x86 有两套不同的 I/O 体系，以及为什么需要用 `volatile` 关键字。

---

## 第一步 —— 理解端口 I/O 的历史

在现代计算机体系结构中，CPU 与外设通信主要有两种方式：内存映射 I/O（Memory-Mapped I/O, MMIO）和端口映射 I/O（Port-Mapped I/O, PMIO）。

**内存映射 I/O** 把设备寄存器映射到物理内存地址空间，CPU 用普通的 `mov` 指令就能访问。这种方式在 ARM、MIPS、RISC-V 等架构上是主流。

**端口映射 I/O** 则有独立的 I/O 地址空间，CPU 必须用专门的 `in`/`out` 指令访问。这是 x86 架构的特色——或者说，历史遗留。

为什么 x86 要这样设计？这得从 1970 年代说起。

当年的 Intel 8080 CPU 只有 16 位地址线，能寻址 64KB 内存。如果还要把设备寄存器塞进这个地址空间，那就更不够用了。所以 Intel 设计了独立的 I/O 空间，用 `in`/`out` 指令访问，不占用内存地址。

到了 1981 年，IBM PC 发布，使用了 Intel 8088 CPU（8086 的 8 位总线版本）。PC 的设计延续了端口 I/O 的传统，串口、并口、键盘控制器等设备都分配了 I/O 端口地址。

虽然现代 x86 CPU 有 64 位地址空间，完全可以用内存映射 I/O，但为了兼容性，端口 I/O 一直保留至今。这就是为什么我们今天还要学习 `in`/`out` 指令——为了访问那些传统的设备。

串口设备位于 I/O 端口空间，COM1 的基地址是 `0x3F8`。这几乎是 PC 行业的标准，从 1981 年到现在就没变过。

## 第三步 —— 实现端口 I/O 函数

我们先来看最简单的实现，然后逐步解释每个细节。

创建头文件 `kernel/driver/io/io.h`：

```c
/**
 * @file io.h
 * @brief x86 Port I/O operations
 */
#pragma once

#include "defines/types.h"

/**
 * @brief Read one byte from the specified port
 * @param port Port number (0-65535)
 * @return Byte read from port
 */
uint8_t inb(uint16_t port);

/**
 * @brief Write one byte to the specified port
 * @param port Port number (0-65535)
 * @param data Byte to write
 */
void outb(uint16_t port, uint8_t data);
```

创建实现文件 `kernel/driver/io/io.c`：

```c
#include "io.h"

// Port I/O functions (will be inlined by compiler)
uint8_t inb(uint16_t port) {
    uint8_t result;
    __asm__ volatile("inb %1, %0" : "=a"(result) : "Nd"(port));
    return result;
}

void outb(uint16_t port, uint8_t data) {
    __asm__ volatile("outb %0, %1" : : "a"(data), "Nd"(port));
}
```

代码很短，但每一行都有讲究。

---

## 第四步 —— 理解内联汇编

这里我们使用 GCC 内联汇编，让我逐行解释 `inb` 函数：

```c
__asm__ volatile("inb %1, %0" : "=a"(result) : "Nd"(port));
//      ^        ^            ^           ^
//      |        |            |           |
//    volatile  汇编模板    输出操作数   输入操作数
```

**汇编模板部分**：`"inb %1, %0"`

这是我们要 GCC 生成的汇编指令。`%0` 和 `%1` 是占位符，分别对应输出和输入操作数。`inb` 指令的格式是 `inb 端口, 目标`，所以 `%1` 是端口，`%0` 是目标。

**输出操作数部分**：`"=a"(result)`

这部分告诉 GCC：汇编的结果要输出到 `result` 变量，而且 `result` 必须放在 `a` 寄存器中。`=` 表示这是只写输出。

在 x86 上，`a` 寄存器根据整数大小自动选择：
- 对于 8 位操作数：AL 寄存器
- 对于 16 位操作数：AX 寄存器
- 对于 32 位操作数：EAX 寄存器
- 对于 64 位操作数：RAX 寄存器

因为 `result` 是 `uint8_t` 类型，GCC 会自动使用 AL 寄存器。

**输入操作数部分**：`"Nd"(port)`

这部分告诉 GCC：`port` 变量是输入，而且必须满足 `Nd` 约束。

- `N`：表示这是一个 0-255 之间的立即数
- `d`：表示使用 DX 寄存器

所以 `Nd` 的意思是：如果 `port` 是编译时常量且在 0-255 范围内，直接编码成立即数；否则，使用 DX 寄存器。

为什么要这样？因为 `inb` 指令的端口操作数只能是立即数（0-255）或 DX 寄存器。这是硬件决定的，不是我们能改变的。

### outb 函数的分解

```c
__asm__ volatile("outb %0, %1" : : "a"(data), "Nd"(port));
//                     ^           ^
//                     |           |
//               没有输出      两个输入
```

`outb` 指令的格式是 `outb 数据, 端口`，所以：
- `%0` = `data`（在 AL 寄存器中）
- `%1` = `port`（立即数或 DX 寄存器）

注意到这里没有输出操作数，所以输出操作数部分是空的，只有一个冒号。

## 第五步 —— 为什么需要 volatile

这是一个非常重要的坑点。很多人第一次写端口 I/O 代码时，都会忘记加 `volatile`，然后发现代码不工作。

让我们看看没有 `volatile` 会发生什么：

```c
// 没有 volatile 的版本
uint8_t inb_bad(uint16_t port) {
    uint8_t result;
    __asm__("inb %1, %0" : "=a"(result) : "Nd"(port));
    return result;
}
```

这段代码看起来没问题，但 GCC 的优化器可能会把它优化成这样：

```asm
inb_bad:
    xor eax, eax      ; 直接返回 0，完全跳过了 inb 指令！
    ret
```

为什么会这样？让我们从编译器的角度思考。

编译器看到这段代码时，它不知道 `inb` 指令有副作用。它只看到：
1. `inb` 指令的输入是 `port`
2. `inb` 指令的输出存到 `result`
3. `result` 被返回

如果在某个优化级别下，编译器发现 `result` 的值没有被使用（比如调用者没有检查返回值），它可能会认为这个函数没有任何作用，直接删除整个函数。

即使 `result` 被使用了，编译器也可能会认为多次调用 `inb_bad(port)` 返回相同的值，然后把调用优化成只调用一次。这对于内存读取可能是对的，但对于 I/O 端口来说是完全错误的——端口读取可能每次返回不同的值（比如读取串口接收到的数据）。

**`volatile` 的作用就是告诉编译器：这条指令有副作用，绝对不能删除或重排。**

```c
// 有 volatile 的版本
__asm__ volatile("inb %1, %0" : "=a"(result) : "Nd"(port));
```

加上 `volatile` 后，编译器保证：
1. 这条指令一定会被执行
2. 这条指令不会被移动到其他位置（除非必要）
3. 多次调用不会合并成一次

对于 I/O 操作来说，这些都是必需的。副作用就是"读写硬件设备"，这在 C 代码中是看不见的，编译器也无法推断。

### volatile 的其他用途

`volatile` 在内核开发中还有很多用途。比如：

1. **内存映射的设备寄存器**：虽然我们用的是端口 I/O，但很多设备（如 VGA 显存）使用内存映射 I/O。访问这些寄存器时也需要 `volatile`。

2. **多线程共享变量**：在没有锁保护的情况下，多个 CPU 可能同时访问某个变量。用 `volatile` 可以确保每次都从内存读取，而不是使用寄存器中的缓存值。

3. **信号处理程序中的变量**：信号处理程序可能修改主程序的变量，这些变量需要声明为 `volatile`。

在我们的内核中，端口 I/O 是最常见需要 `volatile` 的场景。

## 第六步 —— 端口 I/O 时序考虑

在现代 CPU 上，`in` 和 `out` 指令还有一些特殊的时序行为，值得了解。

**I/O 指令是串行化指令**

在 x86 上，`in` 和 `out` 指令会串行化执行。这意味着 CPU 会等待所有之前的指令完成，然后执行 I/O 指令，之后才执行后面的指令。

这很重要，因为硬件设备的操作往往有严格的时序要求。比如，你必须先写命令寄存器，然后再写数据寄存器。如果这两个写操作的顺序被颠倒，设备可能不会正确响应。

**现代 CPU 的乱序执行**

现代 CPU 会乱序执行指令以提高性能。比如，CPU 可能会先执行后面的指令，再执行前面的指令，只要结果正确就行。

但对于 I/O 指令来说，这会出问题。想象一下：你写了一个数据到端口，然后立即读取状态寄存器。如果 CPU 先执行读取，再执行写入，你会读到错误的状态。

幸好，`in` 和 `out` 指令天然串行化，不会有这个问题。但如果你用内存映射 I/O（比如通过 MMIO 访问 PCI 设备），就需要显式使用内存屏障（memory barrier）指令。

**I/O 指令的性能开销**

由于串行化的特性，I/O 指令的性能开销比较大。每次执行 I/O 指令，CPU 都要刷新流水线，等待之前的指令完成。

在串口初始化时，我们需要连续执行多个 `outb` 指令。这些指令无法并行执行，所以初始化速度比较慢。但对于初始化这种只执行一次的操作来说，这不是问题。

真正需要关注的是 `sync_serial_putc` 中的忙等待循环：

```c
while ((inb(SERIAL_LINE_STATUS_REG(base)) & SERIAL_LSR_READY_TO_SEND) == 0) {
    // 忙等待
}
outb(SERIAL_DATA_REG(base), (uint8_t)c);
```

这个循环会反复读取 LSR 寄存器，直到串口准备好发送。在等待期间，CPU 一直在执行 `inb` 指令，性能开销不小。

如果将来我们实现了中断驱动，就可以用中断代替轮询，CPU 就不用一直忙等待了。但那是后话，现在我们先用简单的轮询方式。

## 第八步 —— 验证内联汇编输出

让我们看看编译器实际生成了什么代码：

```bash
# 构建
cmake --build build

# 查看生成的汇编
objdump -d build/kernel/libdriver_io.a
```

你应该能看到类似这样的输出：

```asm
0000000000000000 <inb>:
   0:   55                      push   rbp
   1:   48 89 e5                mov    rbp,rsp
   4:   66 89 fa                mov    dx,di        ; port 参数放入 DX
   7:   ec                      in     al,dx         ; 读取端口
   8:   0f b6 c0                movzx  eax,al       ; 零扩展到 EAX
   b:   5d                      pop    rbp
   c:   c3                      ret
```

关键指令是 `in al,dx`，这就是我们的端口读取指令。注意 GCC 自动生成了 `mov dx,di`，因为我们的 `port` 参数在 `di` 寄存器中（System V AMD64 ABI 的第一个参数），而 `inb` 指令需要端口在 DX 寄存器中。

如果我们用常量调用 `inb`，比如 `inb(0x3F8)`，编译器会生成更高效的代码：

```asm
inb:
    ec                      in     al, 0x3f8    ; 直接使用立即数
    c3                      ret
```

这就是 `Nd` 约束的好处：编译器会自动选择最优的方式。

## 第九步 —— 常见陷阱

### 陷阱 1：忘记 volatile

```c
// ❌ 错误：可能被编译器优化掉
__asm__("inb %1, %0" : "=a"(result) : "Nd"(port));

// ✅ 正确：保证指令执行
__asm__ volatile("inb %1, %0" : "=a"(result) : "Nd"(port));
```

这个坑最容易踩。如果你发现 I/O 操作"不工作"，首先检查有没有加 `volatile`。

### 陷阱 2：错误的寄存器约束

```c
// ❌ 错误：端口必须在 DX 或立即数
__asm__ volatile("inb %1, %0" : "=a"(result) : "b"(port));

// ✅ 正确：使用 "Nd" 约束
__asm__ volatile("inb %1, %0" : "=a"(result) : "Nd"(port));
```

如果用错了约束，GCC 会报错或者生成错误的代码。务必查阅 GCC 文档，了解每个约束的含义。

### 陷阱 3：端口地址范围

I/O 端口是 16 位的，范围是 0-65535。

```c
// COM1 串口基地址
#define SERIAL_COM1 0x3F8  // ✅ 正确

#define SERIAL_COM1 0x3F800  // ❌ 错误：超过 16 位
```

如果你不小心定义了一个超过 16 位的端口地址，编译器可能不会报错，但生成的代码会是错误的。

### 陷阱 4：未初始化的端口

有些端口在硬件初始化之前是不能访问的。比如，如果你在 PCI 设备初始化之前就访问它的 MMIO 寄存器，可能会触发 triple fault。

好在 COM1 串口是传统设备，BIOS 在启动时已经初始化过了，所以我们能直接访问。但如果你将来要操作 PCI 设备，记得先初始化设备。

## 第十步 —— 与内存映射 I/O 的对比

虽然我们在这个项目中用的是端口 I/O，但了解一下内存映射 I/O 也有好处。

内存映射 I/O 把设备寄存器映射到内存地址空间，访问方式就像普通内存一样：

```c
// 假设 VGA 显存映射在 0xB8000
uint16_t* vga = (uint16_t*)0xB8000;
vga[0] = 0x0F20;  // 在第一个字符位置显示一个空格
```

这种方式的好处是：
1. 可以用任何访问内存的指令（`mov`、`lods`、`stos` 等）
2. 可以利用 CPU 的缓存预取和批量访问优化
3. 代码更简洁，不需要特殊的 I/O 指令

但也有缺点：
1. 需要小心缓存和内存对齐问题
2. 需要内存屏障来保证访问顺序
3. 在某些架构上（如 x86 的实模式）可能无法使用

端口 I/O 则相反：
1. 有独立的地址空间，不会和内存冲突
2. 天然串行化，时序有保证
3. 但只能用专门的 `in`/`out` 指令
4. 访问速度较慢（因为串行化）

在现代操作系统驱动开发中，内存映射 I/O 是主流。但对于嵌入式和传统设备（如串口），端口 I/O 仍然常见。

我们的串口驱动使用端口 I/O，因为：
1. COM1 是传统设备，端口地址固定（0x3F8）
2. 串口速度远慢于 CPU，I/O 指令的性能开销不是问题
3. 端口 I/O 更简单，不需要处理缓存和内存屏障
