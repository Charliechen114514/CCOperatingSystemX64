# 09 - 巨大页支持与对齐陷阱

说实话，第一次实现巨大页支持时，我花了一整晚的时间调试对齐问题。那些看似简单的"地址对齐"要求，实际上非常容易出错。

---

## 为什么要用巨大页

在我们深入实现之前，先来回顾一下为什么需要巨大页。TLB（Translation Lookaside Buffer）是 CPU 中缓存虚拟地址到物理地址转换的硬件，但它的容量是有限的，通常只有几十到几百个条目。

使用 4KB 页面时，一个 TLB 条目只能缓存 4KB 的映射。如果要覆盖 1GB 内存，需要 262144 个 TLB 条目，这远远超过了 TLB 的容量。使用 2MB 巨大页时，一个 TLB 条目可以缓存 2MB 的映射，覆盖 1GB 内存只需要 512 个 TLB 条目。使用 1GB 巨大页时，覆盖 1GB 内存只需要 1 个 TLB 条目。

除了减少 TLB 压力，巨大页还能减少页表内存占用。每个页表需要占用一个 4KB 的物理页。使用 4KB 页面时，映射 1GB 内存需要 262144 个页表项，这需要 512 个 4KB 页的页表（2MB）。使用 2MB 巨大页时，映射 1GB 内存只需要 512 个页表项，这只需要 1 个 4KB 页的页表。使用 1GB 巨大页时，映射 1GB 内存只需要 1 个页表项，完全不需要额外的页表。

减少 TLB Miss 的次数意味着更高的内存访问效率。对于需要访问大量内存的程序（如数据库、科学计算），巨大页可以带来显著的性能提升。

---

## x86_64 的两种巨大页

x86_64 支持两种巨大页：2MB 和 1GB。2MB 巨大页在 PD 级别设置 PS 位（位 7），虚拟地址和物理地址必须 2MB 对齐，适用于大多数场景。1GB 巨大页在 PDPT 级别设置 PS 位（位 7），虚拟地址和物理地址必须 1GB 对齐，适用于特殊场景（如大内存数据库）。

1GB 巨大页的对齐要求非常严格，很难满足。大多数情况下，2MB 巨大页已经足够了。

---

## 巨大页的映射差异

在之前文档中我们讲过，普通 4KB 页面需要遍历全部四级页表（PML4 → PDPT → PD → PT → 4KB 物理页），而巨大页可以在更早的级别停止。2MB 巨大页只需要遍历到 PD 级别（PML4 → PDPT → PD (PS=1) → 2MB 物理页），1GB 巨大页只需要遍历到 PDPT 级别（PML4 → PDPT (PS=1) → 1GB 物理页）。

在代码中，这体现在我们可以在 PD 或 PDPT 级别就停止遍历：

```c
/* Handle 1GB huge page mapping */
if (use_1gb) {
    pdpte->value = (paddr & PTE_ADDR_MASK) | pte_flags | PAGE_HUGE_PDPT;
    page_invalidate_tlb(vaddr);
    return PAGE_OK;
}

/* Handle 2MB huge page mapping */
if (use_2mb) {
    pde->value = (paddr & PTE_ADDR_MASK) | pte_flags | PAGE_HUGE_PD;
    page_invalidate_tlb(vaddr);
    return PAGE_OK;
}
```

---

## 对齐陷阱

巨大页最大的陷阱是对齐要求。硬件要求巨大页的虚拟地址和物理地址都必须按照页面大小对齐。在我们的实现中，我们对每个映射都进行对齐检查：

```c
/* Determine alignment requirements */
uint64_t page_size = PAGE_SIZE;
uint64_t page_align = PAGE_SIZE - 1;

if (use_1gb) {
    page_size = PAGE_SIZE_1GB;
    page_align = page_size - 1;
} else if (use_2mb) {
    page_size = PAGE_SIZE_2MB;
    page_align = page_size - 1;
}

/* Validate alignment */
if ((vaddr & page_align) != 0) {
    klog_error("[PAGE] Virtual address not aligned to %llu bytes: 0x%llX\n",
              page_size, vaddr);
    return PAGE_ERR_ALIGNMENT;
}
if ((paddr & page_align) != 0) {
    klog_error("[PAGE] Physical address not aligned to %llu bytes: 0x%X\n",
              page_size, paddr);
    return PAGE_ERR_ALIGNMENT;
}
```

对齐检查使用 `& (page_size - 1)` 而不是取模运算。这是因为 `page_size` 总是 2 的幂次方，位运算比除法快得多。

---

## 连续物理内存的分配

巨大页的另一个陷阱是物理内存的连续性要求。一个 2MB 巨大页需要一个连续的 2MB 物理内存块，一个 1GB 巨大页需要一个连续的 1GB 物理内存块。我们的物理帧分配器（pframe）每次只分配一个 4KB 的物理帧，不保证连续性。这意味着我们需要一个特殊的分配策略。

一种常见的策略是"分配-重试"：分配 2 倍大小的物理帧（比如对于 2MB 页，分配 4MB），在分配的范围内找到对齐的地址，然后释放对齐前后的多余帧。

```c
/* Allocate 2x size to find aligned boundary */
uint64_t frames_needed = page_size / PAGE_SIZE;
uint64_t alloc_frames = frames_needed * 2;

physical_addr_t temp_paddr;
pf_result = pframe_alloc_n(&temp_paddr, alloc_frames);

/* Find aligned address within allocated range */
physical_addr_t paddr = (temp_paddr + page_size - 1) & ~(page_size - 1);

/* Free frames before and after aligned region */
/* ... */
```

这个策略的缺点是可能会浪费物理内存。如果你分配 4MB 但只使用中间对齐的 2MB，会浪费掉对齐前后的内存。

## 测试巨大页映射

我们可以写一个测试来验证巨大页映射是否正常工作：

```c
/* Test 2MB huge page mapping */
void test_2mb_huge_page(void) {
    /* Allocate a 2MB aligned physical page */
    physical_addr_t paddr;
    /* TODO: Implement aligned allocation */
    paddr = 0x2000000;  /* Assume we have this address */

    /* Map a 2MB huge page */
    virtual_addr_t vaddr = 0xFFFFFFFF82000000;  /* 2MB aligned */

    page_result_t result = page_map_page(
        page_get_pml4(),
        vaddr,
        paddr,
        VMAP_FLAG_WRITE | VMAP_FLAG_HUGE_2MB,
        true
    );

    if (result == PAGE_OK) {
        klog_info("[TEST] 2MB huge page mapped successfully\n");

        /* Query to verify it's a huge page */
        page_query_result_t query;
        page_query(page_get_pml4(), vaddr, &query);

        if (query.is_huge) {
            klog_info("[TEST] Confirmed: This is a huge page mapping\n");
        }
    } else {
        klog_error("[TEST] Failed to map 2MB huge page\n");
    }
}
```

---

## 调试时可能会遇到的几种情况

如果对齐检查失败，这通常意味着虚拟地址或物理地址没有按照页面大小对齐。确保虚拟地址是 2MB 或 1GB 的倍数，物理地址也是 2MB 或 1GB 的倍数。

如果映射成功，但访问时触发页错误，这可能是因为物理内存不连续。检查物理帧分配器是否真的分配了连续的物理内存。

如果查询结果显示不是巨大页，检查 `page_map_page` 中是否正确设置了 `PAGE_HUGE_PD` 或 `PAGE_HUGE_PDPT` 标志。
