### 创建 CMakeLists.txt

和内核的其他模块一样，我们需要创建一个 `CMakeLists.txt` 文件来告诉构建系统如何编译这个模块。

```cmake
# kernel/mm/vmm/CMakeLists.txt

# VMM core module
set(VMM_SOURCES
    page.c
    vmm.c
    vmm_debug.c
    fault.c
)

# Create the VMM library
add_library(vmm STATIC ${VMM_SOURCES})
target_include_directories(vmm PUBLIC
    ${CMAKE_CURRENT_SOURCE_DIR}
    ${CMAKE_SOURCE_DIR}/kernel/base
    ${CMAKE_SOURCE_DIR}/kernel/mm
)

# Link with required modules
target_link_libraries(vmm
    pframe
    interrupt
    klogs
)
```

这个 CMakeLists.txt 定义了 VMM 模块的源文件，并设置好依赖关系。`pframe` 是物理帧管理器，`interrupt` 是中断系统，`klogs` 是日志系统——这些都是 VMM 需要依赖的模块。

## page.h 的整体设计

`page.h` 是页表管理模块的头文件，它定义了所有页表相关的数据结构、常量和函数声明。让我们来看看它的整体设计思路。

### 文件头注释

```c
/* ==============================================================================
 * CCOS - Page Table Management for x86_64
 * ==============================================================================
 * This module provides low-level page table management for the x86_64
 * architecture, including four-level page table structures (PML4/PDPT/PD/PT),
 * page table entry manipulation, and address translation functions.
 * ==============================================================================
 */
```

这个注释清楚地说明了这个模块的用途。注意我们使用的是 `/* */` 风格的多行注释，而不是 `//` 风格。这是内核代码的常见风格，因为 `/* */` 在 C 和 C++ 中都能用。

---

## 页大小常量定义

在之前的文档中我们讲过，x86_64 支持 4KB、2MB 和 1GB 三种页面大小。这些常量在 `page.h` 中定义：

```c
/* Define PAGE_SHIFT locally if not already defined */
#ifndef PAGE_SHIFT
#define PAGE_SHIFT       12
#endif

/* Define PAGE_SIZE locally if not already defined */
#ifndef PAGE_SIZE
#define PAGE_SIZE        (1ULL << PAGE_SHIFT)   /* 4096 bytes */
#endif

/* Huge page sizes */
#define PAGE_SIZE_2MB    (2ULL * 1024 * 1024)   /* 2097152 bytes */
#define PAGE_SIZE_1GB    (1ULL * 1024 * 1024 * 1024)  /* 1073741824 bytes */
#define PAGE_SHIFT_2MB   21
#define PAGE_SHIFT_1GB   30
```

⚠️ 注意：`PAGE_SIZE` 和 `PAGE_SHIFT` 实际上是在 `pframe.h` 中定义的。这里我们用 `#ifndef` 来检查是否已经定义，避免重复定义。这是一种常见的头文件保护技巧，叫做"include guard"的变体。

你可能会问：为什么 PAGE_SHIFT 是 12？因为 2^12 = 4096，这就是 4KB。页面大小总是 2 的幂次方，这是因为硬件需要通过位运算来快速提取页表索引。

### 页表级数移位量

```c
/* Page table levels */
#define PML4_SHIFT       39
#define PDPT_SHIFT       30
#define PD_SHIFT         21
#define PT_SHIFT         12
```

这些常量定义了从虚拟地址中提取各级页表索引时需要右移的位数。比如 `PML4_INDEX(vaddr)` 实际上就是 `(vaddr >> 39) & 0x1FF`。

```c
/* Number of entries per page table */
#define PT_ENTRIES       512
```

每个页表有 512 个项。这是因为每级索引是 9 位，2^9 = 512。每个项是 8 字节，所以一个页表正好是 512 × 8 = 4096 字节 = 4KB。

---

## 虚拟地址索引宏

这些宏是从虚拟地址中提取各级页表索引的关键：

```c
#define PML4_INDEX(vaddr) (((vaddr) >> PML4_SHIFT) & 0x1FF)
#define PDPT_INDEX(vaddr) (((vaddr) >> PDPT_SHIFT) & 0x1FF)
#define PD_INDEX(vaddr)  (((vaddr) >> PD_SHIFT) & 0x1FF)
#define PT_INDEX(vaddr)  (((vaddr) >> PT_SHIFT) & 0x1FF)
```

让我解释一下这些宏是如何工作的。以 `PML4_INDEX` 为例：

1. `(vaddr) >> PML4_SHIFT`：把虚拟地址右移 39 位，这样 PML4 索引就落到了低 9 位
2. `& 0x1FF`：用掩码提取低 9 位（0x1FF = 511 = 二进制 111111111）

这些宏会被频繁使用，在性能敏感的代码中，宏定义比函数调用更高效。

---

## 页表项标志位定义

这些标志位我们在上一个文档中详细讲过，这里用宏定义的方式表示：

```c
/* Page Table Entry Flag Bits */
#define PAGE_PRESENT     (1ULL << 0)   /* P: Page present in memory */
#define PAGE_WRITE       (1ULL << 1)   /* R/W: Read/write (1=writable) */
#define PAGE_USER        (1ULL << 2)   /* U/S: User/supervisor (1=user) */
#define PAGE_WRITE_THRU  (1ULL << 3)   /* PWT: Write-through caching */
#define PAGE_NO_CACHE    (1ULL << 4)   /* PCD: Disable cache */
#define PAGE_ACCESSED    (1ULL << 5)   /* A: Page was accessed */
#define PAGE_DIRTY       (1ULL << 6)   /* D: Page was written to */
#define PAGE_GLOBAL      (1ULL << 8)   /* G: Global page */
#define PAGE_NO_EXEC     (1ULL << 63)  /* NX: No-execute bit */

/* Huge page support */
#define PAGE_HUGE_PD    (1ULL << 7)    /* PS: Page size bit for PD (2MB pages) */
#define PAGE_HUGE_PDPT  (1ULL << 7)    /* PS: Page size bit for PDPT (1GB pages) */
```

⚠️ 注意：我们使用 `1ULL` 而不是 `1` 来定义这些常量。`ULL` 后缀表示"unsigned long long"，确保左移 63 位时不会溢出。如果你写成 `1 << 63`，在大多数系统上会导致未定义行为。

### 地址掩码

```c
/* Address mask (physical address bits in a PTE) */
#define PTE_ADDR_MASK    0x000FFFFFFFFFF000ULL  /* Bits 12-51 for physical address */
```

这个掩码用来从页表项中提取物理地址。位 12-51 存储物理页号，所以掩码的高 40 位是 1，低 12 位和高 12 位是 0。

### 常用标志组合

```c
/* Standard kernel page flags */
#define PAGE_KERN_DEFAULT (PAGE_PRESENT | PAGE_WRITE)
#define PAGE_KERN_RO      (PAGE_PRESENT)
#define PAGE_USER_DEFAULT (PAGE_PRESENT | PAGE_WRITE | PAGE_USER)
#define PAGE_USER_RO      (PAGE_PRESENT | PAGE_USER)
```

这些是常用的标志组合，让代码更简洁。比如 `PAGE_KERN_DEFAULT` 表示内核的普通页面（存在、可写），`PAGE_USER_RO` 表示用户只读页面。

## 页表项结构体定义

这是整个 `page.h` 中最重要的数据结构：

```c
typedef union {
    struct {
        uint64_t present      : 1;   /* Bit 0: Present */
        uint64_t writable     : 1;   /* Bit 1: Read/Write */
        uint64_t user         : 1;   /* Bit 2: User/Supervisor */
        uint64_t pwt          : 1;   /* Bit 3: Page-level Write-Through */
        uint64_t pcd          : 1;   /* Bit 4: Page-level Cache Disable */
        uint64_t accessed     : 1;   /* Bit 5: Accessed */
        uint64_t dirty        : 1;   /* Bit 6: Dirty (PD/PT only) */
        uint64_t pat          : 1;   /* Bit 7: Page-Attribute Table (or PS) */
        uint64_t global       : 1;   /* Bit 8: Global */
        uint64_t available    : 3;   /* Bits 9-11: Available for OS use */
        uint64_t frame        : 40;  /* Bits 12-51: Physical frame number */
        uint64_t available2   : 11;  /* Bits 52-62: Available for OS use */
        uint64_t nx           : 1;   /* Bit 63: No-Execute */
    } bits;
    uint64_t value;
} page_table_entry_t;
```

这是一个联合体（union），包含两个成员：一个位域结构体和一个 64 位整数。

### 为什么用联合体

联合体让同一个内存位置可以用不同的方式访问。你可以通过 `entry.bits.present` 来访问 Present 位，也可以通过 `entry.value` 来访问整个 64 位值。

这在某些场景下非常方便。比如，当你想设置整个页表项时，可以直接操作 `entry.value`；当你想检查某个标志位时，可以用 `entry.bits.present`。

### 位域的注意事项

⚠️ 位域的内存布局是由编译器实现的，不是 C 标准规定的。但在 x86_64 上，所有主流编译器（GCC、Clang、MSVC）对于这种结构的实现是一致的：从低位到高位排列。

如果你在代码中发现某些位域的值不对，首先检查编译器版本，然后检查是否有奇怪的编译选项。

## 页表结构体定义

每个级别的页表（PML4、PDPT、PD、PT）都有相同的结构：一个包含 512 个页表项的数组。

```c
typedef struct {
    page_table_entry_t entries[PT_ENTRIES];
} __attribute__((aligned(PAGE_SIZE))) page_table_t;
```

### 为什么用数组而不是链表

你可能会问：为什么用数组而不是链表？答案是性能和硬件要求。

硬件期望页表是数组形式，它通过简单的索引计算就能找到对应的页表项。如果用链表，硬件需要遍历链表，这会大大降低性能。

而且，数组形式让每个页表恰好占 4KB，可以完整地放在一个物理页中，不需要跨页存储。

### `__attribute__((aligned(PAGE_SIZE)))` 的作用

这个 GCC 扩展属性告诉编译器：这个结构体必须 4KB 对齐。这是硬件的要求，因为 CR3 寄存器存储的 PML4 地址必须是 4KB 对齐的。

⚠️ 如果你不加这个属性，编译器可能会在任何位置分配这个结构体，导致硬件无法正确访问页表。

### 类型别名

```c
/* Type aliases for clarity */
typedef page_table_t pml4_t;   /* Page Map Level 4 */
typedef page_table_t pdpt_t;   /* Page Directory Pointer Table */
typedef page_table_t pd_t;     /* Page Directory */
typedef page_table_t pt_t;     /* Page Table */
```

这些类型别名让代码更清晰。`pml4_t *` 比 `page_table_t *` 更能表达意图：这是一个 PML4 表，而不是随便什么页表。

## 错误码定义

为了处理各种错误情况，我们定义了一组错误码：

```c
typedef enum {
    PAGE_OK = 0,
    PAGE_ERR_NOT_INIT = -1,
    PAGE_ERR_OOM = -2,           /* Out of memory */
    PAGE_ERR_INVALID = -3,       /* Invalid argument */
    PAGE_ERR_NOT_PRESENT = -4,   /* Page not present */
    PAGE_ERR_ALREADY_MAPPED = -5,
    PAGE_ERR_NOT_MAPPED = -6,
    PAGE_ERR_ALIGNMENT = -7,
} page_result_t;
```

所有的页表管理函数都会返回 `page_result_t`，调用者可以通过检查返回值来判断操作是否成功。

⚠️ 注意：我们使用负数表示错误，0 表示成功。这是 C 语言中常见的错误处理约定。

## 映射标志定义

除了页表项的硬件标志位，我们还定义了一组软件标志：

```c
typedef enum {
    VMAP_FLAG_NONE = 0,
    VMAP_FLAG_WRITE = (1 << 0),      /* Writable mapping */
    VMAP_FLAG_USER = (1 << 1),       /* User-accessible mapping */
    VMAP_FLAG_NO_EXEC = (1 << 2),    /* No-execute mapping */
    VMAP_FLAG_WRITE_THRU = (1 << 3), /* Write-through caching */
    VMAP_FLAG_NO_CACHE = (1 << 4),   /* Cache disable */
    VMAP_FLAG_HUGE_2MB = (1 << 5),   /* Use 2MB huge pages */
    VMAP_FLAG_HUGE_1GB = (1 << 6),   /* Use 1GB huge pages */
} vmap_flags_t;
```

这些标志是给我们的映射 API 使用的，它们会被转换成页表项的硬件标志位。这样做的好处是 API 更清晰，调用者不需要了解硬件标志位的细节。

## 内联函数：CR 寄存器操作

访问 CR 寄存器需要内联汇编，我们把这些操作封装成内联函数：

```c
static inline uint64_t page_get_cr3(void) {
    uint64_t cr3;
    __asm__ volatile("movq %%cr3, %0" : "=r"(cr3));
    return cr3;
}

static inline void page_set_cr3(uint64_t cr3) {
    __asm__ volatile("movq %0, %%cr3" : : "r"(cr3) : "memory");
}
```

### 内联汇编语法解释

对于不熟悉 GCC 内联汇编的人来说，这几行代码可能有点晦涩。让我解释一下：

- `__asm__ volatile`：告诉编译器这是内联汇编，且不能被优化掉
- `"movq %%cr3, %0"`：汇编指令，把 CR3 寄存器的值移动到输出操作数
- `"=r"(cr3)`：输出操作数，`=` 表示只写，`r` 表示使用通用寄存器
- `: "r"(cr3)`：输入操作数，`r` 表示使用通用寄存器
- `: "memory"`：clobber，告诉编译器这段代码会修改内存

⚠️ 注意：`page_set_cr3` 后面的 `"memory"` clobber 非常重要。它告诉编译器：这个操作会影响内存（因为刷新了 TLB），编译器不能假设之前缓存在寄存器中的内存值仍然有效。
