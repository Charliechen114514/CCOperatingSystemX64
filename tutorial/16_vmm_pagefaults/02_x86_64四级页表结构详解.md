# 02 - x86_64 四级页表结构详解

说实话，第一次看到 x86_64 的四级页表结构时，我脑子里只有一个问题：为什么非要四级？

---

## 从 32 位保护模式说起

在理解 x86_64 的四级页表之前，我们先来看看 32 位保护模式的分页机制。32 位的 x86 处理器使用的是两级页表：页目录（Page Directory，PD）和页表（Page Table，PT）。

32 位虚拟地址被分成三个部分：10 位的 PD 索引、10 位的 PT 索引，以及 12 位的页内偏移。这意味着每个页表有 1024 个项（2^10），每个项 4 字节，一个页表正好占 4KB。

这个设计在 32 位时代工作得很好。但当我们进入 64 位时代时，问题出现了。

64 位的虚拟地址空间是 2^64 字节，这是一个天文数字。如果还是用两级页表，要么页表项变得很大（浪费内存），要么单个页表变得很大（不切实际）。硬件设计师们选择了一个折中方案：增加页表的级数。

### 为什么是四级而不是三级或五级

这是一个设计上的权衡。更多的级数意味着更深的查找链（性能损失），但每级页表可以保持 4KB 大小（内存效率）。

x86-64（早期 AMD64）最初设计使用三级页表，支持 48 位虚拟地址。后来扩展到四级页表，支持 57 位虚拟地址（目前的实现实际使用 48 位）。四级是一个平衡点：既能支持巨大的地址空间，又不会让页表查找变得太慢。

---

## 虚拟地址的拆解

让我们来看看 x86_64 的 64 位虚拟地址是如何被拆解的。虽然地址是 64 位的，但目前实现的 x86_64 处理器只使用了低 48 位（高 16 位必须是符号扩展）。

```
┌────────────────────────────────────────────────────────────────┐
│                         64 位虚拟地址                           │
├─────┬─────┬─────┬─────┬────────────────────────────────────────┤
│ PML4│ PDPT│ PD  │ PT  │            页内偏移                      │
│ 9b  │ 9b  │ 9b  │ 9b  │              12b                        │
└──┬──┴──┬──┴──┬──┴──┬──┴────────────────────────────────────────┘
   │     │     │     │
   v     v     v     v
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│PML4 │→│PDPT │→│ PD  │→│ PT  │→ 物理页 + 偏移
└─────┘ └─────┘ └─────┘ └─────┘
```

### 每一部分的含义

**PML4 索引（位 47-39）**：指向页映射第四级表中的一个项。这是查找链的第一步。

**PDPT 索引（位 38-30）**：指向页目录指针表中的一个项。

**PD 索引（位 29-21）**：指向页目录中的一个项。

**PT 索引（位 20-12）**：指向页表中的一个项。

**页内偏移（位 11-0）**：物理页内的字节偏移量。

### 为什么每级是 9 位

每级索引是 9 位，这意味着每个页表有 2^9 = 512 个项。每个项是 8 字节（64 位），所以一个页表的大小是 512 × 8 = 4096 字节 = 4KB。

这恰好是一个内存页的大小。这意味着每个页表可以完整地放在一个物理页中，不需要跨页存储，大大简化了内存管理。

---

## 逐级查找过程

现在让我们来看看地址转换是如何一步一步进行的。假设我们要转换虚拟地址 `0xFFFFFFFF80000000`。

### 第零步：从 CR3 开始

CR3 寄存器（也叫做页目录基址寄存器）存储的是 PML4 表的物理地址。这是整个地址转换的起点。

```
CR3 = PML4 表的物理地址
```

⚠️ 注意：CR3 的低 12 位必须为 0，这意味着 PML4 表必须 4KB 对齐。这是硬件的要求。

### 第一步：查找 PML4

使用虚拟地址的 PML4 索引（位 47-39）在 PML4 表中找到对应的项。这个项指向一个 PDPT 表的物理地址。

```
PML4 项的物理地址 = CR3 + (PML4 索引 × 8)
PDPT 物理地址 = PML4 项的内容 [位 51:12]
```

对于我们的例子地址 `0xFFFFFFFF80000000`：

```
PML4 索引 = (0xFFFFFFFF80000000 >> 39) & 0x1FF = 0x1FF = 511
```

所以我们要查找 PML4 表的第 511 项。

### 第二步：查找 PDPT

使用虚拟地址的 PDPT 索引（位 38-30）在 PDPT 表中找到对应的项。这个项指向一个 PD 表的物理地址。

```
PD 项的物理地址 = PDPT 物理地址 + (PDPT 索引 × 8)
PD 物理地址 = PDPT 项的内容 [位 51:12]
```

对于我们的例子地址：

```
PDPT 索引 = (0xFFFFFFFF80000000 >> 30) & 0x1FF = 0x100 = 256
```

### 第三步：查找 PD

使用虚拟地址的 PD 索引（位 29-21）在 PD 表中找到对应的项。这个项指向一个 PT 表的物理地址（或者直接指向物理页，如果是巨大页）。

```
PT 项的物理地址 = PD 物理地址 + (PD 索引 × 8)
PT 物理地址 = PD 项的内容 [位 51:12]
```

对于我们的例子地址：

```
PD 索引 = (0xFFFFFFFF80000000 >> 21) & 0x1FF = 0x0 = 0
```

### 第四步：查找 PT

使用虚拟地址的 PT 索引（位 20-12）在 PT 表中找到对应的项。这个项指向最终的物理页。

```
物理页地址 = PT 物理地址 + (PT 索引 × 8)
物理页号 = PT 项的内容 [位 51:12]
```

对于我们的例子地址：

```
PT 索引 = (0xFFFFFFFF80000000 >> 12) & 0x1FF = 0x0 = 0
```

### 第五步：加上页内偏移

最后，把物理页号左移 12 位（乘以 4096），然后加上页内偏移，得到最终的物理地址。

```
最终物理地址 = (物理页号 << 12) | 页内偏移
```

对于我们的例子地址：

```
页内偏移 = 0xFFFFFFFF80000000 & 0xFFF = 0x000
最终物理地址 = (物理页号 << 12) | 0x000
```

---

## 一个具体的例子

让我们用一个更具体的例子来说明。假设 CR3 寄存器的值是 `0x7000`（PML4 表在物理地址 0x7000），我们要转换虚拟地址 `0x0000_0000_1234_5678`。

### 计算各级索引

```c
PML4 索引 = (0x0000000000001234 >> 39) & 0x1FF = 0
PDPT 索引 = (0x0000000000001234 >> 30) & 0x1FF = 0
PD  索引 = (0x0000000000001234 >> 21) & 0x1FF = 0
PT  索引 = (0x0000000000001234 >> 12) & 0x1FF = 1
页内偏移 = 0x234
```

### 逐级查找

1. 从 CR3 获取 PML4 表地址：`0x7000`
2. PML4[0] 指向 PDPT：假设是 `0x8000`
3. PDPT[0] 指向 PD：假设是 `0x9000`
4. PD[0] 指向 PT：假设是 `0xA000`
5. PT[1] 指向物理页：假设是 `0xB000`
6. 最终物理地址：`0xB000` + `0x234` = `0xB234`

这就是地址转换的完整过程。

## 页表项的格式

每一级的页表项格式都是相同的：一个 64 位的值。低 12 位是标志位，高 52 位存储物理地址（实际上是位 12-51，共 40 位，支持 4TB 物理内存）。

```
┌────────────────────────────────────────────────────────────────┐
│                          页表项格式                            │
├────────┬────────┬────────┬────────┬────────┬───────────────────┤
│ 标志位 │              物理页号（40位）                         │
│ 12位   │         位 51-12                                      │
├────────┴────────┴────────┴────────┴────────┴───────────────────┤
│ 63-52 │ 51-12        │ 11-0                                   │
│ 可用  │ 物理页号     │ 标志位                                  │
└────────┴─────────────┴─────────────────────────────────────────┘
```

物理页号左移 12 位后才是真正的物理地址（低 12 位总是 0，保证 4KB 对齐）。

⚠️ 注意：虽然页表项是 64 位的，但只有位 12-51 被用于存储物理地址。这意味着当前 x86_64 实现支持的最大物理内存是 2^40 × 4096 = 1TB。实际上，现代 CPU 扩展到了 52 位物理地址（支持 4PB），但需要使用页表项的"可用"位来存储额外的高位。

---

## 巨大页的加速

四级页表的查找需要四次内存访问，这在性能上是有开销的。为了减少这个开销，x86_64 支持巨大页（Huge Pages）。

### 2MB 巨大页

如果 PD 项的 PS 位（位 7）被设置为 1，那么这个 PD 项直接指向一个 2MB 的物理页，跳过 PT 查找。

```
PML4 → PDPT → PD (PS=1) → 2MB 物理页 + 偏移
```

虚拟地址的 PD 索引之后的 21 位（位 20-0）作为 2MB 页内的偏移。

### 1GB 巨大页

如果 PDPT 项的 PS 位（位 7）被设置为 1，那么这个 PDPT 项直接指向一个 1GB 的物理页，跳过 PD 和 PT 查找。

```
PML4 → PDPT (PS=1) → 1GB 物理页 + 偏移
```

虚拟地址的 PDPT 索引之后的 30 位（位 29-0）作为 1GB 页内的偏移。

### 巨大页的优势

巨大页的优势是显而易见的：减少了页表查找的次数，减少了页表占用的内存，更重要的是减少了 TLB（Translation Lookaside Buffer）的压力。

TLB 是 CPU 中缓存虚拟地址到物理地址转换的硬件。每个 TLB 条目只能缓存一个页面的转换。使用 2MB 巨大页意味着一个 TLB 条目可以覆盖 2MB 内存，而不是只有 4KB。这对于需要访问大量内存的程序来说性能提升非常明显。

---

## TLB 的作用

讲页表就不能不提 TLB。每次内存访问都需要进行四级页表查找，这意味着每次访问内存实际上可能需要五次内存访问（四次查页表 + 一次真正的内存访问）。性能损失是巨大的。

TLB 就是用来解决这个问题的。它是一个缓存，存储最近使用的虚拟地址到物理地址的转换。当 CPU 需要转换一个虚拟地址时，它首先在 TLB 中查找。如果找到了（TLB Hit），就直接使用缓存的物理地址，不需要查页表。如果没找到（TLB Miss），才进行完整的页表查找，并把结果存入 TLB。

⚠️ 注意：当你修改页表后，必须刷新 TLB，否则 CPU 可能继续使用旧的转换结果。这是新手很容易犯的错误，会导致难以调试的问题。

---

## 规范地址的概念

你可能注意到，虽然虚拟地址是 64 位的，但我们只使用了低 48 位。这是因为 x86_64 要求虚拟地址的位 63-48 必须是位 47 的符号扩展。

换句话说，如果位 47 是 0，那么位 63-48 也必须全是 0；如果位 47 是 1，那么位 63-48 也必须全是 1。满足这个条件的地址叫做规范地址（Canonical Address）。

```
用户空间（位 47 = 0，高 16 位全 0）:
0x0000_0000_0000_0000 - 0x0000_7FFF_FFFF_FFFF

非规范空洞（无效地址）:
0x0000_7FFF_FFFF_FFFF - 0xFFFF_8000_0000_0000

内核空间（位 47 = 1，高 16 位全 1）:
0xFFFF_8000_0000_0000 - 0xFFFF_FFFF_FFFF_FFFF
```

⚠️ 访问非规范地址会导致通用保护异常（#GP），而不是页错误。这是硬件的要求，无法绕过。
