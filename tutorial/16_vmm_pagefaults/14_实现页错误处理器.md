# 14 - 实现页错误处理器

说实话，实现页错误处理器是虚拟内存管理的最后一关。如果这里写错了，系统会在最意想不到的时候崩溃。

---

## pf_init 的实现

`pf_init` 函数注册页错误处理函数到 IDT。首先检查是否已经初始化，如果是则直接返回。然后注册页错误处理函数到中断向量 14，最后设置初始化标志并打印日志。

```c
void pf_init(void) {
    if (s_initialized) {
        return;
    }

    /* Register page fault handler for vector 14 */
    idt_set_handler(IDT_PF, pf_handler, 0);

    s_initialized = true;
    klog_info("[PF] Page fault handler registered\n");
}
```

`IDT_PF` 是中断向量 14 的宏定义，`idt_set_handler` 函数把我们的处理函数注册到 IDT。页错误处理函数必须在 `vmm_init` 之后注册，因为它可能需要使用 VMM 的功能（比如分配物理页）。

---

## pf_handler 的实现

`pf_handler` 是页错误的实际处理函数，它在页错误发生时被 CPU 调用。首先我们增加统计计数，然后读取 CR2 获取触发页错误的虚拟地址，解析错误码：

```c
void pf_handler(interrupt_frame_t* frame, uint64_t error_code) {
    /* Increment statistics */
    s_pf_stats.total_faults++;

    /* Read CR2 to get fault address */
    virtual_addr_t fault_addr = pf_get_cr2();

    /* Parse error code */
    page_fault_info_t info;
    pf_parse_error_code(error_code, &info);
    info.fault_addr = fault_addr;

    /* Log the fault */
    klog_error("[PF] Page Fault!\n");
    klog_error("[PF]   Address: 0x%llX\n", fault_addr);
    klog_error("[PF]   Error: 0x%llX\n", error_code);
```

然后我们进行一些基本检查。如果地址不是规范地址，或者设置了保留位，这通常意味着严重的错误，我们直接跳转到内核 panic：

```c
    /* Check for canonical address */
    if (!vmm_is_canonical(fault_addr)) {
        klog_error("[PF] Non-canonical address\n");
        goto kernel_panic;
    }

    /* Check for reserved bit set */
    if (info.reserved_bit) {
        klog_error("[PF] Reserved bit set - possible page table corruption\n");
        goto kernel_panic;
    }
```

处理逻辑取决于特权级别。如果是用户态页错误，我们增加用户态错误计数，但由于还没有进程管理，我们暂时跳转到 panic。如果是内核态页错误，这通常是内核 bug，我们直接 panic：

```c
    /* Handle based on privilege level */
    if (info.user) {
        s_pf_stats.user_faults++;
        /* TODO: Send signal, terminate process, etc. */
        klog_error("[PF] User page fault - not yet handled\n");
        goto kernel_panic;
    } else {
        s_pf_stats.kernel_faults++;
        klog_error("[PF] KERNEL PAGE FAULT - This is a kernel bug!\n");
        goto kernel_panic;
    }

kernel_panic:
    /* Print register dump and halt */
    klog_error("[PF] System halted due to page fault\n");
    __asm__ volatile("cli");
    while (1) {
        __asm__ volatile("hlt");
    }
}
```

当前实现非常简单，所有页错误都导致系统停止。这是因为在实现进程管理之前，我们无法正确处理用户态页错误。

---

## 内核态和用户态的页错误处理

内核态页错误通常表示内核 bug，比如空指针解引用、访问无效的虚拟地址、栈溢出、页表配置错误等。当前策略是直接停止系统，因为继续运行可能导致数据损坏。如果你在开发过程中遇到很多内核页错误，可以先放宽这个策略，打印更多信息而不是立即停止，但最终产品中，内核页错误应该导致系统停止。

用户态页错误的处理依赖于进程管理。我们需要向进程发送 SIGSEGV 信号，如果进程没有处理信号则终止它。如果是写时复制页错误，需要分配新页面并复制内容。如果是按需分页，需要加载所需内容到内存。

当前实现还没有进程管理，所以用户态页错误也导致系统停止。但要注意的是，用户态页错误不一定是错误，它可能是按需分页或写时复制的一部分，需要更复杂的处理逻辑。

## 高级功能框架

写时复制（Copy-on-Write，COW）是一种优化技术，多个进程共享同一个只读页面，当某个进程试图写入时，才复制一份新的页面。`pf_handle_cow` 函数的当前实现只是一个框架，没有实际功能。完整的 COW 实现需要跟踪哪些页面是 COW 页面，这需要额外的数据结构支持。

```c

     */

    s_pf_stats.handled_cow++;
    return PF_NOT_OUR_FAULT;
}
```

## 测试页错误处理

我们可以手动触发一个页错误来验证处理函数：

```c
/* Test page fault handler */
void test_page_fault(void) {
    klog_info("[TEST] Triggering page fault...\n");

    /* Access an unmapped address */
    volatile uint32_t* ptr = (volatile uint32_t*)0xDEADBEEF0000;
    *ptr = 0x12345678;  /* This will trigger a page fault */

    /* This line should never be reached */
    klog_info("[TEST] This should not print\n");
}
```

这个测试会导致系统停止。如果你想在不停机的情况下测试页错误处理，需要实现更完善的错误处理逻辑。
