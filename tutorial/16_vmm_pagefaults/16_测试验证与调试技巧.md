# 16 - 测试验证与调试技巧

说实话，调试虚拟内存管理系统是一门艺术。你需要同时关注页表、TLB、地址转换……任何一个环节出问题都可能导致系统崩溃。

---

## QEMU Monitor 内存调试

QEMU Monitor 是 QEMU 提供的调试界面，你可以在运行 QEMU 时按 `Ctrl+Alt+2`（或 `Ctrl+Alt+Shift+2`）打开它。

### 查看物理内存

使用 `xp` 命令查看物理内存：

```
(qemu) xp /xg 0x100000
0000000000100000: 0x0000000000000000
```

这个命令显示物理地址 0x100000 处的 8 字节内容（`/xg` 表示十六进制，8 字节）。

### 查看虚拟内存

使用 `x` 命令查看虚拟内存：

```
(qemu) x /xg 0xFFFF8000000100000
00000000ffff8000000100000: 0x0000000000000000
```

⚠️ 注意：QEMU Monitor 的虚拟地址查询使用的是 CPU 的当前页表。如果页表配置错误，结果可能不正确。

### 查看 CR3 寄存器

使用 `info registers` 命令查看所有寄存器，包括 CR3：

```
(qemu) info registers
CR0=80000033 CR2=0000000000000000 CR3=0000000000009000
...
```

CR3 的值是当前 PML4 表的物理地址。

## GDB 页表检查

GDB 可以用来调试内核，包括检查页表内容。

### 计算 PML4 索引

首先计算虚拟地址的 PML4 索引：

```c
virtual_addr_t vaddr = 0xFFFFFFFF80000000;
uint64_t pml4_idx = (vaddr >> 39) & 0x1FF;  // = 511
```

### 查看页表内容

假设 PML4 在物理地址 0x9000，直接映射后的虚拟地址是 `0xFFFF800000009000`：

```
(gdb) x/16gx 0xFFFF800000009000+511*8
```

这会显示 PML4 的第 511 项（索引 511，偏移 511*8）。

⚠️ 注意：GDB 的表达式计算能力有限，复杂计算最好在内核代码中完成，然后打印结果。

## VMM 统计信息

VMM 模块提供了统计信息接口，可以用来查看虚拟内存的使用情况。

### page_dump_pml4

```c
page_dump_pml4(page_get_pml4());
```

这个函数打印 PML4 的摘要信息，包括每个 PML4 项是否映射。

### vmm_dump_stats

```c
extern void vmm_dump_stats(void);
```

这个函数打印 VMM 的统计信息，包括映射的页面数、分配的页表数等。

## 页错误处理测试

测试页错误处理最简单的方法是访问一个未映射的地址：

```c
/* Trigger page fault */
volatile uint32_t* ptr = (volatile uint32_t*)0xDEADBEEF0000;
*ptr = 0x12345678;  /* Page fault! */
```

如果页错误处理正常工作，你应该会看到页错误信息输出，然后系统停止。

⚠️ 注意：这个测试会导致系统停止。如果你想在不停机的情况下测试，需要实现更完善的页错误处理。

## 常见问题排查

### 问题 1：页表初始化失败

**症状**：系统启动后立即崩溃，没有任何输出。

**排查方法**：
1. 检查 `page_init` 是否在 `pframe_init` 之后调用
2. 检查 CR3 的值是否正确（应该是 0x9000 左右）
3. 使用 QEMU Monitor 查看物理内存 0x9000 处的内容

**解决方法**：
- 确保初始化顺序正确
- 确保 Bootloader 创建的页表布局与代码中假设的一致

### 问题 2：映射无效

**症状**：映射成功，但访问映射的地址时触发页错误。

**排查方法**：
1. 检查虚拟地址和物理地址是否正确对齐
2. 检查页表项的 Present 位是否设置
3. 检查 TLB 是否刷新

**解决方法**：
- 确保调用 `page_invalidate_tlb` 或重新加载 CR3
- 确保 `phys_to_virt` 返回的虚拟地址在直接映射区域内

### 问题 3：TLB 一致性问题

**症状**：修改页表后，访问仍然使用旧的映射。

**排查方法**：
1. 检查是否调用了 `page_invalidate_tlb`
2. 检查 CR3 重新加载的时机

**解决方法**：
- 每次修改页表后都调用 `page_invalidate_tlb`
- 修改多个页表项后，重新加载 CR3

### 问题 4：巨大页分配失败

**症状**：分配 2MB 或 1GB 巨大页失败。

**排查方法**：
1. 检查虚拟地址和物理地址是否正确对齐
2. 检查物理帧分配器是否返回了连续的物理内存

**解决方法**：
- 确保地址是 2MB 或 1GB 对齐的
- 实现对齐重试逻辑，分配更大的内存块然后找对齐地址

### 问题 5：非规范地址访问

**症状**：访问某些地址时触发 #GP 而不是 #PF。

**排查方法**：
1. 检查地址是否在规范范围内
2. 使用 `vmm_is_canonical` 检查地址

**解决方法**：
- 确保用户空间地址在 `0x0000000000400000 - 0x00007FFFFFFFFFFF` 范围内
- 确保内核空间地址在 `0xFFFF800000000000 - 0xFFFFFFFFFFFFFFFF` 范围内

## 性能观察

### TLB Miss 影响

TLB Miss 对性能有很大影响。你可以通过以下方式观察：

1. 使用性能计数器（如果 CPU 支持）
2. 比较使用 4KB 页面和巨大页的性能差异
3. 观察 TLB 刷新的频率

⚠️ 注意：过多的 TLB 刷新会显著降低性能。尽量使用 `page_invalidate_tlb` 而不是重新加载 CR3。

### 页表遍历开销

页表遍历需要多次内存访问（最多 4 次）。你可以通过以下方式优化：

1. 使用巨大页减少遍历深度
2. 缓存常用的页表项
3. 优化页表布局，减少遍历次数

---

## 调试技巧总结

1. **从简单开始**：先测试 4KB 页面映射，再测试 2MB 和 1GB 巨大页
2. **逐步验证**：每实现一个功能就测试，不要等到所有代码写完再测试
3. **使用日志**：在关键位置打印日志，帮助定位问题
4. **利用 QEMU Monitor**：查看物理内存和寄存器状态
5. **使用 GDB**：单步执行，检查变量值

---

## 完整测试流程

最后，这是一个完整的测试流程：

1. 编译内核：`cmake --build build`
2. 运行 QEMU：`qemu-system-x86_64 -drive format=raw,file=build/boot.img`
3. 观察输出，确认初始化成功
4. 如果有演示程序，确认演示输出正确
5. 如果崩溃，使用 QEMU Monitor 或 GDB 调试
