# 从内核态到用户态 —— 为什么我们需要 Ring 3

## 前言

说实话，写到这个阶段，我看着我们之前的代码，心里总觉得有点不安。

你想想看，Stage 22 我们实现了调度器分类，可以把进程分成实时进程和普通进程了。这确实是个进步，但有一个问题我们一直回避了：**所有的进程，不管是内核进程还是以后要跑的用户程序，统统运行在 Ring 0**。

这意味着什么？意味着如果我们加载一个用户程序，这个程序理论上可以直接访问内核的任何内存，可以直接操作硬件，可以修改页表，可以关闭中断。一旦这个程序有个 bug，或者更糟，是个恶意程序，整个系统就完蛋了。

今年都 2026 年了，如果我们还停留在所有代码都跑在 Ring 0 的阶段，那我们写的就不是一个真正的操作系统，而只是一个"超级单用户程序"。是时候跨过这个门槛了。

---

## 为什么 Ring 0 是件危险的事情

在深入实现之前，我们先来搞清楚，为什么所有代码跑在 Ring 0 是个问题。

### 安全性问题

当你的进程运行在 Ring 0 时，CPU 对它没有任何限制。它可以执行任何指令，包括：

- `cli` / `sti` —— 关闭和开启中断
- 直接修改 `CR3` 寄存器 —— 切换页表
- 直接访问端口 I/O —— 绕过驱动直接操作硬件
- 访问任何物理内存 —— 包括其他进程的内存

你可能会说："但我们写的代码都是我们自己控制的啊，不会有恶意代码。"问题在于，**bug 和恶意代码一样危险**。一个野指针访问、一个数组越界、一个栈溢出，在 Ring 0 下都可能直接把系统干崩。

而且，如果我们以后要支持运行别人写的程序，比如用户编译的 C 程序，那我们根本不能信任这些代码。

### 稳定性问题

还有一个更实际的问题：系统稳定性。

在 Ring 0 下，任何进程的错误都可能破坏整个系统。比如一个进程的代码有个 bug，不小心写错了地址，可能就把内核的数据结构给覆盖了。这种 bug 非常难调试，因为你看到的现象可能是完全不相关的 —— 某个进程崩溃了，但根本原因是另一个进程早些时候把内存写坏了。

现代操作系统的解决方案就是把进程隔离。每个进程有自己独立的地址空间，运行在较低的特权级。这样即使一个进程崩溃了，也不会影响其他进程，更不会影响内核。

### 没有"用户程序"的概念

到目前为止，我们的"进程"其实都是内核线程。它们是内核代码的一部分，编译链接时就固定在内核镜像里。如果你想运行一个新的程序，你得重新编译内核。

这不是我们想要的操作系统。真正的操作系统应该能够：

1. 加载独立的可执行文件（比如 ELF 文件）
2. 把这些程序放在隔离的环境中运行
3. 程序只能通过系统调用来请求内核服务

这些都需要用户态支持。

---

## 用户态能给我们什么

现在让我们来看看，实现用户态之后，我们能得到什么。

### 特权级隔离

x86_64 处理器有四个特权级（Ring 0 到 Ring 3），大多数操作系统只用 Ring 0 和 Ring 3：

```
┌─────────────────────────────────────────────────────────┐
│                    Ring 0 (内核态)                      │
│  - 完全访问所有资源                                     │
│  - 可以执行所有指令                                     │
│  - 访问所有内存                                         │
└─────────────────────────────────────────────────────────┘
                         △
                         │ syscall / iretq
                         │
┌─────────────────────────────────────────────────────────┐
│                    Ring 3 (用户态)                      │
│  - 只能访问用户空间内存                                  │
│  - 不能执行特权指令                                     │
│  - 通过系统调用访问内核服务                             │
└─────────────────────────────────────────────────────────┘
```

当用户程序尝试执行特权指令时，CPU 会触发异常，内核捕获后可以终止这个进程。这样恶意代码或 bug 代码就无法破坏系统。

### 内存保护

每个用户进程有自己独立的页表，只能访问自己的虚拟地址空间。如果一个进程尝试访问不属于自己的内存，CPU 会触发页错误，内核可以检测到这是非法访问并终止进程。

这种隔离不仅保护了内核，也保护了进程之间的隔离。进程 A 无法访问进程 B 的内存。

### 标准化接口

用户程序通过系统调用（syscall）来请求内核服务。这意味着我们可以定义一套清晰的 API，比如：

- `open()` / `read()` / `write()` —— 文件操作
- `brk()` / `mmap()` —— 内存管理
- `fork()` / `exec()` —— 进程控制
- `socket()` / `bind()` / `connect()` —— 网络操作

用户程序不需要知道这些系统调用内部是怎么实现的，它只需要按照约定调用就行。这是现代操作系统的基础。

## 与标准 Linux 用户态的对比

在继续之前，我想说明一下我们即将实现的用户态和标准 Linux 的用户态有什么不同。

### Linux 用户程序

在 Linux 上，你写一个 C 程序：

```c
#include <stdio.h>

int main(int argc, char** argv) {
    printf("Hello, World!\n");
    return 0;
}
```

编译运行，操作系统会：
1. 解析 ELF 文件格式
2. 加载程序段到内存
3. 动态链接 libc.so
4. 设置好栈和环境变量
5. 跳转到 main() 函数

### 我们的实现（第一阶段）

我们的第一阶段实现会简化很多：

```c
// 没有 main()，直接从 _start 开始
void _start(void) {
    const char* msg = "Hello from user mode!\n";
    write(1, msg, 25);  // 系统调用
    exit(0);            // 系统调用
}
```

**主要区别**：

| 特性 | Linux | 我们的第一阶段 |
|------|-------|----------------|
| 程序加载 | ELF 加载器 | 嵌入内核镜像 |
| 动态链接 | ld-linux.so | 静态链接 |
| 标准库 | 完整 glibc | 简化版 userlib |
| 入口点 | main() | _start() |
| 文件系统 | 完整 VFS | 暂时无文件系统 |

这样做是为了先把用户态的核心机制搞通，ELF 加载器和动态链接这些可以后面再加。毕竟一步一步来，先把路走稳。

## 本阶段会实现什么

好了，铺垫了这么多，现在来说说我们这个阶段要做什么。

### 核心功能

1. **用户态支持模块** (`kernel/user/`)
   - Ring 0 到 Ring 3 的切换
   - 用户内存验证和安全访问
   - 用户栈管理

2. **用户内存管理**
   - `brk()` 系统调用 —— 堆管理
   - `mmap()` / `munmap()` 系统调用 —— 内存映射
   - 用户空间区域管理

3. **用户 C 库** (`user/`)
   - 系统调用包装
   - 基础 stdio/stdlib/unistd 函数
   - Freestanding 环境

4. **用户程序构建系统**
   - 独立编译用户程序
   - 嵌入内核镜像
   - 符号重命名和对齐处理

5. **系统调用扩展**
   - `uname()` —— 获取系统信息
   - `brk()` / `mmap()` / `munmap()` —— 内存管理
   - 用户指针验证

### 演示程序

我们会写一个简单的用户程序 `uname_test`，它会：

1. 从 Ring 3 调用 `uname()` 系统调用
2. 获取系统信息
3. 通过 `write()` 系统调用打印出来
4. 通过 `exit()` 系统调用退出

这个程序虽然简单，但它证明了完整的用户态执行链路是通的。
