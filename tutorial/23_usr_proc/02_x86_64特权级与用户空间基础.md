# x86_64 特权级机制与用户空间基础

## 前言

在上一篇文章里，我们讨论了为什么需要用户态。现在，我们得搞清楚 x86_64 处理器到底是怎么实现这种特权级隔离的。

说实话，x86 的特权级机制一开始真的让我头晕。什么 CPL、DPL、RPL，各种缩写满天飞。但这些东西如果搞不清楚，后面写代码的时候就是盲人摸象 —— 你可能代码写对了，但不知道为什么对；或者代码错了，不知道错在哪里。

所以我们这篇文章的目标就是把这些概念彻底讲清楚。虽然可能有点枯燥，但相信我，这些时间投入绝对值得。

---

## x86_64 的四个特权级

x86_64 处理器支持四个特权级，编号从 0 到 3。数字越小，特权越高。

```
            ┌─────────────────────┐
            │     Ring 0          │  内核态
            │   (Kernel Mode)     │  最高特权级
            │                     │  可以执行所有指令
            └─────────────────────┘
                    ▲
                    │
            ┌─────────────────────┐
            │     Ring 1          │  设备驱动（很少使用）
            │   (Driver Mode)     │
            │                     │
            └─────────────────────┘
                    ▲
                    │
            ┌─────────────────────┐
            │     Ring 2          │  系统服务（很少使用）
            │  (Service Mode)     │
            │                     │
            └─────────────────────┘
                    ▲
                    │
            ┌─────────────────────┐
            │     Ring 3          │  用户态
            │   (User Mode)       │  最低特权级
            │                     │  受限的指令集
            └─────────────────────┘
```

### 为什么是四个？

这是历史遗留问题。x86 架构最初设计的时候，设想会有一个更复杂的分层系统：内核在 Ring 0，设备驱动在 Ring 1，系统服务在 Ring 2，应用程序在 Ring 3。

但实际上，现代操作系统（包括 Linux 和 Windows）只用 Ring 0 和 Ring 3。Ring 1 和 Ring 2 基本上被废弃了。原因很简单：

1. **复杂性**：多两级会增加上下文切换的复杂度
2. **性能**：更多层次的切换意味着更多的开销
3. **够用**：大多数驱动和服务都可以在 Ring 0 或 Ring 3 实现

所以我们的系统也只会用 Ring 0 和 Ring 3。

### Ring 0 vs Ring 3 的区别

让我们用一张表来对比一下：

| 特性 | Ring 0 (内核态) | Ring 3 (用户态) |
|------|-----------------|-----------------|
| 可以执行的指令 | 所有指令 | 非特权指令 |
| 可以访问的内存 | 所有内存 | 用户空间内存 |
| 可以直接访问硬件 | 是 | 否 |
| 修改页表 (CR3) | 可以 | 不可以 |
| 关闭中断 (CLI) | 可以 | 不可以 |
| 触发系统调用 | 不需要 | 需要 syscall |

**非特权指令**是那些不会影响系统状态的指令，比如算术运算、逻辑运算、数据传送等。

**特权指令**只能由内核执行，用户程序尝试执行会触发 #GP 异常。这包括：
- 修改控制寄存器 (CR0, CR3, CR4)
- 修改任务寄存器 (TR)
- 访问模型特定寄存器 (MSR)
- 加载段寄存器时的某些操作
- CLI/STI (修改 IF 标志)

## 段选择器和 RPL

在 x86_64 中，特权级信息主要通过段选择器 (Segment Selector) 来传递。虽然 64 位模式下分段基本被废弃了，但段选择器仍然有两个重要的用途：
1. 指定代码段/数据段
2. 指定请求者特权级 (RPL)

### 段选择器的结构

段选择器是一个 16 位的值：

```
┌─────────────────────────────────────────────────────────┐
│  TI   │      Index       │            RPL              │
│  1 bit │     13 bits      │             2 bits          │
└─────────────────────────────────────────────────────────┘
```

- **Index**: GDT (全局描述符表) 或 LDT 的索引
- **TI**: Table Indicator，0 = GDT，1 = LDT
- **RPL**: Requestor Privilege Level，请求者特权级

### RPL 的作用

RPL 是一个非常微妙但重要的概念。它表示"谁在请求这个资源"。

举个例子，假设用户程序 (Ring 3) 想调用一个内核函数。用户程序通过 syscall 指令进入内核，内核代码在 Ring 0 运行。当内核代码试图访问某个数据段时，CPU 会检查：

1. 当前特权级 (CPL) = 0 (我们在内核里)
2. 目标段的 DPL (Descriptor Privilege Level) = 0 (内核段)
3. **RPL** = 3 (请求者是用户程序)

如果只检查 CPL 和 DPL，访问会被允许。但 RPL = 3 表示这是一个"代表用户程序"的请求，所以访问权限应该被降级到 Ring 3。

### 我们的用户段选择器

在我们的系统中，我们定义了以下段选择器：

```c
/* 内核段 (Ring 0) */
#define KERNEL_CS    0x08    // GDT 索引 1, RPL = 0
#define KERNEL_DS    0x10    // GDT 索引 2, RPL = 0

/* 用户段 (Ring 3) */
#define USER_CS      0x18    // GDT 索引 3, RPL = 0
#define USER_DS      0x20    // GDT 索引 4, RPL = 0

/* 带 RPL=3 的用户段选择器 */
#define USER_CS_R3   (0x18 | 3)   // 0x1B
#define USER_SS_R3   (0x20 | 3)   // 0x23
```

注意最后一行。`| 3` 操作把低两位置为 11 (二进制)，这就是 RPL=3。当我们在 iretq 切换到用户态时，必须使用带 RPL=3 的段选择器，这样 CPU 才会知道我们要切换到 Ring 3。

## 特权级切换的方式

在 x86_64 中，有两个主要的指令用于特权级切换：
1. `syscall` / `sysret` —— 快速系统调用 (用户 → 内核)
2. `iretq` —— 中断返回 (内核 → 用户)

### syscall (Ring 3 → Ring 0)

`syscall` 是 AMD 引入的快速系统调用指令，Intel 后来也采用了。它比传统的 `int 0x80` 软中断快得多。

当用户程序执行 `syscall` 时：

```
用户态执行:
    mov rax, 60         ; 系统调用号 (SYS_EXIT)
    mov rdi, 0          ; 参数
    syscall             ; 切换到 Ring 0

CPU 自动执行:
    1. 保存 RCX → 用户 RIP (返回地址)
    2. 保存 R11 → 用户 RFLAGS
    3. 从 IA32_STAR MSR 加载内核 CS:RIP
    4. 切换到 Ring 0
```

**注意**：`syscall` **不会**切换栈。它假定内核栈已经在 TSS 中设置好了。

### iretq (Ring 0 → Ring 3)

`iretq` (Interrupt Return for 64-bit) 是我们从内核返回用户态的关键指令。

iretq 的栈帧结构（从低地址到高地址）：

```
┌─────────────────────────────────────────────────────────┐
│  栈顶 (低地址)                                           │
├─────────────────────────────────────────────────────────┤
│  RIP (8 bytes)       │ 返回地址                         │
│  CS  (8 bytes)       │ 代码段选择器 (带 RPL)            │
│  RFLAGS (8 bytes)    │ 标志寄存器                       │
│  RSP (8 bytes)       │ 用户栈指针 (仅当 CPL 改变)        │
│  SS  (8 bytes)       │ 栈段选择器 (仅当 CPL 改变)        │
├─────────────────────────────────────────────────────────┤
│  栈底 (高地址)                                           │
└─────────────────────────────────────────────────────────┘
```

`iretq` 的执行过程：

```
内核态执行:
    push USER_SS      ; 用户栈段 (0x23)
    push user_rsp     ; 用户栈指针
    push user_rflags  ; 用户 RFLAGS (IF=1)
    push USER_CS      ; 用户代码段 (0x1B)
    push user_rip     ; 用户返回地址
    iretq             ; 切换到 Ring 3

CPU 自动执行:
    1. 弹出 RIP 到指令指针
    2. 弹出 CS 到代码段寄存器，检测到 RPL=3
    3. 弹出 RFLAGS 到标志寄存器
    4. 因为 CPL 改变，弹出 RSP 和 SS
    5. 切换到 Ring 3，开始执行用户代码
```

⚠️ **注意**

iretq 栈帧的顺序非常重要！顺序错了就会崩溃。而且 SS 和 RSP 只有在 CPL 改变时才会被弹出，如果我们是在 Ring 0 → Ring 0 的切换，就不需要这两项。

## 用户空间的地址布局

现在让我们来规划一下用户空间的地址布局。在 x86_64 下，我们有巨大的虚拟地址空间（2^48 = 256TB），需要合理划分。

### 典型的 Unix 风格布局

```
┌─────────────────────────────────────────────────────────┐
│                    内核空间 (高地址)                     │
│  0xFFFF800000000000 - 0xFFFFFFFFFFFFFFFF               │
│  - 内核代码和数据                                       │
│  - 永久映射                                             │
└─────────────────────────────────────────────────────────┘
                    USER_END = 0xFFFF800000000000
                         │
┌─────────────────────────────────────────────────────────┐
│                    用户栈 (1MB)                         │
│  - 向下增长                                             │
│  - 保护页                                               │
├─────────────────────────────────────────────────────────┤
│                    用户堆 (brk)                         │
│  - 向上增长                                             │
│  - brk/mmap 管理                                        │
├─────────────────────────────────────────────────────────┤
│                    用户程序代码                         │
│  - 从 0x400000 开始                                     │
│  - 只读可执行                                           │
├─────────────────────────────────────────────────────────┤
│                    NULL 页保护                          │
│  - 最低 4MB 保护                                        │
└─────────────────────────────────────────────────────────┘
                    USER_BASE = 0x400000
```

### 我们的实现

在我们的系统中，我们定义了以下常量：

```c
/* 用户空间地址范围 */
#define USER_BASE       0x0000000000400000ULL  /* 4MB */
#define USER_END        0xFFFF800000000000ULL  /* 内核空间边界 */

/* 用户栈配置 */
#define USER_STACK_SIZE    (1 * 1024 * 1024)   /* 1MB */
#define USER_STACK_TOP     (USER_END - 8)       /* 栈顶 */
```

**为什么是 4MB 起？**

我们保留了最低 4MB 作为 NULL 页保护区域。如果用户程序尝试访问 NULL 指针，会触发页错误。这是一种安全措施，可以快速捕获空指针解引用。

**为什么用户栈是 1MB？**

1MB 对于大多数用户程序来说足够了。如果程序递归太深或分配太多栈变量，会触发栈溢出，这时我们可以添加栈扩展机制。但 1MB 是一个合理的起点。

**为什么栈在用户空间顶部？**

这是 Unix 的传统。栈向下增长，堆向上增长，它们在中间相遇。这种布局便于检测栈溢出 —— 我们可以在栈底设置一个保护页。

## GDT 用户段配置

要支持用户态，我们需要在 GDT (全局描述符表) 中配置用户段。

### GDT 条目结构

每个 GDT 条目是 8 字节 (64 位)：

```
┌──────────────────────────────────────────────────────────────────────┐
│  Base 31:24  │ G │ D │ L │ AVL │ Limit 19:16 │ P │ DPL │ S │ Type  │
│  (8 bits)    │   │   │   │     │ (4 bits)    │   │(2)  │   │(4)    │
├──────────────────────────────────────────────────────────────────────┤
│  Base 23:0   │                    Limit 15:0                       │
│  (24 bits)   │                      (16 bits)                      │
└──────────────────────────────────────────────────────────────────────┘
```

关键字段：
- **DPL**: Descriptor Privilege Level，描述符特权级 (0-3)
- **S**: System 段标志 (0 = 系统段，1 = 代码/数据段)
- **Type**: 段类型 (代码段/数据段/可读/可写等)
- **L**: Long mode 标志 (64 位代码段必须设置)
- **P**: Present 标志 (段是否在内存中)

### 我们的 GDT 配置

在 `kernel/interrupt/gdt.c` 中，我们有以下 GDT 条目：

```c
/* GDT 条目索引 */
#define GDT_NULL           0
#define GDT_KERNEL_CODE    1
#define GDT_KERNEL_DATA    2
#define GDT_USER_CODE      3   // 用户代码段
#define GDT_USER_DATA      4   // 用户数据段

/* 用户代码段: Base=0, Limit=0xFFFFF, Type=Code, DPL=3 */
gdt_set_entry(GDT_USER_CODE, 0, 0xFFFFF,
    GDT_DESC_CODE | GDT_DESC_DPL(3) | GDT_DESC_PRESENT | GDT_DESC_LONG);

/* 用户数据段: Base=0, Limit=0xFFFFF, Type=Data, DPL=3 */
gdt_set_entry(GDT_USER_DATA, 0, 0xFFFFF,
    GDT_DESC_DATA | GDT_DESC_DPL(3) | GDT_DESC_PRESENT);
```

**关键点**：
- DPL=3 表示 Ring 3 可以访问这个段
- GDT_DESC_LONG 表示这是 64 位代码段
- GDT_DESC_PRESENT 表示段在内存中

### 验证 GDT 配置

在我们继续之前，让我们验证一下 GDT 配置是否正确。你可以在内核启动时添加一些调试代码：

```c
void gdt_verify_user_segments(void) {
    klog_info("=== GDT User Segment Verification ===\n");
    klog_info("USER_CS (0x%02X): RPL=%d\n", USER_CS_R3, USER_CS_R3 & 3);
    klog_info("USER_SS (0x%02X): RPL=%d\n", USER_SS_R3, USER_SS_R3 & 3);

    /* 验证 RPL 正确 */
    if ((USER_CS_R3 & 3) != 3) {
        klog_error("USER_CS RPL is not 3!\n");
    }
    if ((USER_SS_R3 & 3) != 3) {
        klog_error("USER_SS RPL is not 3!\n");
    }
}
```

运行后应该看到：

```
=== GDT User Segment Verification ===
USER_CS (0x1B): RPL=3
USER_SS (0x23): RPL=3
```

## 从 Ring 0 到 Ring 3 的完整流程

现在让我们把所有概念串联起来，看看从内核态切换到用户态的完整流程是什么。

### 流程图

```
┌─────────────────────────────────────────────────────────┐
│                     内核态 (Ring 0)                     │
│                                                         │
│  1. 创建用户进程 PCB                                    │
│  2. 分配用户栈 (1MB)                                    │
│  3. 映射用户程序代码到用户空间                          │
│  4. 设置用户上下文结构                                  │
└────────────────────────┬────────────────────────────────┘
                         │
                         │ 准备 iretq 栈帧
                         ▼
                    ┌─────────┐
                    │  iretq  │
                    └────┬────┘
                         │ CPU 自动切换
                         ▼
┌─────────────────────────────────────────────────────────┐
│                     用户态 (Ring 3)                     │
│                                                         │
│  1. 执行用户程序                                        │
│  2. 用户栈向下增长                                      │
│  3. 需要内核服务时执行 syscall                          │
└────────────────────────┬────────────────────────────────┘
                         │
                         │ syscall
                         ▼
┌─────────────────────────────────────────────────────────┐
│                     内核态 (Ring 0)                     │
│                  系统调用处理程序                        │
└─────────────────────────────────────────────────────────┘
```

### 用户上下文结构

我们需要一个结构来保存切换到用户态所需的信息：

```c
typedef struct user_context {
    virtual_addr_t entry;      /* 入口点 (用户 RIP) */
    virtual_addr_t stack_top;  /* 用户栈顶 (用户 RSP) */
    uint64_t cs;               /* 用户 CS 选择器 */
    uint64_t ss;               /* 用户 SS 选择器 */
    uint64_t rflags;           /* 用户 RFLAGS */
} user_context_t;
```

在切换之前，我们填充这个结构：

```c
user_context_t ctx = {
    .entry = 0x400000,           /* 用户代码入口 */
    .stack_top = USER_END - 8,   /* 用户栈顶 */
    .cs = USER_CS_R3,            /* 0x1B */
    .ss = USER_SS_R3,            /* 0x23 */
    .rflags = 0x202              /* IF = 1 (启用中断) */
};
```

## 常见陷阱

在实现用户态切换时，有几个陷阱特别常见。

### 陷阱 1：忘记设置 RPL

```c
/* 错误：CS 没有设置 RPL=3 */
ctx.cs = 0x18;    // 这是错的！

/* 正确：CS 必须带 RPL=3 */
ctx.cs = 0x1B;    // 0x18 | 3
```

如果 CS 的 RPL 不是 3，iretq 不会切换到 Ring 3，程序会继续在 Ring 0 运行，失去所有保护。

### 陷阱 2：iretq 栈帧顺序错误

```assembly
/* 错误的顺序 */
push user_rip
push user_cs
push user_rflags
push user_rsp
push user_ss
iretq    /* 会崩溃！ */
```

**正确的顺序是 SS, RSP, RFLAGS, CS, RIP（从先压栈到后压栈）**

```assembly
/* 正确的顺序 */
push user_ss      /* 第一个压入 */
push user_rsp     /* 第二个压入 */
push user_rflags  /* 第三个压入 */
push user_cs      /* 第四个压入 */
push user_rip     /* 第五个压入 */
iretq
```

记住：栈向下增长，最后压入的在栈顶。iretq 从栈顶开始弹出，所以 RIP 必须在栈顶。

### 陷阱 3：忘记设置数据段

iretq 只会切换 CS 和 SS，不会自动设置 DS、ES、FS、GS。如果这些段寄存器仍然指向内核段，用户程序访问数据时会出问题。

```assembly
/* 在 iretq 之前设置所有数据段 */
mov ax, USER_SS_R3    ; 0x23
mov ds, ax
mov es, ax
mov fs, ax
mov gs, ax

push user_ss
push user_rsp
; ...
iretq
```
