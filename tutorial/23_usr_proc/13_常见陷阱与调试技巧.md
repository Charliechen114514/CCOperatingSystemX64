# 常见陷阱与调试技巧

## 前言

这是我们 Stage 23 - 用户态进程支持的最后一篇文章。

在开发这个用户态支持系统的过程中，我遇到了无数的陷阱和坑。有些是 x86_64 架构的特殊要求，有些是系统调用的微妙之处，还有些是链接器和编译器的奇怪行为。每一个问题都花了我不少时间去解决。

说实话，如果当初有人告诉我这些陷阱，我可以节省很多时间。所以这篇文章的目的就是：把我踩过的坑都记录下来，让你不必再踩一遍。

---

## Red Zone 问题

### 问题描述

x86_64 ABI 定义了一个 128 字节的"红区"（Red Zone）在栈指针之下。编译器可能使用这个区域来存储临时变量，避免频繁修改栈指针。

但是，`syscall` 指令会破坏这个区域！因为系统调用会切换栈，切换回来时 Red Zone 的内容就不确定了。

### 症状

- 用户程序在系统调用后出现奇怪的值
- 局部变量被莫名其妙地修改
- 偶尔崩溃，难以复现

### 解决方案

**必须使用 `-mno-red-zone` 编译标志**

```cmake
target_compile_options(userlib PRIVATE
    -mno-red-zone
)

target_compile_options(user_program PRIVATE
    -mno-red-zone
)
```

⚠️ **验证方法**

检查汇编代码，确保没有在 `syscall` 前后使用 Red Zone：

```bash
objdump -d user_program.elf | grep -A5 syscall
```

## 段寄存器设置问题

### 问题描述

在切换到用户态时，除了 CS 和 SS，还必须设置 DS、ES、FS、GS。如果它们仍然指向内核段，用户代码访问数据时会出错。

### 症状

- 用户代码访问全局变量时崩溃
- 数据访问总是返回错误的值
- #GP 或 #PF 异常

### 解决方案

在 `user_switch_to_usermode()` 中设置所有数据段寄存器：

```assembly
user_switch_to_usermode:
    /* ... setup iretq frame ... */

    /* Set data segments */
    mov ax, 0x23    ; USER_SS
    mov ds, ax
    mov es, ax
    mov fs, ax
    mov gs, ax

    iretq
```

⚠️ **验证方法**

在用户程序中打印段寄存器的值：

```c
void print_segment_registers(void) {
    uint16_t ds, es, fs, gs;
    __asm__ volatile("mov %%ds, %0" : "=r"(ds));
    __asm__ volatile("mov %%es, %0" : "=r"(es));
    __asm__ volatile("mov %%fs, %0" : "=r"(fs));
    __asm__ volatile("mov %%gs, %0" : "=r"(gs));

    printf("DS=0x%X, ES=0x%X, FS=0x%X, GS=0x%X\n", ds, es, fs, gs);
}
```

应该看到所有段都等于 0x23（USER_SS）。

## 页对齐问题

### 问题描述

用户程序必须页对齐才能正确映射。如果不对齐，可能会跨越多个页，或者映射失败。

### 症状

- 页错误（#PF）
- 映射失败
- 程序执行异常

### 解决方案

**1. 链接器脚本中对齐**

```ld
.user_programs : ALIGN(PAGE_SIZE)
{
    /* ... */
}
```

**2. objcopy 中对齐**

```cmake
COMMAND ${CMAKE_OBJCOPY} --set-section-alignment .user_uname_test=4096
```

**3. 代码中对齐**

```c
virtual_addr_t entry_point = USER_BASE;  /* Already page-aligned */
virtual_addr_t user_stack = (USER_END - USER_STACK_SIZE) & ~(PAGE_SIZE - 1);
```

⚠️ **验证方法**

```bash
objdump -h kernel.elf | grep user_programs
```

检查对齐列，应该是 `2**12`（4096 字节）。

## 符号重命名问题

### 问题描述

`objcopy` 将二进制文件转换为对象文件时，生成的符号名包含完整的构建路径。这在不同机器上不可移植。

### 症状

- 链接时报错找不到符号
- 符号名包含 `/` 或 `\`
- 不同的构建路径产生不同的符号名

### 解决方案

使用 Python 脚本动态重命名符号：

```python
# Get the actual symbol name
binary_start = None
for line in nm_output.splitlines():
    if '_binary_' in line and '_start' in line:
        binary_start = line.split()[2]
        break

# Rename to a consistent name
cmd = [
    objcopy,
    f'--redefine-sym={binary_start}=_binary_user_programs_demo_uname_test_start',
    # ... more redefinitions ...
]
```

⚠️ **验证方法**

```bash
nm build/uname_test_symbols.o | grep binary
```

应该看到简化的符号名，不包含路径。

## 用户指针验证问题

### 问题描述

如果系统调用不验证用户指针，恶意程序可以传递内核地址，导致内核内存被破坏。

### 症状

- 内核数据被莫名其妙地修改
- 安全漏洞
- 系统崩溃

### 解决方案

**总是验证用户指针**

```c
static int64_t sys_uname(syscall_frame_t* frame) {
    struct utsname* buf = (struct utsname*)frame->arg0;

    /* ALWAYS validate user pointers */
    if (!user_validate_pointer(buf, sizeof(struct utsname), true)) {
        return SYS_ERR_INVAL;
    }

    /* ... rest of implementation ... */
}
```

⚠️ **特别注意事项**

- 检查大小溢出：`addr + size < addr`
- 检查范围：`addr >= USER_BASE && addr + size <= USER_END`
- 检查权限：写操作需要验证写权限

## 栈指针问题

### 问题描述

用户栈的设置有很多细节：栈顶、栈底、对齐、初始值...任何一个错误都会导致崩溃。

### 症状

- 立即崩溃（#PF 或 #GP）
- 返回地址错误
- 局部变量访问失败

### 解决方案

**1. 栈顶地址**

```c
virtual_addr_t stack_top = pcb->user_stack + pcb->user_stack_size;
```

**2. 16 字节对齐**

x86_64 ABI 要求栈在函数调用时 16 字节对齐：

```c
virtual_addr_t user_stack = (USER_END - USER_STACK_SIZE) & ~0xF;
```

**3. 确保 user_context 正确**

```c
user_context_t user_ctx = {
    .entry = entry_point,
    .stack_top = pcb->user_stack + pcb->user_stack_size,  /* 注意是顶部！*/
    .cs = USER_CS,
    .ss = USER_SS,
    .rflags = 0x202,
};
```

⚠️ **常见错误**

```c
/* 错误：使用栈底而不是栈顶 */
user_ctx.stack_top = pcb->user_stack;  /* 错！*/

/* 正确：使用栈顶 */
user_ctx.stack_top = pcb->user_stack + pcb->user_stack_size;  /* 对 */
```

## 系统调用参数传递问题

### 问题描述

System V AMD64 ABI 定义了 6 个参数的寄存器传递顺序，但这与 syscall 指令略有不同。

### 症状

- 系统调用收到错误的参数
- 参数顺序混乱
- 某些参数丢失

### 解决方案

**寄存器映射**

| 参数 | 函数调用 | syscall |
|------|----------|---------|
| 1    | RDI      | RDI     |
| 2    | RSI      | RSI     |
| 3    | RDX      | RDX     |
| 4    | RCX      | R10     |
| 5    | R8       | R8      |
| 6    | R9       | R9      |

⚠️ **关键区别**

第 4 个参数：
- 函数调用：`RCX`
- syscall：`R10`

这是因为 `syscall` 会覆盖 `RCX`（保存 RIP）。

**正确的包装函数**

```c
static inline long syscall6(long num, long arg1, long arg2, long arg3,
                             long arg4, long arg5, long arg6) {
    register long r10 asm("r10") = arg4;  /* 注意：r10 不是 rcx！*/
    register long r8 asm("r8") = arg5;
    register long r9 asm("r9") = arg6;
    long ret;
    __asm__ volatile("syscall"
                      : "=a"(ret)
                      : "a"(num), "D"(arg1), "S"(arg2), "d"(arg3),
                        "r"(r10), "r"(r8), "r"(r9)
                      : "rcx", "r11", "memory");
    return ret;
}
```

## 物理地址类型问题

### 问题描述

Stage 22 使用 `uint32_t` 作为 `physical_addr_t`，但这不足以表示高物理内存。

### 症状

- 高物理内存无法访问
- 页表映射错误
- 截断的地址

### 解决方案

**改为 64 位类型**

```c
/* Stage 22 (错误) */
typedef uint32_t physical_addr_t;

/* Stage 23 (正确) */
typedef uint64_t physical_addr_t;
```

⚠️ **注意**

x86_64 支持最大 2^52 字节的物理地址。32 位类型只能到 4GB，对于现代系统是不够的。

## 调试技巧

### 使用 QEMU GDB

调试用户态代码比内核代码更困难，但仍然可以做到。

```bash
# 启动 QEMU
qemu-system-x86_64 -kernel build/kernel.elf -m 512M -serial stdio -s -S

# 在另一个终端启动 GDB
gdb build/kernel.elf
(gdb) target remote :1234
(gdb) break _start    # 用户程序入口
(gdb) continue
```

### 添加调试输出

在系统调用处理中添加日志：

```c
static int64_t sys_uname(syscall_frame_t* frame) {
    struct utsname* buf = (struct utsname*)frame->arg0;

    klog_debug("[SYSCALL] uname(buf=0x%llX)\n", (virtual_addr_t)buf);

    /* ... */
}
```

### 使用 objdump 反汇编

```bash
objdump -d build/uname_test
```

检查生成的汇编代码，确认：
- 没有使用 Red Zone
- 系统调用包装正确
- 没有意外的库调用

### 检查段表

```bash
readelf -S build/kernel.elf | grep user
```

确认用户程序段正确对齐和放置。

## 常见编译错误

### 错误 1：未定义的引用

```
undefined reference to `_syscall6'
```

**解决**：实现 `_syscall6` 包装函数

### 错误 2：段类型错误

```
error: section .user_uname_test can't be allocated in segment 0
```

**解决**：检查链接器脚本中的段定义，确保有合适的 VMA

### 错误 3：重定位溢出

```
relocation truncated to fit: R_X86_64_32
```

**解决**：确保使用 `-mcmodel=large` 编译标志

## 性能考虑

虽然我们当前不关注性能，但有一些简单的优化值得考虑：

### 系统调用批处理

一次系统调用完成多个操作，减少切换次数。

### 缓存用户指针验证结果

如果同一个指针被多次验证，可以缓存结果。

### 延迟物理页清零

只在真正需要时清零页，而不是立即清零。

## 安全考虑

用户态是安全的边界，需要特别注意：

### 防止 TOCTOU

Time-of-check to time-of-use 漏洞：

```c
/* 错误：有 TOCTOU 漏洞 */
if (user_validate_pointer(ptr, size, true)) {
    /* 用户可能在此时修改 ptr */
    memcpy(data, ptr, size);  /* 不安全 */
}

/* 正确：使用安全的复制函数 */
int64_t result = user_copy_from_user(data, ptr, size);
```

### 防止整数溢出

```c
/* 错误：可能溢出 */
if (addr + size > USER_END) { /* ... */ }

/* 正确：检查溢出 */
if (addr + size < addr || addr + size > USER_END) { /* ... */ }
```
