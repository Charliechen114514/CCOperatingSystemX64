# 19-1 为什么需要进程管理

## 前言

说实话，写到 Stage 19 的时候我真的是松了一口气。回头看 Stage 18，我们搞定了写时复制（COW）和异常处理，内存管理这块算是有了个像样的底子。但这时候问题来了 —— 你发现没有，我们现在的内核其实就是个"单任务大循环"，所有代码都在内核态跑，没有真正的"进程"概念。

这就像你只有一间房子的多功能厅，什么活动都在这里面搞，没法隔离。一旦某个程序出了问题，整个系统就炸了。而且更尴尬的是，我们连最基本的 fork、exit、wait4 这些系统调用都没实现完整，说自己是操作系统都有点心虚。

所以这一阶段，我们要做的事情很明确：把进程管理这块硬骨头啃下来。这包括设计并实现进程控制块（PCB）、PID 分配器、上下文切换、调度器，还有那些核心的进程相关系统调用。

## 为什么需要进程管理

我们先来聊聊为什么进程管理这么重要。从操作系统原理的角度看，进程是资源分配的基本单位，也是系统调度的基本单位。没有进程管理，你的操作系统就只是个"加了设备驱动的单程序执行器"，而不是真正的多任务系统。

具体来说，我们目前面临几个问题：

第一，没有进程隔离。所有代码共享同一个地址空间，一个程序崩溃可以把整个内核带沟里去。我们需要为每个进程提供独立的虚拟地址空间。

第二，无法并发执行。虽然有中断机制，但我们没有"保存当前状态、切换到另一个程序、以后还能切回来"的能力。这就是上下文切换要解决的问题。

第三，缺少核心系统调用。fork、exit、wait4 这些 POSIX 标准的系统调用都没实现，用户程序根本没法做进程管理相关的事情。

## 进程的核心概念

在深入代码之前，我们需要先明确几个核心概念。

进程控制块（PCB）是进程管理的核心数据结构。你可以把它理解成进程的"身份证"，里面记录了关于这个进程的所有信息：进程 ID（PID）、父进程 ID（PPID）、当前状态、CPU 上下文、内存上下文等等。当进程被切换出去的时候，它的状态就保存在 PCB 里；等到再轮到它运行的时候，系统就从 PCB 里恢复这些状态。

进程状态也很关键。一个进程在其生命周期里会经历几种状态：就绪（READY）、运行（RUNNING）、阻塞（BLOCKED）、僵尸（ZOMBIE）。就绪状态意味着进程已经准备好运行了，只是在排队等 CPU；运行状态就是正在 CPU 上执行；阻塞状态是在等待某个事件（比如 I/O 完成）；僵尸状态是进程已经执行完了，但父进程还没回收它。

上下文切换是进程管理的底层机制。当系统决定从一个进程切换到另一个进程时，需要先把当前进程的 CPU 寄存器状态保存下来，然后把目标进程之前保存的状态恢复到 CPU 里。这个过程必须非常精确，任何寄存器的遗漏都会导致系统崩溃。

## 环境说明

在开始编码之前，我们先明确一下开发环境。这是基于 Stage 18 代码继续开发的，所以你需要确保已经完成了前面所有阶段的工作。

硬件平台是 x86_64，这是目前最常见的 64 位架构。编译工具链是 GCC 的交叉编译版本，目标架构是 x86_64-elf。运行环境是 QEMU 模拟器，这大大方便了调试。

内核代码使用 C 语言编写，但上下文切换这种底层操作必须用汇编实现。我们会用到 NASM 汇编器，因为它的语法相对友好。

## 设计决策讨论

在动手写代码之前，有几个设计决策需要我们先想清楚。这些决策会影响整个进程管理子系统的架构，所以不能偷懒。

### PCB 结构设计

PCB 应该包含哪些字段？这个问题看似简单，但仔细想想会涉及很多考虑。

首先，进程标识是必须的：PID 和 PPID。这两个字段让进程可以被唯一标识，也建立了父子关系。

进程状态也很重要：state 字段记录当前处于哪种状态，exit_code 在进程退出时保存退出码。

调度相关字段：我们需要把进程组织到队列里，所以要有链表节点。run_list 用于调度队列，children 和 zombie_children 用于管理子进程关系。

内存上下文：mm 字段保存地址空间信息，最重要的是 pml4_phys，这是进程页表的物理地址。brk 是程序断点，用于堆扩展；stack_start 是用户栈的起始地址。

CPU 上下文：cpu_ctx 是一个指针，指向保存的寄存器状态。为什么要用指针而不是内嵌结构？因为这样可以让 PCB 结构更紧凑，而且上下文切换时只需要交换指针值。

内核栈：kernel_stack 是内核栈的栈顶地址，用于中断和系统调用。每个进程都需要独立的内核栈，这是 x86_64 硬件的要求。

统计信息：start_time 记录创建时间，comm 是命令名（最多 16 个字符）。

还有一些字段是为后续功能预留的，比如线程相关的 tgid、is_thread 等。这些在 Stage 19 可能用不到，但先把结构设计好可以减少以后的重构工作。

整个 PCB 结构大概 500 多字节，不算小但也不算太大。考虑到我们每个字段都有明确用途，这个大小是可以接受的。

### PID 分配方案选择

PID 分配器的设计也有几种方案可选。

最简单的是计数器方案：维护一个全局计数器，每次分配就加一。但这个方案有个致命问题 —— 计数器溢出后怎么办？虽然 32 位计数器理论上可以支持 42 亿个进程，但实际系统中 PID 用完之后怎么处理是个麻烦事。

第二种方案是位图（bitmap）。预先分配一个位数组，每一位对应一个 PID。分配时找第一个为 0 的位，释放时就把对应位清零。这个方案的优点是 O(1) 分配和释放，实现简单，而且可以精确控制最大进程数。

第三种方案是哈希表或者更复杂的数据结构。这些方案可以支持更大的 PID 空间，但实现复杂度高，对于我们的简单 OS 来说有点杀鸡用牛刀。

最终我们选择了位图方案。最大进程数设为 32768，这对于单机操作系统来说绰绰有余。bitmap_find_first_zero() 函数可以高效地找到空闲位，分配和释放都是常数时间操作。

需要注意的是，PID 0 被保留。在 Unix 系统中，PID 0 属于内核调度进程，PID 1 是 init 进程。我们虽然不一定完全照搬 Unix 设计，但保留 PID 0 可以避免和系统约定冲突。

### 进程状态机设计

进程状态机的设计直接决定了调度器的复杂度。我们采用经典的四状态模型：

READY 状态表示进程已经准备好运行，正在等待 CPU。调度器从就绪队列中选择进程时，选中的就是 READY 状态的进程。

RUNNING 状态表示进程正在 CPU 上执行。同一时刻只有一个进程处于 RUNNING 状态（单核系统）。

BLOCKED 状态表示进程在等待某个事件。比如等待 I/O 完成，或者等待子进程退出。阻塞状态的进程不在就绪队列里。

ZOMBIE 状态表示进程已经执行完毕，但父进程还没有回收。进程的资源大部分已经释放，但 PCB 还保留着，等待父进程读取退出码。

状态转换的规则也很清晰：fork 创建新进程时，子进程初始状态是 READY；调度器选择进程运行时，从 READY 转换到 RUNNING；进程用完时间片或者主动让出 CPU 时，从 RUNNING 转回 READY；进程等待事件时，从 RUNNING 转到 BLOCKED；事件发生时，从 BLOCKED 转回 READY；进程退出时，从 RUNNING 转到 ZOMBIE；父进程回收时，ZOMBIE 被彻底清除。

### 内存布局问题

在 Stage 19 开发过程中，我们发现了一个严重的地址空间冲突问题，这个问题在之前的阶段一直存在，但直到我们开始大量使用 VMM 分配内存时才暴露出来。

问题的根源是堆分配器和 VMM 通用分配使用了同一块虚拟地址范围。堆分配器使用 vmm_alloc_pages_at() 在固定地址分配，地址从 KERNEL_HEAP_BASE 开始递增。而 VMM demo 程序使用 vmm_alloc_pages() 分配，也是从 KERNEL_HEAP_BASE 开始搜索空闲地址。结果就是两者会争抢同一块地址空间，导致"Page already mapped"错误。

解决方案是把虚拟地址空间分离成两个独立的区域。堆分配器独占 0xFFFFFFFF81000000 - 0xFFFFFFFF81080000 这 128MB 区域，通用分配使用 0xFFFFFFFF88000000 - 0xFFFFFFFF88080000 这 128MB 区域。这样两者互不干扰，问题解决。

这个修复涉及修改 VMM 的初始 hint 地址，以及把堆区域注册为保留区域。虽然改动不大，但这是一个很重要的架构调整，如果不修复，后续开发会一直被这个问题困扰。

kernel/process 目录将存放所有进程管理相关的代码，包括 process.h、process.c、switch.s 等文件。kernel/demo/process_simple 目录将存放进程演示程序。
