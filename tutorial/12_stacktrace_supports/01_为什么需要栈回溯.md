# 为什么需要栈回溯 —— Stage 12 调试基础设施实战指南

## 前言

写到 Stage 12 的时候，我意识到一个被忽略很久的问题：我们的内核已经跑起来了，有了日志系统，有了串口输出，但当出问题时，我们只知道"出错了"，却不知道"是在哪里出错的"。

这种感觉我太熟了。你在内核里某个地方触发了错误，屏幕上只显示一个冷冰冰的错误码或者地址，比如 `0x10045a`。这是什么鬼？是哪个函数的地址？是从哪里调过来的？如果没有栈回溯，你只能靠猜，靠打日志，靠反复编译测试来定位问题。说实话，这种调试方式让人血压拉满。

所以这一篇我们会一起实现一个完整的栈回溯系统。别担心，我们不会跳过任何步骤，每写一个函数都会解释清楚它是怎么工作的，为什么要这么写，有哪些坑需要避开。准备好了吗？我们开始。

在开始之前，先确认一下你的开发环境。这篇文章假设你已经完成了 Stage 11，链表、数学库和位图都已经实现完毕。

```
操作系统: Ubuntu 22.04 LTS / WSL2 / Arch WSL
编译器:   GCC x86_64-elf-gcc 或类似交叉编译器
构建工具: CMake 3.25 或更高版本
模拟器:   QEMU 7.0 或更高版本
Python:   Python 3.8 或更高版本（用于符号提取脚本）
```

可能有人会问，为什么需要 Python？这是因为我们需要从编译出来的 ELF 文件中提取符号信息，自动生成符号表。当然你也可以手工维护一个地址到函数名的映射表，但每次函数地址变化都要手动更新，这种事情我绝对不会干第二次。

## 调试痛点：没有栈回溯时的困境

让我们先想象一下，当你的内核出现问题时，会发生什么。假设你在某个函数里触发了一个断言失败：

```c
void some_obscure_function(int x) {
    if (x < 0) {
        klog_error("Error: x is negative!\n");
        // 然后呢？是谁调用了这个函数？
        // 从哪里调过来的？中间经过了哪些函数？
        system_halt();
    }
}
```

你只看到了错误消息，但不知道完整的调用链。也许 `some_obscure_function` 被十个不同的地方调用，每个地方的调用条件都不一样，你怎么知道是哪条路径触发的？

更糟糕的情况是，如果你的内核因为空指针解引用或者其他原因直接崩溃了，你连错误消息都看不到，只能对着 QEMU 的死机界面发呆。这时候如果有一个类似 Linux kernel 的 `dump_stack()` 功能，能够打印出当前的调用栈，那该多好。

```
Stack trace:
  #0 0x10045a - some_obscure_function
  #1 0x100320 - middle_layer_function
  #2 0x1001a0 - top_level_handler
  #3 0x100050 - kernel_main
```

一眼就能看出调用路径，问题定位效率提升十倍不止。这就是栈回溯的价值。

## 技术方案对比：如何实现栈回溯

在 x86_64 架构上，有几种常见的栈回溯方法，每种都有其优缺点。我们得先搞清楚它们之间的区别，才能做出正确的选择。

### 方案一：帧指针 (Frame Pointer)

这是最传统也最简单的方案。x86_64 的 System V 调用约定规定，每个函数可以选择使用 RBP 寄存器作为"帧指针"，指向当前栈帧的基址。栈帧的结构非常固定：

```
高地址
    +------------------+  <- 上一个栈帧的 RBP
    |  保存的 RBP      |
    +------------------+  <- 当前 RBP 指向这里
    |  返回地址 (RIP)  |  (RBP + 8)
    +------------------+
    |  局部变量        |  (RBP - 8, -16, ...)
    +------------------+
    |     ...          |
    +------------------+  <- 当前 RSP
低地址
```

遍历栈帧的方法很简单：从当前 RBP 开始，读取保存的 RBP 获取上一个栈帧的位置，读取 RBP+8 获取返回地址。然后重复这个过程，直到 RBP 为 0。

这个方案的优点是简单、可靠、不需要额外的调试信息。缺点是必须保证编译器生成帧指针，这会占用一个通用寄存器（RBP），稍微影响性能。不过对于内核调试来说，这点性能损失完全值得。

### 方案二：DWARF 调试信息

DWARF 是一种调试信息格式，可以精确描述每个函数的栈帧布局，即使没有帧指针也能正确回溯。GCC 可以在编译时生成 DWARF 信息，存放在 ELF 文件的调试段里。

这个方案的优点是精确，即使开启了各种优化也能正确工作。缺点是实现复杂，需要解析 DWARF 格式，这本身就是一个庞大的工程。而且调试信息会显著增加内核镜像的大小。

说实话，如果你只是想做一个简单的内核调试工具，DWARF 简直是杀鸡用牛刀。

### 方案三：ORC (Oops Rewind)

这是 Linux kernel 自己发明的一种栈回溯格式，专门为了解决 DWARF 的问题。ORC 格式更紧凑、解析更快，但它的格式没有公开文档，而且只适用于 Linux 内核。

如果你在做自己的操作系统，这个方案基本不考虑。

### 我们的选择：帧指针

经过上面的分析，答案很清楚了。我们使用帧指针方案，因为：

1. **实现简单** - 只需要遍历链表，几十行代码就能搞定
2. **无需额外数据** - 不需要解析调试信息
3. **编译器支持良好** - GCC/Clang 都有开关控制帧指针生成

代价是需要给编译器加上 `-fno-omit-frame-pointer` 选项，确保它不会优化掉帧指针。这点性能损失对于内核调试来说完全值得接受。

## x86_64 调用约定简介

既然我们选择了帧指针方案，那必须先理解 System V AMD64 ABI 调用约定。这个约定定义了函数调用时寄存器和栈的使用方式。

### 寄存器用途

x86_64 有 16 个通用寄存器，调用约定把它们分成了几类：

| 寄存器 | 分类 | 用途 |
|--------|------|------|
| RAX | 返回值 | 函数返回值 |
| RBX | 被调用者保存 | 跨调用保持不变 |
| RCX | 参数传递 | 第 4 个整数参数 |
| RDX | 参数传递 | 第 3 个整数参数 |
| RSI | 参数传递 | 第 2 个整数参数 |
| RDI | 参数传递 | 第 1 个整数参数 |
| RBP | 被调用者保存 | 帧指针（可选） |
| RSP | 特殊 | 栈指针 |
| R8-R15 | 参数/被调用者保存 | 第 5-6 个参数或被调用者保存 |

这里我们需要关注的是 RBP 和 RSP。RSP 永远指向栈顶，RBP 如果被用作帧指针，就指向当前栈帧的基址。

### 参数传递规则

前 6 个整数/指针参数通过寄存器传递：RDI, RSI, RDX, RCX, R8, R9。第 7 个及以后的参数通过栈传递。浮点参数使用 XMM0-XMM7。

### 栈帧结构

当一个函数被调用时，典型的栈帧变化过程是这样的：

```
调用前:
    RSP 指向某个位置

调用指令 (call):
    1. push 返回地址 (RIP)
    2. RSP -= 8
    3. 跳转到目标函数

函数序言:
    push rbp           # 保存调用者的 RBP
    mov rbp, rsp       # 设置当前帧指针

    [可选] sub rsp, N  # 为局部变量分配空间

此时栈帧布局:
    +------------------+  <- 原来的 RSP
    |  返回地址 (RIP)  |
    +------------------+
    |  保存的 RBP      |  <- 新的 RBP 指向这里
    +------------------+
    |  局部变量区域    |
    +------------------+  <- 新的 RSP

函数尾声:
    leave              # mov rsp, rbp; pop rbp
    ret                # pop RIP; 跳转
```

理解这个结构是实现栈回溯的关键。每个栈帧都保存了上一个栈帧的 RBP，这就像链表一样，把所有栈帧串起来了。

## 我们要实现的目标

现在我们对背景知识有了足够的了解，可以明确一下我们这个阶段要做什么：

1. **栈回溯核心功能** - 能够遍历调用栈，收集返回地址
2. **符号解析系统** - 能够把地址转换成可读的函数名
3. **自动化符号表生成** - 从 ELF 文件自动提取符号，不需要手工维护
4. **美观的输出格式** - 用表格形式展示栈回溯信息

实现之后，我们在内核里任何地方调用 `dump_stack()`，都能看到类似这样的输出：

```
╔═══════════════════════════════════════════════════════════════╗
║                      Stack Trace                             ║
╠═══════════════════════════════════════════════════════════════╣
║  RSP: 0x0000000000007f00                                    ║
║  RBP: 0x0000000000007f20                                    ║
╠═══════════════════════════════════════════════════════════════╣
║  #  Address           Function                           ║
╠═══════════════════════════════════════════════════════════════╣
║  0   0x0000000000010120  kernel_main                    ║
║  1   0x00000000000100a0  test_function                 ║
║  2   0x0000000000010050  another_function              ║
╚═══════════════════════════════════════════════════════════════╝
```

不仅能看到地址，还能看到对应的函数名。如果地址在函数中间，还能显示偏移量，比如 `function_name + 0x1c`。
