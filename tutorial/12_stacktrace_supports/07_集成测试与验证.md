## 第一步：在欢迎界面添加栈回溯测试

我们希望在内核启动时自动演示栈回溯功能，这样每次启动都能验证功能正常。修改 `kernel/welcomes/serial_welcome.c`：

```c
#include "stacktrace/stacktrace.h"

// 测试函数 - 创建多层调用
static void demo_level_3(void) {
    // 这里会打印当前调用栈
    dump_stack(10);
}

static void demo_level_2(void) {
    demo_level_3();
}

static void demo_level_1(void) {
    demo_level_2();
}

// 在欢迎信息的最后添加测试
void serial_welcome(void) {
    // ... 原有的欢迎信息代码 ...

    klog_info("\n");
    klog_info("╔═══════════════════════════════════════════════════════════════╗\n");
    klog_info("║           Stack Trace Demo - Calling dump_stack()           ║\n");
    klog_info("╚═══════════════════════════════════════════════════════════════╝\n");
    klog_info("\n");

    demo_level_1();
}
```

这样当内核启动时，欢迎界面会自动触发一次栈回溯，显示从 `demo_level_3` → `demo_level_2` → `demo_level_1` → `serial_welcome` → `kernel_main` 的调用链。

## 第三步：用 GDB 验证栈帧

GDB 是验证栈回溯正确性的最好工具。我们可以用 GDB 查看实际的栈帧结构，然后和我们实现的栈回溯结果对比。

首先，用调试模式启动 QEMU：

```bash
cd build
qemu-system-x86_64 -drive format=raw,file=disk.img -nographic -serial mon:stdio -s -S
```

`-s` 参数让 QEMU 监听 1234 端口的 GDB 连接，`-S` 让 CPU 在启动时暂停。

然后在另一个终端启动 GDB：

```bash
gdb build/kernel/kernel.elf
```

在 GDB 中连接到 QEMU：

```
(gdb) target remote :1234
Remote debugging using :1234
0x000000000001000a in kernel_entry ()
```

现在设置断点并继续运行：

```
(gdb) break demo_level_3
Breakpoint 1 at 0x101a0
(gdb) continue
Continuing.

Breakpoint 1, demo_level_3 () at kernel/stacktrace/stacktrace.c:XX
```

现在用 GDB 查看栈帧：

```
(gdb) backtrace
#0  demo_level_3 ()
#1  0x00000000000101b0 in demo_level_2 ()
#2  0x00000000000101c0 in demo_level_1 ()
#3  0x0000000000010050 in serial_welcome ()
#4  0x000000000001000a in kernel_main ()
```

对比一下我们栈回溯的输出，应该能看到完全一致的调用链。如果 GDB 的 `backtrace` 和我们的 `dump_stack` 输出一致，说明实现是正确的。

还可以查看具体的栈帧内容：

```
(gdb) info frame
Stack level 0, frame at 0x7ea0:
 rip = 0x101a0 in demo_level_3; saved rip = 0x101b0
 called by frame at 0x7ec0
 Arglist at 0x7e90, args:
 Locals at 0x7e90, Previous frame's sp is 0x7ea0
 Saved registers:
  rbp at 0x7e90, rip at 0x7e98

(gdb) print $rbp
$1 = 0x7e90

(gdb) print $rsp
$2 = 0x7e80

(gdb) x/2gx $rbp
0x7e90:	0x0000000000007eb0	0x00000000000101b0
```

`x/2gx $rbp` 的输出显示了栈帧内容：
- `0x7e90` 处的值 `0x7eb0` 是保存的上一个 RBP
- `0x7e98` 处的值 `0x101b0` 是返回地址（`demo_level_2` 的入口）

这和我们在栈回溯中读取的值一致，验证了遍历逻辑的正确性。

## 第四步：创建错误处理场景

栈回溯最实用的场景是在错误处理中。让我们创建一个模拟的错误处理函数：

```c
#include "stacktrace/stacktrace.h"

// 系统停机函数（假设你已经实现了）
extern void system_halt(void);

// 内核恐慌函数
void kernel_panic(const char* message) {
    kprintf(KLOG_BACKEND_SERIAL, "\n");
    kprintf(KLOG_BACKEND_SERIAL, "╔═══════════════════════════════════════════════════════════════╗\n");
    kprintf(KLOG_BACKEND_SERIAL, "║                      KERNEL PANIC                           ║\n");
    kprintf(KLOG_BACKEND_SERIAL, "╠═══════════════════════════════════════════════════════════════╣\n");
    kprintf(KLOG_BACKEND_SERIAL, "║  %-55s ║\n", message);
    kprintf(KLOG_BACKEND_SERIAL, "╚═══════════════════════════════════════════════════════════════╝\n");
    kprintf(KLOG_BACKEND_SERIAL, "\n");

    // 打印栈回溯
    dump_stack_full();

    klog_error("System halted. Please restart.\n");
    system_halt();
}

// 测试触发恐慌
void test_panic(void) {
    kernel_panic("This is a test panic message");
}

void kernel_main(void) {
    // ... 初始化代码 ...

    // 如果想测试恐慌，取消注释下面这行
    // test_panic();

    // ... 其他代码 ...
}
```

当你触发恐慌时，不仅能看到错误消息，还能看到完整的调用栈，这对调试非常有帮助。

## 第五步：验证符号解析的准确性

我们来验证符号解析是否准确。用 `readelf` 查看符号表：

```bash
readelf -s build/kernel/kernel.elf | grep -E "(demo_level|serial_welcome|kernel_main)"
```

输出类似：

```
    51: 00000000000101a0    10 FUNC    LOCAL  DEFAULT    1 demo_level_3
    52: 00000000000101b0    10 FUNC    LOCAL  DEFAULT    1 demo_level_2
    53: 00000000000101c0    10 FUNC    LOCAL  DEFAULT    1 demo_level_1
    ...
```

对比栈回溯输出的地址，应该和 `readelf` 显示的地址一致。如果发现地址不匹配，可能是：

1. 符号表没有更新 —— 重新编译
2. 函数被内联了 —— 加上 `__attribute__((noinline))`
3. 帧指针被优化掉了 —— 检查编译选项

## 第六步：常见问题排查

这里列出一些常见问题及其解决方法。

### 问题一：符号显示为 `???`

**症状**：栈回溯输出中函数名显示为 `???` 而不是实际名称。

**原因**：
1. 符号表文件没有生成
2. 符号表是空的占位符
3. 地址不在 `.text` 段范围内

**解决方法**：
```bash
# 检查符号文件是否存在
ls -la kernel/stacktrace/symbols.c

# 检查符号文件内容
cat kernel/stacktrace/symbols.c

# 如果是空的，手动运行符号提取脚本
python3 scripts/extract_symbols.py build/kernel/kernel.elf -o kernel/stacktrace

# 重新编译
cd build && make
```

### 问题二：栈回溯只有一帧

**症状**：栈回溯只打印当前函数，然后就没有了。

**原因**：帧指针被编译器优化掉了。

**解决方法**：检查编译选项，确保有 `-fno-omit-frame-pointer`。

在根 `CMakeLists.txt` 中添加：

```cmake
option(CCOS_ENABLE_FRAME_POINTER "Enable frame pointer for stack tracing" ON)

if(CCOS_ENABLE_FRAME_POINTER)
    target_compile_options(kernel PRIVATE
        -fno-omit-frame-pointer
        -fno-optimize-sibling-calls
    )
endif()
```

### 问题三：显示 `<invalid frame>`

**症状**：栈回溯输出中某帧显示 `<invalid frame>`。

**原因**：栈帧地址验证失败，可能是：
1. 栈地址范围设置不对
2. 栈帧被越界写破坏

**解决方法**：
用 GDB 查看实际的 RBP 值，调整 `STACK_BASE` 和 `STACK_SIZE`：

```c
#define STACK_BASE    0x80000UL
#define STACK_SIZE    0x10000UL
```

### 问题四：函数顺序不对

**症状**：栈回溯显示的函数顺序和实际调用顺序不一致。

**原因**：这通常不会发生，除非栈帧被破坏。

**解决方法**：用 GDB 验证实际的栈帧结构：

```
(gdb) backtrace
(gdb) info frame
(gdb) x/10gx $rsp
```

## 第七步：性能考虑

栈回溯虽然很有用，但也会带来一些开销：

1. **编译开销**：`-fno-omit-frame-pointer` 会占用一个寄存器，可能稍微影响性能
2. **运行时开销**：每次调用 `dump_stack` 都要遍历栈帧
3. **符号表空间**：符号表会占用一定的内核空间

如果你的系统对性能非常敏感，可以考虑：

1. 只在 Debug 构建中启用栈回溯
2. 减少默认的栈帧深度
3. 使用压缩的符号表格式

但对于内核开发来说，这些开销完全值得。栈回溯带来的调试便利性远大于性能损失。
