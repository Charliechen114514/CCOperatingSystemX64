# 为什么要做这些 —— VGA 图形界面与调试体验升级

说实话，之前那个黑底白字的启动界面我实在绷不住了。

都 2026 年了，我们的 CCOS 启动时还是一坨纯文本输出，跟几十年前的 DOS 没啥两样。而且每次想调试个东西，还得手动去跑 CMake 构建，然后启动 QEMU，再打开 VSCode 连接 GDB —— 这一套流程下来，本来就烦躁的调试心情更加雪上加霜。

你可能会说："内核开发嘛，能用就行了，要什么花哨。"

但我不是这样想的。操作系统本来就是一个给人"看"和"用"的东西，第一印象太重要了。用户按下电源键，首先看到的就是启动界面，如果这东西做得像上世纪 80 年代的产物，谁还相信你的系统能干正经事？

更实际一点说，调试体验直接决定开发效率。每次改一行代码就要手动跑一遍编译、启动、连接的流程，这套繁琐的步骤我真的是受够了。所以这一阶段我们要干两件事：给 CCOS 换个好看的"脸"，让调试体验不那么痛苦。

---

## 我们现在有什么

在 stage 06 阶段，我们已经打下了不错的基础。VGA 文本模式驱动已经能工作了，我们可以打印字符、设置颜色，还能通过 GDB 远程调试。VSCode 也能 attach 到 QEMU 进行图形化调试。

但问题也很明显，或者说问题还很突出。

当你启动系统的时候，屏幕上会出现这样一段纯文本输出：

```
========================
CCOperating System X64
Version 0.1.0 [Alpha]
========================

> _ （光标在闪烁）
```

就这？完了？

是的，就这。没有动画，没有视觉冲击力，没有任何"这是一个现代操作系统"的感觉。这就是上世纪 70 年代 Unix 系统启动时的风格，或者更准确地说，连那个年代的系统都不如。

再看调试流程。每次你想调试的时候，都要手动执行这么一堆命令：

```bash
cmake --build build                    # 手动构建，确保是最新代码
qemu-system-x86_64 -drive format=raw,file=build/boot.img \
    -vga std -display vnc=:0 -s -S &   # 启动 QEMU
vncviewer localhost:5900                 # 打开 VNC 查看输出
```

然后在 VSCode 里按 F5 启动调试。调完之后还得记得手动清理 QEMU 进程，否则下次启动端口就被占用了。

这一套流程跑下来，改一行代码测试一下的时间都够我煮碗泡面了。而且最容易忘的就是清理 QEMU 进程，结果后台就堆了一堆僵尸 qemu-system，吃内存不说，还占用着调试端口。

---

## 我们要达成什么

我们的目标很明确，分为两个方向。

第一个方向是视觉上的升级。我们想要一个像样的启动界面，而不是那个干巴巴的文本输出。具体来说，我们希望看到这样的启动体验：一个黑色的屏幕开始点亮，然后星星点点的光斑开始闪烁，像夜空一样。接着，一个彩色的边框慢慢出现，颜色在青蓝、蓝色、紫色、红色、黄色、绿色之间流动，给人一种"系统正在苏醒"的感觉。

在边框的中央，是我们精心设计的 ASCII Art Logo。用字符勾勒出的 "CCOS" 字样，配合简洁的系统名称和版本信息，整体呈现出一种专业而不失个性的风格。背景中还有那些闪烁的星点，给整个界面增添了一份科技感和神秘感。

这种启动界面虽然简单，但传递出的信号是完全不同的：这是一个经过精心设计的系统，而不是一个随便拼凑的玩具。

第二个方向是调试体验的升级。我们希望调试流程能变成这样：只需要一个命令 `./scripts/launch_qemu_for_vscode_debug.sh`，脚本就会自动完成所有准备工作。它会清理 build 目录确保调试的是最新代码，然后用 Debug 模式重新构建，接着启动 QEMU 调试模式并开始监控 GDB 连接状态。

在 VSCode 端，只需要按 F5 启动调试就行了。停止调试的时候，QEMU 会自动停止，不需要手动清理进程。不需要记一堆命令，不用担心忘记清理，整个流程丝滑得像在调试用户态程序一样。

---

## 技术路线

我们分几个阶段来实现这些目标。

第一阶段是 VGA 辅助函数。现在的 VGA 驱动只能顺序输出字符，想定位到屏幕指定位置输出很麻烦。我们需要添加一个 `vga_put_char_at()` 函数，能够在任意坐标画一个字符。还需要一个 `vga_delay()` 延迟函数，这是实现动画效果的基础。这些函数看起来简单，但它们是所有后续图形功能的基础。

第二阶段是 GUI 绘图库。有了定位输出的能力，我们就可以构建更高级的绘图原语。我们会实现矩形边框、填充矩形、水平线和垂直线这些基础图形，然后在这个基础上构建面板系统（带标题的边框）、居中文本、进度条等高级组件。这些组件可以组合使用，快速构建出各种 UI 界面。

第三阶段是欢迎界面实现。有了绘图库之后，我们就可以开始创作启动界面了。首先要设计 ASCII Art Logo，这需要一些艺术感，但更重要的是保持字符对齐和合适的宽度。然后实现星空背景效果，通过伪随机算法在屏幕上分布星点。接着是彩色动画边框，通过颜色循环和位置偏移实现流动效果。最后是打字机文本效果，让系统信息像有人在打字一样逐字符出现。

第四阶段是调试脚本改进。我们会写一个智能的调试脚本 `launch_qemu_for_vscode_debug.sh`。这个脚本会自动清理并重新构建项目，确保你调试的是最新代码。它会启动 QEMU 调试模式，然后监控 GDB 的连接状态。当检测到 GDB 断开连接时，它会自动停止 QEMU，彻底解决了进程残留的问题。我们还需要配置 VSCode 的 launch.json，让它能正确连接到 QEMU 的 GDB 服务器。

## 环境确认

在开始之前，我们先确认一下环境是否就绪。

你应该已经完成了 stage 06 的工作，拥有基础的 VGA 驱动。检查一下 `kernel/driver/vga/` 目录，应该能看到 `vga.c`、`vga.h`、`vga_config.h` 这些文件。类型定义应该在 `kernel/defines/types.h` 中，GDB 调试脚本 `scripts/debug.sh` 应该也能正常工作。

VSCode 的基础调试配置应该已经有了，至少能 attach 到 QEMU 进行简单的调试。

让我们验证一下当前状态是否正常。首先确认你在项目根目录，然后检查 VGA 驱动文件是否存在。接着尝试构建项目，使用 Debug 模式配置 CMake 并编译。最后尝试运行 `cmake --build build --target vga-run`，如果 QEMU 窗口能正常启动并且有输出，那我们就可以开始了。

如果以上步骤有问题，建议先回到 stage 06 的教程把基础打牢。调试基础设施和 VGA 驱动是在一个能工作的系统上添加便利工具，不是在一堆问题上面叠加新东西。
