# 02 - 写时复制机制详解

说实话，第一次真正理解 COW 的工作原理时，我被它的巧妙设计震撼了——这么简单却这么高效。

---

## COW 的基本原理

写时复制的核心思想可以用一句话概括：**共享直到修改**。

### 从 fork() 说起

让我们先看看传统 fork() 的问题：

```
父进程地址空间: [代码段][数据段][堆][栈]
                      ↓ 复制全部
子进程地址空间: [代码段][数据段][堆][栈]  (独立物理内存)
```

这种方式的问题很明显：大量内存复制，即使父子进程不会修改大部分内容。

现在看看 COW fork() 的做法：

```
父进程地址空间: [代码段][数据段][堆][栈]
                      ↓ 共享物理页
子进程地址空间: [代码段][数据段][堆][栈]  (相同物理内存)

物理内存: [代码页][数据页][堆页][栈页]  ← 只有一份
```

父子进程的页表都指向相同的物理页，但这些页被标记为只读。

### 写入时发生了什么

当某个进程尝试写入时，硬件会触发页错误：

```
进程尝试写入共享页
    ↓
CPU 检测到写权限不足
    ↓
触发 #PF (Page Fault)
    ↓
内核页错误处理器
    ↓
检查 COW 标志 → 这是 COW 页!
    ↓
分配新物理页 + 复制内容
    ↓
更新页表 → 指向新页，设置写权限
    ↓
恢复进程执行
    ↓
写入指令重新执行 → 成功!
```

这个过程对进程是完全透明的——它感觉不到任何 COW 的存在，只是写入操作正常完成了。

## 引用计数管理

COW 的一个关键问题是：我们需要知道有多少个进程在共享同一个物理页。这就是引用计数的作用。

### 引用计数的作用

每个被 COW 保护的物理页都有一个引用计数：

```
初始状态（fork 后）:
    物理页 X 的引用计数 = 2 (父子进程各一)

如果父进程写入:
    引用计数减 1 → 变成 1
    因为 refcount = 1，不需要复制!
    直接设置写权限，父进程独占该页

如果此时子进程也写入同一页:
    引用计数减 1 → 变成 0 (不可能，父进程已经独占)
    子进程有自己的副本，不会冲突
```

### 引用计数 = 1 的优化

这是一个重要的优化：当引用计数变成 1 时，意味着只有一个进程在使用这个页，不需要复制。我们只需要：

1. 把引用计数从 1 减到 0（从 COW 跟踪中移除）
2. 直接设置页表项的写权限
3. 恢复执行

这样避免了不必要的内存复制，提高了性能。

### 引用计数的数据结构

我们需要为每个 COW 页存储：

```c
typedef struct cow_block {
    physical_addr_t    orig_phys;     // 原始物理页地址
    atomic_t           refcount;      // 原子引用计数
} cow_block_t;
```

使用 `atomic_t` 是因为多核 CPU 上可能同时有多个 CPU 触发 COW，原子操作保证了引用计数的正确性。

## COW 页表标志位设计

如何在页错误时知道这是一个 COW 页而不是真正的权限错误？答案是使用页表项的保留位。

### x86_64 页表项的保留位

x86_64 页表项格式中有几个"可用位"（Available bits），软件可以自由使用：

```
┌────────┬────────┬────────┬────────┬────────┬────────┐
│ 可用位  │              物理页号              │ 标志位  │
│ 位 63-52│            位 51-12               │ 位 11-0 │
└────────┴────────┴────────┴────────┴────────┴────────┘
          ↑
      我们可以用这些位存储 COW 标志
```

我们选择使用第 9 位作为 COW 标志：

```c
#define COW_FLAG_MASK    (1ULL << 9)   // 使用第9位
```

### COW 标志的作用

当一个页被设置为 COW 时，我们这样做：

1. 清除页表项的 RW（读写）位 → 页变成只读
2. 设置 COW_FLAG_MASK → 标记为 COW 页

页错误处理时，我们检查：

```c
if (!(error_code & PF_ERROR_WRITE)) {
    // 不是写入错误，不是 COW
    return COW_ERR_NOT_COW;
}

page_query(pml4, fault_addr, &query);

if (!cow_is_cow_page(query.flags)) {
    // 没有 COW 标志，不是 COW 页错误
    return COW_ERR_NOT_COW;
}

// 这是 COW 页错误，继续处理...
```

### 为什么不用软件结构？

你可能会问：为什么不直接在软件里维护一个 COW 页列表，而要用页表标志？

答案是性能。页错误时，CPU 已经把页表项放在寄存器里了，检查一个标志位只需要一条指令。如果用软件结构，我们需要：

1. 从页错误地址计算页号
2. 在哈希表中查找
3. 检查是否是 COW 页

这比直接检查页表项标志慢得多。

## COW 处理完整流程

现在让我们把所有部分组合起来，看看 COW 处理的完整流程。

### 场景：fork() 后父子进程共享内存

```
1. fork() 之前:
   父进程: 虚拟地址 0x1000 → 物理页 0x5000 (可写)

2. fork() 创建 COW:
   父进程: 虚拟地址 0x1000 → 物理页 0x5000 (只读 + COW)
   子进程: 虚拟地址 0x1000 → 物理页 0x5000 (只读 + COW)
   COW 块: { orig_phys: 0x5000, refcount: 2 }

3. 父进程尝试写入 0x1000:
   → 触发 #PF (写入只读页)
   → pf_handler 被调用
   → 检测到 COW 标志
   → 查找 COW 块
   → refcount = 2 > 1
   → 分配新页 0x6000
   → 复制 0x5000 的内容到 0x6000
   → 更新父进程页表: 0x1000 → 0x6000 (可写)
   → 减少引用计数: refcount = 1
   → 恢复父进程执行
   → 父进程的写入成功完成

4. 此时状态:
   父进程: 虚拟地址 0x1000 → 物理页 0x6000 (可写)
   子进程: 虚拟地址 0x1000 → 物理页 0x5000 (只读 + COW)
   COW 块: { orig_phys: 0x5000, refcount: 1 }

5. 子进程尝试写入 0x1000:
   → 触发 #PF
   → 检测到 COW 标志
   → 查找 COW 块
   → refcount = 1
   → 直接设置写权限，不需要复制!
   → 子进程页表: 0x1000 → 0x5000 (可写)
   → refcount = 0，从 COW 跟踪中移除
   → 恢复子进程执行
```

### 关键点总结

1. **初始状态**：fork() 后所有共享页都是只读的，带有 COW 标志
2. **第一次写入**：refcount > 1，需要分配新页并复制
3. **后续写入**：refcount = 1，直接设置写权限
4. **进程退出**：减少所有 COW 页的引用计数，refcount = 0 时释放

## 其他操作系统的 COW 实现

了解其他系统如何实现 COW 有助于我们理解不同设计权衡。

### Linux 的 COW 实现

Linux 使用 `struct page` 中的 `_count` 和 `_mapcount` 字段来跟踪页面引用：

- `_count`：页面的引用计数
- `_mapcount`：页面被映射到多少个页表

Linux 的 fork() 实现：

1. 遍历父进程的所有 VMA（虚拟内存区域）
2. 对每个区域，复制页表项到子进程
3. 增加页面的 `_mapcount`
4. 清除 RW 位，设置只读

当发生写入页错误时：

1. 检查 `vm_area_struct` 的 `VM_SHARED` 标志
2. 如果不是共享映射，调用 `do_wp_page()` 处理 COW
3. 如果是共享映射，触发 SIGSEGV

### FreeBSD 的 COW 实现

FreeBSD 使用类似的机制，但有一些优化：

1. **页着色**：考虑 CPU 缓存拓扑，分配相同颜色的页
2. **零页优化**：全零的页面不分配物理内存，映射到共享的零页
3. **COW 合并**：定期扫描相同内容的页，合并为 COW

### Windows 的 COW 实现

Windows 的进程创建使用 `CreateProcess` 而非 fork，但内存管理器也支持 COW：

- 内存映射文件可以指定 COW 属性
- 进程间共享内存可以使用 COW
- 堆管理器使用 COW 优化大块分配

## COW 优化技术

现代操作系统在基础 COW 之上做了很多优化。

### 页面合并 (Page Coalescing)

定期扫描内存，发现相同内容的页可以让它们共享物理页：

```
扫描前:
   进程 A: 页 X (内容 = "Hello")
   进程 B: 页 Y (内容 = "Hello")
   浪费: 2 个物理页

扫描后:
   进程 A: 页 X → 物理页 P (只读 + COW)
   进程 B: 页 Y → 物理页 P (只读 + COW)
   节省: 1 个物理页
```

Linux 的 KSM (Kernel Samepage Merging) 就是这个功能。

### 写时合并 (Copy-on-Write Merging)

多个写入者同时修改同一页时，可以延迟复制：

```
多个进程同时写入同一 COW 页:
    ↓
只复制一次，所有写入者使用同一副本
    ↓
分别应用各自的修改
```

这减少了复制的次数，但实现复杂度很高。

### 零页优化

全零的页面不需要分配物理内存：

```
所有进程的未初始化数据 (BSS)
    ↓
映射到同一个预先清零的物理页
    ↓
首次写入时才真正分配
```

这大大减少了 BSS 段的内存占用。

## 下一步

现在我们已经理解了 COW 机制的原理，包括引用计数、页表标志、处理流程等。但还有一个关键问题：如何高效地管理和查找 COW 块？

我们需要一个数据结构来存储所有 COW 页的元数据，支持快速的查找、插入和删除操作。这就是下一节要讲的泛型哈希表。

哈希表是实现 COW 的基础，理解它的设计和工作原理对于实现高效的 COW 系统至关重要。
