# CCOS CMake 构建系统与 C 内核 - 开发笔记

本文档记录了 CCOS 从 Makefile 迁移到 CMake，以及内核从纯汇编切换到 C 语言过程中的开发经验和设计决策。

---

## 1. 迁移动机

### 1.1 为什么迁移到 CMake？

在 `stage/03_unified_boots` 阶段，我们使用简单的 Makefile：

```makefile
# 简单但有限制的 Makefile
AS = nasm
ASFLAGS = -f bin
...
$(BOOTLOADER_BIN): $(BOOTLOADER_ASM)
    $(AS) $(ASFLAGS) $< -o $@
```

**Makefile 的局限性**：

1. **依赖检测不完善** - 增加新文件需要手动修改 Makefile
2. **构建配置单一** - 难以支持 Debug/Release 两种配置
3. **工具链检测** - 无法自动检测 NASM、QEMU 是否安装
4. **跨平台能力** - 虽然目标是 x86_64，但开发者可能在不同平台上构建
5. **IDE 集成** - 现代IDE对 CMake 支持更好

**CMake 的优势**：

1. **自动依赖扫描** - 源文件变化自动处理
2. **多配置支持** - Debug/Release/MinSizeRel 等内置配置
3. **工具链检测** - `find_program()` 自动查找工具
4. **模块化构建** - `add_subdirectory()` 清晰分离子项目
5. **生成器表达式** - 强大的条件编译支持

### 1.2 为什么切换到 C 内核？

在 `stage/03` 阶段，内核是纯汇编代码：

```nasm
; kernel.asm - 纯汇编内核
section .text
    org 0x10000
    bits 64

kernel_start:
    mov rdi, 0xB8000 + 160 * 5
    mov word [rdi], 0x1F58
    cli
    hlt
    jmp kernel_start
```

**纯汇编的问题**：

1. **可读性差** - 复杂逻辑难以理解
2. **维护困难** - 修改代码风险高
3. **开发效率低** - 简单操作需要大量代码
4. **调试困难** - 没有高级语言的调试支持
5. **可移植性** - 汇编绑定特定架构

**C 语言的优势**：

1. **代码清晰** - 高层结构更易理解
2. **快速开发** - 表达力强，代码量少
3. **调试友好** - GDB 源码级调试
4. **现代工具** - 静态分析、代码格式化等工具支持
5. **团队协作** - C 代码更易于协作开发

## 2. CMake 架构设计

### 2.1 目录结构设计

```
CMakeLists.txt           # 根配置
├── boot/
│   └── CMakeLists.txt   # Bootloader 子项目
├── kernel/
│   └── CMakeLists.txt   # 内核子项目
└── cmake/
    └── ccos_config.h.in # 配置头文件模板
```

**设计原则**：

1. **单一职责** - 每个 CMakeLists.txt 只负责一个模块
2. **层次清晰** - 根配置协调子项目
3. **易于扩展** - 添加新模块只需 `add_subdirectory()`

### 2.2 根 CMakeLists.txt 设计

```cmake
cmake_minimum_required(VERSION 3.20)
project(CCOS_x64 ASM C)

# 工具链检测
find_program(NASM nasm REQUIRED)
find_program(QEMU qemu-system-x86_64 REQUIRED)

# 编译器标志
add_compile_options(
    $<$<COMPILE_LANGUAGE:C>:-ffreestanding>
    $<$<COMPILE_LANGUAGE:C>:-fno-builtin>
    ...
)

# 子目录
add_subdirectory(boot)
add_subdirectory(kernel)

# 自定义目标
add_custom_target(run ...)
add_custom_target(vga-run ...)
add_custom_target(debug ...)
```

**关键设计点**：

1. **`find_program`** - 确保构建前检查工具是否存在
2. **生成器表达式** - `$<COMPILE_LANGUAGE:C>` 只对 C 应用标志
3. **自定义目标** - 封装常用操作为 make 目标

### 2.3 内核 CMakeLists.txt 设计

```cmake
# 汇编入口
add_custom_command(
    OUTPUT kernel_entry.o
    COMMAND nasm -f elf64 kernel_entry.asm -o kernel_entry.o
    ...
)

# C 代码
add_library(kernel_main OBJECT kernel_main.c)

# 链接
add_custom_command(
    OUTPUT kernel.elf
    COMMAND ld -m elf_x86_64 -T linker.ld ... -o kernel.elf
    ...
)

# 提取二进制
add_custom_command(
    OUTPUT kernel.bin
    COMMAND objcopy -O binary kernel.elf kernel.bin
    ...
)
```

**设计思路**：

1. **分离编译和链接** - 先编译成 .o，再链接成 .elf，最后提取 .bin
2. **保留 ELF 文件** - 用于 GDB 调试（包含符号信息）
3. **使用 OBJECT 库** - 便于未来添加更多 C 文件

## 3. C 内核架构设计

### 3.1 两阶段入口设计

为什么保留汇编入口而不直接从 C 开始？

**问题**：在调用 C 代码前，需要准备好运行环境：

1. 设置栈指针 (RSP)
2. 清零 BSS 段
3. 可能的硬件初始化

这些操作用汇编更直接。

**架构**：

```
┌─────────────────────────────────────────┐
│   bootloader (跳转到 0x10000)           │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   kernel_entry.asm (汇编入口)            │
│   ┌─────────────────────────────────┐   │
│   │ 1. 关中断 (cli)                 │   │
│   │ 2. 设置栈 (rsp = 0x80000)      │   │
│   │ 3. 清零 BSS                     │   │
│   │ 4. 调用 kernel_main()           │   │
│   └─────────────────────────────────┘   │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   kernel_main.c (C 主函数)              │
│   ┌─────────────────────────────────┐   │
│   │ - VGA 输出 'C'                  │   │
│   │ - 初始化代码                    │   │
│   │ - 主循环                        │   │
│   └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

### 3.2 BSS 清零的重要性

```assembly
; 清零 BSS 段
extern __bss_start
extern __bss_end
mov rdi, __bss_start
mov rcx, __bss_end
sub rcx, rdi        ; 计算 BSS 大小
shr rcx, 3          ; 转换为 qwords
xor eax, eax        ; eax = 0 (用于 stosq)
rep stosq           ; 填充 0
```

**什么是 BSS？**
- BSS (Block Started by Symbol) 存放未初始化的全局/静态变量
- C 标准要求这些变量初始化为 0
- 链接器在 ELF 中标记 `__bss_start` 和 `__bss_end`

**不清零的后果**：
- 未初始化变量包含随机内存内容
- 程序行为不可预测
- 可能导致安全漏洞

### 3.3 类型定义设计

```c
// types.h - 基础类型定义
#ifndef CCOS_TYPES_H
#define CCOS_TYPES_H

typedef unsigned char      uint8_t;
typedef unsigned short     uint16_t;
typedef unsigned int       uint32_t;
typedef unsigned long long uint64_t;

#endif
```

**为什么自己定义类型？**
- Freestanding 环境没有 `<stdint.h>`
- 需要确保类型大小固定
- 与汇编代码接口需要精确类型

## 4. 关键决策与取舍

### 4.1 编译模型选择：`-mcmodel=large`

GCC 提供三种代码模型：
- **small** - 代码和数据在 2GB 以内，可使用相对寻址
- **kernel** - 类似 small，但代码在负地址空间
- **large** - 无限制，任何地方都可寻址

**选择 large 的原因**：
- 内核未来可能增长很大
- 可能加载内核到高地址
- 更灵活的内存布局

**代价**：
- 指针更大（需要 64 位绝对地址）
- 略微降低性能
- 代码体积稍大

### 4.2 链接脚本设计

```ld
ENTRY(kernel_start)

SECTIONS
{
    . = 0x10000;    /* 内核加载地址 */

    .text : { *(.text) }
    .rodata : { *(.rodata) }
    .data : { *(.data) }

    .bss : {
        __bss_start = .;
        *(.bss)
        __bss_end = .;
    }

    /DISCARD/ : { *(.comment) *(.eh_frame) }
}
```

**设计考虑**：

1. **明确的加载地址** - `. = 0x10000` 与 bootloader 一致
2. **BSS 符号导出** - 供汇编代码使用
3. **丢弃无用段** - 减小最终二进制大小

### 4.3 运行目标设计

```cmake
# 文本模式运行
add_custom_target(run
    COMMAND ${QEMU} -drive format=raw,file=boot.img -nographic
)

# VGA 运行 (VNC 后端)
add_custom_target(vga-run
    COMMAND ${QEMU} -drive format=raw,file=boot.img -vga std -display vnc=:0
)

# 调试模式
add_custom_target(debug
    COMMAND ${QEMU} -drive format=raw,file=boot.img -s -S
)
```

**为什么使用 VNC 后端？**
- GTK/SDL 在 WSL 上可能有兼容问题
- VNC 更稳定，跨平台一致性好
- 可以远程连接调试

## 5. 开发中的挑战

### 5.1 挑战：CMake 与 NASM 的集成

**问题**：NASM 的 `%include` 依赖如何处理？

CMake 不能自动解析 NASM 的 `%include` 指令。

**解决方案**：
```cmake
# 简单方案：只列出主文件，NASM 会处理 include
add_custom_command(
    OUTPUT bootloader.bin
    COMMAND ${NASM} -f bin bootloader.asm -o bootloader.bin
    DEPENDS bootloader.asm  # NASM 会处理 %include
)
```

**更完善的方案**（未来改进）：
- 使用 CMake 的 dependency scanner
- 或手动列出所有依赖文件

### 5.2 挑战：Freestanding 环境的限制

**问题**：没有标准库，很多常用函数不能用

**限制清单**：
- ❌ `printf()` - 需要自己实现 `kprintf()`
- ❌ `memcpy()` - 使用 builtin 或自己实现
- ❌ `memset()` - 使用 builtin 或自己实现
- ❌ `assert()` - 需要自己实现

**当前处理**：
```c
// 使用 inline 汇编实现简单的 halt
while (1) {
    __asm__ volatile("hlt");
}
```

**未来方向**：
- 实现基础 libc 替代 (`string.c`, `stdio.c`)
- 或使用编译器 builtin (`__builtin_memcpy`)

### 5.3 挑战：栈地址选择

**问题**：栈应该放在哪里？

**考虑因素**：
- 不能与代码/数据冲突
- 不能太小导致溢出
- 不能随意放置（未来可能有页表）

**当前选择**：`0x80000`

**内存布局**：
```
0x10000 - 0x7FFFF   内核 (约 448KB)
0x80000             栈顶 (向下增长)
```

**未来改进**：
- 使用链接脚本分配专门的栈段
- 实现栈溢出检测

## 6. 测试策略

### 6.1 验证 C 代码正常工作

**测试方法**：在不同 VGA 行输出不同字符

```assembly
; kernel_entry.asm - 输出 'X' 到第 5 行
mov rdi, 0xB8000 + 160 * 5
mov word [rdi], 0x1F58  ; 'X'
```

```c
// kernel_main.c - 输出 'C' 到第 6 行
volatile uint16_t *vga = (uint16_t *)0xB8000;
vga[160 * 6] = 0x1F43;  // 'C'
```

**预期结果**：
```
第 5 行: X
第 6 行: C
```

**含义**：
- 看到 X → 汇编入口执行成功
- 看到 C → C 代码执行成功

### 6.2 验证 BSS 清零

```c
// 未初始化的全局变量应该在 BSS
static int uninitialized_var;

void kernel_main(void) {
    if (uninitialized_var == 0) {
        // BSS 清零成功
        vga[0] = 0x1F4F;  // 'O' for OK
    } else {
        // BSS 未清零
        vga[0] = 0x1F45;  // 'E' for Error
    }
}
```

### 6.3 验证链接脚本

使用 `objdump` 查看最终布局：

```bash
objdump -h build/kernel.elf
```

预期输出：
```
Sections:
Idx Name          Size      VMA       LMA
  0 .text         00000120  00010000  00010000
  1 .rodata       00000000  00010120  00010120
  2 .data         00000000  00010120  00010120
  3 .bss          00000004  00010120  00010120
```

## 7. 性能考虑

### 7.1 编译优化

当前配置：
```cmake
set(CMAKE_C_FLAGS_DEBUG "-g -O0")      # 无优化，方便调试
set(CMAKE_C_FLAGS_RELEASE "-O2 -DNDEBUG")  # O2 优化
```

**优化级别选择**：
- `-O0` - 调试构建，无优化，单步调试准确
- `-O2` - 发布构建，平衡性能和编译时间
- `-Os` - 优化体积（未来可能考虑）
- `-O3` - 最大优化（可能增加体积，暂不考虑）

### 7.2 内联考虑

```c
// 使用 volatile 防止优化
volatile uint16_t *vga = (uint16_t *)0xB8000;
vga[0] = 0x1F43;

// 使用 inline 汇编
__asm__ volatile("hlt");
```

**volatile 的作用**：
- 防止编译器优化掉"无用"的内存写入
- 确保每次访问都真实发生

## 9. 经验总结

### 9.1 做对的事情

1. **渐进式迁移** - 先迁移构建系统，再迁移代码
2. **保持 ELF 文件** - 调试时非常有用
3. **模块化设计** - CMake 子目录易于管理
4. **生成器表达式** - CMake 的强大功能值得学习

### 9.2 可以改进的地方

1. **依赖管理** - NASM include 依赖可以更完善
2. **测试覆盖** - 缺少自动化测试
3. **文档同步** - 代码变更后文档更新有时滞后

### 9.3 给未来的建议

1. **先设计后实现** - 构建系统改动影响大，需仔细规划
2. **保持简单** - CMake 功能强大，但不要过度使用
3. **调试友好** - Debug 构建应该优先考虑调试体验
4. **文档先行** - 记录重要决策的原因
