## 为什么需要调度类框架

### 1. 单一调度算法的局限

Stage 21 实现了简单的进程管理，但调度算法是硬编码的单一 Round-Robin：

```c
// Stage 21 的简单调度
void schedule(void) {
    if (list_is_empty(&scheduler.run_queue)) {
        return;
    }
    next = list_first_entry(&scheduler.run_queue, pcb_t, run_list);
    list_del_init(&next->run_list);
    // ... 切换到 next
}
```

**存在的问题**：
- 无法为不同类型进程提供不同策略
- 添加新调度算法需要修改核心代码
- 系统进程和用户进程使用同一策略
- 无法支持实时调度需求

### 2. 模块化设计的优势

调度类框架解决了上述问题：

- **多策略共存**：RR、Priority、CFS 等可同时运行
- **易于扩展**：添加新算法只需实现调度类接口
- **类型隔离**：系统进程用 Priority，用户进程用 RR
- **策略灵活**：运行时可切换进程的调度策略

### 3. 与 Linux 调度器的对比

Linux 的调度类架构：

```c
// Linux 调度类（简化）
struct sched_class {
    void (*enqueue_task)(struct rq *rq, struct task_struct *p, int flags);
    void (*dequeue_task)(struct rq *rq, struct task_struct *p, int flags);
    struct task_struct *(*pick_next_task)(struct rq *rq);
    void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
    // ...
};

// Linux 的调度类
extern const struct sched_class stop_sched_class;
extern const struct sched_class dl_sched_class;    // Deadline
extern const struct sched_class rt_sched_class;    // Real-time
extern const struct sched_class fair_sched_class;  // CFS
extern const struct sched_class idle_sched_class;
```

**我们的实现**：
- 相同的虚函数表模式
- 简化的功能子集
- 专注于两种基础策略

## 调度类设计基础

### 1. 调度类抽象接口

调度类定义了一组操作，每个具体算法必须实现：

```c
typedef struct sched_class {
    const char* name;              // 类名称（调试用）
    sched_policy_t policy;         // 策略标识

    // ===== 队列管理 =====
    void (*enqueue_task)(struct sched_rq* rq, struct pcb* pcb, bool head);
    void (*dequeue_task)(struct sched_rq* rq, struct pcb* pcb);

    // ===== 任务选择 =====
    struct pcb* (*pick_next_task)(struct sched_rq* rq, struct pcb* prev);
    bool (*should_preempt)(struct pcb* p, struct pcb* curr);

    // ===== 时间管理 =====
    void (*task_tick)(struct sched_rq* rq, struct pcb* pcb);
    uint32_t (*get_time_slice)(const struct pcb* pcb);

    // ===== 生命周期 =====
    void (*task_fork)(struct pcb* pcb, int nice);
} sched_class_t;
```

**接口说明**：

| 方法 | 作用 | 调用时机 |
|------|------|----------|
| `enqueue_task` | 将任务加入运行队列 | 进程创建、唤醒 |
| `dequeue_task` | 将任务移出运行队列 | 进程阻塞、退出 |
| `pick_next_task` | 选择下一个运行任务 | 调度发生时 |
| `should_preempt` | 判断是否应抢占 | 任务就绪时 |
| `task_tick` | 定时器回调 | 每个时钟 tick |
| `task_fork` | fork 时初始化 | 进程创建 |
| `get_time_slice` | 获取时间片 | 初始化、重置时 |

### 2. 调度实体 (sched_entity)

每个进程 PCB 中嵌入调度实体：

```c
typedef struct sched_entity {
    sched_policy_t    policy;         // 调度策略
    sched_class_t*    sched_class;    // 指向调度类
    uint32_t          time_slice;     // 剩余时间片 (ms)
    uint32_t          time_slice_total; // 完整时间片 (ms)
    int               priority;       // 优先级 (0-127)
    int               nice;           // Nice 值（预留）
    uint64_t          last_ran;       // 上次运行时间（预留）
    list_head         run_list;       // 队列节点
} sched_entity_t;

typedef struct pcb {
    // ...
    sched_entity_t     sched_entity;   // 调度实体
    // ...
} pcb_t;
```

### 3. Per-Policy 运行队列

每个调度策略维护独立的运行队列：

```c
typedef struct sched_rq {
    sched_class_t* sched_class;    // 关联的调度类
    list_head        queue;         // 通用运行队列
    uint32_t         nr_running;    // 队列中的任务数
    void*            class_data;    // 类特定的私有数据
} sched_rq_t;

// 全局运行队列数组
static sched_rq_t s_run_queues[SCHED_MAX];
// SCHED_NORMAL (RR)   -> s_run_queues[0]
// SCHED_PRIORITY      -> s_run_queues[1]
```

**class_data 的使用**：

Priority 调度类需要多个优先级队列，使用 class_data：

```c
// Priority 调度类的私有数据
typedef struct prio_rq_data {
    list_head    active[PRIO_LEVELS];   // 128 个活跃队列
    list_head    expired[PRIO_LEVELS];  // 128 个过期队列
    uint32_t     nr_active;
    uint32_t     nr_expired;
    int          highest_prio;
    bool         active_expired;
} prio_rq_data_t;

// 初始化时分配
rq->class_data = kmalloc(sizeof(prio_rq_data_t));
```

## 设计决策

### 1. 为什么选择虚函数表模式

#### 决策：使用函数指针实现多态

```c
// 通过函数指针调用
pcb->sched_entity.sched_class->task_tick(rq, pcb);
```

**理由**：
- C 语言没有类和继承，虚函数表是标准的 OOP 替代方案
- 运行时多态，不需要重新编译
- 添加新调度类无需修改框架代码
- 与 Linux 调度器一致的设计

**替代方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 虚函数表 | 运行时多态、扩展性强 | 函数调用开销 |
| switch-case | 简单直接 | 添加策略需修改核心代码 |
| 宏定义 | 零开销 | 类型不安全、难维护 |

### 2. RR 和 Priority 的选择理由

#### Round-Robin (RR)
- **目标**：普通用户进程
- **特点**：公平、简单、无饥饿
- **时间片**：固定 10ms
- **适用场景**：分时系统、交互式程序

#### Priority
- **目标**：系统关键进程
- **特点**：优先级抢占、响应快
- **优先级**：0-127（0 最高）
- **适用场景**：内核线程、实时任务

**为什么不是 CFS**：
- CFS 实现复杂（需要红黑树、vruntime）
- 当前阶段重点是建立框架
- RR + Priority 已能满足演示需求
- 后续可扩展

### 3. Active/Expired 队列设计

#### 决策：Priority 调度使用两级队列

```c
typedef struct prio_rq_data {
    list_head active[PRIO_LEVELS];   // 当前可运行
    list_head expired[PRIO_LEVELS];  // 时间片用完
} prio_rq_data_t;
```

**工作原理**：

1. 任务初始加入 `active[priority]`
2. 时间片用完后移到 `expired[priority]`
3. 所有 `active` 队列为空时，交换 `active` 和 `expired`
4. 保证同一优先级的任务轮流执行

**好处**：
- 防止高优先级任务饿死低优先级任务
- 公平性保证
- 与 Linux 的 O(1) 调度器类似

**简化之处**：
- 不考虑优先级动态调整
- 不考虑时间片借用

## 实现细节

### 1. 调度类注册机制

```c
// 注册调度类
int sched_class_register(sched_class_t* class, sched_policy_t policy) {
    if (s_classes[policy] != NULL) {
        return -1;  // 已注册
    }
    s_classes[policy] = class;
    s_run_queues[policy].sched_class = class;
    return 0;
}

// 使用示例
int sched_rr_init(void) {
    return sched_class_register(&rr_sched_class, SCHED_NORMAL);
}
```

### 2. task_tick 处理

**RR 的 task_tick**：

```c
static void rr_task_tick(struct sched_rq* rq, struct pcb* pcb) {
    // 递减时间片
    if (pcb->sched_entity.time_slice > 0) {
        pcb->sched_entity.time_slice--;
    }

    // 时间片用完，触发重调度
    if (pcb->sched_entity.time_slice == 0) {
        sched_set_resched();
    }
}
```

**Priority 的 task_tick**：

```c
static void prio_task_tick(struct sched_rq* rq, struct pcb* pcb) {
    prio_rq_data_t* data = prio_rq_data(rq);

    // 递减时间片
    if (pcb->sched_entity.time_slice > 0) {
        pcb->sched_entity.time_slice--;
    }

    // 时间片用完，移到过期队列
    if (pcb->sched_entity.time_slice == 0) {
        int prio = pcb->sched_entity.priority;

        // 从 active 移到 expired
        list_del_init(&pcb->sched_entity.run_list);
        list_add_tail(&pcb->sched_entity.run_list, &data->expired[prio]);

        data->nr_active--;
        data->nr_expired++;

        sched_set_resched();
    }
}
```

### 3. pick_next_task 逻辑

```c
struct pcb* sched_pick_next_task(void) {
    pcb_t* prev = scheduler.current;

    // 1. 如果当前进程仍有时间片，保持运行
    if (prev && prev->state == PROC_RUNNING) {
        if (prev->sched_entity.time_slice > 0) {
            // 检查是否有更高优先级任务
            if (prio_rq->nr_running > 0 &&
                prio_rq->sched_class->should_preempt(prio_task, prev)) {
                return prio_task;
            }
            return prev;  // 保持当前
        }
    }

    // 2. 优先检查 Priority 队列
    if (prio_rq->nr_running > 0) {
        return prio_rq->sched_class->pick_next_task(prio_rq, prev);
    }

    // 3. 回退到 RR 队列
    if (rr_rq->nr_running > 0) {
        return rr_rq->sched_class->pick_next_task(rr_rq, prev);
    }

    return NULL;  // 运行 idle
}
```

### 4. 抢占判断

```c
// Priority 的抢占逻辑
static bool prio_should_preempt(struct pcb* p, struct pcb* curr) {
    // 高优先级（数值小）抢占低优先级
    if (p->sched_entity.priority < curr->sched_entity.priority) {
        return true;
    }

    // 同优先级：仅当当前时间片用完
    if (p->sched_entity.priority == curr->sched_entity.priority) {
        return (curr->sched_entity.time_slice == 0);
    }

    return false;
}

// RR 的抢占逻辑
static bool rr_should_preempt(struct pcb* p, struct pcb* curr) {
    (void)p;  // RR 不考虑任务本身
    // 仅在当前时间片用完时允许"抢占"
    return (curr->sched_entity.time_slice == 0);
}
```

### 5. 进程创建集成

```c
int32_t proc_fork(void) {
    pcb_t* child = proc_alloc_pcb();

    // 设置调度策略
    sched_set_policy(child, SCHED_NORMAL, 0);
    //   ├─ 调用 rr_task_fork(child, 0)
    //   │  └─ 初始化 sched_entity
    //   └─ 设置 time_slice = RR_TIMESLICE_DEFAULT

    // 加入运行队列
    sched_enqueue_task(child, false);
    //   └─ 调用 rr_sched_class.enqueue_task()

    return child->pid;
}
```

## 常见陷阱与注意事项

### 1. 时间片管理

**问题**：忘记重置时间片

```c
// 错误：任务重新入队后时间片仍是 0
if (prev->state == PROC_READY) {
    sched_enqueue_task(prev, false);  // time_slice = 0!
}

// 正确：先重置时间片
sched_reset_time_slice(next);  // 在 pick_next_task 之后
```

**解决方案**：在 `schedule()` 中切换到新任务后重置时间片。

### 2. 优先级反转风险

**问题**：低优先级任务持有高优先级任务需要的资源

```
时间线：
  High Prio 任务: 等待资源
  Low Prio 任务:  持有资源，但被 Medium Prio 抢占
  Medium Prio:    运行中...
  结果：High Prio 被 Medium "间接"阻塞
```

**当前处理**：未实现（需要优先级继承或天花板协议）

**未来改进**：
- 优先级继承（Priority Inheritance）
- 优先级天花板（Priority Ceiling）

### 3. 队列空指针处理

**问题**：访问空的运行队列

```c
// 危险：未检查队列是否为空
pcb_t* next = list_first_entry(&rq->queue, pcb_t, run_list);

// 安全：先检查
if (list_is_empty(&rq->queue)) {
    return NULL;
}
pcb_t* next = list_first_entry(&rq->queue, pcb_t, run_list);
```

### 4. class_data 未初始化

**问题**：Priority 类的 class_data 未分配

```c
// 初始化时必须分配
int sched_prio_init(void) {
    prio_rq_data_t* data = kmalloc(sizeof(prio_rq_data_t));
    if (!data) return -1;

    // 初始化队列...
    for (int i = 0; i < PRIO_LEVELS; i++) {
        INIT_LIST_HEAD(&data->active[i]);
        INIT_LIST_HEAD(&data->expired[i]);
    }

    rq->class_data = data;  // 关键！
}
```

### 5. sched_class 空指针

**问题**：进程的 sched_class 未设置

```c
// 在 alloc_pcb 中初始化
pcb->sched_entity.sched_class = NULL;  // 初始为 NULL

// 在 set_policy 中设置
pcb->sched_entity.sched_class = s_classes[policy];

// 使用前检查
if (pcb->sched_entity.sched_class) {
    pcb->sched_entity.sched_class->task_tick(rq, pcb);
}
```

### 1. CFS 调度类

### 3. 实时调度策略

```c
// SCHED_FIFO - 先进先出
// SCHED_RR - 实时轮转
#define SCHED_FIFO    2
#define SCHED_RR      3
```

```c
// Linux O(1) 调度器的优先级计算
static void recalc_task_prio(struct pcb* pcb, uint64_t now) {
    uint64_t sleep_time = now - pcb->sched_entity.last_ran;
    int bonus = (sleep_time < NS_TO_MS(100)) ? 0 : 5;

    pcb->sched_entity.priority -= bonus;
    // 限制在 [PRIO_MAX, PRIO_MIN]
}
```
