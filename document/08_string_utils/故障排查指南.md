# 字符串工具库与断言系统 - 故障排查指南

本文档提供字符串工具库和断言系统阶段常见问题的诊断和解决方案。

---

## 1. 字符串函数问题

### 1.1 strlen 返回错误的长度

**症状**: 字符串长度计算不正确

**可能原因**:

| 原因 | 检查方法 | 解决方案 |
|------|----------|----------|
| 字符串未空终止 | 检查缓冲区是否包含 `\0` | 确保字符串正确终止 |
| 指针问题 | 使用 GDB 检查指针值 | 验证指针有效性 |
| 内存损坏 | 检查缓冲区边界 | 修复缓冲区溢出 |

**调试步骤**:
```c
// 使用 GDB 检查字符串内容
(gdb) print/s (char*)0xAddress
(gdb) x/50bx 0xAddress  // 查看字节内容

// 检查是否有终止符
(gdb) print *(char*)(0xAddress + length)
```

### 1.2 strcpy 导致缓冲区溢出

**症状**: 程序崩溃或内存被意外修改

**可能原因**:
1. 源字符串长度超过目标缓冲区
2. 未计算缓冲区大小
3. 使用了错误的指针

**解决方案**:
```c
// 错误用法
char buffer[10];
strcpy(buffer, "This string is too long");  // 溢出！

// 正确用法
char buffer[10];
strncpy(buffer, source, sizeof(buffer) - 1);
buffer[sizeof(buffer) - 1] = '\0';

// 或使用断言检查
CCOS_ASSERT(strlen(source) < sizeof(buffer));
strcpy(buffer, source);
```

**检测方法**:
```bash
# 使用 Valgrind 检测内存问题（主机测试）
valgrind --leak-check=full ./build/test/test_string

# 在内核中使用断言
CCOS_ASSERT(dest != NULL);
CCOS_ASSERT(src != NULL);
CCOS_ASSERT(strlen(src) < buffer_size);
```

### 1.3 strcmp 返回意外的结果

**症状**: 比较结果与预期不符

**可能原因**:
1. 字符串未空终止
2. 大小写不匹配
3. 包含不可见字符

**调试方法**:
```c
// 检查字符串内容
printf("s1 = [%s] len=%zu\n", s1, strlen(s1));
printf("s2 = [%s] len=%zu\n", s2, strlen(s2));

// 逐字节比较
for (size_t i = 0; i < 10; i++) {
    printf("[%zu] s1=%02x s2=%02x\n", i, s1[i], s2[i]);
}

// 使用忽略大小写版本
if (strcasecmp(s1, s2) == 0) {
    // 字符串匹配（忽略大小写）
}
```

### 1.4 strtok 破坏原字符串

**症状**: 原字符串内容被修改

**说明**: 这是 `strtok` 的预期行为

**解决方案**:
```c
// 方法 1: 复制原字符串
char str[] = "hello,world,tokens";
char str_copy[100];
strcpy(str_copy, str);

char* token = strtok(str_copy, ",");

// 方法 2: 使用 strtok_r（线程安全）
char str[] = "hello,world,tokens";
char* saveptr;
char* token = strtok_r(str, ",", &saveptr);

// 方法 3: 使用非破坏性分割（需自己实现）
```

### 1.5 strstr 找不到存在的子串

**症状**: `strstr` 返回 NULL 但子串明显存在

**可能原因**:
1. 大小写不匹配
2. 包含空格或特殊字符
3. 字符串编码问题

**解决方案**:
```c
// 检查实际内容
printf("haystack: [%s]\n", haystack);
printf("needle: [%s]\n", needle);

// 转换为小写再搜索
char haystack_lower[100];
char needle_lower[100];
strcpy(haystack_lower, haystack);
strcpy(needle_lower, needle);
// 转小价...

char* result = strstr(haystack_lower, needle_lower);
```

## 2. 断言系统问题

### 2.1 断言未触发

**症状**: 明明条件为假但断言不触发

**可能原因**:
1. 使用了 `CCOS_DEBUG_ASSERT` 但在 Release 模式
2. 条件始终为真
3. 断言被意外禁用

**检查方法**:
```c
// 确认使用的断言类型
CCOS_ASSERT(x > 0);        // 始终启用
CCOS_DEBUG_ASSERT(x > 0);  // 仅 Debug 模式

// 检查 NDEBUG 宏
#ifdef NDEBUG
    #error "Debug assertions disabled!"
#endif

// 添加测试断言
CCOS_ASSERT(false);  // 应该总是触发
```

### 2.2 VGA 断言信息不显示

**症状**: 断言触发但 VGA 上无错误信息

**可能原因**:
1. VGA 未初始化
2. VGA 实例指针无效
3. 光标位置超出屏幕

**解决方案**:
```c
// 确保断言前 VGA 已初始化
void kernel_init(void) {
    system_vga_init();
    // 现在断言可以显示
}

// 手动测试 VGA 输出
assert_backend_to_vga(__FILE__, __LINE__, __func__, "test");
```

**调试步骤**:
```gdb
# 检查 VGA 实例
(gdb) print vga_instance()
(gdb) print *vga_instance()

# 检查光标位置
(gdb) print vga_instance()->native_cursor_pos
(gdb) print vga_instance()->width
(gdb) print vga_instance()->height
```

### 2.3 断言后系统无响应

**症状**: 断言触发后系统完全冻结

**说明**: 这是预期行为，`assert_failed_action()` 会停止系统

**行为**:
- Debug 模式: 触发 `int3` 断点，通知调试器
- 所有模式: `cli` + `hlt` 循环

**如何继续调试**:
```gdb
# 在 GDB 中，断言后会暂停
(gdb) backtrace  # 查看调用栈
(gdb) print condition  # 查看失败的值
(gdb) frame 2  # 切换到调用者帧
```

### 2.4 断言文件名被截断

**症状**: VGA 显示的文件路径不完整

**原因**: VGA 屏幕宽度限制（80 字符）

**解决方案**:
```c
// 在 assert_action_backend.c 中
// 只显示文件名而非完整路径
const char* filename = file;
// 从路径中提取文件名
const char* last_slash = strrchr(file, '/');
if (last_slash) {
    filename = last_slash + 1;
}
```

## 3. 测试框架问题

### 3.1 主机测试编译失败

**症状**: `test_string` 编译错误

**常见错误**:

| 错误 | 原因 | 解决方案 |
|------|------|----------|
| `undefined reference to strlen` | 链接问题 | 确保 CMakeLists.txt 正确配置 |
| `conflicting types` | 头文件问题 | 检查 host_support.h |
| `virtual memory exhausted` | 资源限制 | 增加 swap 或减少测试 |

**解决方案**:
```bash
# 清理并重新构建
rm -rf build
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target test_string

# 检查链接命令
cmake --build build --target test_string --verbose
```

### 3.2 测试全部通过但内核中失败

**症状**: 主机测试正常，内核中字符串函数异常

**可能原因**:
1. 内存布局不同
2. 编译器优化差异
3. 内核环境特殊性

**调试方法**:
```c
// 在内核中添加测试
void kernel_test_string(void) {
    char buffer[100];
    strcpy(buffer, "test");
    CCOS_ASSERT(strcmp(buffer, "test") == 0);

    // VGA 显示测试结果
    vga_print_string(vga, "String test passed!\n");
}
```

### 3.3 TEST_ASSERT_EQ 报告失败但值看起来相等

**症状**: 测试报告 `expected X got X`

**可能原因**:
1. 类型不匹配（有符号 vs 无符号）
2. 浮点精度问题
3. 字符串比较问题

**解决方案**:
```c
// 显式转换类型
TEST_ASSERT_EQ((int)actual, (int)expected, "message");

// 使用字符串专用断言
TEST_ASSERT_STR_EQ(actual_str, expected_str, "message");

// 打印实际值
printf("actual: %d (0x%x)\n", actual, actual);
printf("expected: %d (0x%x)\n", expected, expected);
```

## 4. 链接和构建问题

### 4.1 undefined reference to string 函数

**症状**: 链接时找不到字符串函数

**可能原因**:
1. 未链接 `kernel_base` 库
2. CMakeLists.txt 配置错误
3. 函数声明但未定义

**解决方案**:
```cmake
# 确保 kernel/base/CMakeLists.txt 正确
add_library(kernel_base STATIC
    string.c
    # ...
)

# 确保链接
target_link_libraries(kernel PRIVATE kernel_base)
```

**检查方法**:
```bash
# 查看符号是否存在
nm build/kernel/kernel_base.a | grep strlen

# 查看链接命令
cmake --build build --verbose | grep kernel.elf
```

### 4.2 multiple definition 错误

**症状**: 链接器报告重复定义

**常见原因**:
1. 头文件中定义函数（应该只是声明）
2. 多个源文件定义相同函数
3. 内联函数处理不当

**解决方案**:
```c
// 头文件应该只有声明
// string.h
size_t strlen(const char* s);

// 实现在 .c 文件
// string.c
size_t strlen(const char* s) {
    // ...
}
```

### 4.3 内联函数链接错误

**症状**: `undefined reference to` 内联函数

**解决方案**:
```c
// 方法 1: 使用 static inline
static inline size_t fast_strlen(const char* s) {
    // ...
}

// 方法 2: 移到头文件并使用 inline
// string.h
extern inline size_t fast_strlen(const char* s);

// 方法 3: 不使用 inline，直接编译为函数
```

## 5. 性能问题

### 5.1 字符串操作太慢

**症状**: 字符串处理成为性能瓶颈

**诊断方法**:
```c
// 使用 RDTSC 测量周期
uint64_t start = rdtsc();
strlen(long_string);
uint64_t end = rdtsc();
uint64_t cycles = end - start;
```

**优化方案**:
```c
// 1. 缓存字符串长度
size_t len = strlen(str);
// 后续使用 len 而非重复调用 strlen

// 2. 使用更快的算法
// 对齐访问、SIMD 等

// 3. 避免不必要的拷贝
const char* result = str;  // 而非 strcpy
```

### 5.2 断言影响性能

**症状**: 频繁的断言检查降低性能

**解决方案**:
```c
// 1. 使用 CCOS_DEBUG_ASSERT 替代 CCOS_ASSERT
// 2. 在 Release 构建中禁用调试断言
cmake -DCMAKE_BUILD_TYPE=Release -B build

// 3. 将检查移出循环
// 错误
for (int i = 0; i < 1000000; i++) {
    CCOS_DEBUG_ASSERT(ptr != NULL);
    *ptr++ = i;
}

// 正确
CCOS_DEBUG_ASSERT(ptr != NULL);
for (int i = 0; i < 1000000; i++) {
    *ptr++ = i;
}
```

## 6. 问题诊断清单

遇到问题时，按顺序检查：

### 字符串函数问题
- [ ] 指针是否有效？
- [ ] 字符串是否空终止？
- [ ] 缓冲区是否足够大？
- [ ] 是否使用了正确的函数（strcpy vs strncpy）？

### 断言问题
- [ ] VGA 是否已初始化？
- [ ] 使用的是哪种断言？
- [ ] 是否在 Debug 模式？
- [ ] 调试器是否连接？

### 测试问题
- [ ] 主机测试是否通过？
- [ ] 链接是否正确？
- [ ] 类型是否匹配？
- [ ] 是否有内存损坏？

## 7. 常用调试命令

### GDB 命令

```gdb
# 查看字符串
(gdb) print/s variable

# 查看内存
(gdb) x/50bx 0xaddress

# 查看调用栈
(gdb) backtrace
(gdb) frame N

# 在断言处停止
(gdb) break ccos_assert_impl
(gdb) continue

# 查看汇编
(gdb) disassemble
```

### Shell 命令

```bash
# 查找符号
nm build/kernel.elf | grep strlen

# 检查未定义引用
ldd build/test/test_string  # 主机测试

# 内存检查
valgrind ./build/test/test_string

# 反汇编
objdump -d build/kernel.elf | grep strlen
```
